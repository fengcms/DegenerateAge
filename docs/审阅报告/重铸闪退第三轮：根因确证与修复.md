## 0. 一句话结论

闪退的真因是 **`FloatingWindow` 的布局自激闭环把 Godot 消息队列撑爆**，不是渲染层、不是存档、不是竞态、不是内存不够。

修复只有一处实质改动：`scripts/ui/floating_window.gd` 新增 `_schedule_layout()`，按**帧号**去重布局请求。

修复后同一套探针、同一台机器、同一个必崩窗口尺寸：**崩溃消失，`resized` 单帧触发从 105400 次降到 0**。

---

## 1. 引擎留下的决定性证词

第二轮日志（`user://logs/godot.log`）里唯一一条不是普通报错、而是**引擎自认撑不住**的输出：

```
Failed method: CanvasItem::_redraw_callback. Message queue out of memory.
```

后面紧跟引擎自己的建议：

```
Try increasing 'memory/limits/message_queue/max_size_mb' in project settings.
```

崩溃点就在 `CanvasItem::_redraw_callback` —— 引擎在这个回调**开头**就已经把 `pending_redraw` 清了，然后访问队列里的绘制命令；队列已被撑爆，访问的是失效内存 → `EXC_BAD_ACCESS` / `SIGSEGV`。

这条信息把方向从「谁把画面画坏了」整体扭转到「**谁在无限地往消息队列里塞东西**」。

> 🔴 引擎那句「调大 `max_size_mb`」是**误导性建议**。实测把上限从 4MB 调到 32MB、128MB，照样崩 —— 只是多活几百毫秒。真正要修的是「谁在塞」，不是「塞的容器多大」。

## 2. 因果链（每一环都有实测数字）

```
① 玩家点「重铸」
   ↓  _on_reforge() → _refresh_choices() 重建下拉（**一百多项**，实测 147～156，随背包装备数变化）
   ↓  _feedback 文本 113 字 → 128 字（多一行「本次是最好的 17 次结果」）
② 内容自然高度跨过临界值
   ↓  fit_content() 的 overhead 与 scroll.custom_minimum_size 互相追尾
③ wanted 在 930 / 956 之间振荡，scrollmin 在 853 / 827 之间振荡
   （差值 26 —— 正好一行文字高度，说明是「多一行就装不下、少一行又装得下」的临界抖动）
   ↓  is_equal_approx() 那道刹车永不成立
④ 每轮 _layout() 都改 scroll.custom_minimum_size
   ↓  → panel_box.minimum_size_changed 信号
   ↓  → 又排一条 _layout.call_deferred()
⑤ 🔴 deferred 在**同一帧**的 flush 里就被执行了
   ↓  「排进去 → 立刻执行 → 又排放」= 同帧无限循环
⑥ PanelChrome 的 resized.connect(queue_redraw) 每条都进消息队列
   ↓  实测单帧 105400 次
⑦ 队列耗尽 → 引擎报 Message queue out of memory → 崩在 _redraw_callback
```

### 2.1 第 ⑤ 环是最反直觉的一环

`call_deferred()` 的名字让人以为是「下一帧再说」。**不是。**

Godot 的 `MessageQueue` 在**当前帧**的 idle 阶段就会 flush。所以：

```gdscript
func _layout() -> void:
    ...改尺寸...
    # 尺寸一变就触发 minimum_size_changed
    # 那个信号又调 _layout.call_deferred()
```

写起来像是「晚点再布局」，实际是「**在同一次 flush 里立刻再布局一次，然后它又排一条，循环到队列爆掉**」。

### 2.2 为什么布尔标记挡不住

第一版防御写的是布尔 `_layout_pending`，在 `_layout()` **结尾**清掉。但清理发生在 deferred 执行时，也就是**同一帧内** —— 清了之后，同帧下一次 `minimum_size_changed` 又能排一条。

所以必须用**帧号**：

```gdscript
var _layout_frame := -1

func _schedule_layout() -> void:
    var frame := Engine.get_process_frames()
    if frame == _layout_frame:
        return          # 本帧已经排过，丢弃
    _layout_frame = frame
    _layout.call_deferred()
```

帧号判定才是真正的「每帧最多一次」。振荡仍在，但每帧只算一次，队列不再增长。

### 3.1 「窗口越高越容易崩」一度被误读成渲染问题

真实原因是：窗口越高 → `fit_content` 的可用高度越大 → 内容在「装得下」与「需要滚动条」之间越容易反复横跳 → 闭环每帧都成立。

这是**布局**问题借**渲染**的外表出现。

## 4. 修复内容

### 4.1 主体修复：`scripts/ui/floating_window.gd`

| 位置 | 改动 |
|---|---|
| 新增 `_layout_frame` | 记录本帧是否已排过布局 |
| 新增 `_schedule_layout()` | 唯一的延迟布局入口，按帧号去重 |
| `panel_box.minimum_size_changed` | `func() -> void: _layout.call_deferred()` → `_schedule_layout` |
| `owner_panel.resized` | `_layout` → `_schedule_layout` |
| `setup()` 末尾 | `_layout.call_deferred()` → `_schedule_layout()` |
| `set_content_scroll()` | `_layout.call_deferred()` → `_schedule_layout()` |

### 4.2 辅助加固：`fit_content()` 第 2 轮起单调收小

```gdscript
if _i > 0:
    wanted = Vector2(minf(wanted.x, scroll.custom_minimum_size.x),
        minf(wanted.y, scroll.custom_minimum_size.y))
    if scroll.custom_minimum_size.is_equal_approx(wanted):
        return
scroll.custom_minimum_size = wanted
```

这条是**辅助**，不是必需的。它让单次 `fit_content` 内部一定在 4 轮内停住，把「振荡」本身也压掉。代价是可能比理论最优小几像素 —— 有滚动条兜底，可接受；崩溃不可接受。

### 4.3 配置加固：`project.godot`

`memory/limits/message_queue/max_size_mb = 16`（默认 4MB 的 4 倍）。

**这一条不是修复手段**，只是余量：面板一次性重建（一百多项下拉 + 词条行 + 材料格）的重绘洪峰在默认 4MB 下贴得太近。文件里的注释已写明这一点，避免后人误以为「调大上限就是修复」。

## 6. 遗留风险：其他面板有同形写法（未修）

`reforge_panel` 自身**没有**接 `minimum_size_changed`，布局完全依赖 `FloatingWindow` —— 这正是本次修复能一击生效的原因。

但下面三个面板是**自带闭环**：

| 文件 | 写法 |
|---|---|
| `scripts/ui/shop_panel.gd:235` | `_box.minimum_size_changed.connect(func() -> void: _update_layout.call_deferred())` |
| `scripts/ui/carter_panel.gd:161` | 同上 |
| `scripts/ui/boss_token_panel.gd:186` | 同上 |

且它们的 `_update_layout()` 内部都调 `FloatingWindow.fit_content(...)` —— 也就是说，`fit_content` 改尺寸 → `_box.minimum_size_changed` → 自己再排一条 deferred，与本次崩溃**同形**。

### 为什么现在没崩

因为 4.2 的单调收小让 `fit_content` 单次调用内部一定收敛；而且这些面板的内容高度不像重铸面板那样卡在「一行文字」的临界点上。

### 🔴 为什么仍是风险

单调收小只约束**单次调用内部**的轮次。跨调用的第 0 轮是不受限的（`_i > 0` 才对），所以「A 次调成 930 → 信号 → B 次调成 956 → 信号 → C 次又调回 930」这条跨调用振荡路径**仍然存在**。

**建议**：把 `_schedule_layout` 这套按帧号去重下沉为一个公共工具（或直接暴露成 `FloatingWindow.schedule_fit(panel)`），三个面板改接它。属独立工单，不在本次范围。

## 7. 本轮的三个自我推翻（记录在案）

| 轮次 | 当时的结论 | 为什么错 |
|---|---|---|
| 首轮 | 布局尺寸算出 NaN | 把「玩家 3 小时崩」与「AI 自己 21 秒的测试进程」当成同一现象 |
| 第二轮 | 「重铸不是触发条件」 | 本轮日志显示 `reforge.begin → result ok=tries=17 → end` 后**立刻**死亡，重铸就是触发条件 |
| 第二轮 | 「竞态型，难复现」 | 完全可确定复现：窗口高 ≥960 + 有材料即崩，100% 命中 |
| 第二轮 | 「100 只 boss 挤同格导致」 | 那是**正常设计状态**（墓碑堆叠），且只加载世界不重铸不崩 |

教训：**「难复现」这个判断本身必须先被验证**。一旦给出「偶发/竞态」的定性，就会自动放弃确定性实验，从而错过 100% 命中率的复现条件 —— 本轮就是靠「窗口高度」这一个确定性变量翻盘的。

## 8. 给玩家的操作结论

不需要任何特殊操作。正常大窗口、正常重铸即可，已不会再崩。

如果你之前把编辑器的 Game 面板缩小过 —— 可以恢复原来的大小了，那个「缩小窗口就不崩」的现象，本质是「窗口矮了，布局不再抖」，属于规避而非修复。
