# 重铸闪退修复独立复核与历史负债清理建议

> 实施状态：本报告识别的收口项与三项已登记美术债务已分节点实施。最终完整扫描195项通过，无失败、无已知欠账跳过。详见[实施与验收记录](../工程文档/重铸闪退与历史负债收口实施记录.md)。下文保留审阅当时的证据和建议。

2026-11-02。审阅基线159c78ab，重点检查01d9520a之后同步的重铸闪退修复、诊断工具及相关历史负债。本轮仅形成审阅结论，没有修改生产逻辑、配置或测试断言。

## 一、结论

**核心修复方向合理，建议保留；仍有可清理的稳定性与工程债务，不建议照原样认定整个布局系统已彻底收敛。**

用户已在原场景验证闪退消失；本轮另在实际窗口中用合成数据复核高窗口重铸成功。把布局反馈的限流放到FloatingWindow，而不是修改重铸交易或技能数值，职责归属正确。NaN/INF守卫也是可保留的边界防御，但应与本次确认的布局反馈原因分开叙述。

主要待办是：布局请求的末次更新不能丢；货郎、车夫和随身Boss面板也需要同等调度保护；16MB配置的“默认4MB、扩大四倍”依据错误；诊断日志需要运行期轮转。两项既有红测也能按现有产品规则修复，无需通过改玩法使测试通过。

## 三、具体审阅发现

### 1. 帧号限流应保留，但不能丢失末次请求（P2，已实测入口行为）

位置：`scripts/ui/floating_window.gd:188–199`。

_schedule_layout按请求所在帧号去重，确实切断了同一帧deferred无限自激。但在已执行本帧布局后，又发生内容/宿主尺寸变化时，第二次请求直接return，没有dirty标记，也没有保证下一帧补算。代码注释假定下一帧自然再发信号，这不是调度器自身保证；探针等待5帧也未补算。

因此它适合作为止血限流，尚不等于可靠的更新合并器。建议改为“本帧至多一次，新增请求保留dirty，必要时通过process_frame在下一帧执行”，并测试同帧后续更新最终生效。单纯把帧号换回_layout结束时清空的布尔值会重新放开旧闭环，不能这样回退。

另外，show_window、set_origin、set_docked、set_pinned仍同步调用_layout；人物面板`character_panel.gd:387`也直接调私有_layout。因此“每帧最多一次”目前只适用于该延迟入口，不是全部布局调用。这里也包含本会话之前加入的防护代码，应一并收口到公开请求入口，而不是只清理另一台AI写的部分。

### 2. 三个旧面板仍保留相同类型的无限排队路径（P2，结构确认，触发条件待实测）

位置：`shop_panel.gd:235`、`carter_panel.gd:161`、`boss_token_panel.gd:186`。

它们自己的minimum_size_changed直接排_update_layout.call_deferred，内部再调用FloatingWindow.fit_content。共享FloatingWindow实例的帧号去重并不包住这些独立回调。

fit_content新增的单调收小仅约束同一次调用第2～4轮；下一次调用的第0轮仍可放大。因此不能把它当成跨调用收敛证明。旧实现本来就有4轮上限，本次问题不在一次函数调用会无穷循环，而在函数反复被重新排队。

建议与第1项共用一个具备dirty保留的布局调度工具，逐个接入三个面板，并在接近滚动阈值的窗口尺寸、长文案和切页条件下验证。当前没有在这三个正式面板复现闪退，故本项是同类风险，不应说它们现在必崩。

### 3. 队列“余量加固”的默认值写反了（P2，已实测）

位置：`project.godot:235–248`，相关提交effc65c7。

当前引擎无覆盖时默认32MB，显式设16MB是将上限减半，不是从4MB扩大四倍。它没有让本轮17次取优失败，但不能以“提高余量”作为保留依据。

建议删除覆盖回到目标引擎默认值，或明确按目标版本设定经过测量的上限，并修正文档与注释。修正容量不能取代调度修复；也不建议反向把上限无限放大掩盖循环。

### 4. CrashTrace边界与长期运行成本尚未收口（P2，边界已实测，帧率影响未测）

位置：`scripts/systems/crash_trace.gd:69–105`、`scripts/world/spawner.gd:297`。

CrashTrace单独成模块、关键事件立即落盘、心跳限频以及不持有静态Node引用，这些选择合理。问题在于_rotate_if_needed只在首次_open时执行；一旦_file存在，mark持续追加却不再检查文件大小。所以上限是启动前检查阈值，不是运行期文件上限。

另外ENABLED默认真，普通怪死亡也逐条写文件并flush；这是主线程同步I/O，不能仅凭“心跳节流”认定运行成本足够低。本轮没有测量它对实际帧时间的影响，不报告虚构的性能退化数字。

MAX_LINES统计包括关键事件，却只停止心跳：重铸每次至少5条关键记录，若按原报告的一万六千次操作，仅重铸就有八万条。此时心跳可能早于预期停止，关键日志却仍无限追加。

建议增加运行期安全轮转并检查rename结果，分离心跳与关键事件预算；再明确日常诊断模式和深度取证模式。核心交易完成、切图失败等记录可保留即时flush，普通怪死亡可采样或聚合。不要为降低I/O静默删掉仍需要的崩溃证据。

### 5. 本次真正的闪退条件还没有正式回归闸门（P2）

NanGuardTest能检验非法尺寸防御，却不能检验布局反馈、同帧请求和高窗口重铸。几个tools探针依赖slot_1及手工隔离约定，不是可由干净仓库稳定运行的回归测试。

建议新增正式布局回归：候选约150项、四件紫装、四枚钻石如意、反馈高度跨行；尺寸至少覆盖800/940/960/1200高度。验收同时检查请求有上限、末次状态生效、布局若干帧内稳定、标题和底部结果可见、17次取优交易只结算一次。窗口测试与无头调度测试分开，不以headless无崩溃替代真实绘制。

## 五、代码组织评价

- **合理部分**：共用布局稳定性放FloatingWindow；数值有限性放SettingsRuntime；CrashTrace独立服务；生产重铸仍走GameState原交易入口。没有发现本次修复通过修改金币、材料扣除或重铸概率掩盖闪退。
- **需要收口部分**：布局有FloatingWindow调度、三个面板私有调度、人物面板直接调用私有布局等多个入口；应统一调度职责。避免把每个面板都复制一份帧号判断。
- **测试与工具分工**：确定性契约放tests；需要外部存档或调查变量的探针留tools并强制隔离。生产代码注释保留简明职责与不变量，长篇调查过程放已归档报告。
- **提交组织**：核心布局、容量配置、诊断服务分别提交便于回退，整体合理。Windows导出预设与闪退修复无直接关系，今后宜独立验收与提交；本轮不重写已有历史。

## 六、建议实施顺序

1. **先补正式回归，再收口布局调度**：保留现有止血修复，补末次请求、同帧上限及高窗口17次取优用例；实现dirty保留，统一三个旧面板和人物面板入口。窗口阈值复核通过后提交。
2. **校正消息队列与结论注释**：按实际引擎默认值处理16MB覆盖；保留NaN防御，撤下过时根因断言。定向回归通过后独立提交。
3. **修测试债务**：修成功标记、NaN测试退出，以及合铸前后工具补领夹具；随后运行全量并将已知美术欠账单列。不能把之前两项失败继续当成永久免责项。
4. **收口取证工具与日志**：运行期轮转、事件分级与强制隔离；测试长运行尺寸上限和日志失败路径，再提交。
5. **单独处理美术债务**：按对应素材文档更新样板和图标；实际渲染与既有断言复绿后移出KNOWN_ART_DEBT。

本轮没有建议推倒已验证有效的修复。稳定性收口应以保留其防自激能力为前提，小步提交、逐步扩展验证。

## 七、外部语义核对

Godot官方明确说明：call_deferred会在当前idle周期持续处理，递归排入仍可能在同一周期执行；若要跨帧应使用process_frame/physics_frame。因此本次禁止同帧无限排队的思路有官方语义支持。[Object.call_deferred文档](https://docs.godotengine.org/en/4.5/classes/class_object.html#class-object-method-call-deferred)。

官方4.6文档列出的message_queue/max_size_mb默认值也是32；本轮仍以实际使用的4.7.2空项目实测为最终依据，避免再次套用旧版本的4MB数字。[ProjectSettings文档](https://docs.godotengine.org/en/4.6/classes/class_projectsettings.html#class-projectsettings-property-memory-limits-message-queue-max-size-mb)。
