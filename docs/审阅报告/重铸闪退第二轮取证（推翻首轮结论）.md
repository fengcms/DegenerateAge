## 5. 目前最可疑的两处（尚未证实）

### 5.0 先排除一个误判：100 条墓碑本身是**正常设计状态**

我一开始看到「100 条 Boss 墓碑」以为数据异常，核对后确认是正常的：

- `data/maps/ch07/c7_boss_field/map.json` 的 `bossSpawns` 是 **10 种 Boss × 10 席 = 100 条**，每条 `respawnTime=600`、`tombstone=true`、`kind=boss`；
- 存档 `spawnRespawn` 里 `c7_boss_field#` 前缀正好 **100 条**，key 分布为 10 种 × 10 个，`readyAt` 全部在未来（剩余 72~525 秒）；
- 也就是说：玩家把百首禁域 100 只 Boss 全清了，它们都在等重生。

**这解释了「为什么只有这张图会崩」**（全服只有这里会同时存在 100 个墓碑节点），但**不代表数据坏了**。

### 5.1 「100 只 boss 全部挤在同一个格」

`scripts/world/spawner.gd:328-330`：

```gdscript
if _ground != null and _ground.cave != null and String(point.get("monster_id", "")) == "boss_corrupted_beast":
    var boss_cell: Array = _ground.cave.points.get("beast", _ground.cave.points.get("boss_arena", [40, 26]))
    return Iso.grid_to_world(Vector2i(int(boss_cell[0]), int(boss_cell[1])))
```

这条特判是给「腐化源头」**单 Boss 图**写的（读 `cave.points.beast`）。而百首禁域的 100 个席位**复用同一个 `monster_id`**，于是 100 只 Boss 会被算到**同一个格子**上。

- 影响面：只有在**同时存活**时才会真正堆叠；玩家档里 100 只全是墓碑（`readyAt` 均未到期），所以**本次崩溃时并未触发**。
- 但这是真实缺陷，一旦 100 只同时重生（例如玩家离线很久后回来），物理与绘制会瞬间叠加在一点。
- 🔴 修改属**平衡/设计变更**，须单独立项，不能顺手改。

### 5.2 渲染层（macOS + `gl_compatibility`）

本轮崩溃是 `SIGBUS / KERN_PROTECTION_FAILURE`（首轮玩家那次是 `SIGSEGV` 后 abort）。两者栈一致但信号不同，且**只在真实渲染 + 满负载时出现、加 verbose/fixed-fps 就消失**。这符合「引擎渲染层在特定时序下访问失效映射」的画像，属于**引擎侧**嫌疑。孤证，暂无法在应用层证实。

## 9. 方案 C 落地记录（埋点已上线）

### 9.1 设计约束：埋点不能把 bug 吓跑

本 bug 对**帧时序高度敏感**（加 `--verbose` / `--fixed-fps` 就复现不出来），所以埋点的第一原则不是「记得多」，而是「**轻到不影响时序**」。据此定了四条硬约束：

| 约束 | 做法 | 为什么 |
|---|---|---|
| 崩溃时不能丢最后几行 | 每条 `mark()` 立即 `flush()` | 进程被信号杀死，用户态缓冲区不会落盘 |
| 不能拖慢主循环 | 逐帧信息走闸门：先比整数毫秒，过了才拼字符串 | 每帧只多一次整数比较 |
| 崩溃后重开不能清掉证据 | 追加写（`READ_WRITE` + `seek_end`），写满则**归档成 `.prev`**，绝不覆盖 | 玩家崩溃后第一反应就是重开游戏看一眼 |
| 不能影响既有测试 | 不挂 autoload，用 `static var`；心跳节点不存静态引用 | 避免污染 `--quit` 的 leak 基线 |

### 9.2 日志必须活到崩溃那一刻（本轮踩到的两个坑）

第一版埋点有两个**会让整个方案白做**的缺陷，都已修正：

1. **心跳只够 66 分钟**。原来固定 0.5 秒一条、上限 8000 行 ⇒ 66 分钟后就停记。而玩家是**玩到 3 小时 10 分**才崩的，等于崩溃前两小时的现场是空白。现改为两档：前 10 分钟 0.5 秒（看得清细节），之后 2 秒（够用且省盘），3 小时约 6000 行。
2. **写满会覆盖崩溃记录**。原来超 2MB 直接整体重置，而重置发生在**下一次启动**，正好把上一次崩溃的证据删掉。现改为归档：`crash_trace.log` → `crash_trace.prev.log`（只留最近一份，不无限堆）。

另外补了一个真实盲区：面板一打开就 `get_tree().paused = true`，`Game._process` 整体停摆，逐帧心跳跟着断——**而玩家正是在开面板操作时崩的**。现在另挂一个 `PROCESS_MODE_ALWAYS` 的空节点专做心跳，只写日志、不碰任何游戏状态（只读 `paused`）。

### 9.5 交付方式（崩了怎么给我日志）

```

```

- 崩溃后**不要立刻反复重开游戏**（虽然追加写不会丢，但少折腾更稳）；

`scripts/systems/crash_trace.gd` 顶部 `const ENABLED := true` 改 `false` 即可，其余代码一行都不用动。
