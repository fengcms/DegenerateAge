## 发现的问题

### [P1] 过宽的存档有效性判断会把不完整存档当成可恢复档

位置：[autoload/save_manager.gd:482](/Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd:482)、[autoload/save_manager.gd:287](/Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd:287)

`_is_valid_save()` 只检查顶层值是字典且 `player` 是字典。像 `{"player": {}}` 这样的不完整 JSON 会被认作有效主档。应用时，缺少的金币、背包、装备和任务数据会分别回落为空值；如果随后自动保存，当前这个“有效”主档还会被复制为 `.bak`，从而覆盖此前可用的备份。

**影响：** 存档字段缺失或被部分编辑时，读档可能静默清空进度，并在下一次保存后破坏回退备份，违背存档损坏恢复的预期。

**建议：** 在接受存档前校验当前 schema 必需字段与类型；检查等级、HP/MP、地图 ID 等关键值范围。旧版本先迁移到当前 schema，再对迁移结果做完整校验。若校验失败，应走 `.bak` 回退流程。

### [P2] 背包已满时更换已穿戴装备会被错误拒绝

位置：[scripts/systems/equipment.gd:128](/Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/equipment.gd:128)

穿戴流程在清空新装备所在格之前，先检查旧装备能否放入背包。背包满时该检查必然失败；但紧接着代码本来会清空新装备的格子，并注释说明旧装备可复用这个空位。

**复现条件：** 背包 40 格均占用，角色已穿戴某槽装备，背包中另有该槽的替换装备。选择新装备会提示“背包已满”，即使交换后物品数量不变、空间足够。

**建议：** 校验时把即将腾出的 `inv_index` 视作可用空间，或先做不落地的交换可行性计算，再原子地更新背包与装备槽。

### [P2] 多件堆叠入包时会截断数量并仍报告成功

位置：[scripts/systems/inventory.gd:32](/Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/inventory.gd:32)、[scripts/systems/inventory.gd:44](/Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/inventory.gd:44)

`has_space_for()` 只要找到一个未满堆就返回 `true`，没有计算本次数量还需要几个空格。`add()` 随后只更新第一个堆，并用 `mini(max_n, cur + add_n)` 截断溢出数量，然后返回成功。

**复现条件：** 某药水堆叠上限为 99，当前有 98 个，再添加 5 个；调用返回 `true`，背包只增加 1 个，其余 4 个无提示丢失。当前多数掉落/商店入口一次只传 1 个，但 `Inventory.add()` 和 `ItemFactory.make_any(..., count)` 都提供了多件数量路径。

**建议：** `has_space_for()` 按堆叠余量和空格容量计算是否能容纳完整数量；`add()` 要么完整分配全部数量，要么在不修改背包的前提下失败。
