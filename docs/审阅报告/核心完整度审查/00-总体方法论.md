# 核心完整度审查 · 总体方法论

> 审查对象：《末法纪元：最后的守护者》（Godot 4.7.2 / GDScript）**核心系统**的完整度与健壮性。
> 发起人诉求：试玩后认为「核心打怪升级链路」已基本健全，希望确认「除美术、后续任务、地图、装备配置之外，当前游戏是否已比较完整」。
> 基线快照：`773b7d1`。
> 文档定位：本文件只说明**怎么审、按什么标准判、产出什么**，不承载具体结论。具体结论见各问题域独立报告。

---

## 1. 审查目标

回答一个问题：**当前版本在「核心玩法闭环 + 系统健壮性 + 可交付性」三个维度上，是否已经达到「核心完整」的标准？**

「核心完整」在本项目中的具体含义（判定基准，不自行发明）：

| 维度 | 「完整」的定义 | 反面 |
|---|---|---|
| 玩法闭环 | 产品文档 00《核心循环总览图》中每个节点都有可运行实现与反馈，能从头到尾走通一遍 | 某节点只有数据/文档没有接线，或走到一半断链 |
| 系统健壮性 | AGENT.md §6/§9 的生命周期、边界、错误处理、存档兼容约束全部满足 | 可复现的进度丢失、重复结算、静默失败、崩溃 |
| 可交付性 | 能导出、能长时间游玩、能读档续玩，验收入口（测试/压测）可用且结论可信 | 只有开发环境可跑，或测试结论与真实行为不符 |

## 2. 审查边界

**在范围内（本次审查）**

- 核心循环与战斗结算：伤害公式、暴击/闪避/上限、目标选择、死亡与复活、等级差、精英词缀、Boss 阶段与首通。
- 系统架构与数据驱动：数据表加载与校验、单一事实源、模块职责边界、Autoload 使用、公共接口稳定性、跨表引用完整性。
- 装备/背包/仓库/技能/消耗品/坐骑/**系统逻辑**（不含具体数值与素材）。
- 经济与成长**逻辑**：金币收支路径、升级结转、派生属性缓存与失效。
- 存档与兼容：schema 版本、迁移、备份恢复、原子性、跨图/跨档状态一致性、运行态与落档边界。
- 任务**系统机制**（状态机、进度推进、奖励结算、放弃重接），不含后续任务内容。
- 地图**系统机制**（加载、切换、迷雾、寻路、刷新、墓碑、门禁），不含后续地图内容。
- 性能与长时稳定：热路径、缓存失效、节点/内存增长、既有压测基准。
- UI/输入健壮性、错误处理与边界、测试覆盖、发布就绪度。

**明确排除（用户已声明为后续工作，不作为本次「完整度」扣分项）**

- 美术资源（形象、场景、图标、特效素材）。
- 后续章节的地图、任务、怪物内容。
- 具体装备/物品/数值配置的填充与调平。
- 第二章及以后的功能开发。

> 排除项若**影响核心机制正确性**（例如某系统代码已写但没有任何可用数据导致链路实际不可走），仍会在对应报告中被记录为「内容缺口」而非「系统缺陷」，并明确区分。

## 3. 审查准则来源（唯一权威）

| 来源 | 用途 |
|---|---|
| `AGENT.md` | 性能架构、游戏体验、注释与可读性、生命周期、存档、提交规范——**判定工程健壮性的主要依据** |
| `docs/产品文档/`（00–12 + 附录A） | 玩法事实源：核心循环、伤害/成长公式、系统规格——**判定「玩法是否按设计实现」依据** |
| `docs/工程文档/`（01–27） | 各里程碑实施方案与验收记录——**对照「计划已声明完成」与「代码实际接线」** |
| `docs/审阅报告/第一轮代码审阅.md` 及回复 | 上一轮结论与修复记录，用于确认旧问题是否已闭环、是否引入新问题 |
| `docs/素材设计/`、`docs/游戏创意/` | 仅在涉及机制（如换装 look、掉落持久化）时作为补充依据 |

**准则优先级**：产品文档定义「应该是什么」，代码定义「实际是什么」，AGENT.md 定义「怎样才算做得对」。三者冲突时，以产品文档为需求基准，并在报告中标注实现偏差。

## 4. 判定标准

### 4.1 完整度分级（用于「核心是否完整」）

| 级别 | 判据 |
|---|---|
| **A 已闭环** | 有实现、有反馈、可存档、有对应自动化验证；边界与错误路径已处理 |
| **B 基本可用** | 主路径可走通，但边界/异常/长时稳定性存在未处理项，或缺少自动化验证 |
| **C 部分接线** | 数据/文档存在但运行时代码只实现了一部分，主路径不完整 |
| **D 缺失** | 需求存在但无实现 |
| **E 已知缺口** | 实施计划已声明「后续/待做」，且不属本次边界（记为事实，不扣分） |

### 4.2 缺陷严重度（用于具体问题）

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0 阻断** | 导致进度丢失、崩溃、核心循环不可走通 | 坏档清空进度、Boss 流程死锁 |
| **P1 严重** | 可复现的错误行为、重复结算、静默失败、明显体验断裂 | 重复发放奖励、购买扣钱不给货 |
| **P2 一般** | 边界不严谨、缺少校验、缓存未失效、提示不清 | 极端输入截断、UI 状态残留 |
| **P3 建议** | 可读性、注释、结构一致性、可维护性 | 命名、注释缺失、重复逻辑 |

### 4.3 证据等级

| 等级 | 说明 |
|---|---|
| **E1 运行证据** | 隔离测试通过/失败输出、实测压测数据、原生窗口复现截图 |
| **E2 代码证据** | 具体文件与行号的静态阅读结论，可被他人复核 |
| **E3 文档证据** | 数据表、产品/工程文档中明确记录的事实 |
| **E4 推断** | 无直接证据、基于经验的合理推断——**报告中必须显式标注「推断」，不得与实测结论混排** |

**原则**：能测量的必须先测量（AGENT.md §10）。无法测量的结论一律标注推断。

## 5. 证据采集手段

1. **静态阅读**：逐域通读相关脚本、Autoload、数据表，交叉核对产品/工程文档。
2. **隔离测试**：`python3 tools/run_isolated_tests.py <TestName>`（隔离工程 + 独立 `user://`，不触碰真实存档）；必要时 `--committed-tree` 取改动前基线。判定通过需退出码 0、输出含「全部通过/PASS」、无 `SCRIPT ERROR`。
3. **数据表交叉校验**：对照数据加载器的启动校验输出，核对跨表引用（quests→monsters→maps、dropTables→equipments 等）。
4. **基准对照**：性能类结论对照 `docs/审阅报告/大地图性能优化实施记录.md` 等既有基准；引擎/地图/玩法有显著变化时重新测量。
5. **既有报告回归**：确认第一轮审阅 4 项是否闭环，是否引入新回归。

> 环境约定：Godot 可执行文件 `/Applications/Godot.app/Contents/MacOS/Godot`；测试须在非沙箱模式下运行（Godot 需写 `~/Library/Application Support/Godot`）。测试前若新增 `class_name`，先跑一次 `--import` 注册全局类。

## 6. 执行流程（四段式）

```
① 总体方法论（本文件）
        ▼
② 完整审计计划（01-审计计划.md：问题域划分 / 每域查什么 / 证据来源 / 判定标准 / 产出清单）
        ▼
③ 用户确认方法论与计划（NotifyUser）
        ▼
④ 按计划逐域执行 → 每域一份独立报告（含证据、结论、改进建议、落地优化方案）
        ▼
⑤ 交付物清单（文件 / 内容 / 核心发现）
```

**每域报告结构固定**：

1. 覆盖范围与未覆盖项
2. 完整度评估（A–E 分级 + 依据）
3. 发现的问题（P0–P3，含位置链接、复现条件、影响、建议）
4. 证据与复核方法（命令 / 文件行号）
5. 落地优化方案（可执行的改造步骤）
6. 与既有文档的差异说明

## 7. 交付物规范

- 全部为**独立中文 Markdown 文档**，不得合并为单一汇总文档；对话中只给摘要与链接。
- 落点：`docs/审阅报告/核心完整度审查/`。
- 最终汇总产出**交付物清单**：文件名 / 内容 / 核心发现一行摘要。
- 分析过程使用的临时探针、脚本、截图不入库，用完即删。
- 本审查只产出文档与建议，**默认不改动代码**；如需修复，另行确认后单独提交。
