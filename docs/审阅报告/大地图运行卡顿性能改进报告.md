# 大地图运行卡顿性能改进报告

> 日期：2026-10-14。依据：当前工作区实际代码（包含尚未提交的修改），以及《大地图运行卡顿性能诊断报告》。
> 方法：静态调用链审查、Python 核算实际地图掩码与采样点数量、核对 Godot 官方绘制机制。检测到本机 Godot 为 4.7.2；本轮未启动游戏采集帧时间，也未修改游戏代码。以下优先级为实施与验证建议，不是已经测出的耗时排名。

## 一、结论与原报告修正

可以改进，且有几项可以先做范围较小的优化，再决定是否重构地形。

1. **优先拆分小地图底图与动态标记，并缓存投影参数。** 当前全图扫描之外，还有逐格重复地图查询、投影计算和数组分配，原报告低估了这一调用链。
2. **消除刷新器循环中的重复活跃计数。** 问题成立，但最坏平方级扫描只发生在通过距离、解锁等前置筛选的待生成普通怪点上，不能把全部 131 点当成每帧都执行全量计数。
3. **新增自动巡游集中寻路的改进项。** 最大地图首次巡游可能在一个物理帧中执行 624 次完整路线查询，是值得优先测量的尖峰来源。
4. **地形分块保留，但不应未经采样就作为第一项大改。** `ground.gd` 只在 `_ready()` 请求一次重绘；全图循环通常是首次构建绘制命令的成本，并非每帧执行 GDScript 全图循环。缓存命令的后续渲染仍有成本，是否成为持续瓶颈需要单独测量。
5. **碰撞合并与布局缓存主要针对切图。** 数量估算正确，但不能据此推断稳定游玩物理开销必然很高。

Godot 官方明确说明 `_draw()` 的命令会缓存，调用 `queue_redraw()` 才重新执行绘制逻辑：[Custom drawing in 2D — Updating](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html#updating)。因此必须区分“脚本重建绘制命令”和“渲染已有命令”。

## 三、优先改进方案

### P1：小地图分层、缓存与减少内层查询

代码依据：`scripts/ui/map_canvas.gd:23-44, 47-65, 104-126`，`scripts/systems/fog.gd:9-23`，`autoload/map_service.gd:114-129`，`autoload/data_loader.gd:75-85`。

当前链路：

- 可见时每 0.2 秒检查玩家和标记变化；有变化才请求重绘，因此站定且标记稳定时并非固定每秒重画 5 次。
- `fog_changed` 还会直接请求重绘；探索新区域时重绘频率可能超过 5 次/秒。同一帧的请求会合并，不能简单相加。
- 洞窟底图每次重绘遍历所有格，调用 `Fog.is_explored()` 的次数等于可行走格数。
- 每个探索查询经 `contains()`、`block_id()`、`block_grid()` 重复获取地图尺寸；地图表为数组，`get_entry()` 会线性查找地图。
- 每个已探索格 `_polygon()` 调用 4 次 `world_to_canvas()`；每次后者调用 `world_rect()` 和 `map_scale()`，而 `map_scale()` 又调用 `world_rect()`。也就是每格 8 次世界边界构造及地图尺寸查询。

在 lower_works 全探索时，仅洞窟底图循环就产生 **28,740 × (2 + 8) = 287,400 次地图尺寸查询/次重绘**，还不包含标记等开销。持续移动且按 5 次/秒重绘，约为 143.7 万次/秒。这是调用次数估算，不能直接换算毫秒或 FPS；未全探索时，投影调用数会更少。

建议分两步：

1. 每次绘制或尺寸变化时计算一次 dims、world_rect、中心与 scale，逐格仅做仿射变换；缓存本图探索字典和区块宽度，按区块查询探索状态，避免逐格调用通用查询链。底图仍按可行走格绘制，保留洞壁遮罩。
2. 分成底图 CanvasItem 与动态覆盖 CanvasItem。玩家位置、任务/Boss/NPC 标记只重画覆盖层；底图仅在地图变化、尺寸变化、探索变化时重建。先利用 Godot 自带绘制命令缓存，无需一开始引入 SubViewport。

继续优化：以 4×4 探索区块建立可行走几何缓存；为 `fog_changed` 增加新增区块信息或版本号。当前信号只有 map_id，无法直接得知脏区块。若使用纹理缓存，必须在新增探索时更新纹理内容；仅让节点重绘并不会自动更新缓存纹理。

失效条件：切图、读档/新档重置探索、控件缩放或尺寸变化；任务、解锁、语言、刷新点位置变化要更新标记缓存。保留地图点击坐标逆变换与出口可见性规则。

### P1：刷新器改为一次计数并复用，随后增加重试节流

代码依据：`scripts/world/spawner.gd:110-124, 143-182`。

当前每帧至少 O(N) 遍历；对通过距离与解锁筛选的待生成普通点，再 O(N) 统计存活数量。令 K 为这些候选点数，复杂度更准确地表述为 O(N + K×N)。10 只预算只约束章节二 normal，不能套用于精英或 Boss。

第一步建议采用**每轮一次统计的局部预算**，比立即引入长期计数器更容易控制一致性：

- `_process()` 开始统计一次有效普通怪数。
- 同轮成功生成普通怪时立即增加局部计数，退场时立即减少，确保同帧不会突破 10 只。
- 批量初始化的 `spawn_from_specs()` 也复用预算；不能仅修正运行循环而遗漏初始化 `_spawn()`。
- 存活节点判定、死亡清空 entry 与 `queue_free()` 的时序保持一致。

若改为长期计数器，应统一生成、死亡、距离退场和外部释放的注销入口，且有一次性标记，防止死亡与 tree_exited 双重减数。保留调试期全量校验。

第二步对满额/远距离点使用 0.1～0.2 秒候选检查间隔（建议值，需验证体验）；死亡、解锁或玩家跨区可触发提前检查。墓碑显示更新可独立降频，刷新到期仍从 `GameState.world_time` 判断，保持跨图跨档计时。最后再评估空间桶；131 点规模未必需要先引入空间索引。

### P1：自动巡游建立过程去掉逐点完整寻路

代码依据：`scripts/systems/auto_battle.gd:433-438, 480-509`，`scripts/world/ground.gd:107-117`，`scripts/world/cave_layout.gd:64-103`。

`_tick_roam()` 在巡游点为空时同步调用 `_build_roam_points()`。后者以 7 格间隔采样，并对每个可行走点执行 `ground.route()`；该函数同时执行 A* 和路径平滑，而此处只需要判断能否到达。lower_works 有 624 个这样的候选点。如果最终列表一直为空，还会在后续巡游帧重复构建。

推荐：

- 静态布局预计算连通区域编号，巡游候选只需检查与玩家是否属于同一连通区域；真正选中巡游目标后才构造平滑路线。
- 连通标记使用与 AStar 相同的通行规则；若采用四邻接，在当前要求对角两侧均开放的规则下可保持连通性判断，但仍需回归验证。连通性判断不能替代最终带碰撞半径的路线与移动验证。
- 增加“已构建”状态，区分未初始化与合法空列表；切图或布局变化时失效。
- 如暂不实现连通标记，可先按每帧时间预算分批生成巡游点，并把可达性查询与平滑路线分离。

附带优化：`_find_target()` / `_find_loot()`（auto_battle.gd:358-409）当前对多个候选构建平滑路径。先执行 Boss/黑名单/距离等便宜过滤，再按现有距离与血量规则排序，依次判断可达性直到找到首个有效目标；若需要路径，可复用已经计算的结果，避免选中后重复寻路。

`CaveNavigator.direction()`（cave_navigator.gd:14-28）已有缓存，但目标跨格会重新寻路。多个怪物追同一移动玩家时可能集中重算；应先记录每帧 route 次数和耗时，再决定是否加入重算间隔与错峰预算。任何节流都必须保留偏航处理和碰撞安全，不能用穿墙直线兜底。

### P2：按测量结果实施地形分块

代码依据：`scripts/world/ground.gd:47-75, 169-247`。

先确认 `_draw()` 调用次数与首次构建耗时，以及隐藏 Ground 的对照帧时间。如果脚本尖峰来自首次构建，则分帧建立或预生成静态几何；如果稳定阶段渲染明显受 Ground 影响，则采用 16×16 或 32×32 格分块进行可见性管理（候选参数，需比较）。

分块应使用相机可见矩形反投影到网格，增加纹理/悬崖外扩边距与预加载环；只在可见块集合变化时处理，不随每个像素移动重建。首轮可保持全部块加载，先测可见性收益，再考虑按需实例化。

避免给每格创建独立 Node2D。章节二目前是阻挡多边形与线网格，直接换 TileMapLayer 并不保证收益。若后续正式纹理采用 TileMapLayer，应对照现有方案测量，不承诺自动减少 draw call 或 GPU 耗时。corruption_source 分块必须预先保留全局墙边端点计数及绘制顺序，防止块边界出现假断头、接缝或遮挡错误。

### P2：布局重复构建与边界碰撞

代码依据：`scripts/world/cave_layout.gd:12-46`，`scripts/world/ground.gd:135-153`，`autoload/map_service.gd:430-444`。

`entry_point()` 为获取一个默认出生点会新建完整 CaveLayout（含 AStar）；Ground 载入地图又会新建同一布局。该默认落点路径被调用时会有重复构建。可优先缓存按布局资源版本区分的默认可行走落点，避免为单个坐标重复建立 AStar；布局掩码、边界列表与连通标记也可缓存。共享 AStar 前要明确其可变配置和使用方式，不宜无条件把所有布局实例改成同一可变对象。

522 个洞壁 shape 是静态边界，不是 522 个独立刚体。第一步可让这些碰撞节点共享同一个不再修改的 ConvexPolygonShape2D 资源，减少资源重复分配；形状实例数量仍然相同。仅当初始化/物理采样证实有收益时，再合并共线边界。必须验证合并后的接触轮廓、角落和玩家碰撞半径，不能直接合并包围盒造成走廊封堵。

## 四、验证与实施顺序

先增加可关闭的计数/耗时采样：MapCanvas 重绘次数及底图耗时、Spawner 候选数与计数调用次数、route 次数与总耗时、巡游构建耗时、布局构建与碰撞装配耗时。用 `Time.get_ticks_usec()` 记录函数时间；以低频汇总输出，避免逐格/逐帧日志影响结果。

| 场景 | 重点指标 | 对照方式 |
|---|---|---|
| 进入 lower_works，等待稳定 | 切图耗时、首帧峰值、布局实例数 | 区分资源加载、布局、碰撞、首次绘制 |
| 站定 / 已探索区域移动 / 新区域移动各 60 秒 | 帧时间中位数、P95、P99、小地图重绘次数 | 隐藏地图 UI 与正常 UI 对比 |
| 打开大地图并持续移动 | 两个 MapCanvas 各自耗时 | 检查是否同时重建底图 |
| 达到 10 只普通怪，靠近密集刷新区 | 计数调用数、候选数、脚本时间 | 一次计数前后对比 |
| 首次进入无怪巡游状态 | 巡游构建峰值、route 次数 | 624 个候选集中查询与连通缓存对比 |
| 战斗追逐与大量掉落 | 物理帧寻路峰值、重算分布 | 检查候选筛选与路径复用 |
| 保留碰撞并临时隐藏 Ground | 稳定帧时间、渲染相关指标 | 判定是否值得实施地形分块 |

固定目标设备、角色状态、分辨率、缩放与地图路线；对冷加载与热加载分别记录。使用实际窗口运行测渲染；headless 只适合布局、计数、寻路等逻辑基准，不能作为 GPU/真实帧率证据。

建议按独立改动实施：**采样基线 → 小地图投影缓存及分层 → 刷新器预算复用 → 巡游可达性缓存 → 根据结果选择地形分块或加载优化**。每项独立比较，避免多项同时修改后无法归因。

验收重点：玩家移动不再触发静态底图重建；刷新预算不超限且倒计时持久化正确；巡游构建不再逐点平滑寻路；探索不泄露洞壁；地图点击、任务标记、Boss 墓碑、自动拾取及无路目标行为保持正确。回归可选用现有 CaveNavigationTest、CaveAutoBattleTest、ChapterTwoEncountersTest 和 ChapterTwoRoutesTest，具体入口参照现有测试场景与隔离运行器。

以 60 FPS 为目标时，整帧预算约 16.67 ms，但是否达标应由目标设备实测决定。本报告不提供未经测量的 FPS 增幅或工期承诺。
