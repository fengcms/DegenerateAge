# 81 · 装备重铸：词条锁定（保留满意词条，只重掷其余）

> 状态：**已落地**（Q1—Q6 全部按建议拍板）｜2026-10-21
> 需求原文：「重铸目前是完全随机的。如果我特别满意某条属性，应该可以保留这条属性，然后重铸其他的属性。」
> 本文给出根因、设计与分层改造方案；**拍板结果与实施记录见 §4 / §7**。

---

## 0. 一句话结论

| 项 | 现状 | 建议 |
|---|---|---|
| 重掷范围 | **整件重掷**：`ItemFactory.reroll_affixes` 丢弃全部旧词条，按品质重新掷满 `affixCount` 条 | 新增「锁定集合」：锁定的 `stat` 连同**数值**原样保留，其余重掷 |
| 可锁对象 | 无 | 只锁**词条**（`affixes` / `pctAttrs`）；基底 `rawBaseAttrs`、品质、星级、等级仍不动 |
| 锁定条数 | 无 | **最多 `affixCount − 1` 条**（普通 0、优秀 0、稀有 1、史诗 2、传说 3），全锁＝花钱没反应 → 拒绝 |
| 计价 | `500 × (60 + 0.75L)`，与锁定数无关 | 锁定加价：`cost × (1 + lockFactor × n)`，`lockFactor` 建议 **0.5**（每条 +50%） |
| 落档 | — | **不落档**：面板内按 `instanceId` 记忆，关面板清空 ⇒ schema 不变（13 个存档零影响） |

🔴 **最大约束**：`ItemFactory._roll_affixes` 的随机数调用顺序被 `ReforgeTest` 用例 14 的
**20 行固定种子快照**锁死。锁定功能必须做到「**零锁定时逐字节同结果**」——加参数、不加分支重排。

## 1. 现状盘点

### 1.1 重铸链路（三层，各司其职）

```
scripts/ui/reforge_panel.gd（选装备 → 看词条 → 点按钮）
  └─ GameState.reforge_equipment(source, key, expected_id, rng)   autoload/game_state.gd:1232
       ├─ Reforge.can_reforge(item)            scripts/systems/reforge.gd:72   四道拒绝
       ├─ Reforge.cost(Equipment.level_req())  scripts/systems/reforge.gd:41   500×(60+0.75L)
       ├─ ItemFactory.reroll_affixes(item, rng) scripts/systems/item_factory.gd:210
       │    └─ _roll_affixes(item_id, quality, affix_scale, rng)   ← 唯一的掷词条实现
       ├─ add_gold(-price)  →  写回 item["affixes"] / item["pctAttrs"]
       └─ EventBus.equipment_changed / inventory_changed + toast
```

`reforge_panel` 只是个「选装备 + 显示 + 按按钮」的壳，**规则全在 `Reforge`、掷点在 `ItemFactory`**。
因此锁定要落的点很清楚：**`_roll_affixes` 的输入多一个「锁定集合」**，其余三层各加一个透传参数。

### 1.2 词条到底长什么样（决定「锁什么」）

```jsonc
"affixes":  [{"stat": "atk", "value": 21}, {"stat": "hp", "value": 124}]   // 固定值，按实例等级缩放
"pctAttrs": [{"stat": "hpPercent", "value": 0.054}]                        // 百分比，最多 1 条
```

- 条数 = 品质 `affixCount`：**普通 0 / 优秀 1 / 稀有 2 / 史诗 3 / 传说 4**（`equipmentRules.json`）。
- 词条池：60 个模板的 `affixPool` **全部是同一组 7 个** `atk / def / hp / mp / hpPercent / mpPercent / cdr`；
  其中 `fixedAffixes` 登记 4 个（atk/def/hp/mp）、`percentAffixes` 登记 3 个（hpPercent/mpPercent/cdr），
  **池内每个 stat 都有归属**，不存在「无法归类的锁定目标」。
- 同一实例内 **stat 不重复**：固定词条从候选里 `remove_at` 后不再放回，百分比最多 1 条。
  ⇒ **可以用 `stat` 字符串当锁定键**，比用数组下标稳（重掷后顺序会变，下标会错位）。

### 1.3 🔴 随机数红线（改动前必读，`item_factory.gd:154`）

```
randf()（是否出百分比）→ randi_range（选哪个百分比属性）→ randf_range（百分比数值）
  → 循环 { randi_range（选固定属性）→ randi_range（固定数值） }
```

移动任何一次调用，1—60 级所有掉落全部改变，而游戏照常运行、零报错 —— 只有
`tests/reforge_test.gd` 用例 14 的 20 行快照能发现。**锁定的实现必须保证空锁定时这条序列原样执行。**

### 1.4 现有面板（`reforge_panel.gd`）

- 词条区是**单个多行 `Label`**（`_affixes.text = "\n".join(lines)`），没有行级控件 ⇒ 没有地方放锁按钮。
- 价格行 `ui.reforge_panel.p006`（费用 / 持有）；按钮 `p004`；反馈 `p008`（旧 → 新）。
- **一掷即改、无二次确认**；重掷结果与原来完全相同时会提示 `p009`（防「以为按钮坏了」）。

### 1.5 费用与节奏（改动会影响谁）

| 项 | 值 | 谁在断言 |
|---|---|---|
| `Reforge.cost(L)` | L60 52,500 / L70 56,250 / L100 67,500 / L1000 405,000 | `ReforgeTest` 用例 1、2、3 |
| 修理费（`Durability`） | `Reforge.cost(L) × 0.075` | `DurabilityTest`（**传 0 条锁定，不受影响**） |
| 重铸频率 | 四档约 5.2 / 5.2 / 5.9 / 8.8 次每小时 | `EconomyTest` 用例 3（落在 5—9） |

⇒ **基础 `cost` 一律不动**，只在「有锁定」时乘系数。`EconomyTest` / `DurabilityTest` 天然不受影响。

## 2. 设计要点（六条）

### 2.1 锁定粒度：整条（`stat` + `value` 全保留）

锁定的那条**数值也不变**——玩家说的是「保留这条属性」，属性是「生命 +124」这个整体。
（备选：只锁 `stat`、数值仍在区间内重掷。见 Q1。）

### 2.2 上限 `affixCount − 1`，全锁必须拒绝

锁满 = 花 131,250 金买一个「什么都没变」，比普通品质重铸更恶劣（那时至少玩家知道没词条）。
`Reforge` 侧直接拒绝并返回原因，**扣费前**拦下（与现有「金币不足 / 普通品质 / 脏实例」同口径）。

### 2.3 锁定的 `stat` 必须从候选池里剔除

否则未锁定部分可能又掷出同一个 `stat` ⇒ 出现两条 `hp`。⚠ 这个 bug **不会报错**：
`Equipment.bonus()` 是把词条按 stat 累加的，两条 `hp` 只是静默叠加，玩家看到的是「我锁的那条数值变了」。

### 2.4 百分比词条特殊处理：跳过 `randf()` 判定

百分比词条的有无由 `randf() < percentChance(0.5)` 决定。**锁定 `hpPercent` 后必须跳过这次判定**，
否则 50% 概率整条消失 —— 表现为「锁了却没保住」，且是间歇性的，最难查。

### 2.5 结果顺序：锁定条目排前面

`fixed = [锁定条目（按原顺序）] + [新掷条目]`。零锁定时为空前缀 ⇒ 与原顺序完全一致；
有锁定时玩家一眼看到「这几条没动」。UI 的行顺序跟着数组走，无需额外排序。

### 2.6 不落档

锁定是**面板内的一次性选择**，写进存档要动 schema / 迁移 / 校验三处，收益却只是「下次打开还记得」
（而玩家通常一次会话内连续重掷完）。故：`_locked: Array[String]` 只活在面板里，
按 `instanceId` 记忆 —— 重铸后 `instanceId` 不变 ⇒ **连续重掷时锁定保留**（这是关键体验），
切换到另一件装备或关闭面板则清空。

## 4b. 待拍板（Q1—Q6，给出推荐与依据）

### Q1 · 锁定粒度

| 选项 | 含义 | 评价 |
|---|---|---|
| **A（推荐）整条锁定**：`stat` + `value` 全部保留 | 「生命 +124」原封不动 | 与需求原文一致；实现最简，判据最硬（逐字节相等） |
| B 只锁属性类型：`stat` 保留，数值在区间内重掷 | 保留「生命」但可能从 +124 变成 +80 | 符合「追求极限数值」的刷词条玩法；但玩家说「保留这条属性」通常指整体，且可能出现「锁了反而变差」的挫败 |
| C 只锁类型 + 数值只增不减 | 多次掷取 max | 语义复杂、费用模型也要跟着变，本期不建议 |

### Q2 · 锁定条数上限

| 选项 | 含义 | 评价 |
|---|---|---|
| **A（推荐）最多 `affixCount − 1`** | 传说 3 / 史诗 2 / 稀有 1 / 优秀 0 / 普通 0 | 永远至少有一条在变，重铸才成立 |
| B 不限（允许全锁） | 玩家可锁全部 | 等于花钱买「什么都没变」，必须额外做提示拦截，纯增复杂度 |

### Q3 · 计价（🔴 不涨价会让「锁定」成为严格优势 —— 没有任何理由不锁）

| 选项 | 系数 | L60 锁 1/2/3 条 | L1000 锁 1/2/3 条 | 评价 |
|---|---|---|---|---|
| **A（推荐）每条 +50%** | 1.5× / 2× / 2.5× | 78,750 / 105,000 / 131,250 | 607,500 / 810,000 / 1,012,500 | 明显肉疼但不至于锁不起；保留「锁 vs 不锁」的真取舍 |
| B 每条 +100% | 2× / 3× / 4× | 105,000 / 157,500 / 210,000 | 810,000 / 1,215,000 / 1,620,000 | 只适合「锁定即毕业」的后期定位；中期基本锁不起 |
| C 不涨价 | 1× | 52,500 | 405,000 | ⚠ **否决**：无成本 ⇒ 全员常锁，重铸从「赌博」退化成「定向洗练」，打金节奏（每小时 5—9 次）失衡 |

⚠ **如实标注**：锁定会把**实际**重铸频率从 5.2—8.8 次/小时拉低到（锁 1 条）3.5—5.9 次/小时。
这是玩家自愿加价的结果，**不改 `D-17` 的基础口径**，`EconomyTest` 的 5—9 断言仍按无锁定计算。

## 5. 验证口径

### 5.1 正向（`ReforgeLockTest`，12 组）

1. **空锁定回归**：同一固定种子下 `reroll_affixes(item, rng, [])` 与 `reroll_affixes(item, rng)` 逐条相等（守卫随机数红线）。
2. **锁定条目逐字节保留**：传说装备锁 `hp`，30 轮重掷后 `hp` 仍在、数值恒等。
3. **无重复 stat**：30 轮里结果 stat 集合无重复（防候选池漏剔）。
4. **百分比锁定**：锁 `hpPercent`，20 轮**全部**保留（防 `randf()` 抹掉）。
5. **条数守恒**：锁定后总条数仍等于品质 `affixCount`（五品质各测）。
6. **全锁拒绝**：锁满 → `ok=false`、原因含「全部」、金币不变、词条不变。
7. **非法 stat 拒绝**：锁一个不在该装备上的 stat → 拒绝且不扣费。
8. **费用随锁定数上涨**：`cost(L,1) > cost(L,0)`，且 **`gold_before − gold_after == cost(L,n)`**（有牙）。
9. **参数真接线**：手改 `json.lockFactor = 1.0` 后 L60 锁 1 条 = 105,000（写死常量即红）；还原后回落。
10. **已穿戴**：锁定后重铸，`Equipment.bonus()` 的变化量 = 未锁定词条的差值（锁定部分贡献为零）。
11. **不落档**：重铸后存档 JSON 无 `lock` 相关键；`save` → `load` 往返后 `_is_valid_save` 通过。
12. **UI**：锁按钮数 == 词条数；点 1 条后价格文本变化；锁到上限后按钮禁用 + tooltip 有原因。

### 7.2 三条实现红线（改前必读）

1. **空锁定必须逐句同路径**：`_roll_affixes` 只加两个默认空数组参数，锁定条目进结果**不消耗随机数**；
   「是否出百分比」的 `randf()` 判定只在 `locked_pct` 为空时执行。`ReforgeTest` 用例 14 的 20 行快照 + 本工程用例 1 双保险。
2. **锁定 stat 必须从两张候选池里剔除**（固定池与百分比池）—— 否则掷出两条同 stat，`Equipment.bonus()` 按 stat 累加 ⇒ 静默叠加、零报错。
3. **百分比锁定必须跳过 `randf()`** —— 不跳就 50% 概率整条消失；而「总数守恒」断言**抓不住**它（固定词条少掷一条补上），
   必须断「百分比最多 1 条」+「该 stat 恰好 1 条」（见 §7.4）。

### 7.4 ⚠ 首轮两条负向假绿（本批最大教训）

| 注入 | 首轮结果 | 根因 | 修法 |
|---|---|---|---|
| N-3 百分比锁定仍走 `randf()` | **绿** | 只断言「hpPercent 还在」——`percent` 先装锁定条目再加一条新掷的，取第一条仍是锁定值；**总数依旧守恒**（固定词条少掷一条），条数断言也绿 | 补「`pctAttrs` 最多 1 条」+「hpPercent 恰好出现 1 次」 |
| N-7 非法 stat 静默丢弃 | **绿** | 双保险：`Reforge.validate_locks` 之外，`_split_locked_entries` 取不到也会失败 ⇒ **只删一层被另一层接住** | 注入改为两层一起静默丢弃（与真 bug 同形） |

> 两条都不是「代码是对的」，而是**断言/注入本身不够硬**。
> 判据：① 「某条还在」这类**存在性**断言，永远要配一条**计数**断言（恰好 1 次 / 至多 N 条）；
> ② 负向没红先怀疑注入形态，尤其是「双保险只拆一层」——这与 §7 坑 20 同源。
