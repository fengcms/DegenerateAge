# 套装加成（品质套装 + 星级阶梯）分析与实现方案

> 状态：**✅ 已完成**（2026-10-20）。拍板结果：**D1 = B / D2 = A / D3 = A / D4 = A**，落地记录见 §10。核对日期：2026-10-20。
> 需求原话：全身穿整套同颜色装备有加成 —— 蓝 2% / 绿 5% / 金 10% / 紫 20%；
> 另按星级叠加 —— 全身 +6 星 3% / +8 星 5% / +10 星 10% / +12 星 20%；
> 全紫全 12 星共 **40%**。请分析是否合理、怎么实现。

## 0. 一句话结论

**机制合理、代码上很好落（一个纯函数 + 四个门面改法），但你给的两个数字背后有三件事必须先定：**
① 「全身」到底多严 —— 严格 14 件同品质在当前的随机掉落体系下，紫档实际几乎不可能达成，还会诱导玩家**故意穿更差的装备**；
② 「全部属性」的边界 —— 照字面乘会把生命**二次放大到 1.96 倍**，把攻击间隔乘成**负收益**；
③ 40% 是叠在「品质 2.4× × 星级 2.2× = 5.28×」之上的，最终 ×1.4 —— 量级对得上「终局奖励」，但会让 L60 的 Boss **从「打不动」变成「早就打不动」**。

真数值见 §3，全部用真实模板与 `Balance` 基线算出来的，不是估的。

## 1. 需求口径对齐

### 1.1 颜色 → 品质映射（这一步最容易错）

| 你说的 | 配置里的 key | 产品名 | 代码色值 | 品质倍率 | 词条数 |
|---|---|---|---|---|---|
| 白（没提） | `common` | 普通 | `d8d8d8` | 1.0× | 0 |
| **蓝** | `uncommon` | 优秀 | `4aa3e0` | 1.2× | 1 |
| **绿** | `rare` | 稀有 | `46c46a` | 1.5× | 2 |
| **金** | `epic` | 史诗 | `e0c04a` | 1.9× | 3 |
| **紫** | `legendary` | 传说 | `b46ae0` | 2.4× | 4 |

⚠️ 注意产品正文里 `epic` 叫「**史诗**」、界面色是**金黄**；`legendary` 叫「**传说**」、色是紫。
你说的「金装 / 紫装」正好对应 `epic` / `legendary`，本方案按此实现。**白色 `common` 不给加成**（它是过渡品，也是节奏基线，见 §4.4）。

### 1.2 两个维度独立判定、**相加**

```
套装加成 = 品质档 + 星级档
全紫全 12 星 = 20% + 20% = 40%   ← 与你说的 40% 一致，确认是加法不是乘法
```
若是乘法会得到 1.20 × 1.20 − 1 = **44%**，与你的 40% 对不上，所以按加法实现。

### 1.3 「全身」的判定基数 = **14 个槽**

`Equipment.SLOT_DEFS` 是 14 槽（10 种部位，护腕 / 护膝 / 手镯 / 戒指各两格）。
判定：**14 槽全部有装备**，且**全部 ≥ 目标品质** → 取其中**最低品质**那一档。
星级同理：**全 14 件的最低星级** ≥ 6/8/10/12 中的某一档。

- 空 1 槽 ⇒ 无品质加成、无星级加成（显示「还差 1 件」）
- 13 件紫 + 1 件蓝 ⇒ 算**蓝档 2%**（最低品质决定），这是「整套」语义的必然结果
- 13 件 +12 星 + 1 件 0 星 ⇒ 星级档为 0

## 2. 现状勘察：改动点在哪儿、会不会漏

### 2.1 属性链路只有四个出口（好消息）

```
Equipment.bonus(v14槽)      ← 汇总已穿戴装备的固定值 + 百分比
        ↓
GameState.equip_bonus()
        ↓
   total_attack()      ← 各 1 处实现
   total_defense()
   max_hp()            ← 内部还调 total_attack / total_defense
   max_mp()
        ↓
玩家战斗 / 怪物结算 / 人物面板 / HUD / 血蓝条 / 药水百分比  全都走这四个门面
```

全部调用方（已扫）：`player.gd`（攻击、施法、复活、红蓝条）、`monster.gd`（受击两处）、
`consumable.gd`（药水百分比上限）、`character_panel.gd`（面板显示）、`save_manager.gd`（读档收敛 HP）。

**结论：只改 `game_state.gd` 这四个函数，全局生效，不需要碰战斗与 UI 的数值逻辑。**

### 2.2 🔴 最大的技术陷阱：`max_hp()` 会二次放大

现在的公式是：

```gdscript
max_hp = (BASE_HP + 等级×HP_PER_LV + total_attack×2.0 + total_defense×4.0) × (1+hpPct) + hpFlat
```

如果直接把套装加成做进 `total_attack()` / `total_defense()`，那么 HP 会变成
`1.4 × 1.4 = 1.96 倍` —— 玩家看到的是「+40%」，实际血条涨了 **96%**。

**正确做法：拆一个「不含套装」的内层函数，`max_hp()` 内部继续用内层值，只在最外层乘一次：**

```gdscript
func _base_attack() -> int:  # 不含套装
	return int(player.attack) + int(round(float(equip_bonus().get("atk", 0.0))))

func total_attack() -> int:
	return int(round(float(_base_attack()) * (1.0 + set_bonus_pct())))

func max_hp() -> int:
	var base := BASE_HP + level*HP_PER_LV + _base_attack()*HP_PER_ATK + _base_defense()*HP_PER_DEF
	var raw := base * (1.0 + pct) + flat
	return int(round(raw * (1.0 + set_bonus_pct())))   # 只在这里乘一次
```

这样「全部属性 +40%」精确等于「面板上攻击 / 防御 / 生命 / 法力四项各 ×1.4」，可断言、可验证。

### 2.3 🔴 第二个陷阱：`attackInterval` 乘 1.4 = **变弱 40%**

`BONUS_KEYS` 里有 13 个键，其中：

| 键 | 乘 1.4 的后果 |
|---|---|
| `attackInterval` | 攻击间隔**变长** ⇒ 攻速掉 29%，**负收益** |
| `movementSpeed` | 移速 ×1.4 ⇒ 手感与地图引导全变，且不在「属性」直觉内 |
| `cdr` / `criticalChance` / `dodge` / `block` | 乘 1.4 会被推向上限（CDR 上限 50%），战斗节奏剧变 |
| `criticalMultiplier` | 2.0× → 2.8×，单条改动 = 全盘伤害 ×1.4 |

**所以「全部属性」必须给出明确边界**，见 §6 D1。我推荐只乘 **4 项主属性**（攻 / 防 / 生命 / 法力）。

### 2.4 现有代码里没有「套装」概念

已搜全仓：`套装` 只在两处出现 —— `item_factory.gd` 的「第 N 套装备基底」（这是**等级档**，同名不同义）和
`docs/产品文档/1-20级装备现行目录.md:27` 的「**不制作…套装奖励**」。
👉 后者是本需求的**直接冲突项**，落地时产品文档必须同步改写口径。

## 3. 数值影响（全部按真实模板算，不是估）

### 3.1 L60 满 14 件各档战力（纯基底，不含词条）

基准：基础攻 130 / 防 64（`Balance`），L60 一套循环套基底合计 **攻 137 / 防 196**。

| 套装状态 | 套装% | 总攻 | 总防 | 最大 HP | 击杀归一 Boss 次数 | 可挨打次数 |
|---|---|---|---|---|---|---|
| 全 common 0★（= `PaceTest` 基线） | 0 | 267.0 | 260.0 | 2,104 | **123.7** | **7.3** |
| 全蓝 0★ | 2 | 300.3 | 305.2 | 2,362 | 105.7 | 8.8 |
| 全绿 0★ | 5 | 352.3 | 375.9 | 2,765 | 86.2 | 11.9 |
| 全金 0★ | 10 | 429.3 | 480.0 | 3,362 | 67.7 | 18.7 |
| 全紫 0★ | 20 | 550.6 | 641.3 | 4,302 | 50.6 | 43.3 |
| 全金 6★ | 10 | 601.1 | 725.8 | 4,689 | 45.8 | 82.1 |
| 全紫 6★ | 23 | 807.0 | 1,004.5 | 6,284 | 33.0 | **∞** |
| 全紫 8★ | 25 | 902.3 | 1,138.4 | 7,021 | 29.2 | **∞** |
| 全紫 10★ | 30 | 1,023.9 | 1,306.2 | 7,962 | 25.5 | **∞** |
| **全紫 12★** | **40** | **1,194.7** | **1,538.4** | **9,285** | **21.6** | **∞** |

> 表里只算**基底**。`legendary` 还有 4 条词条、`epic` 3 条 —— 实际值比上表更高。

### 3.2 🔴 一条必须说清的红线：破防阈值

`Combat` 的减伤是 `怪攻 − 玩防 × 0.5`，L60 归一 Boss 攻 **420** ⇒ **防御 ≥ 840 就完全不掉血**。

- 全紫 0★：防 641（还能打，43 次）
- **全紫 6★：防 1,004 → 直接越线**，可挨打变 ∞

也就是说：**在套装加成之前，「全紫 +6 星」已经让 L60 的 Boss 打不动玩家了。**
套装加成只是把这条线**提前到「全金 +6 星」（725.8，临界）**，再往前推到「全紫 0★」附近。

**这不是套装引入的新问题，是把既有问题放大了 1.4 倍。** 但作为产品判断，必须知道：
「+40% 全属性」不是「让玩家爽一点点」，而是**在已经溢出的曲线上再乘一个数**。

### 3.3 🔴 金币投入：全 12 星 = **2,057 万**

`Upgrade` 的成功率 100/90/80/70/60/50/40/30/20/10/10/5，费用 `500 × 1.5^星`。
单件**期望**成本（含失败重试）：

| 门槛 | 单件期望 | ×14 件 |
|---|---|---|
| +6 星 | 16,963 | **237,487** |
| +8 星 | 59,678 | **835,485** |
| +10 星 | 315,968 | **4,423,545** |
| +12 星 | 1,469,278 | **20,569,885** |

对照：L70 循环 Boss 单只 9,759 金币 ⇒ 全 12 星 ≈ **2,108 只 Boss**，而 60→70 升级只需 135 只。

**这是本项目迄今最大的单一金币 sink（≥ 15 个「60→70」的时长）。**
它会与 D-17 的重铸频率口径（5.20/5.20/5.89/8.84 次/h，按「金币全用于重铸」算）**抢同一笔钱**，
产品 13 的经济台账需要补一行说明：**升星优先的未来会显著压低重铸次数**，这是玩家选择，不是数值 bug。

### 3.4 品质档的可达性（这条最影响体验）

循环 Boss 的装备掉落（`DT_C7_Arena_Boss`）：

| 组 | 概率 | 品质分布 |
|---|---|---|
| 装备 1 | 100% | common 70 / uncommon 30 |
| 装备 2 | 100% | rare 75 / epic 25 |
| 装备 3 | 5% | legendary 100 |

粗算每只 Boss 的期望件数：`uncommon 0.30` / `rare 0.75` / `epic 0.25` / **`legendary 0.05`**。

而「全紫」需要集齐 **14 个槽**（10 种部位，4 种要两件）—— 这是典型的集邮问题，约需 **40–50 件传说**
⇒ **800–1,000 只 Boss**；「全金」约 160–200 只。全蓝约 130 只。

**结论：紫档是长线终局目标（以「天」计），金档是「周」级目标，蓝档才是多数玩家真正能吃到的那一档。**
这与你要的「诱导收集」并不矛盾 —— 但**必须让玩家看得见差距**，否则他不知道自己为什么没加成（见 §5.4）。

## 4. 三个真正的设计缺陷（这是你要的「是否合理」）

### 4.1 🔴 P1 · 严格整套会诱导玩家「故意穿更差的装备」

因为档位由**最低品质**决定，会出现这种局面：

> 玩家有 13 件绿装 + 1 件金装。当前套装档 = **绿 5%**。
> 若把金装换成绿装，单件属性下降，但套装档仍是 5% —— 没损失也没收益。
> 但如果反过来：13 件绿 + 刚打到 1 件金，想升到金档需要**再凑 13 件金** ——
> 中间这段时间，那件金装**放在背包里比穿在身上更「正确」**（穿了会拉高最低品质？不会，最低还是绿）。

实际不会「降级」，但会产生**另一种扭曲**：玩家会把「差一件就成套」的槽位**锁死穿旧件**，
拒绝升级单件（因为升级单件不涨档，反而占用了本该给"冲档"的槽位）。**结果是最优策略变成「平均分配、不许冒尖」**，与 RPG 玩家「优先强化武器」的直觉完全相反。

### 4.2 🔴 P2 · 「全部属性」没有边界

见 §2.2 / §2.3：`max_hp` 二次放大到 1.96 倍；`attackInterval` 变负收益；CDR / 暴击撞上限。
**必须给「全部属性」下一个可执行的清单**，见 D1。

### 4.3 ⚠ P3 · 与 `PaceTest` 的关系（好消息）

`PaceTest._dress()` 全部用 **`common`**（为了「纯基底、`affixCount = 0`」）。

👉 **只要白色 `common` 不给套装加成，`PaceTest` 的三条护栏（≤1.30 / 锯齿 ±2% / 可挨打 ≥5.5）一个都不会动。**
这是本方案能低成本落地的关键前提，也会写成守护断言 —— 若有人「顺手给白装也加 1%」，`PaceTest` 会立刻全红。

### 4.4 我的判断

| 维度 | 评价 |
|---|---|
| 机制形态 | ✅ **合理**。加法叠加、双维度独立、阶梯与稀有度匹配，是成熟做法 |
| 品质档数值 2/5/10/20 | ✅ 比例合适（品质倍率 1.2/1.5/1.9/2.4，加成 2/5/10/20 基本同构） |
| 星级档数值 3/5/10/20 | ✅ 与升星成本曲线（1.7万 / 6.0万 / 31.6万 / 147万）匹配，越投入越值 |
| 判定严格度 | ⚠ **偏严**。紫档实际不可达，且诱导「平均分配」 |
| 40% 的绝对量级 | ⚠ **偏激**。叠在 5.28× 之上，直接把 L60 Boss 的破防线打穿 |
| 落地成本 | ✅ **低**。一个纯函数 + 四个门面 + 一个 UI 行，**存档零改动** |

**建议：机制照做、数值照你给的做，但把「判定严格度」和「属性边界」两个开关做成配置项**，
后续调平衡不用改代码（见 §5.2）。

## 5. 实现方案

### 5.1 新增 `scripts/systems/set_bonus.gd`（纯静态、不引 GameState）

```gdscript
class_name SetBonus
extends RefCounted
## 套装加成：品质档 + 星级档，独立判定后相加。
## 唯一入口 `evaluate()`，只读 14 槽字典，不依赖 GameState / UI。

## 品质 → 加成（common 恒 0：它是节奏基线，且 PaceTest 全用 common）
static func quality_table() -> Dictionary
static func star_table() -> Dictionary

## 返回 {
##   "pct": float,              # 总加成，0.0 – 0.40
##   "quality": String,         # 达成的最低品质 key
##   "quality_pct": float,
##   "star": int,               # 达成的最低星级档（0/6/8/10/12）
##   "star_pct": float,
##   "worn": int, "missing": int,          # 已穿件数 / 空槽数
##   "next_quality": String, "next_quality_need": int,   # 距下一品质档还差几件
##   "next_star": int, "next_star_need": int,
## }
static func evaluate(slots: Dictionary) -> Dictionary
```

🔴 **遍历 `Equipment.SLOT_DEFS`，不遍历 `slots.keys()`**：脏档可能多出非标准键，
遍历 keys 会漏掉「某槽空着」的判定，直接让空槽白拿加成。

### 5.2 数值进配置，不进代码

`data/equipmentRules.json` 追加（**加字段，不 bump `ruleVersion`** —— 该字段无 schema 校验，只被 `.get()` 读）：

```json
"setBonus": {
  "quality": { "common": 0.0, "uncommon": 0.02, "rare": 0.05, "epic": 0.10, "legendary": 0.20 },
  "star":    { "6": 0.03, "8": 0.05, "10": 0.10, "12": 0.20 },
  "requiredSlots": 14
}
```

好处：以后调数值（比如嫌紫档太强改成 0.15）只动 JSON，不碰代码、不重跑负向。

### 5.3 `GameState` 四个门面

```gdscript
## 套装加成（品质档 + 星级档，相加）。派生值，不落档。
func set_bonus() -> Dictionary:
	return SetBonus.evaluate(equipment)

func set_bonus_pct() -> float:
	return float(set_bonus().get("pct", 0.0))

func _base_attack() -> int:      # 不含套装，供 max_hp 内部使用
func _base_defense() -> int:
func total_attack() -> int:      # = round(_base_attack * (1 + pct))
func total_defense() -> int:
func max_hp() -> int:            # 内部用 _base_*，最外层乘一次
func max_mp() -> int:
```

**不落档、不进 schema**：与 `equip_bonus()` 完全同源，读档后由装备重算，`_is_valid_save` 零改动。

### 5.4 人物面板（诱导闭环的关键，别省）

现状：`ui.character_panel.p005` 是一个 14 参数的大格式串，`stats_card` 里只有一个 `Label`。

推荐：在 `_stats` 文本**末尾追加**两段（零结构改动、零布局风险）：

```
战斗属性
……
冷却缩减  12.0%

套装  稀有（14/14）  +5.0%
　　　距 史诗 还差 3 件
强化  全 +6 星        +3.0%
　　　距 +8 星 还差 5 件
```

未成套时：
```
套装  未成套（13/14）  +0.0%
　　　还差 1 件，且 1 件品质不足
```

**这一行不是「锦上添花」**：没有它，玩家只会觉得「穿了紫装怎么没变强」，不会去凑。
RPG 里「差 1 件」的可见性，比加成本身更能驱动收集。

## 10. 落地记录（2026-10-20）

### 10.1 拍板结果与它改变的东西

**D1 = B**：不止四项主属性，**暴击率 / 暴伤 / 闪避 / 格挡 / CDR / 移速全部纳入**；`attackInterval` 反向。
这一条把 §2.3 里「排除 `movementSpeed`」的保守做法推翻 —— 移速 4.0 → **5.6 格/秒**，手感变化明显。
若试玩嫌快，把 `movementSpeed` 从 `equipmentRules.setBonus.scaledKeys` 里删掉即可（一行 JSON，不动代码）。

**「反着计算」的精确口径**：`attackInterval` 用 **÷ (1+pct)**，不是 **× (1−pct)**。
- 除法：0.8 ÷ 1.4 = **0.571 秒**，等价于「攻速 +40%」，与「全属性 +40%」对称。
- 乘法：0.8 × 0.6 = 0.48 秒 ⇒ 攻速 **+66.7%**，超出约定值。
`SetBonus.inverse_scale()` 只此一处，负向 N-6 就是用来钉死它的。

**D2 = A / D3 = A / D4 = A**：严格 14 槽、显示「还差 N 件」、白装 0%。
