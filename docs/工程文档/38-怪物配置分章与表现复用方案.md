# 怪物配置分章与表现复用方案

本文确定怪物数据拆分、外观复用和技能归属的工程方案，并记录实施状态。现状盘点按 2026-10-16 原始工作区核对；示例 ID 为设计示意，不代表已经存在的怪物。

## 一、结论与目标

把“地图刷出的具体怪物”和“可复用的美术动作资源”分开是合理的。一个怪物可以换外观，一套外观也可以供多个怪物使用。地图、任务、掉落和存档仍引用**具体怪物 ID**，而具体怪物再引用**外观 ID**。

但“技能”需要拆清含义：攻击、施法、受击、死亡的**动画**属于外观；技能的伤害、范围、冷却、目标选择、预警和异常状态属于**战斗规则**。不建议把战斗规则放进美术实体，否则只想复用野狼动画，却可能顺带继承另一只怪的伤害与招式。推荐以三层建模：

```text
地图刷新点 / 任务目标 / 掉落来源
       │ monsterId（稳定身份）
       ▼
具体怪物模板：名称、等级、数值、AI、奖励、外观引用、可选能力引用
       ├── appearanceId ──> 表现档案：贴图、方向、动画、帧率、锚点、头顶 UI 位置
       └── abilitySetId ───> 能力档案：招式规则、冷却、命中形状、效果、动画提示名
                                  （仅在确有可复用能力时抽取）
```

第一轮迁移先落地**具体怪物 + 外观**两层；已有 `bossSkill` / `specialAttack` 保留原位，确保行为不变。只有至少两个怪物实际共用同一规则，或者新增怪物需要复用已验证招式时，再引入独立能力档案。避免为 87 只怪物各建一个毫无复用价值的技能文件。

## 二、现状证据与问题范围

| 证据 | 当前行为 | 带来的限制 |
|---|---|---|
| `data/monsters.json` | 实测有 **87** 个条目，第一至六章依次为 **8、16、15、15、18、15** 个；每条混合名称、数值、掉落、`bossSkill`、`specialAttack`，个别还写 `headHpY` | 扩充章节时多人易改同一大文件；表现位置与战斗数值混在一起 |
| `autoload/data_loader.gd` | `TABLES.monsters` 指向单个文件；启动后建 ID 索引，`get_entry("monsters", id)` 查询 | 已有统一查询接口，可无感改为按清单聚合 |
| `scripts/entities/monster.gd` | 以 `monster_id` 选择第一章动画包、`c2_` 美术清单、四只怪的手写贴图分支；数个技能/行为也按 ID 或章节前缀分支 | 改数据文件本身不能实现外观复用，也不能立即把所有 AI 变为纯配置 |
| `scripts/entities/monster_actor_art.gd`、`scripts/entities/monster_animation_library.gd` | 第一章部分动画按怪物 ID 登记；后者为生成的 `preload` 表 | 动画已与伤害结算分离，但复用键仍是怪物 ID；预载数量与纹理成本需关注 |
| `scripts/entities/chapter_two_art.gd`、`data/chapter2_art_manifest.json` | 第二章按怪物 ID 查找可选美术包；本次读取的清单 `actors` 为空，缺包会回退占位表现 | 有帧尺寸、脚底锚点、状态校验基础，但接口仅服务第二章 |
| `data/maps/index.json`、`data/maps/chNN/*/map.json` | 地图已分文件，索引聚合后保留 `maps` 表接口；刷新点写 `monsterId` | 怪物可借用同一模式，地图引用无须变更 |
| `tools/balance_check.py` 等 | 仍有工具直接读写 `data/monsters.json` | 拆分时必须迁移工具入口，不能只改游戏加载器 |

从现有代码推断：视觉复用能降低重复贴图制作和维护成本，但**不会自动改善帧率**。特别是 `MonsterAnimationLibrary` 目前使用 `preload`，若把大量美术继续集中预载，启动耗时和常驻纹理内存仍可能增长。此项需要实施时同场景测量。

## 三、数据责任与引用规则

| 层 | 应包含 | 不应包含 |
|---|---|---|
| 具体怪物 `monsterId` | 稳定 ID、显示名称、种类、基础等级和数值、攻击范围/频率、移动与 AI、经验金币掉落、词缀、特殊行为配置、`appearanceId`、可选 `abilitySetId` | 贴图路径、帧尺寸、动画帧率 |
| 表现档案 `appearanceId` | 精灵/图集路径、方向顺序、帧数/帧率、脚底锚点、渲染倍率、名字血条相对位置、动画状态与技能动画提示名 | HP、攻击力、伤害系数、掉落、怪物名字、战斗冷却 |
| 能力档案 `abilitySetId`（后续按需） | 可复用技能的规则、形状、预警/冷却时间、效果、动画提示名 | 贴图、帧数据、独有怪物的等级/奖励；不能独立执行全套 AI |
| 运行实例 | 当前 HP、仇恨目标、冷却计时、所抽词缀、状态机、地图刷新等级 | 反写全局模板或共享美术资源 |

这里的 `kind`（普通/精英/Boss）是**玩法身份**，不能单靠共用外观改变。需要让精英/Boss 可辨识时，可由其专用表现档案或明确的局部视觉变体实现；共用图集时依然须检查轮廓、体型、预警和头顶标签可读性。碰撞与攻击距离属于玩法，不能只凭图像大小隐式决定；可见点击范围和头顶 UI 偏移可在表现档案配置，但必须与实际命中/交互测试一致。

## 四、目录与配置草案

沿用地图的章节清单与 README 做法，但一个章节下维护一个怪物数组，避免每只怪物都拥有一层目录：

```text
data/monsters/
  index.json                  # ["ch01/monsters.json", ..., "ch06/monsters.json"]
  README.md                   # 字段、章节归属和编辑流程
  ch01/monsters.json          # 本章拥有的具体怪物模板
  ch01/README.md              # 本章用途、怪物清单、地图/任务关系、数值口径
  ... ch02 至 ch06 同上
data/monster_appearances/
  index.json                  # 表现档案文件路径列表
  README.md                   # 方向、锚点、动画状态、素材来源及复用约束
  corrupted_wolf.json         # 一套外观一个档案；只为实际不同的外观建文件
  ...
assets/sprites/monsters/     # 继续使用现有贴图目录，必要时逐步按外观 ID 归整
```

章节归属取**模板设计归属**，不按刷新时实际等级自动搬家。比如第一章定义的怪物在别章地图按 `spawn_level` 刷新，仍归第一章；否则一个 ID 会因地图复用而在多个文件重复定义。索引只决定读取路径及顺序，不重复存放怪物属性。新增章节应登记索引并写章节 README。JSON 不添加注释；任何数据含义、来源、平衡意图和地图引用在 README 说明，修改时同步更新。

示意配置（省略其他沿用字段；两个代码块均为合法 JSON，数值与素材元数据仅作示意）：

```json
{
  "id": "c3_wolf_scout",
  "name": "灰谷游狼",
  "level": 23,
  "hpBase": 820,
  "attack": 72,
  "dropTableId": "DT_Example_C3",
  "appearanceId": "corrupted_wolf"
}
```

```json
{
  "id": "corrupted_wolf",
  "renderer": "directional_atlas",
  "frameSize": [40, 64],
  "footAnchor": [20, 58],
  "displayScale": 1.0,
  "headHpOffsetY": -64,
  "states": {
    "idle": {"path": "res://assets/sprites/monsters/wolf_corrupted/wolf_atlas.png", "frames": 8, "fps": 8},
    "walk": {"path": "res://assets/sprites/monsters/wolf_corrupted/wolf_walk_atlas.png", "frames": 8, "fps": 10}
  }
}
```

第二只新怪可以有不同 `id`、名称、等级、攻击与掉落，却引用相同 `appearanceId`。两只的任务追踪、击杀统计与存档身份仍独立。上例的帧数、锚点、名称与路径只是字段形状示意，**实施时须以真实图集尺寸/方向/帧数核定**；缺失 `attack` 等动画时先用现有可验证的回退规则，不直接将示例投入运行。

能力复用的最小接口可在第二阶段加 `abilitySetId`，指向 `data/monster_abilities/<id>.json`。具体怪物依旧持有普通攻击与 AI 参数；能力档案只表达可组合的招式，例如线形预警的半径、持续时间、伤害系数与 `animationCue`。如果要对同一能力改数值，优先新建明确版本 ID；暂不设计多层继承、任意深度覆盖或根据外观推断技能。动画提示必须能映射到表现档案的状态，或有经测试的中性回退。配置与结算事件的时钟以战斗系统为准，动画 `contact` 帧只做表现同步，不驱动伤害结算。

## 五、加载、校验与运行边界

1. `DataLoader` 参照现有 `_load_maps()`，读取 `data/monsters/index.json`，聚合数组，再建唯一 ID 索引。保持 `get_table("monsters")`、`get_entry("monsters", monsterId)`、地图 `monsterId`、任务和掉落引用原样可用。不在每个怪物的 `_process()` 中解析 JSON、扫描章节文件或动态合并字典。
2. 加载表现索引，按 `appearanceId` 建只读查找表；`Monster._ready()` 由统一工厂按外观 ID 装配，逐步撤掉怪物 ID、`c2_` 前缀的美术分支。现有第一章生成包和第二章可选清单通过适配/转换逐步接入，不能把空清单误认为已有美术。
3. 启动校验：索引路径不能越界或重复；每份文件类型正确；全局怪物 ID/外观 ID 唯一；每只怪物引用已登记外观或明确的 `placeholder`；检查地图/任务/掉落引用、战斗数值范围、动画必需状态、贴图存在、方向和帧尺寸、接触帧索引、技能动画提示。开发/构建阶段将正式配置错误报清楚并使验证失败；运行时缺少可选美术资源沿用占位回退并限频告警。
4. 共享的配置与纹理不可被某只怪物实例改写；HP、随机词缀、冷却与受击闪烁属于实例。贴图由资源系统/按地图或外观缓存复用，不为相同外观的每个实例重新生成图集。切图与数据重载时明确缓存生命周期。资源导出检查索引、JSON、引用的图集均被打入包；不得依赖编辑器里存在而导出缺失的动态路径。
5. 头顶血条、名字和体型先与脚底锚点统一坐标约定，再验证不同倍率、精英/Boss 与同图复用的布局。`headHpY` 等旧怪物级视觉字段迁移到表现档案前需盘点是否存在**同外观但不同角色尺寸**的合法差异；必要时允许极少量、明确命名的视觉覆盖，不能用它覆盖玩法碰撞。

## 六、实施顺序与每步验收

| 节点 | 交付内容 | 最低验收与提交边界 |
|---|---|---|
| 1. 清理数据入口 | 按 `ch01`—`ch06` 拆分 87 个具体怪物，建立索引、章节 README，迁移 `DataLoader` 加载；现有 ID 与全部字段逐条不变 | 用脚本比较拆分前后规范化条目的数量、ID、字段和值；启动校验、地图刷新/任务追踪/掉落及存档加载通过；独立提交 |
| 2. 改造工具与说明 | 更新 `tools/balance_check.py`、`tools/build_chapter_two_encounters.py`、`tools/extend_chapter_two_equipment.py`、`tools/check_chapter_two_art.py` 等直接读写总表的入口，更新 `docs/产品文档/10-数据配置与存档技术.md`、根目录 `AGENT.md` 中维护规则 | `rg 'data/monsters.json'` 排查活跃脚本；生成器只改所属章节且可重复运行；README 同步检查通过；独立提交 |
| 3. 外观档案与统一装配 | 为现有真实图集建立**唯一**表现档案；没有美术的共用明确占位配置；把第一章生成包和第二章清单接到统一解析器；为具体怪物加 `appearanceId` | 两个不同怪物 ID 指向同一外观时贴图/动画共享、数值/奖励/任务独立；原四只手写美术、首章精英/Boss、缺包回退均回归；独立提交 |
| 4. 可复用技能（有实际需求时） | 选至少一个重复招式迁出为能力档案；消除所覆盖的 ID 硬编码，其他旧技能保留 | 预警、命中、冷却、死亡中断、召唤、Boss 阶段与原行为对照；不得因为换外观改变伤害；独立提交 |

节点 1 可先于美术 AI 的资源整理完成。节点 3 不要求为所有 87 个模板制作新贴图；既有未完成的怪继续使用占位表现。节点 4 是**条件性**工作，不把所有章节 Boss AI 一次性重写。每步均按项目约定使用 Conventional Commits，并只提交本步相关文件。

## 七、风险、边界与复核方法

- **对游戏规则的影响**：目标是数据组织与资源复用，不调整现有 HP、攻击、爆率、刷新、跨地图任务链或 AI。只有重新设计能力时才另开数值评审。由于 `Monster` 中仍有按 ID/章节前缀的行为分支，把它们一概视为可通过 JSON 自动替换是错误的；逐个迁移并保留回归样本。
- **存档**：旧存档、地图和任务仍用原 `monsterId`，此方案不更名怪物 ID，也不把 `appearanceId` 写进存档。若后续不得不重命名，需单独迁移；不可借拆文件之机静默更名。
- **视觉辨识**：外观共享太多会让不同怪难认。重要任务怪、精英、Boss 可以使用独立外观或有明确差异的色相/轮廓档案；不能只换名字和数值便假定玩家能识别。
- **资源成本**：验收时固定地图、同时活动怪物数、镜头和设置，比较冷启动、首次刷出、切图、稳定战斗的加载耗时、帧时间中位/P95、纹理内存及资源数量。复用贴图可能减少重复资源，但在未测量前不承诺 FPS 提升。
- **检查方法**：静态校验覆盖 87 条原数据、全局 ID 唯一和所有跨表引用；隔离运行器跑 `SmokeTest` 以及受影响的刷新、战斗、任务、掉落与艺术验收；在有图形窗口下复核方向、脚底、血条、命中与缺包回退。导出模板做一次正式资源装包与启动测试。分析与测试一律使用隔离存档，不覆盖玩家真实槽位。

**决策建议**：批准“分章存具体怪物 + 独立表现档案 + 可选能力档案”三层结构。先完成不改玩法的数据分章和工具迁移，再统一美术装配；新能力复用有明确场景时再抽取。这样既能扩充新怪共用美术，也能让数值、任务和地图身份保持清晰。

## 八、实施记录（2026-10-16）

- 节点 1 已完成：87 条模板按六章拆分；与旧 `data/monsters.json` 逐项比较，字段和值相同，`DataLoader` 对外仍提供同名表与稳定 ID 查询。
- 节点 2 已完成：数值和第二章生成工具改用章节入口；章节 README 有自动清单区，`tools/check_monster_catalog.py` 校验全局 ID 与说明一致。旧 `tools/balance_check.py` 仍在其装备售价示例引用已不存在的 `weapon_starter`，这是独立于怪物迁移的既有问题，不作为本次数值正确性证据。
- 节点 3 已完成：加入 `data/monster_appearances/` 和统一装配入口。首章已有的 8 套真实表现各有档案，其余怪物引用同一个 `placeholder`；原怪物 ID 不变，`headHpY` 从木桩模板移至其外观档案。第二章美术清单目前没有 `actors`，后续接入真实资源时可用 `chapter2_manifest` 适配器或直接建外观档案；现有怪物继续使用占位图。
- 节点 4 暂不实施：现有 14 份非空 `bossSkill` 配置逐项比较均不相同，尚无可原样复用的技能规则。已有共享 `BossAction` 组件继续承担线/扇/圈等形状处理；等真实新怪提出同招式需求，再抽 `abilitySetId` 并单独验证伤害与预警时序。
- 数据和隔离运行验证：87 条具体怪物除新增 `appearanceId`、木桩头顶视觉字段迁移外，全部玩法字段与迁移前相同；9 个外观档案中 8 个对应现有真实表现，1 个为公共占位。两只不同怪物临时共用野狼外观的隔离测试验证纹理共享与身份/血量/攻击/掉落独立；怪物动画、第一章美术、第二章战斗、启动冒烟及默认 28 项隔离回归通过。
- 全量隔离回归还报告若干素材、营地编辑器与要求实际渲染的场景失败。其中 `ArtSampleTest`、`QualityFrameTest`、`CampMapEditorTest` 在本节点实施前的已提交快照中同样失败；木桩血条的旧高度断言也在该快照中失败，已把外观档案高度上移并单独复测通过。`MapRenderBenchmark` 要求实际渲染，不能以 headless 的 `--all` 结果判断。其余营地展示场景没有成功结束标记，需在对应美术/编辑器任务中单独复核。
- 导出验证：从外观复用节点已提交快照生成 macOS 调试包成功；另用隔离 Godot 项目加载导出 `.pck`，确认怪物章节索引、末章数据、表现档案索引和示例档案以及装配脚本均存在，六章路径可被解析。本次只验证资源装包与加载，没有在真实玩家存档目录启动导出游戏，也没有据此声称实际窗口帧率提升。
