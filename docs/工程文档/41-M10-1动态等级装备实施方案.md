# 41 · M10-1 动态等级装备实施方案（可执行细案）

> 日期：2026-10-18　｜　性质：**已落地**（代码与测试均已入库）　｜　上级文档：产品 13 §2.4 / §3 / §7 P-1～P-3
> 前置：**M10-0 已落地**（`e5f2abc`）——`Balance.scale()` 与 9999 级 / 99,999,999 属性上界已就位。
> 范围：**只做「循环装备实例」的生成与存档口**——v5 实例能生成、能穿、能存、能读、不被剔除。
> **不做**：掉落表接入（M10-2）、循环 Boss 图（M10-3）、随身三件套（M10-4～7）、重铸（M10-8）、药水百分比（M10-10）。

## 1. 一页结论

| 项 | 结论 |
|---|---|
| 改动文件 | **4 个既有 + 1 个新测试场景**：`scripts/systems/item_factory.gd`、`autoload/save_manager.gd`、`autoload/data_loader.gd`（不加也能跑，见 §7 纠错）、新增 `tests/dynamic_equip_test.gd` + `.tscn` |
| 净增代码 | ≈ 110 行（`item_factory` 约 25 行，`save_manager` 约 20 行，测试约 65 行） |
| schema | **不变（仍 14）**——`equipmentRuleVersion` 是**实例字段**，不是存档版本号 |
| 1–60 影响 | **零**：`make_equip_roll` 默认参数 `dynamic_level = 0` 走原分支，随机数调用顺序一字不改 |
| 数据文件 | **零改动**（复用 `c6_equip_*` 十个 tier51 型号） |
| 最大风险 | 放宽 `_valid_item` 时把 **v4 也放宽** ⇒ 1–60 的旧档可被改档造出 70 级「新手剑」；所以校验**按版本分流**，不是统一放宽 |

**三句话**

1. **不新增型号、不新增函数体**：`make_equip_roll` 加一个可选参数 `dynamic_level`，v5 只是同一个函数的另一条分支 ⇒ 随机流与词条抽取逻辑不复制、不分叉。
2. **两个存档入口都要改**（产品 13 §3 已点明）：`_whole(..., 4, 4)` 的**上限**放行 5，`_valid_item` 的等级判定按版本分流。只改后者，v5 实例在读档第一步就被判坏（P-1）。
3. **只放宽 v5，不动 v4**：v4 仍严格要求 `requiredLevel == 模板 requiredLevel`（51–60），这样「改档把普通装备抬成 70 级」这条路依然堵着。

## 3. 存档校验：v4 / v5 判别表

**判别只用一个字段：`equipmentRuleVersion`。**

| 校验项 | v4（1–60，存量） | v5（61+，动态） |
|---|---|---|
| 版本号 | `_whole(..., 4, 4)` | `_whole(..., 5, 5)` |
| `requiredLevel` | **严格等于**模板 `requiredLevel`（51–60） | `> 60` 且 `≤ PLAYER_LEVEL_CAP` |
| `level` | `== requiredLevel` | `== requiredLevel` |
| 所属套 | `tierBases` 唯一且含 `tier_start_for_template(id)` | 同上，且该套必须是 **51**（动态实例只复用 tier51） |
| `rawBaseAttrs` | 非空、键 ∈ {atk,def,hp,mp}、值 ≥ 0 | 非空、键同上、值 **> 0** |
| 词条 | `affixes + pctAttrs ≤ 4`、`pctAttrs ≤ 1`、白名单、不重复、值 ≥ 0 | 同左 |
| 品质 / 星级 / 快照 | 品质合法、`star ∈ [0,12]`、quality 快照 ∈ (0,100]、star 快照 ∈ [0,1] | 同左 |

> **🔑 为什么不校验「`rawBaseAttrs` == 基底 × S(level−60)」**：实例基底是**生成时快照**（F-4 的既有设计）。
> 一旦强校验，将来任何一次 `Balance.scale` 调参都会让玩家手上的 v5 装备整批失效 —— 这正是 v4 当初刻意避免的坑。
> 数值口径由生成函数保证（§4），存档只保结构。

**落点（`save_manager.gd:_valid_item` 装备分支）**

```gdscript
if not _whole(item.get("equipmentRuleVersion"), 4, 5) or not item.get("rawBaseAttrs") is Dictionary \
        or not item.get("affixes") is Array or not item.get("pctAttrs") is Array:
    return false
...
var rule_version := int(item.equipmentRuleVersion)
var template: Dictionary = DataLoader.get_entry("equipments", String(item.itemId))
var bases: Dictionary = template.get("tierBases", {})
var tier_key := str(ItemFactory.tier_start_for_template(String(item.itemId)))
# M10-1：v4 保持「严格等于模板等级」（5.7）；v5 是动态实例，等级由生成时决定。
var level_ok := false
if rule_version == 5:
    level_ok = bases.size() == 1 and bases.has(tier_key) \
        and tier_key == str(ItemFactory.DYNAMIC_BASE_TIER) \
        and int(item.requiredLevel) > Balance.SOFTCAP_LEVEL \
        and int(item.requiredLevel) <= GameState.PLAYER_LEVEL_CAP
else:
    level_ok = bases.size() == 1 and bases.has(tier_key) \
        and int(item.requiredLevel) == int(template.get("requiredLevel", 0))
if not level_ok:
    return false
```

> `_valid_item` 在 `SaveManager` 里，`Balance` / `GameState` / `ItemFactory` 三个类都是全局可见（class_name / autoload / class_name），直接引用无循环依赖。

## 4. 生成入口：给 `make_equip_roll` 加一条分支（不复制函数）

```gdscript
## 循环装备只复用第 51 套的十个型号；改这个常量等于改整套经济口径。
const DYNAMIC_BASE_TIER := 51
## 动态实例的规则版本（v4 = 1–60 存量，v5 = 61+ 动态）。
const DYNAMIC_RULE_VERSION := 5

## 按型号所属套生成实例；传入其他套起点时显式失败。
## `dynamic_level > 60` 时改走 M10-1 动态分支：等级取该值、基底 × S(level−60)、
## 词条 × affixTierScale[51] × S(level−60)、版本标 5。
## 默认 `dynamic_level = 0` ⇒ 1–60 行为与随机数调用顺序**逐字不变**。
static func make_equip_roll(item_id: String, tier_start: int, quality: String,
        rng: RandomNumberGenerator = null, instance_prefix: String = "inst",
        dynamic_level: int = 0) -> Dictionary:
```

分支只改**三处取值**，抽取逻辑共用：

| 取值 | 原（`dynamic_level == 0`） | 动态（`dynamic_level > 60`） |
|---|---|---|
| `required_level` | 模板 `requiredLevel` | `dynamic_level` |
| 词条 `scale` | `affixTierScale[str(tier_start)]`（51 → 6.0） | `affixTierScale["51"] × Balance.scale(dynamic_level − 60)` |
| 返回的基底 / 版本 | `bases[tier_start]` / 4 | 逐项 `maxi(1, round(基底 × S))` / 5 |

```gdscript
	var dynamic := dynamic_level > Balance.SOFTCAP_LEVEL
	var required_level := int(tpl.get("requiredLevel", 0))
	if dynamic:
		required_level = dynamic_level
	elif required_level < tier_start or required_level >= tier_start + 10:
		push_error("[ItemFactory] %s 穿戴等级与所属套不符" % item_id)
		return {}
	...
	var affix_scale := float(scale_values[str(tier_start if not dynamic else DYNAMIC_BASE_TIER)])
	if dynamic:
		affix_scale *= Balance.scale(required_level - Balance.SOFTCAP_LEVEL)
	...
	# 循环末尾组装
	var raw := (raw_bases[str(tier_start)] as Dictionary).duplicate(true)
	if dynamic:
		var s := Balance.scale(required_level - Balance.SOFTCAP_LEVEL)
		var scaled := {}
		for stat in raw:
			scaled[String(stat)] = maxi(1, int(round(float(raw[stat]) * s)))
		raw = scaled
	return {
		...
		"equipmentRuleVersion": DYNAMIC_RULE_VERSION if dynamic else 4,
		"requiredLevel": required_level, "level": required_level,
		"rawBaseAttrs": raw,
		...
	}
```

**对外门面**（掉落 / 任务 / 商店后续都走它，M10-2 只改调用处）：

```gdscript
## M10-1：循环装备实例。`level ≤ 60` 时退回普通路径（60 级拿到的仍是 tier51 原版）。
static func make_equip_dynamic(item_id: String, level: int, quality: String,
        rng: RandomNumberGenerator = null, instance_prefix: String = "dyn") -> Dictionary:
	if level <= Balance.SOFTCAP_LEVEL:
		return make_equip_roll(item_id, ItemFactory.tier_for_level(level), quality, rng, instance_prefix)
	if not int(tier_start_for_template(item_id)) == DYNAMIC_BASE_TIER:
		push_error("[ItemFactory] %s 不在循环装备型号表" % item_id)
		return {}
	return make_equip_roll(item_id, DYNAMIC_BASE_TIER, quality, rng, instance_prefix, level)
```

## 7. 三处对产品 13 的纠错（落地前必须知道）

| # | 产品 13 原文 | 实际情况 | 处置 |
|---|---|---|---|
| E-1 | 「`data_loader.gd` 启动校验增加『v5 实例 `level ≥ 61`』」 | `data_loader` 校验的是**数据表**（`equipments.json` / `dropTables.json`），**从不接触存档实例**。实例校验只有 `SaveManager._valid_item` 一个地方 | 该条改到 `_valid_item`（§3），`data_loader` 不动 |
| E-2 | 「必须连带改的 4 处」里第 4 处是 `data_loader.gd:618-629`（掉落表允许 `levelFromBoss` 与 `tierStart` 互斥） | 这条属于**掉落表接入**（M10-2）：本批不新增掉落条目，`dropTables.json` 零改动 ⇒ 启动校验不会失败 | 移到 M10-2 |
| E-3 | 表格里「铠甲 63 → def 54」与「武器 61 → 84」混排 | 两者**不是同一等级**：铠甲模板 reqLv 53，band 0 起点是 63；武器模板 reqLv 51，起点 61。公式 `60 + 10b + (reqLv − 50)` 本身正确 | 文档保留，§5 表按实际等级列全 |

> 结论：**M10-1 不需要碰 `data_loader.gd`**。少改一个 autoload，少一份启动校验回归风险。

## 8. 风险与处置

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| **R1** | 放宽时把 v4 一起放宽 | 改档可造「70 级新手剑」，1–60 口径被污染 | 校验**按版本分流**；N-4 专锁这条 |
| **R2** | 引用 `Balance` 造成循环依赖 | 编译期报错 | `Balance` 不引用任何 autoload（M10-0 已约束），`_valid_item` 单向引用 safe |
| **R3** | v5 实例的 `rawBaseAttrs` 被当作「与曲线不符」而拒 | 调一次曲线就毁玩家装备 | 只验结构不验数值（F-4 的既有设计） |
| **R4** | `make_equip_roll` 新增参数改变随机流 | 1–60 掉落结果变化，既有掉落测试可能变红 | 参数默认 0 走原分支，**随机调用顺序不动**；`DynamicEquipTest` 里加一条「60 级生成结果与改动前一致」的固定种子比对 |
| **R5** | 动态实例进商店/仓库后 `base_value` 仍按 tier51 计价 | 1000 级装备回收价只有 300–480 金 | 产品 13 §6.1 既定口径（金币不缩放）；M10-8 重铸再谈「轻缩放」，本批不改 |
| **R6** | `_migrate_equipment_catalog` 里「等级不足则脱下」对 v5 生效 | 若玩家等级被改低，v5 装备会被塞进背包/未领取 | 这是正确行为（穿戴门槛），保留；测试不覆盖降级场景 |
| **R7** | `upgrade.gd`（升星）改 `rawBaseAttrs` 却不改版本 | v5 升星后仍合法 | `upgrade` 只读实例字段、不写版本（已核无 `equipmentRuleVersion` 引用），无需改 |
| **R8** | 将来若新增 tier61+ 型号，`DYNAMIC_BASE_TIER` 硬编码 51 会挡路 | 扩展时改造 | 常量集中一处，扩展时只改它 + §3 的校验分支 |

| 负向 | N-1 6 项红（含真文件往返剔除）｜N-2 1 项红｜N-3 17 项红｜N-4 1 项红 |

**实现与方案的两处偏差（均为收紧，不是放宽）**

1. `make_equip_roll` 动态分支**要求 `tier_start == DYNAMIC_BASE_TIER`**，否则 `push_error` 返回 `{}`。
   方案原文只要求门面校验；但 `make_equip_roll` 是公共函数，绕过门面直接传「动态等级 + 第 41 套」
   会生成词条倍率取 6.0 而基底取 41 套的畸形实例。现在这条路显式失败（`_test_foreign_template` 覆盖）。
2. 词条倍率先算成 `affix_scale` 变量再进循环（原方案在循环内每轮读 `scale_values`）。
   只影响可读性，**不改变随机数调用顺序**，1—60 掉落逐字不变。

## 11. 一句话总结

**M10-1 不是「加一套装备」，而是「让等级成为实例字段，并且只给 61 级以上开这个口子」。**
两个存档入口（版本上限 + 等级相等）都要收放到位：v5 放开、v4 不动；数值靠生成函数算，存档只保结构。
