# 百首禁域倍速视野剧烈跳动原因分析

本文针对“百首禁域开启时间倍率、Boss与掉落较多时，视野急剧切换甚至晃到地图外”的反馈，记录2026-11-01的代码核查与隔离实测。用户确认倍速通过编辑器/控制台修改引擎时间倍率。本轮仅分析，没有修改游戏或相机实现。

## 1. 核心结论

已经实测复现：当前Camera2D原生平滑在高时间倍率/大帧步长下会过冲，达到一定条件后往返震荡并放大，最后在相机边界两端跳转，极端时内部状态变成非有限值。角色不需要瞬移、场景中也不需要Boss或掉落，就能产生这一现象。

因此“平滑跟随使用受倍速放大的delta、插值系数无稳定性保护”是已证实的相机缺陷，与用户描述高度一致。Boss和掉落增加负载、造成较长绘制帧，会降低触发所需的倍速；攻击击退、追怪与拾取转向也会不断改变跟随目标位置，提供扰动。用户当次实际倍率和帧时间尚未采集，因此不能断言其每一次晃动都只有这一原因，也不能将具体卡顿都归咎于掉落扫描。

## 2. 项目中的直接证据

|入口|核查结果|
|---|---|
|`scenes/entities/Player.tscn`的Camera2D|开启`position_smoothing_enabled`，`position_smoothing_speed=8.0`，没有自定义相机脚本|
|相机更新模式|场景未覆盖默认值；官方Camera2D默认按idle/render流程处理，使用受Engine.time_scale影响的process delta|
|`scripts/world/game.gd:172–178`|地图加载时将Ground世界包围盒写入四向limit，应用zoom，再reset_smoothing；没有运行期防发散或非有限值恢复|
|`scripts/world/ground.gd:296–323`|相机范围是等距菱形的轴对齐矩形包围盒，不是逐点限制在可走地面上|
|`scripts/entities/player.gd:395–397,468–508`|正常移动走move_and_slide；Boss击退另按积分修改玩家位置、检查落点掩码并clamp。缺省击退48像素/0.18游戏秒，与数千像素镜头跳幅不是同一数量级|
|`scripts/systems/auto_battle.gd`|自动找怪/巡游只输出移动方向，未直接更改相机、zoom或传送玩家；拾取转向会改变运动，但不是原生平滑发散的必要条件|
|相机相关调用检索|正式运行侧未发现Boss技能主动震屏、随机切相机或逐帧修改zoom；旅行物品仅在明确传送后reset_smoothing|

原生平滑公式来自[Godot官方4.7-stable Camera2D源码](https://github.com/godotengine/godot/blob/4.7-stable/scene/2d/camera_2d.cpp#L178-L191)：

```text
c = position_smoothing_speed × scaled_delta
smooth_position += (target_position - smooth_position) × c
```

公式没有将c限制在0～1，也没有用指数衰减。默认更新模式见[官方camera_2d.h](https://github.com/godotengine/godot/blob/4.7-stable/scene/2d/camera_2d.h#L98)。所查源码为4.7-stable标签；本机实际引擎为`4.7.2.stable.official.ed1daf0bf`，以下数值实测验证了同一行为，不能将源码标签冒称本机完整构建源码。

## 3. 为什么倍速和卡顿会叠加

在正常逐帧更新近似下，scaled_delta≈真实帧间隔×时间倍率。项目平滑速度为8，因此：

- 0<c≤1：镜头朝玩家靠近，没有越过目标。
- 1<c<2：越过目标，左右交替，理想固定目标下误差仍会衰减，但观感会反复晃。
- c=2：误差左右翻转而不衰减。
- c>2：误差每次反转并变大。最终输出即使被边界裁住，内部平滑状态仍可能继续放大。

这是对上述公式误差递推`e_next=(1-c)×e`的推导，不是对用户现场帧率的测量。引擎具体delta截断及同帧多次更新可能影响现场幅度，不能把理论阈值当成精确帧率诊断工具。

|时间倍率|开始过冲的真实帧间隔（c>1）|不再收敛的真实帧间隔（c≥2）|
|---|---:|---:|
|1×|>125ms|≥250ms|
|2×|>62.5ms|≥125ms|
|4×|>31.25ms|≥62.5ms|
|8×|>15.625ms|≥31.25ms|
|16×|>7.8125ms|≥15.625ms|

例：8倍时约30FPS的帧间隔已足以持续放大误差；4倍时约15FPS亦然。无需一直低帧率，偶发大帧也会突然把镜头推过目标，随后角色运动/新扰动可能再触发。

## 4. 隔离数值实测

在仓库外临时项目运行原生Camera2D，不加载地图怪物、掉落、寻路或UI。视口1280×800，zoom=1；相机属性复现Player.tscn的平滑开关与速度8。边界复现百首禁域200×120地图投影包围盒：left=-3840、right=6400、top=-5104、bottom=16。

跟随目标从(1280,-2544)向右移动100像素至(1380,-2544)，随后保持静止。每组观察120帧，只读取get_screen_center_position，不在每帧额外force_update_scroll，避免测量本身重复推进相机。

以`--fixed-fps 60`消除机器抖动；30/15FPS案例通过相应调节时间倍率，产生与该“帧间隔×倍率”相同的scaled delta。这是受控步长等效试验，不是实测机器掉到了30/15FPS，也不证明GPU性能。

下表镜头数值为相对初始x=1280的偏移；玩家最终偏移始终为100。

|等效FPS×倍率|c|前几帧镜头偏移 px|结果|
|---|---:|---|---|
|60×1|0.133|13.333、24.889、34.904、43.583|正常收敛到100|
|60×4|0.533|53.333、78.222、89.837、95.257|正常收敛到100|
|60×8|1.067|106.667、99.556、100.030、99.998|出现过冲与轻微反向修正|
|60×16|2.133|213.333、-28.444、245.570、-64.980、286.977…|持续放大，最大单帧跳幅8960像素|
|30×8|2.133|与60×16一致|持续放大，最大单帧跳幅8960像素|
|15×4|2.133|与60×16一致|持续放大，最大单帧跳幅8960像素|
|30×16|4.267|426.667、-967.111、3585.897，随后在边界跳动|继续更新后出现非有限状态|

对照组只关闭原生position smoothing，保留同样边界、视口、目标移动与时间步长：60×8、60×16、30×8、30×16全部直接稳定在玩家x=1380，静止后误差0，不再往返。这是临时隔离对照，没有修改仓库配置，也不是建议正式版永久取消所有平滑。

### “晃到地图外”为什么不一定是玩家越界

上述边界和视口下，相机中心可在x=-3200与x=5760之间切换，单次横跨8960像素；玩家仍停在x=1380。相机中心y=-2544时，两侧对应地图格约(29.5,129.5)和(169.5,-10.5)，已在120行地图的范围外，但仍位于菱形的矩形包围盒内。

所以矩形camera limit存在并不意味着画面不会出现地图外区域；它也没有修复内部平滑发散。极端案例里的NaN还可能破坏普通大小比较。不能仅凭“看到了地图外”就认定玩家被击退穿出了地图。

## 5. 密集Boss与掉落的作用：已知与未证实部分

百首禁域有100个Boss刷新席位，不代表100只在任意时刻都活动或同屏。活动距离、预算、当前视口与掉落持久化共同决定负载。倍速还会让一定真实时间内发生更多攻击、掉落、拾取、目标切换和物理工作。

已有工程记录确实显示游戏窗口存在较长尾帧（例如此前其他地图短跑峰值约63–91ms），但该历史记录既不是本次百首禁域用户现场，也不能证明掉落就是唯一瓶颈。当前拾取已有满背包缓存、普通掉落失效与持久奖励规则，不能在未分析Profiler前简单关闭掉落或吞奖励换性能。

本轮已证明：无需任何怪物或掉落即可复现镜头失稳；因此应优先修相机的时间与数值稳定性。之后再在真实100席地图采样Boss数、地面物品数、物理/脚本/绘制耗时和真实帧间隔，定位放大因素。玩家位置与相机中心必须同时记录，否则无法区分击退、寻路折返和镜头发散。

## 6. 建议修复顺序

1. **先隔离镜头与游戏倍速时钟。** 游戏逻辑继续按原时间倍率推进；跟随视觉用真实时间进行稳定平滑。建议关闭该原生线性平滑，改为`alpha=1-exp(-k×real_delta)`的指数跟随，保证任意正常非负delta下alpha处于0～1。真实时间使用单调时钟，不直接拿受倍速放大的delta；暂停恢复、切图、明确传送、缩放和首帧需要按既有流程初始化/复位。
2. **为最终镜头增加数值与范围兜底。** 内部跟随状态和输出都检查有限值，异常时回到玩家附近的合法相机目标并清理历史平滑状态。继续复用现有地图边界/zoom，不能只裁显示位置而放任内部状态发散。菱形边缘出现少量地图外留白与异常飞到远处是不同问题，不要为隐藏留白缩小玩家可探索地图。
3. **短期验证可关闭原生平滑。** 用于确认问题消失，正式体验仍应提供稳定平滑。只调低speed、每帧reset_smoothing、仅改physics callback或只提高physics tick数量都不是完整修复；尤其不能在密集负载下无限加物理频率。
4. **再做密集场景性能定位。** 倍率1/2/4/8/16，zoom0.8/1/2，分别采空场、多个Boss、多个Boss＋大量掉落；记录真实帧间隔、scaled delta、玩家位移、相机位移、活动物品/怪物数、脚本/物理/渲染耗时和节点/内存。保留奖励、碰撞和输入正确性，不以缩减掉落或缩小判定掩盖卡顿。

建议验收：目标静止后相机误差单调收敛、不反复越过目标；高倍率及人为大帧步长下内部值始终有限；玩家不动时不出现数千像素镜头跳转；Boss击退仍保留原玩法；旅行/死亡复活/暂停恢复不拖着旧镜头位置飞行；高倍率长跑不增加镜头节点、计时器或缓存。

## 7. 复核与交付边界

本轮使用隔离原生相机测试验证数值逻辑，没有把无头结果当作渲染帧率验收。临时项目、日志与探针均在/tmp，结论入文档后清理，不进入游戏依赖；未读取或改写玩家存档。

复核入口：本机Godot4.7.2、新建Camera2D平滑速度8、1280×800、上述百首禁域四向边界，给跟随父节点100像素阶跃后保持静止；以固定步长运行并记录目标位置与get_screen_center_position。比较scaled delta=1/60、4/60、8/60、16/60及关闭平滑对照，即可重现收敛、过冲、发散的差别。测试无需显示高速闪动的实际窗口。

本轮没有发布修复；实际用户倍率与百首禁域现场Profiler尚未采集。结论是已定位可独立复现的主缺陷及其触发机制，下一开发节点应先修镜头稳定性，再评估密集负载优化。
