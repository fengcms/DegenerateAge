# 71 · 面板打开时「鼠标点快捷栏格子没反应」原因分析与修复方案

> 现象提出：打开面板的情况下，用鼠标点击快捷栏里的格子（如 `-`、`=` 两格），不执行该格绑定的操作。
> 结论一句话：**不是点不到，也不是漏改——是 `hud.gd::_activate_hotbar` 里一条 `GameState.panel_open and not from_keyboard` 守卫，把「面板打开时的所有鼠标点击」直接吃掉了。** 键盘路径在 2026-10-17 已放开，鼠标路径被有意保留为「防拖放误用」，并已明文写进产品规范。

---

## 1. 现象的可观测判据

| 操作 | 现状 |
| --- | --- |
| **无面板**时鼠标点快捷格 | 正常触发（吃药 / 放技能 / 用回城卷） |
| **有面板**时鼠标点同一格 | 无反应，也没有任何 toast 提示 |
| **有面板**时按数字键 / `-` / `=` | 正常触发（键盘路径已放行） |

→ 「键盘能用、鼠标不能用」已经把差异锁死在 `from_keyboard` 这一个参数上。

---

## 2. 根因（代码事实）

`scripts/ui/hud.gd:526-529`：

```gdscript
## 键盘快捷栏可在普通面板打开时使用；鼠标点格在拖放模式下保持原有防误触规则。
func _activate_hotbar(index: int, from_keyboard: bool = false) -> void:
	if index < 0 or index >= 12 or GameState.world_controls_blocked() or (GameState.panel_open and not from_keyboard):
		return
```

两个调用点，一个放行、一个被拦：

- **键盘**：`hud.gd:397-404`（`_unhandled_input`）→ `_activate_hotbar(i, true)` → `from_keyboard = true` → `panel_open` 这一条被绕过。
- **鼠标**：`hud.gd:435` 的 `slot.pressed.connect(_activate_hotbar.bind(i))` **只绑了 index** → `from_keyboard` 取默认值 `false` → 只要 `panel_open` 为真就 `return`。

`GameState.panel_open`（`autoload/game_state.gd:60`、`:1395-1400`）在**任意**一个面板登记打开时即为 `true`（背包、人物、技能、坐骑、任务、货郎、仓库、铁匠、车夫、大地图、随身商店、升级 / 重铸 / 四金合成、Boss 令牌……），与「是否阻断世界输入」无关——后者是 `world_controls_blocked()`（`:1404-1409`），只认 5 个模态面板 + 文字框聚焦。

**鼠标事件确实能到达快捷格**，不是「点不到」：

- 背包打开时 `hud._hotbar.z_index = 100`（`hud.gd:506-509`）；
- `tests/hotbar_ui_test.gd:19-34` 用**真实鼠标**从背包拖到快捷格并成功落格，证明该坐标上最顶层的控件就是 `HotbarSlot`。

所以链路是完整的：`HotbarSlot.pressed` → `_activate_hotbar(i)` → 被守卫 `return`。

### 2.1 这条守卫的来源

`git: cf189f6d`「fix(input): 恢复普通面板打开时的角色与快捷键操作」（2026-10-17）。该次提交把「面板可见」与「模态接管」拆开，**键盘**路径改为 `world_controls_blocked()`，但**鼠标**路径有意保留旧规则，产品规范同步写死：

- `docs/产品文档/09-UI与交互规范.md:44`：「…快捷栏在面板打开时保留拖放操作，**鼠标单击快捷格仍不触发物品，防止拖放误用**。」
- `docs/工程文档/面板打开时世界操作恢复分析与方案.md`（§根因与产品决定）：「面板覆盖区域的鼠标点击继续由 GUI 接收；全屏遮罩的既有鼠标行为不因本次键盘修复而改变。」

**结论：这不是 bug 漏改，是一条被明文写进产品规范的设计选择。** 本次反馈等于要推翻它，属于产品口径变更，不是纯技术修复。

### 2.2 「防拖放误用」这条理由是否成立

值得商榷。它隐含假设「拖放会顺带触发一次点击」，但 Godot 的 `BaseButton` **只在按下与松开都落在同一个按钮上**时才发 `pressed`：从背包 / 技能面板拖到快捷格时，按下点在被拖走的**源控件**上，快捷格只接收 `_drop_data`（`scripts/ui/hotbar_slot.gd:156-158`），不会收到 `pressed`。

仓库里已有真实鼠标拖放用例通过（`tests/hotbar_ui_test.gd:19-34`、`:37-56`），说明拖放链路本身不需要这条守卫来保护。

→ 若成立，这条守卫就是**纯粹的误伤**。但这是推断，不是实证：实施时必须补一条「拖放落到已绑定药品的格子 → 绑定替换且库存不被消耗」的用例，才能确认删掉守卫后拖放不会误吃药。

## 3. 影响面：谁被误伤

| 面板 | `panel_open` | `world_controls_blocked()` | 鼠标点快捷格现状 | 期望 |
| --- | --- | --- | --- | --- |
| 背包、人物、技能、坐骑、大地图、任务 | true | false | **无效** | 应生效 |
| 货郎、仓库、铁匠、车夫、随身商店 | true | false | **无效** | 应生效 |
| 升级、重铸、四金合成、Boss 令牌 | true | false | **无效** | 应生效 |
| ESC 主菜单、设置、存档、死亡、装备确认 | true | true | 无效 | **保持无效（正确）** |
| 任意面板 + 文字输入框聚焦 | true | true | 无效 | **保持无效（正确）** |

**一个必须排除的边界**：若某个面板窗口**物理覆盖**了快捷栏那一格，鼠标会被 GUI 命中面板自身——这是正确行为，不算本条缺陷。所以验收时要确认点的是**没被面板遮住**的格子（快捷栏位于屏幕下方居中，多数常驻浮窗不与它重叠）。

右键清空（`hotbar_slot.gd:119-122`）走 `_gui_input`，与本守卫无关，应一直可用——可顺带确认。

## 4. 修复方案

| 编号 | 做法 | 效果 | 影响面 / 代价 |
| --- | --- | --- | --- |
| **P1**（推荐） | 删掉 `not from_keyboard` 例外：`_activate_hotbar` 只保留 `world_controls_blocked()` 一条判据，`from_keyboard` 参数与 `_unhandled_input` 里的 `true` 一并去掉 | 鼠标与键盘口径统一。普通面板打开时点快捷格照常生效；模态面板与文字框聚焦仍然拦 | 需同步改 `09-UI与交互规范.md:44` 那一句，并**翻转** `tests/input_feedback_test.gd:149-150` 的断言（该断言正是当前行为的守护者，本身就是这次现象的成因之一） |
| **P2** | 保留例外，但对背包 / 技能 / 铁匠这几个「拖放面板」维持旧规则 | 只在拖放场景防误触 | 规则更复杂、用户仍会在背包与铁匠下点不动快捷格 —— **不推荐** |
| **P3** | 保留例外，但把判据从 `panel_open` 收紧为「真在拖放中」（如 `get_viewport().gui_is_dragging()`） | 只在拖放进行中抑制一次点击 | 与 P1 效果差别很小、实现更绕、多一处状态依赖 —— 不必要 |

不建议的做法：① 只放开前 12 格、对后 4 个面板入口格保持关闭——那 4 格本来就是「打开面板」，与面板打开不冲突；② 直接删掉 `panel_open` 判据——会连模态面板一起放开（那些面板的拦阻实际来自 `world_controls_blocked()`，删错地方会同时破坏死亡 / 确认框保护）。

**P1 是唯一与「键盘已放行」自洽的口径：同一个快捷格，键盘能按、鼠标也应能点。**

## 5. 验证计划

1. **有牙用例**（这三条必须同时成立，缺一条都不算修好）：
   - 背包打开 + 鼠标**单击**已绑定药品的快捷格 → 断言药品**被消耗**（旧口径下必红，可先注入旧守卫反证）；
   - 背包打开 + 鼠标**拖放**背包药品到**已绑定药品**的快捷格 → 断言绑定被替换**且库存不被消耗**（把 §2.2 的推断变成实证）；
   - 模态面板（设置）打开 + 鼠标点快捷格 → 断言**仍被拦**（不许把模态保护一起放开）。
2. **回归**：`python3 tools/run_isolated_tests.py`（默认集 48 项）全绿，重点 `InputFeedbackTest`、`HotbarUiTest`、`TownScrollTest`、`SettingsTest`。
3. **实机**：分别在背包、人物、大地图、铁匠四个面板打开时点几格，确认动作生效、且点在面板控件上不穿透到世界。

## 6. 已确认项

- **修复范围 = P1**（用户 2026-10-20 拍板）：鼠标与键盘完全统一，删掉 `not from_keyboard` 例外。P2 / P3 未采纳。
- 现象复现点确认为**未被面板遮住**的格子（快捷栏位于屏幕下方居中）——即 §3 的「必须排除的边界」不成立，属本条缺陷。
- 其余格内操作（右键清空 / 拖入 / 拖出）均正常，验证见 §7，不存在第二条链路。

### 7.2 与方案的两处偏差（如实记录）

1. **`from_keyboard` 参数直接删除，而非保留**。方案 §4 P1 写「参数与 `true` 一并去掉」，实施按此执行——保留一个恒定无用的默认参数会继续误导后来者。
2. **验证计划 §5 的「注入旧守卫反证」改为正向断言**。旧守卫若重新注入，`InputFeedbackTest` 的守卫层断言（普通面板内点格应真正触发操作）会立即变红；该断言本身就是有效的反向保护，无需再写一次改写守卫的临时用例。

### 7.3 排障记录：三条新断言首轮全红，根因是药水冷却而非输入链路

首轮运行 `InputFeedbackTest` 时新增三条断言全部失败，一度被误判为「真实鼠标点击送不到快捷格」。实测诊断值：

```
失败：面板打开时快捷栏数字键仍能使用药品｜实际 count={"kind":"potion","itemId":"potion_hp_small","count":2}
失败：背包打开时真实鼠标点快捷格应消耗药品｜实际 count=同上 点=(303.0,1209.0)
```

**根因**：`Consumable._cd`（`scripts/systems/consumable.gd:35`）是**按 `item_id` 独立、且不落档**的静态运行态冷却表，跨断言残留。前一条守卫层断言刚喝掉一口 `potion_hp_small`（cd 8s），后两条断言在同一瞬间再次使用同一瓶 → 被冷却拒绝（`consumable.gd:106-108`），库存自然不变。

这与输入链路无关的旁证：`HotbarUiTest` 用同一坐标做真实鼠标拖放**一直通过**，说明 `点=(303.0,1209.0)` 这个坐标空间是可达且正确的（`window/stretch/mode="canvas_items"` 下 `Control.get_global_rect()` 给的是画布坐标，正是 `push_input` 期望的空间）。

**修复**：三条断言各自在调用前 `Consumable.reset()`，并各自准备独立库存与扣血前置，消除断言间的冷却耦合。修复后三条全绿。

> 教训：药水冷却不落档且按 `item_id` 隔离，**跨断言共享**——凡是围绕「同一瓶药被用掉」做多段验证的测试，必须在每段之前显式 `Consumable.reset()`，否则会把「守卫放行」伪证成「守卫拦下」。
