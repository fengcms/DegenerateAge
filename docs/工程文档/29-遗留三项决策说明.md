## 一、D7 · `cdr`（冷却缩减）上限与叠加口径

### 问题是什么

- `cdr` = cooldown reduction（冷却缩减），是装备词条 / 角色属性中的一项，角色面板会把它显示出来。
- 产品 03 §3.8 规定「冷却缩减 ≤50%」，即效果封顶 50%。
- 但代码里 `cdr` **只是被收集、被展示，从未参与真正的冷却计算**：施放技能时直接写冷却原值——[player.gd L479](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/entities/player.gd#L479)（增益型）、[L489](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/entities/player.gd#L489)（攻击型），均为 `skill_cooldowns[id] = skill.cooldown`，没有乘 `(1 − cdr)`。
- 结果：**带 `cdr` 词条的装备是「死属性」**，玩家穿装备后技能冷却毫无变化，与配置预期不符。（A 报告 P2-1）

### 需要你给的三样（必须一起定）

1. **上限值**：到底封顶多少？（产品写 50%，但 D2 选了「暂缓展示战斗词条加成」，需确认上限是否仍按 50%）
2. **叠加方式**：多条 `cdr` 相加时是 **加算**（0.2 + 0.2 = 0.4）还是 **乘算**（1 − 0.8 × 0.8 = 0.36）？
3. **本轮是否接线**：并入批次六一起做，还是继续只记录？

### 为什么不能自行拍板

接线会**抬高战斗数值天花板**（技能可以放得更频繁），属「数值调平」，超出了本次「只修已识别问题、不顺手改数值」的边界；叠加方式不同，在接近上限时结果差异明显，必须由产品定义。

### 现状代码位置（给出后改这里才生效）

- 结构上界已存在，但只是防篡改占位：[game_state.gd L21](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/game_state.gd#L21) `PLAYER_CDR_CAP := 1.0`（注释已标「玩法上的实际上限待产品给值」）
- 读档校验已按此拦截越界值：[save_manager.gd L953](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L953)
- 真正的结算落点（改这里才会生效）：[player.gd L479](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/entities/player.gd#L479)、[L489](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/entities/player.gd#L489)

### 给出后怎么改

新增单一入口（如 `Combat.apply_cdr(base, cdr_sum, cap)`），在上两处统一调用；把 `PLAYER_CDR_CAP` 换成产品给的上限值，让**校验 / 展示 / 结算三处共用同一个常量**；补单测「`cdr` = 上限 → 冷却减半」。

## 二、C-P3-7 · v11 档装备实例 `equipmentRuleVersion` 的口径

### 背景：`equipmentRuleVersion` 是什么

每件**具体的**装备（装备实例）在存档里带一个字段 `equipmentRuleVersion`，标记它由「哪一版装备数值规则」生成。存档结构版本从 v11 升到 v13，中间有两次装备迁移：

- **v11→v12**：只处理 `equipmentRuleVersion == 2` 的旧装备，把型号归并到「每档每部位唯一型号」，并把版本号改成 3（[save_manager.gd L498](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L498)、[L508](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L508)）。
- **v12→v13**：只处理 `equipmentRuleVersion == 3` 的装备，同步穿戴等级，并把版本号改成 4（[L537](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L537)、[L544](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L544)）。
- 最终校验要求装备实例 `equipmentRuleVersion == 4`（[L1070](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L1070)）。

### 问题是什么

迁移链**只认识「恰好 2」和「恰好 3」**。若某个 v11 存档里的装备实例版本号**不是 2**（字段缺失、已是 3/4、或其它值），迁移会跳过它，随后校验以「不是 4」为由**拒绝整份存档**——不是丢一件装备，而是**整档读不出来**，只能靠 `.bak` 恢复。这与项目既有的宽容口径「地图 / 数据变动不应导致读档失败」相冲突。

### 证据等级：E4（推断）

本仓库**没有**真实 v11 构建写出的存档样本，无法证明现实中出现过「版本号 ≠ 2 的 v11 档」。所以这条目前只是「理论上可能」，也是必须先用口径把它坐实的原因。

### 需要你确认的一句话

> **v11 那个版本，写入的 `equipmentRuleVersion` 到底是 2，还是别的值？**

### 两种结论对应的改法

- **若确认 v11 写的就是 2** → 迁移链本身正确；只做**宽容化**：对无法识别的旧装备**逐件丢弃并明确提示**，而不是把整档判为损坏（C 报告 §6 建议 6）。
- **若确认 v11 写的是 4（或根本不该走这条迁移）** → 迁移的**前置判断写错了**，需要修正版本闸门条件。

## 三、H-P3-1 · 发布版本号

### 问题是什么

三处版本号目前都是项目模板的占位值 `0.1.0-scaffold`：

- [project.godot L19](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/project.godot#L19) `config/version`
- [export_presets.cfg L28](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/export_presets.cfg#L28) `application/short_version`
- [export_presets.cfg L29](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/export_presets.cfg#L29) `application/version`

`-scaffold` 是 Godot 脚手架后缀。正式包挂这个号，玩家反馈、发行平台记录、后续升级比对都**没有有效版本标识**。

### 需要你给的

一个正式版本号（例如 `0.1.0`、`0.1.0-alpha1`、或 `1.0.0-preview`）。

### 给出后怎么改

把上述三处改成**同一个正式号**并保持一致。
（另：[export_presets.cfg](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/export_presets.cfg) 中 `application/icon` 仍是 `res://icon.svg` 占位，属美术范围，另议。）
