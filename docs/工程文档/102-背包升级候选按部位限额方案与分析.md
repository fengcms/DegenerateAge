## 一、需求梳理

### 1.1 你的原话

> 当前玩家在挂机时，背包内拾取的装备，只会和玩家穿戴的装备进行对比，导致背包内有大量的绿色的玩家暂时穿不上的装备。如果全卖也不合适。我的建议是，这些装备不但要和玩家穿戴的装备对比，还要和背包内的装备对比。比如戒指，只要背包内有两个戒指是高于玩家穿戴的，剩下的即便高于玩家穿戴的，但只要不是金色紫色的，都可以直接卖出（按照玩家设定的卖出规则，积极）。背包内始终只保留两个高于玩家穿戴的即可。

### 1.2 翻译成可执行规则

| 术语 | 定义 | 现有代码里的对应物 |
|---|---|---|
| **部位** | 10 种：武器/盾牌/头盔/护甲/鞋子/项链/护腕/护膝/手镯/戒指 | `Equipment.slot_kinds()` |
| **槽位** | 14 个；护腕/护膝/手镯/戒指各 2 个，其余各 1 个 | `Equipment.SLOT_DEFS` |
| **已穿戴基线** | 该部位**会被替换**的那一件（双槽取两件里较差的那件） | `Equipment.replacement_preview()` → `auto_slot_for()` |
| **升级候选** | 背包里**评分高于已穿戴基线**的装备 | `_judge()` 的 `stronger`（今天等价于 `upgrade` 理由） |
| **额度 N** | 该部位的槽位数：四类双槽 = 2，其余 = 1 | `Equipment.slots_for_kind(kind).size()` |
| **保留集** | 该部位升级候选里**评分最高的前 N 件** | 本方案新增 |
| **超出集** | 排名 > N 的升级候选 | 本方案新增 |

**一句话规则**：同一部位，背包里最多「保护」N 件升级候选；超出的那些**不再享受「评分可提升」这条保护**，于是按你选的预设（积极 = 普通/优秀/稀有、零星、不限等级）正常卖掉。金/紫本来就过不了品质上限，因此照旧不卖。

### 1.3 关键口径（按你的原话取的，请确认）

**口径 B：金/紫也占额度。**

你的例子是「只要背包内有两个戒指是高于玩家穿戴的，剩下的…都可以直接卖出」——这里的「两个」数的是**全部高于已穿戴的戒指**，不分品质。所以：

> 戒指：1 金 + 4 稀 都高于已穿戴 → 按分数取前 2（金 + 最好的稀）→ 剩下 3 稀卖出。背包留 2 件。

如果反过来做（口径 A：金紫不占额度），背包会留 1 金 + 2 稀 = 3 件，清得更少。两种口径实测差 4 件（见 §三）。

## 二、现状：为什么只跟「已穿戴」比

`sell_gear_policy.gd::_judge()` 里这一条就是全部原因：

```gdscript
var stronger := not bool(preview.get("empty", true)) and bool(preview.get("score_increase", false))
if stronger:
    reasons.append("upgrade")          # ← 否决默认勾选
```

`replacement_preview()` 只拿 `equipment`（已穿戴）比，**完全不知道背包里还有什么**。所以：

- 背包里同部位的第 1、2、3…N 件升级候选，全都拿到 `upgrade`，全都不勾选；
- 自动出售（`auto_sell()`）同样走 `_judge()`，所以**拾取瞬间也一律不卖**；
- 于是「比身上好」就够格永久占格 —— 不管已经有多少件同类。

这条规则是工程 58 引入的，当时是对的：评分是「换上这件会不会更好」，而「更好」只有跟已穿戴比才有意义。它缺的是**第二问**：*这件在同类候选里排第几*。

## 四、方案（推荐：口径 B + 驱逐）

### 4.1 一句话

**只改一条判据的寿命**：`upgrade`（评分可提升）从「无条件保护」变成「在同类候选里排名 ≤ N 才保护」。

其余全部不动：品质上限、等级门槛、旧套、星级、收藏、破损、金币上限、空槽否决。

### 4.2 算法

```
输入：inventory, player_level, equipment, preset
① 一次遍历背包装备，对每件算 _judge() 已有的 stronger（复用，不另立标准）
② 按 item_kind 分组，只保留 stronger 的件
③ 组内按 Equipment.score() 降序排；同分时按背包格序升序（🔴 必须有确定 tiebreak）
④ 每组取前 N 件 → keep_ids（N = Equipment.slots_for_kind(kind).size()）
⑤ entry()/auto_sell() 判到 stronger 时：
     若 instanceId ∈ keep_ids → 照旧加 upgrade（不勾选）
     否则                   → 不加 upgrade，改加一条仅提示的 duplicate
```

`duplicate` 走「仅提示」通道，但和工程 99 的 `damaged` **方向相反**：

| 理由 | 手动清单 `entry()` | 拾取自动出售 `auto_sell()` |
|---|---|---|
| `damaged` | 仅提示（不否决勾选） | **否决**（无撤销，宁可留着） |
| `duplicate` | 仅提示（已在勾选，展示原因） | **不否决**（它就是要被卖掉的那件） |

实现上拆成两个显式过滤器，避免「一个原因集承载两种语义」重蹈工程 99 前的覆辙：

```gdscript
const NOTES_ONLY := ["damaged", "duplicate"]   # entry(): 展示但不否决
const SELL_THROUGH := ["duplicate"]            # auto_sell(): 见它不算否决

static func blocking_reasons(r) -> ...         # entry 用
static func auto_sell_blockers(r) -> ...       # auto_sell 用
```

### 4.3 拾取时怎么判（这是最容易做错的一步）

`pickup_loot()` 在**入包之前**调用 `auto_sell()`，所以新件必须和「已在背包里的候选 + 自己」一起排：

```
候选 = 背包里 stronger 的件（按分数降序）
若 len(候选) < N            → 留（额度没满）
否则 若 新件分数 > 第 N 名分数 → 新件顶进去，第 N 名被「驱逐」
否则                        → 新件卖掉落
```

**驱逐（D2 推荐 β）**：新件挤掉谁，就当场把谁卖掉，让背包严格等于 N。

- 若只判新件、不驱逐（α），背包会随「每破一次纪录 +1」慢慢回涨，做不到你说的「始终只保留两个」；
- 驱逐的护栏：被驱逐件必须**本身可卖**（品质 ≤ 预设上限、非星级、非收藏、非破损）—— 否则它根本不会被驱逐，改由后面的候选让位；
- 同分时**保留已在背包里的那件**（新件让位），避免「刚捡的顶掉刚留的」这种观感事故。

### 4.4 接口改动（4 处）

| 文件 | 改动 | 风险 |

| `autoload/game_state.gd` | `preview_equipment_sale()` 与 `validate_equipment_sale()` **各自**算一次 `rank_context`（同一份 inventory ⇒ 结果一致）；`auto_sell()` 多传 `inventory` | 口径一致性 |
| `scripts/ui/equipment_sale_preview.gd` | 无需改逻辑（`reason_duplicate` 走现有 reasons 渲染），只在 `_reasons_text` 已覆盖 | 零 |

### 4.5 与现有机制的交互（逐条确认，全部保持原样）

| 机制 | 交互结果 |
|---|---|
| **空槽**（工程 63 `empty_slot` 否决） | 不变：某部位槽位空时，拾取的第一件永远不卖 |
| **破损件**（工程 77/99） | 不变：`damaged` 在自动出售仍否决；破损件评分低，通常排在候选末尾，自然落入超出集 |
| **收藏 / 升星** | 不变：两条硬保护优先于额度；但它们**占额度**（口径 B），因此会挤掉排在后面的稀有件 |
| **金币满**（工程 56/63） | 不变：满金币时一件都不卖，也就不产生驱逐 |
| **仓库** | **不参与**：仓库是玩家主动存放，读它会让「存起来的好装备」占掉额度 |
| **货郎托盘** | 托盘件已出背包，`entry()` 传空 `keep_ids` ⇒ 维持今天的语义（不再按额度重算） |
| **暴力预设** | 不变：暴力跳过全部价值判断，额度对它无意义 |
| **谨慎 / 标准** | 额度同样生效，但它们的品质上限（普通 / 稀有）与等级门槛照旧先拦 |

## 五、备选方案与排除理由

| 方案 | 做法 | 为什么不做 |
|---|---|---|
| A. 只判新件、不驱逐 | 见 §4.3 α | 背包仍会缓慢回涨，达不到「始终只保留 N 件」 |
| C. 给每个部位加「保留上限」设置项 | 玩家自己填数字 | 新增存档键 + 设置 UI + 本地化 + 校验，收益不抵成本；且「额度 = 槽位数」本身就是最自然的取值 |
| D. 按「能不能立刻穿」二次排序 | 可穿的优先占额度 | 会把「5 级后就能穿的传说」判成可卖，和玩家直觉相反；实测暂时穿不上的 20 件全是金紫，本来就不卖，排了也没用 |
| E. 加一个「一键整理背包」按钮 | 玩家手动触发全量整理 | 不解决挂机场景（正是挂机时背包才涨）；可作为将来独立工程 |
| F. 同部位重复件按售价折算成材料 | 拆解系统 | 新系统，量大，与本次目标无关 |

## 六、🔴 风险与待决项

### R1（高）漏传 `keep_ids` = 静默退化
`rank_context` 是可选参数，漏传就回到旧行为，**不报错、不崩溃、测试可能照样绿** —— 这正是坑清单第 65 条（纯数据开关漏配）的形态。
⇒ 必须有**端到端**断言：走 `GameState.preview_equipment_sale()`，用真实背包造出「超额度」场景，断言那件被勾选；负向里专门做一条「删掉 `build_preview` 的透传」必须变红。

### R2（高）排序 tiebreak 缺失 ⇒ 确认时假报「清单已变化」
`validate_equipment_sale()` 会逐行重算 `entry()` 并比对 `default_selected`。若同分件排序在两次调用间翻转，行状态就翻，玩家会看到「装备清单已变化，请重新核对」却什么都没变。
⇒ 排序键必须是全序：`(score desc, 背包格序 asc)`；`auto_sell` 用严格 `>`（同分新件让位）。配一条「同分两件，连续两次 `build_preview` 结果完全一致」的断言。

### R3（高）自动出售无撤销
驱逐会在玩家没看见的情况下卖掉一件**之前已经留在背包里的**装备。
⇒ 护栏四层：品质 ≤ 预设上限、非星级、非收藏、非破损；且只在 60 级 + 开关打开 + 金币未满时发生。仍需实机确认这种感觉可接受（见 §八 点验第 4 条）。

### R4（中）先卖后加，失败要能退
驱逐腾出的格正是新件要占的格。若 `add_item` 失败（理论上不会，但背包长度受扩容约束），不能出现「东西卖了、新件也没了」。
⇒ 顺序固定为「先卖出驱逐件 → 再 `add_item`」，并断言 `ok` 与金币同时正确。

### R5（中）性能
峰值 20 件/秒掉落 × 背包 137 件 ⇒ 最坏 2,740 次 `Equipment.score()`/秒。当前量级应可忽略，但**先测再谈优化**；若单次超过 0.2ms，再考虑按 `inventory` 变更版本做缓存（不得改成逐帧扫描背包）。

### R6（中）「额度」只对可卖品质成立
金紫永远保留，所以最终形态是「**背包最多 N 件可售候选 + 任意多件金紫**」。文档与设置页文案必须这么写，否则玩家会认为「说好只留 2 件，怎么还有 6 件」。

### R7（低）与 `matches_low_gear` 那条旧链路无关
`Shop.matches_low_gear()` 的破损排除目前没有 UI 入口（工程 99 记的第 64 条遗留）。本方案**不碰它**，避免顺手扩大战线。

### D4（待你拍板）金紫要不要也限量
实测 Lv75 背包 41 件金紫（其中 20 件 76—80 级穿不上），本方案一件不动。如果你也想压这部分，可选：
- ① 维持现状（推荐先这样，符合你原话）；
- ② 同部位金紫只保留 N 件，超出的也卖（收益大、但违背「金紫不卖」的直觉）；
- ③ 给清单加「同部位已有更优」标注，让玩家自己批量勾（不改自动出售，纯可见性）。

## 八、实施批次

## 十一、一句话结论

**这条需求本质是把「评分可提升」从绝对保护改成相对排位**：同一个部位，只有排名前 N（N = 槽位数）的升级候选值得留，其余回归预设的普通规则。

改动集中在 `sell_gear_policy.gd` 一个文件加两个调用点，零数值改动、零存档结构改动。但要先接受两个事实：
1. 它清的是**重复候选**（你 Lv75 档实测 9 件稀有里清 7 件），**不是金紫存量**（41 件一件不动）；
2. 要做到「始终只保留 N 件」，拾取时必须允许**驱逐**——即在你看不见的时候卖掉一件之前留下的、更差的那件。
