## 0. 一句话结论

**这在技术上不是新功能，是「第四个随身道具」。**

M10-4 已经把 `useType: "panel"` → `PanelRouter` 的执行链、`requiresLevel` 任务门槛、`ToolReclaim` 读档补领、`can_drop_item` 不可丢弃、随身商店拒收全部做完了 —— 而且**这几处全部是数据驱动**（扫 `useType == "panel"`），加第四件道具**零改动就自动受保护**。铁匠面板本身也已经是一个「菜单壳」：它的 5 个服务全部是 `EventBus` 跳到别的面板，没有一个依赖「玩家站在 NPC 旁边」。

所以真正的成本不在代码，在**两处口径**：

1. 产品 13 §5.6 白纸黑字写着「随身铁匠 = 待评估、当前不实现」，并规定了「先改本节再动代码」。**必须先改文档**（§3）。
2. 工程 77 已经给了随身商店「1.5× 溢价修理」，铁匠是 1.0×。随身铁匠若照搬 1.0×，商店那行修理当场变成「同样的便利、更贵的价格」的坑（§4 Q3）。

代码量估计：**4 个文件、约 60 行**；数据 **3 处**；测试 **1 个新文件 + 4 处补断言**。

| 你的诉求 | 落到哪里 | 现状 |
|---|---|---|
| 「达到 80 级之后」 | 任务加 `requiresLevel: 80` | ✅ 能力已有（`MAX_QUEST_REQUIRES_LEVEL := 9999`，纯函数） |

### 1.1 先对齐「所有功能」到底是哪些

`blacksmith_panel.gd` 的服务菜单一共 **3 组 8 项**，全部是跳转到别的面板：

| 组 | 服务 | 落到哪 |
|---|---|---|
| 强化 | 升星装备 | `upgrade_panel.gd`（317 行） |
| 强化 | 重铸词条 | `reforge_panel.gd`（727 行） |
| 合成 | 四金合紫 / 四紫定向 / 四紫升紫 / 保星升级 | `equipment_fusion_panel.gd`（663 行） |
| 维护与转化 | 一键修理（身上 14 件） | 就地执行 `GameState.repair_equipment(1.0)` |
| 维护与转化 | 紫装献祭 | `equipment_fusion_panel.gd` 的 `SACRIFICE` 模式 |

这 5 个面板/动作**没有一处读 `npc`、`map`、`distance`** —— 它们只操作 `GameState.equipment` / `inventory` / 金币。这正是「随身复用」能成立的技术前提，也是本方案唯一的好消息。

> 🔑 所以「复用」不是复制代码，而是**让那个菜单壳能在没有 NPC 的情况下打开**。

## 2. 地基盘点：可复用的 90%

| 能力 | 现在的实现 | 随身铁匠要不要动 |
|---|---|---|
| 双击道具开面板 | `GameState._use_misc` → `useType == "panel"` → `PanelRouter.open(panelId)` | **不动**（纯数据驱动） |
| `panelId` 白名单 | `PanelRouter.PANELS`（启动期 `DataLoader` 查同一张表，脏 id 直接报错） | **加 1 行** |
| 任务等级门槛 | `requiresLevel` + 校验 | **不动** |
| 读档补领缺失工具 | `ToolReclaim.panel_tool_ids()` 扫 `useType == "panel"` | **不动**（注释要改，见 🔴 R5） |
| 工具不可丢弃 | `can_drop_item` 第一顺位查 `panel_tool_ids()` | **不动** |

> 一句话：**除了铁匠面板要认识「我是被道具打开的」，别的地方一行不用动。**

## 4. 四个决策点（需要你拍板）

### Q1 · 任务挂在哪个 NPC？

**推荐 A。**

| 选项 | 做法 | 代价 | 叙事 |
|---|---|---|---|
| **A 营地铁匠** | 给 `camp/map.json` 的铁匠加 `npcId: "camp_smith"` | 要改 1 行地图数据；**80 级后第一次点铁匠会先弹任务面板**（见下） | ★★★ 铁匠亲手给你打一把缩小版 |
| B 长老 `elder` | 零改动地图 | 长老已是纯任务官，交互零冲突 | ★★ 长老代发，功能味 |
| C 卫澄 `c6_npc01` | 接在 C6S07 后面 | 玩家要跑到 51 级的 `c6_map00` | ★★★ 剧情连贯（三件套 → 铁匠） |

**A 的副作用必须提前知道**：`game.gd::_interact_with` 的顺序是「**先任务、后 role**」——

```gdscript
Quest.on_npc_talk(npc_id)
if not npc_id.is_empty() and Quest.has_actionable_at_npc(npc_id):
    EventBus.quest_panel_requested.emit(npc_id)   # 有可接/可交任务 ⇒ 先进任务面板
    return true
...
if npc.role == "blacksmith":                       # 否则才进铁匠面板
```

所以营地铁匠一旦有了 `npcId`，**80 级后身上挂着这个任务时，点它会先开任务面板**；接完/交完后 `has_actionable_at_npc` 转假，恢复成铁匠面板。

这个行为**不是 bug**：`quest_panel._open_npc_service()` 本来就有一条 `"blacksmith"` 分支，点「铁匠服务」按钮会关掉任务面板再开铁匠 —— 这条路径在 M10-4 就建好了，只是到现在**没有任何铁匠承担过任务**，所以从来没人走到过。可以说是「顺着既有架构走」，也可以说是「把一条睡了三年的通路唤醒」。

> 如果你不想让铁匠的交互变复杂，选 B 最省事：长老发，铁匠只负责干活。

### Q2 · 任务目标做什么？

**推荐 A。**

| 选项 | 目标 | 评价 |
|---|---|---|
| **A `talk`** | 回城找发任务的 NPC 说一句话 | 与 C6S07「轻装远行」完全同构；零新物品、零新掉落表、零新校验 |
| B `collect` | 交 N 个材料 | 要定「材料从哪来」，还可能和 `spirit_shard` 的既有任务用途撞车（它已被 `Q003` 占着） |
| C `kill` | 在循环图杀 N 只 | 循环图的怪清一色清完即重生，`kill` 计数能记，但玩家已经在循环图刷了 20 级，再叠一道 grind 只是延迟便利功能 |

理由：这是**便利性解锁**，不是战力解锁。80 级功能如果还要「再打 2 小时才能用」，玩家在拿到它的那一刻只会觉得烦。C6S07 用 `talk` 把三件套发出去，同一条路走第二遍最稳。

### Q3 · 🔴 修理费率（与工程 77 直接冲突）

现状：`shop_panel.gd:450` 注释写着「随身商店修理行：**1.5× 便利费，铁匠 1.0× 仍是回城最优解**」。

如果随身铁匠原样搬 `repair_equipment(1.0)`，那商店那行就变成**同样远程、价格贵 50%** 的坑。

| 选项 | 做法 | 后果 |
|---|---|---|
| P1 随身也 1.5× | 铁匠面板按模式区分费率 | 回城 1.0× 仍最优；与「随身商店 +20%」同构；**但「复用全部功能」就不算全等** |
| **P2 随身 1.0× + 删商店修理行** | 铁匠收 1.0×，同时删掉 `shop_panel` 的修理行 | 只留一条远程修理通道，无坑；工程 77 的 R1「挂机断装死亡螺旋」防护**不减弱**（换成铁匠） |
| P3 并存 | 铁匠 1.0×，商店那行不动 | 留一个「同便利更贵」的误导路径 —— 不建议 |

**推荐 P2**，但它要动 `shop_panel.gd` + `PortableShopTest` 里关于修理行的断言，属于「顺手改别人的功能」，需要你明确同意。

### Q4 · 服务费要不要溢价？

| 选项 | 评价 |
|---|---|
| **A 不溢价（推荐）** | 「+20%」是**买货**的便利费（工程 47 定），铁匠服务是**成长消费**（升星动辄数万金）。给成长加 20% 惩罚，恰好惩罚了玩家最需要用随身铁匠做的事 |
| B 全部 +20% | 口径统一，但会让 10→11 段升星从 2 万变 2.4 万，玩家会算出来并厌恶它 |

> 与 Q3 不矛盾：**修理是「维护」，可以收便利费；升星/重铸/合成是「成长」，不收。**

{
  "id": "C7S01",
  "name": "炉火随行",
  "type": "side",
  "giver": "camp_smith",
  "turnIn": "camp_smith",
  "objective": { "kind": "talk", "targetId": "camp_smith", "count": 1 },
  "reward": {
    "gold": 0, "xp": 0,

### 5.2 代码（4 处，约 60 行）

| 文件 | 改什么 | 为什么 |
|---|---|---|
| `scripts/systems/panel_router.gd` | `PANELS` 加 `"blacksmith": {"ready": true, "title": "ui.panel.portable_blacksmith"}`；`open()` 加 `match` 分支 emit `blacksmith_panel_requested("", "", true)` | 这是唯一入口，别在别处直连信号 |
| `autoload/event_bus.gd` | 信号改三参 `blacksmith_panel_requested(npc_name: String, greeting: String, portable: bool)` | 见 🔴 R2 |
| `autoload/event_bus.gd` 的三个 emit 点 | `game.gd:508` / `quest_panel.gd:400` / `tests/equipment_fusion_ui_test.gd:21` 各补第三参 `false` | **GDScript 信号参数不支持默认值**，漏一处就是运行期 `too few arguments` |
| `scripts/ui/blacksmith_panel.gd` | 加 `var _portable := false`；`_on_requested` 第三参；`set_open(true)` 按 `_portable` 决定初态；`_show_menu()` 里在随身模式隐藏「离开」 | 见 §5.3 |
| `scripts/ui/hotbar_visual.gd` | `SHORT_LABEL_KEYS` 加 `"tool_portable_blacksmith": "ui.hud.tool_smith_short"` | 不加就显示名称首字「随」，与「随身商队」「随身车夫」三个字撞车 |

**`set_open` 的关键改法（这是全案唯一有坑的地方）：**

现状是硬编码「问候卡可见 / 服务卡隐藏」：

```gdscript
func set_open(open: bool) -> void:
    visible = open
    ...
    if open:
        _continue.visible = true          # ← 问候卡才有的「继续」
        _upgrade.visible = false
        ...
        _greeting_card.visible = true
        _service_card.visible = false     # ← 随身模式要反过来
```

改法：随身模式下**直接进服务菜单**，不显示问候卡与「继续」按钮 —— 因为没有 NPC 可问候，一屏空话 + 一次多余点击是纯摩擦。

```gdscript
if open:
    if _portable:
        _show_menu()      # 复用现成的切换函数，不复制一份状态
    else:
        # …原问候卡初态
```

> 🔑 复用 `_show_menu()` 而不是复制它的 8 行：那 8 行里包含 `_refresh_repair_button()`（修理价格要现算）和 `set_content_scroll()`（高度要重结算），复制一份必然漏掉其中一个。

### 5.3 界面：两种模式的差异

| 元素 | 回城铁匠 | 随身铁匠 |
|---|---|---|
| 标题 | NPC 名（`npc_name`） | `随身铁匠`（`PanelRouter.title("blacksmith")`） |
| 问候卡 + 头像 + 「继续」 | 有 | **跳过**，直接服务菜单 |
| 8 项服务 | 全有 | **全有，一个不少** |
| 「离开」按钮 | 有 | **隐藏**（无对话可离开，右上角 × 足够；底部留一个空按钮会让人以为漏了什么） |
| 修理费 | 1.0× | 1.0×（Q3 选 P2 后商店那行删除） |
| 升星/重铸/合成/献祭费 | 原价 | 原价（Q4-A） |

### 5.4 交互链路（走一遍，确认没有断点）

```
背包双击「随身铁匠」
  → GameState.use_item(index)
  → _use_misc()  读 useType = "panel"
  → PanelRouter.open("blacksmith")
  → 查 PANELS（脏 id 启动期就死了，这里是兜底）
  → is_openable() 为 true
  → EventBus.blacksmith_panel_requested.emit("", "", true)
  → blacksmith_panel._on_requested(_, _, true)
     → _portable = true；标题 = PanelRouter.title("blacksmith") = 「随身铁匠」
     → set_open(true) → _show_menu() → 8 项服务可点
  → 点「升星装备」→ set_open(false) → upgrade_panel_requested
  → 升完关掉升级面板 → 回到游戏（**不会自动重开随身铁匠**，与回城铁匠行为一致）
```

**道具不消耗**：`_use_misc` 的 `panel` 分支直接 `return {"ok": true}`，不动背包 —— 这条已有测试守着（`PortableToolsTest` 用例 5），新道具自动继承。

## 9. 一个建议：把「80 级」当卖点，而不是门槛

任务文案建议写成「铁匠追不上你」而不是「你获得了一件工具」。80 级正好是进入聚金地脉的等级（`entryGate.minLevel`），玩家在这一刻的心理是「我要开始长期蹲在图里了」—— 在这个节点把「家」的一部分塞进行囊，比任何数值奖励都贴合这条循环的节奏。

同理，**不建议**给这件道具加任何战力加成。它的价值就在于「不用回城」，一旦带上属性，就会被拿去和装备比较，反而显得不伦不类。

## 10. 附：为什么不做「随身铁匠 NPC 实体」

一个自然会想到的替代方案是「召出一个铁匠 NPC 跟着你走」。不推荐，理由三条：

1. 铁匠面板**本来就没有依赖 NPC**，召唤只是多一层实体，不带来任何能力；
2. 一个跟随实体要进 `z_index` 排序、要参与碰撞、要在 2400 件积压的场景里占绘制预算（工程 104 的 2.1 ms/帧是省出来的）；
3. 它会让「随身」的第二层含义（可以边走边开）变成「必须在某个位置开」，反而更差。

> 结论：**道具 → 面板**是这条链的最短路径，也是既有架构已经铺好的一条。

### 11.2 Q2 的具体化：kill 任务怎么设计

**数据结构**（`kill` 型全库 44 条，`targetId` 是具体 `monsterId`，不是怪群）：

```json
"objective": { "kind": "kill", "targetId": "c6_normal01", "count": 20 },
"mapScope": ["c7_gold_field"],
"requiresLevel": 80,
"prev": "C6S07"
```

**选 `c6_normal01` 的理由**：聚金地脉的 `spawnPoints` 里它是 12 只/轮、15 秒重生，是最常见的那一种；杀 20 只 ≈ 两轮刷新。玩家 80 级后本来就在这张图挂机，**挂着挂着就完成了**，不需要专门去凑。

**⚠ 必须让你知道的一个事实：kill 型比 talk 型多一整趟往返。**

| 方案 | 玩家动作 | 回营地次数 |
|---|---|---|
| talk（v1 推荐） | 80 级 → 回营地 → 说话 → 拿到 | **1 次** |
| **kill（你选的）** | 80 级 → 回营地**接**任务 → 回聚金地脉杀 20 只 → 回营地**交**任务 → 拿到 | **2 次** |

原因：`c7_gold_field` 的 `npcs: []`（这正是要做随身铁匠的根因），所以**接和交都只能发生在营地**。而玩家 80 级的那一刻，人正在聚金地脉里（`entryGate.minLevel = 80`）。

这不是缺陷，是「任务感」的代价。如果你觉得两趟太重，有两个轻量修法（都不改架构）：

- **修法 A**：`count` 降到 12（一轮刷新就够），配合「挂着就完成」，实际只多花一次回城
- **修法 B**：把 `prev` 从 `C6S07` 改成空 —— 但那样 60 级玩家做完三件套就能看到 80 级任务（被 `requiresLevel` 挡住，看得见接不了），体验更差，**不建议**

> 我按 `count: 20` + `prev: C6S07` 写进待办。要改成 12 随时说。

**已拍板（2026-10-29）：`count: 20`，`prev: C6S07`，`targetId: c6_normal01`，`mapScope: ["c7_gold_field"]`。**

### 11.3 🔴 Q4「全部 +20%」的真实代价

**先纠正 v1 的一个估计错误**：我在 v1 §0 写「代码 4 个文件、约 60 行」，那是**不含溢价**的。加了溢价之后不是 60 行。

原因是本项目有一条执行链上的特点：**费用的「显示」和「扣费」是两处独立算的**，不是同一个变量传下去。

| 服务 | 显示（面板） | 扣费（GameState） | 是否同源 |
|---|---|---|---|
| 升星 | `upgrade_panel.gd:280` `Upgrade.cost(star)` | `game_state.gd:1554` `Upgrade.cost(star)` | ❌ 各算一次 |
| 重铸 | `reforge_panel.gd:402` `Reforge.cost(level, locks)` | `game_state.gd:1636` `Reforge.cost(...)` | ❌ 各算一次 |
| 保星跨档 | 读 `plan_transfer()["cost"]` | 同一份 plan | ✅ 单一来源 |
| 四金合紫 / 四紫定向 / 四紫升紫 | — | — | **无金币费用**，只消耗材料 |
| 献祭 | — | — | **无金币费用**，换经验 |
| 修理 | `blacksmith_panel._refresh_repair_button()` | `GameState.repair_equipment(rate)` | ✅ 费率已参数化 |

**结论：`+20%` 实际只需要加在 3 个地方（升星 / 重铸 / 保星），但升星与重铸各有「显示」和「扣费」两个独立计算点 ⇒ 一共 4 处必须同时改、且算法必须逐位一致。**

漏一处的后果，是玩家能立刻发现的：

| 漏哪一处 | 玩家看到的现象 |
|---|---|
| 只改扣费、不改显示 | 按钮写「43,240 金」，实际扣 51,888 —— **看起来像偷钱** |
| 只改显示、不改扣费 | 按钮写「51,888」，实际扣 43,240 —— 玩家会以为赚了，然后在回城时发现不一致 |
| 一处用 `round`、一处用 `ceil` | 金价差 1 金，`--all` 的逐值断言抓不到，但玩家对账时能发现 |

**实现方案（推荐）—— 单一纯函数，显示与扣费都调它：**

```gdscript
# scripts/systems/service_fee.gd（新建，约 20 行）
class_name ServiceFee
extends RefCounted

## 随身通道的成长服务费率（产品 13 §5.6 / 工程 108 Q4）。
const PORTABLE_RATE := 1.2

## 唯一的取整口径。**显示与扣费必须都走这里** ——
## 两个面板各写一次 ceil 就会差 1 金，而这种差在测试里看不出来。
static func apply(base: int, rate: float) -> int:
	if rate <= 1.0:
		return base
	return int(ceil(float(base) * rate))

static func rate_for(portable: bool) -> float:
	return PORTABLE_RATE if portable else 1.0
```

**然后 4 个点改成：**

```gdscript
# upgrade_panel.gd:280（显示）
var price := ServiceFee.apply(Upgrade.cost(star), ServiceFee.rate_for(_portable))
# game_state.gd:1554（扣费）—— 函数加 fee_rate 参数
var price := ServiceFee.apply(Upgrade.cost(star), fee_rate)
```

**这里冒出一个新问题：面板怎么知道自己是「随身打开的」？**

`upgrade_panel` 是被 `EventBus.upgrade_panel_requested.emit()` 打开的，**这个信号没有参数**。所以要把 `portable` 一路传下去，必须改 3 个信号：

| 信号 | 现状 | 要改成 |
|---|---|---|
| `upgrade_panel_requested` | 无参 | `(portable: bool)` |
| `reforge_panel_requested` | 无参 | `(portable: bool)` |
| `equipment_fusion_panel_requested` | `(mode: String)` | `(mode: String, portable: bool)` |

每个信号的 emit 点都要同步（铁匠面板 3 处 + 可能的测试）。**合计：6 个文件、约 15 个改动点。**

> 🔴 这是「Q4 = 全部 +20%」必须付的账。我不会偷偷缩成「只给升星加价」—— 但你如果觉得这 15 个点不值，**有一个降级选项**：
>
> **降级 L**：只给**修理**收 1.5×（Q3 已定），成长服务**不加价**。改动点从 15 个降到 0 个（修理费率已参数化）。
> 代价是「随身升星和回城一个价」，与「随身商店 +20%」的口径不完全统一。
>
> 我的判断：**值得做**。理由不是「口径统一」这种形式理由，而是 —— 如果随身铁匠完全不加价，那么回城铁匠在 80 级后**永久失业**，往后任何「回城」的理由都少一条；而 +20% 恰好把「回城」保留成一个**有意义的选择**（省 20% 换一趟路）。这是设计上的正收益，不是惩罚玩家。

### 12.2 负向 7 条（逐条确认「红在对的断言上」）

| # | 注入 | 应红判据 | 实测 |
|---|---|---|---|
| N-1 | 删 `PANELS["blacksmith"]` | 面板登记 | ✅ 红 |

| N-5 | `reward.unlocks` → 单数 `unlock` | unlocks 数组 | ✅ 红 |
| N-6 | 升星只改扣费不改显示 | 实扣 ≠ 显示 | ✅ 红（实扣 2026 ≠ 显示 1688） |
| N-7 | 重铸显示用截断、扣费用 ceil | 实扣 ≠ 显示 | ✅ 红（实扣 88426 ≠ 显示 88425） |

**⚠ 判据层被实测推翻并修正的两处（改的是判据/注入形态，一个游戏数值没动）：**

- **N-5 首轮假绿**：判据原写 `reward.get("unlocks", []) is Array` —— 字段被改名成单数后 `get` 返回默认 `[]`（仍是 Array），恒绿。真正在守的是「不得出现单数 unlock」和「unlocks 含该道具」两条。修法：`check(reward.has("unlocks") and unlocks is Array, ...)`，让「必须是数组」这条真有牙（字段缺失也红）。
- **N-7 首轮假绿**：注入形态选错。`round(x*1.2)` 在重铸当前数据下**永远等于** `ceil(x*1.2)` —— 重铸 base（`baseGold=500 / levelFactor=0.75 / lockFactor=0.5`）mod 5 只会是 0 或 3，×1.2 分别是整数或小数 0.6，round 都向上 = ceil。改注入为**截断 `int(x*1.2)` vs 进位 `ceil`**，并把测试样本切到**锁一条词条**（`locked.size()=1` ⇒ base=73688，×1.2=88425.6 才非整数）⇒ 差 1 金，稳定红。

### 12.3 负向脚本自身的坑 76 加固

`verify_108_negative.py` 首轮曾报 N-3「仍绿（断言无效）· 实际红项：无」，重跑却稳定红 —— 是 Godot 偶发启动失败（输出无 `{Test}: PASS/FAIL` 结论行）被误读成「没牙」。已给 `run_test()` / `bootstrap_warnings()` 加**结论行有效性判定 + 最多 3 次重试**，并在汇总里区分「无效轮次」与「断言真没牙」，否则负向报告本身不可信。

### 12.4 落地中暴露并修掉的真 bug

**改信号回调签名，只搜 `emit` 点不够 —— 测试会「直接调用」回调方法。** D-5 把 `equipment_fusion_panel._on_requested` 从单参 `(mode)` 改成双参 `(mode, portable)`，只补齐了 signal `emit` 和 `blacksmith_panel._open_fusion`，漏了 `equipment_fusion_ui_test.gd`（9 处）与 `star_transfer_level_hint_test.gd`（1 处）**直接调 `_on_requested(mode)`** ⇒ 默认集当场红 2 项（`SCRIPT ERROR: Expected 2 argument(s)`）。

修法**刻意不用默认值**：虽然 `carter_panel._on_requested` 有 `portable: bool = false` 的先例，但 fusion 面板注释自己写了「将来给合成加服务费只有这一个入口接线」—— 给默认值会让「随身打开却按回城口径」在将来静默发生。改为**补全 10 处直接调用为双参**，保持强制签名，漏传当场炸。

> 🔴 这条同时纠了一个认知：`--all` 之前的默认集是「有人区」，我改信号参数时只盯 emit，差点把「直接调用」这条更隐蔽的路径漏过去 —— 是默认集红出来才发现的。宁可签名强制让漏传炸，也不要默认值掐掉这层保护。

## 13. 追记：发布点从营地铁匠改到镇脉前哨铁匠（2026-10-30 实机反馈）

玩家 80 级后实测反馈「在铁匠那里看不到任务」：当时人站在 `c6_map00`（镇脉前哨），点的
是本图铁匠**闻钧（c6_npc02）**，而任务发布人挂在第一章**营地铁匠（camp_smith）**——
两个铁匠不是同一个人，玩家自然找不到。这不是逻辑 bug，是**发布点选择的引导失败**：
支线任务没有主线式「下一站」提示，玩家对「回第一章营地」零预期。

**拍板变更（2026-10-30）**：

| 项 | 改前 | 改后 |
|---|---|---|
| `giver` / `turnIn` | `camp_smith`（营地） | **`c6_npc02`（镇脉前哨·闻钧）** |

  `tooltip_text`，标记不会被 `QuestInlineText.markup` 转换，tooltip 会漏出花括号。
  全库 36 个任务 desc 均无 `{`，维持该惯例。

  删掉反而多一次无谓的数据面变更。
