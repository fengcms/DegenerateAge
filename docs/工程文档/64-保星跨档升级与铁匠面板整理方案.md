# 保星升级「跨档可选」与铁匠面板整理方案（工程 64）

> 状态：**已实施（2026-10-20）**。三个决策点 D1/D2/D3 全部按推荐 A 落地，落地记录与负向结果见 §9。
> 核对日期：2026-10-20。
> 需求来源：① 去掉保星升级「低档 12★ 只能升到紧邻下一档」的限制，允许升到任意更高档，
> 金币按跨档数线性放大（跨 1 档 = x，跨 2 档 = 2x，跨 3 档 = 3x……）；
> ② 铁匠面板「有点乱」，重新整理。

---

## 1. 需求复述与我的理解

| 你的原话 | 我的理解 |
|---|---|
| 100 级 12★ 装备只能升 110 级，不能升 120 级 | 现状是 `new_tier == old_tier + 10` 的**硬相等**判断，越一档直接拒绝 |
| 去掉这个限制，低等级 12★ 项链可以升高等级项链 | 只要**同部位、更高档、0 星紫装**，档差可以是 1、2、3……任意正整数 |
| 100→110 扣 x，100→120 扣 2x，100→130 扣 3x | 费用 = `基础价 × 跨档数`，基础价仍是现有的 12 次全成功金币和 **128,747** |
| 铁匠面板有点乱 | 见 §4，三个具体病灶 + 重排方案 |

⚠️ 有一处口径我要先讲清，免得实现完对不上你的预期：**「100 级升 110 / 120」在代码里是按十级档算的**。
100 级装备落在 **101—110** 这一档（`suit_start(100) = 101`），所以：

| 你的说法 | 代码里的档位 | 跨档数 | 费用 |
|---|---|---|---|
| 100 升 110 | 101 → 111 | 1 | 128,747 |
| 100 升 120 | 101 → 121 | 2 | 257,494 |
| 100 升 130 | 101 → 131 | 3 | 386,241 |
| 100 升 200 | 101 → 201 | 10 | 1,287,470 |

也就是说「升到 110」在档位上其实是**升到 111—120 那一档**（装备的需求等级会落在 111—120 之间，按部位偏移）。
这跟现有 51→61 的口径完全一致，不是新引入的偏差。

## 2. 现状勘察

### 2.1 唯一的门在规则层，只有一行

`scripts/systems/equipment_fusion.gd:138`：

```gdscript
if old_tier == 0 or new_tier != old_tier + ItemFactory.TIER_SPAN or kind.is_empty() \
        or Equipment.item_kind(new_item) != kind:
    return {"ok": false, "reason": "只能向相邻高一档的同类型紫装保星升级"}
```

费用在下一行，与档位**无关**：

```gdscript
return {"ok": true, "tier": new_tier, "target_kind": kind, "cost": full_star_cost(), "reason": ""}
```

`full_star_cost()` = `Σ Upgrade.cost(0…11)` = **128,747**（`UP_BASE=500`、`UP_R=1.5`）。
所以现在 51→61 和 101→111 是一个价。**改成「基础价 × 跨档数」不需要动这个函数**，只改 `plan_transfer` 的返回。

### 2.2 上游与下游都不用改

| 层 | 是否受影响 |
|---|---|
| `GameState.forge_equipment()` | 只读 `plan.cost` / `plan.tier`，**零改动** |
| `EquipmentFusion.make_output()` | 按 `tier` 生成；>60 走 `make_equip_dynamic` 动态分支，已支持任意档 |
| `template_for(tier, kind)` | 51 档以上一律复用第 51 套型号（D-21），**任何档都有型号** |
| UI 材料格 | 第二格只校验「0★ / 紫 / 同部位」，档位由 `plan_transfer` 判 |
| 存档 | 产物是普通实例，schema 不变 |

### 2.3 🔴 两处现存但被「相邻」掩盖的缺口

1. **档位上限没有前置判断。** `plan_transfer` 只查 `template_for(new_tier, kind)` 非空，
   而 51 档以上恒非空；真正的上限在 `make_output` 里（`dynamic_level_for` 必须 ≤ 9999）。
   一旦允许跨档，玩家可以算出「100 档跳到 9990 档」这种在 `make_output` 才失败的组合，
   届时错误文案是「目标装备生成失败，未消耗材料」—— 玩家看不出是自己选太高了。
   **建议在规则层前置**：`new_tier > INSTANCE_LEVEL_CAP - (TIER_SPAN - 1)` 直接给「目标档超出装备等级上限」。

2. **产物可能超出玩家等级。** 现在只允许相邻档，所以「升完穿不上」最多差 9 级，几乎见不到；
   跨档后 100 级玩家完全可以把 12★ 升到 200 档 —— 装备合法、但**穿不上**。
   规则层不该拦（材料是玩家自己的），但**预览里必须提示**，否则玩家会以为合成把装备弄坏了。

### 2.4 跨档倍数的经济性（顺带算了一遍，没有漏洞）

装备战力随等级走 `Balance.scale`：`1 + 0.12·d + 0.0022·(d−12)²`（d = 等级 − 60），**近似二次**。
以 101 档为基准：

| 目标档 | 跨档数 | 费用 | 战力涨幅 | 每份金币换来的涨幅 |
|---|---|---|---|---|
| 111 | 1 | 128,747 | +34.8% | 34.8% |
| 121 | 2 | 257,494 | +75.0% | 37.5% |

看起来「跨 2 档」的单位收益略高，但**总涨幅只有 1.30 倍，价格却是 2 倍** —— 单位金币收益反而更低。
结论：**线性倍数天然抑制大跳，不需要再加「最多跨 N 档」的额外限制**（除非你另有想法，见 §5 D1）。

真正的门槛在**材料**：想升到 200 档，你得先有一件 200 档的 0 星同部位紫装，而那只有打到那个等级才掉。

## 3. 方案：规则层

### R1 新增跨档数计算

```gdscript
## 保星跨档数：档差必须是十级的整数倍，否则返回 0（同档 / 降档 / 非整档）。
static func transfer_gap(old_tier: int, new_tier: int) -> int:
    var diff := new_tier - old_tier
    if old_tier <= 0 or diff <= 0 or diff % ItemFactory.TIER_SPAN != 0:
        return 0
    return diff / ItemFactory.TIER_SPAN
```

### R2 `plan_transfer` 改造

```gdscript
var gap := transfer_gap(old_tier, new_tier)
if old_tier == 0 or gap == 0 or kind.is_empty() or Equipment.item_kind(new_item) != kind:
    return {"ok": false, "reason": "只能向更高档的同类型紫装保星升级"}
if new_tier > ItemFactory.INSTANCE_LEVEL_CAP - (ItemFactory.TIER_SPAN - 1):
    return {"ok": false, "reason": "目标档已超出装备等级上限"}
if template_for(new_tier, kind).is_empty():
    return {"ok": false, "reason": "目标等级档缺少装备型号"}
return {"ok": true, "tier": new_tier, "target_kind": kind, "gap": gap,
        "cost": full_star_cost() * gap, "reason": ""}
```

`gap` 是新字段，只供界面显示；`GameState` 仍然只认 `cost` / `tier`。

### R3 星级 / 品质 / 收藏 / 部位规则**一律不变**

- 旧件必须 **12★ 紫装**，新件必须 **0★ 紫装**，同部位，两件都未收藏、都在背包。
- 产物仍是全新 instanceId 的 **12★ 紫装**，词条重随机。
- 与四金 / 四紫的边界不变（12★ 紫装仍不可投四紫定向）。

## 4. 方案：铁匠面板整理

### 4.1 三个具体病灶（都能量化）

截图里乱的不是配色，是**结构**：

| # | 病灶 | 成因 |
|---|---|---|
| 1 | 「离开」独占第一行左边，右边一大片空白，看起来像服务项 | 它和「继续」共用同一个 2 列 `GridContainer`；`_show_menu()` 把「继续」隐藏后，离开占左格、弹性 spacer 占右格 |
| 2 | 「保星升级」单独一行，右格空着 | 5 个服务塞 2 列 = 6 格，必然剩 1 个孤格 |
| 3 | 说明文字被横向截断，底部露出半行字，还要滚动 | 三段说明拼成一个 `Label` 塞进高度 54—150 的 `ScrollContainer`；连「可用服务」标题也一起被滚走 |

### 4.2 重排方案

```
◆ 闻钧                                    ×
──────────────────────────────────────────
◆ 强化
[ 升星装备        ] [ 装备重铸        ]
  升星消耗材料与金币，可查看本次成功率；
  重铸重掷全部词条，品质与星级不变

◆ 合成
[ 四金合紫        ] [ 四紫定向        ]
  四金换随机部位紫装，四紫换指定部位紫装

[ 保星升级                            ]   ← 整行，强调它是高级服务
  12★ 紫装传承到更高档：跨 1 档为基准价，
  每多跨 1 档多扣 1 份金币
──────────────────────────────────────────
[ 离开 ]                        [ 继续 ]
```

四条改动：

1. **「离开」移出服务网格**，和「继续」一起放进底部固定操作行。服务区只剩 5 个服务，
   不再有「离开看起来像个服务」的歧义。
2. **按「强化 / 合成」分组**，两组各带一条 12px 灰字说明，替代原来的长段落。
   组标题 + 说明让玩家一眼知道「我在哪一组」。
3. **「保星升级」整行独占**（不是半格）。它现在是唯一带「跨档扣费」规则的复杂服务，
   半格按钮放不下说明。
4. **说明不再靠滚动**：`ScrollContainer` 保留（200% 缩放下仍需要兜底），但 100% 缩放下
   内容整体放得下，滚动条不会出现。滚动区高度改成
   `clampf(logical.y − 250, 54, 320)`：100% 时给到 320（内容约 250，不滚）；
   200% 时给到 110（内容仍滚动，面板不会顶出屏幕）。

### 4.3 文案改动

| 旧 | 新 |
|---|---|
| `p005` 三段式长文（升星） | 删除，改 `hint_enhance` 一句话 |
| `p006` 三段式长文（重铸） | 合并进 `hint_enhance` |
| `p009` 三段式长文（合成与保星） | 删除，改 `hint_forge` + `hint_transfer` |
| — | 新增 `group_enhance`「强化」、`group_forge`「合成」 |

保星说明必须把新规则写进去（「跨 1 档为基准价，每多跨 1 档多扣 1 份金币」），
否则玩家只会觉得「怎么突然贵了」。

### 4.4 顺带修的语义文案

| key | 现值 | 改为 |
|---|---|---|
| `ui.fusion.star_hint` | 消耗旧档 12★ 与**相邻高档**同类型 0★ | 消耗 12★ 与**任意更高档**同类型 0★；跨档越远金币越多 |
| `ui.fusion.new_role` | 第二格需要**相邻高档**同类型 0 星紫装 | 第二格需要**更高档**同类型 0 星紫装 |
