# 110 · 兑换数量弹框（批量兑换）方案与分析

> 前置：工程 109《金币兑换金条金砖（仓库NPC双向兑换）》已落地（提交 `0bf001be` / `6c525bc4` / `3ba7f62f` / `84a18e9d`）。
> 本文只改**交互层**，汇率、落账、校验、数据一行不动。

---

## 1. 问题

109 交付的兑换区是「**单击换 1 次，按住 Shift 单击换到上限**」。实机第一反应就暴露了问题：

> 「我要换 100 个金条，鼠标点击累死了。」

具体两处不合理：

| 问题 | 后果 |
|---|---|
| 「换到上限」绑在 **Shift** 上 | Shift 是玩家常按的修饰键。想换 1 块却手滑按着 Shift ⇒ **1 亿金币瞬间清零**，且无二次确认。这是个不可逆的**误操作陷阱**，不是便捷功能 |
| 没有「任意数量」的概念 | 只有「1」和「全部」两个档位。玩家要 100 块（上限 1234）时，除 Shift 全换外无路可走 |

玩家提出的方案是对的：**点按钮 → 弹框 → 输数字 → 确认**。

## 2. 现状盘点（先确认哪些不用动）

| 层 | 现状 | 本工程是否需要改 |
|---|---|---|
| `GoldExchange.plan(pair_id, times)` | 已支持任意 `times ≥ 1`，返回目标状态 | **零改动** |
| `GoldExchange.check(pair_id, times)` | 任意 `times` 的可行性判定 | **零改动** |
| `GoldExchange.max_times(pair_id)` | 源量 / 仓容 / 金币上限三者取小 | **零改动** |
| `GameState.exchange(pair_id, times = 1)` | 一次性赋值落账，失败一分不动 | **零改动** |
| `data/exchange.json` | 四条汇率 | **零改动** |
| 仓库面板布局 | 弹框是浮层，不占 `WAREHOUSE_VERTICAL_CHROME_BUDGET` | **零改动** |

结论：**逻辑层天然支持批量，109 只是没把入口给出来。** 本工程要写的全部是 UI。

### 2.1 可复用与不复用的判断

| 组件 | 结论 | 理由 |
|---|---|---|
| `PanelConfirmDialog` | 🔴 **不复用** | 它被**存档覆盖**与**设置改键冲突**两处共用，职责是「标题 + 说明 + 确认/取消」。加输入框会让一个三处共用的组件长出「可选输入模式」分支，而这两处永远用不到。08 坑 91 的口径：共用组件的模式开关，宁可新写一个，不要给默认值 |
| `PanelChrome`（外框/标题/按钮/分隔线样式） | ✅ **复用** | 纯样式，无状态 |
| `PanelChrome.style_line_edit` | ✅ **复用** | 已有 LineEdit 皮肤 |
| `save_panel` 的输入行结构 | ✅ **参照**（抄结构不抄类） | `LineEdit` + `max_length` + `custom_minimum_size` 的既有做法 |

### 2.2 输入冲突：已确认安全

弹框输入数字时，会不会顺手触发游戏操作？查过三条链路：

| 链路 | 判据 | 结果 |
|---|---|---|
| 快捷栏（数字键 1—8） | `hud.gd:417` 首行 `if GameState.world_controls_blocked(): return` | ✅ 屏蔽 |
| 角色移动 / 攻击 | `player.gd:353` 读 `world_controls_blocked()` | ✅ 屏蔽 |
| 世界目标切换（Tab） | `game.gd:373` 同样读该判据 | ✅ 屏蔽 |

而 `world_controls_blocked()`（`game_state.gd:2028`）除了看 `WORLD_INPUT_BLOCKING_PANEL_IDS`，还额外判：

```gdscript
var focus := get_viewport().gui_get_focus_owner()
return focus != null and focus.is_visible_in_tree() and (focus is LineEdit or focus is TextEdit)
```

**LineEdit 拿到焦点即自动屏蔽世界输入，无需往 `WORLD_INPUT_BLOCKING_PANEL_IDS` 加 `"warehouse"`。** 这一点很重要：仓库面板打开时挂机战斗仍在跑（金币会变），我们不想把整张地图封住。

## 3. 交互设计

### 3.1 入口

点四个兑换按钮中的任意一个 ⇒ 弹出数量框。**Shift 全兑彻底移除**（拍板结论）。

### 3.2 弹框布局

```
┌─ 金币 → 金条 ──────────────────────────┐
│                                        │
│  1 次 = 1,000,000 金币 → 金条 ×1        │   ← 汇率说明（从 exchange.json 推导）
│                                        │
│  兑换次数   [    100    ]   [ 最大 1234 ] │   ← 输入框（默认 1，全选）+ 最大按钮
│                                        │
│  将消耗 100,000,000 金币                 │   ← 实时预览：消耗
│  得到 金条 ×100                          │   ← 实时预览：得到
│                                        │
│                      [ 取消 ]  [ 确认兑换 ] │
└────────────────────────────────────────┘
```

### 3.3 三条行为规则

| 场景 | 行为 |
|---|---|
| 弹框打开 | 输入框**默认填 `1` 并全选**（玩家直接敲数字即覆盖，不用先删） |
| 输入合法（`1 ≤ n ≤ max`） | 确认按钮可用；预览实时更新 |
| 输入非法（空 / 0 / 非数字 / `> max`） | 确认按钮**禁用**，预览行位置改显失败原因。**不是点了才报错** |
| 回车（`text_submitted`） | 等同点确认（合法时）；非法时无效 |
| Esc | **只关弹框，不关仓库面板**（`set_input_as_handled()` 抢在面板 `_unhandled_input` 之前） |
| 确认成功 | 弹框关闭，面板底部 `_detail` 显示「兑换完成：金条 ×100」，库存与「可换 N 次」立即刷新 |
| 确认失败 | 弹框关闭，`_detail` 显示失败原因（沿用 109 的 `msg.exchange.p00x`） |

### 3.4 输入框的数字 = **兑换次数**（拍板结论）

四种兑法口径统一，配合实时预览消除歧义：

| 兑换对 | 输 100 的含义 |
|---|---|
| 金币 → 金条 | 花 1 亿金币，得 100 块条 |
| 金条 → 金砖 | 花 1000 块条，得 100 块砖 |
| 金条 → 金币 | 花 100 块条，得 1 亿金币 |
| 金砖 → 金币 | 花 100 块砖，得 10 亿金币 |

> 备选方案「输想要的产出数量」被否：对两个 →金币 兑法要输 `10000000` 这种 8 位大数，且必须是 100 万的整倍数，输错只能报错。

## 4. 组件设计：`PanelAmountDialog`

新建 `scripts/ui/panel_amount_dialog.gd`（`class_name PanelAmountDialog`）。

**职责边界与 `PanelConfirmDialog` 完全一致：只负责呈现与收集，不决定业务状态。** 它不知道汇率、不知道仓库、不知道金币——只知道自己有一个 `max` 和用户输了个数。

```gdscript
signal submitted(times: int)

var title: String            # 「金币 → 金条」
var rate_text: String        # 「1 次 = 1,000,000 金币 → 金条 ×1」
var max_times: int           # 由调用方查询后传入
var preview_text: String     # 「将消耗 … / 得到 …」，由调用方在 times 变化时算
```

调用方（仓库面板）负责：

```gdscript
dialog.max_times = GoldExchange.max_times(pair_id)
dialog.rate_text = GoldExchange.rate_text(pair_id)
dialog.submitted.connect(func(n: int) -> void: _do_exchange(pair_id, n))
dialog.popup()
```

**为什么预览文案由调用方算而不由弹框算**：弹框一旦自己要算「消耗多少 / 得到多少」，就得读 `exchange.json`、`ItemUtil.display_name`、`GameState`——它立刻从一个哑组件变成半个业务层，且这套换算会与 `GoldExchange` 里的口径形成第二份实现。**预览必须和真正提交同源。**

## 6. 风险与对策

### 🔴 R1 · 弹框打开期间 max 会变

仓库面板**不在** `WORLD_INPUT_BLOCKING_PANEL_IDS`，挂机战斗仍在跑，金币会涨。玩家开框时 max=1234，输 1234，确认时金币又涨了 —— 无害；但反向场景（金币被消耗、仓库被塞满）会让「弹框算的 max」过时。

**对策**：弹框只负责**收集数字**，确认时必须走 `GameState.exchange()` —— 它内部重新 `plan()`，失败返回原因。**绝不在 UI 层拿弹框打开时算的 max 去夹取**再提交（那等于用一个过时快照改写玩家输入）。

### 🔴 R2 · 焦点（实测结论：只需要"打开时抓"）

`world_controls_blocked()` 里的 `is_visible_in_tree()` 判据已经覆盖"隐藏即不屏蔽"。
**方案原本要写的 `close()` 里 `release_focus()` 实测是无效防御** —— Godot 在控件隐藏时
自动释放焦点，删掉那行行为完全一致（负向 N-2 第一次注入时「仍绿」暴露了这一点）。
因此代码里刻意**不写**它，只在 `popup()` 里抓焦点；断言也随之改成「打开时必须聚焦」。
详见 §10.2。

### 🔴 R3 · 数字解析边界

| 输入 | 处理 |
|---|---|
| 空串 / 纯空格 | 确认禁用 |
| `0` / 负数 | 确认禁用（`-` 在过滤阶段就被剔除，负数进不来） |
| 非数字字符（粘贴「1e5」） | `text_changed` 过滤掉；过滤后为空则禁用 |
| 超长数字（粘贴 20 位） | `max_length = 7` 截断 + `is_valid_int()` 双保险。**不能直接 `to_int()`**：GDScript 的字符串转 int 在溢出时行为不确定，实测不可依赖 |
| `> max` | 确认禁用 + 显示 `p029` |

### 🔴 R4 · Esc 的归属

`warehouse_panel._unhandled_input` 在 visible 时监听 `pause` 关面板。弹框的 `_input` 里处理 `pause` 并 `set_input_as_handled()` —— `_input` 早于 `_unhandled_input`，所以 Esc 只关弹框。**这条要有测试**，否则很容易在后续重构里退化成「Esc 一下全关了」。

### 🔴 R5 · 移除 Shift 后 `_on_exchange` 的语义变了

函数名从「执行兑换」变成「打开弹框」。**按 08 坑 86 的口径：改函数语义前全局搜同类调用**，确认没有别处直接调 `_on_exchange`。改完跑 `--all`（默认集之外是无人区）。

>   那次注入抓到的是"无效防御"而不是"断言有牙"。改成删 `grab_focus`：那才真的会让玩家

## 9. 不做什么

| 不做 | 理由 |
|---|---|
| 千分位格式化（`100,000,000` → `1亿` 之类） | 全库金币显示都是裸 `%d`（`金币：%d`）。单点引入会与「金币上限 999,999,999」等处的显示不一致，属于**独立的数字格式化工程**。本文的预览行跟随全库惯例用裸数字 |
| 记住上次输入的数量 | 需要新存档键 ⇒ 触「加存档键 = 存量档判损坏」（坑 60）。收益不抵风险 |
| 弹框内做「+10 / −10」步进 | 「最大」按钮 + 直接输入已覆盖真实场景。步进按钮是给「不想打字」的人，但打两位数字比点 10 次按钮快 |
| 把 `"warehouse"` 加入 `WORLD_INPUT_BLOCKING_PANEL_IDS` | 仓库面板打开时挂机应继续跑（玩家看着仓库整理装备，背后还在打怪）。用 LineEdit 焦点做局部屏蔽即可 |

## 10. 落地记录与实测（2026-10-30，已完成）

### 10.1 与方案的三处偏离

| # | 方案写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 1 | `close()` 里 `_edit.release_focus()`，并称之为「两层保险的第二层」 | **不写**，只在 `popup()` 里 `grab_focus()` | 实测 Godot 在控件隐藏时自动释放焦点，那行删了行为完全一致 ⇒ 是无效防御。详见 §10.2 |
| 2 | 错误提示单独一行 `_hint` | **合进第一行 `_cost_label`**，非法输入时改显原因并转 `DANGER` 色 | 独立一行在「显示/隐藏」之间切换会让弹框整体高度变化，玩家一输超限值整个框和底部按钮就跳一下 |
| 3 | 负向 N-2 / N-5 的注入形态 | 两条都换掉了 | 原形态实测**都不会红**，见 §7.3 的说明 |

### 10.2 「关闭时要不要释放焦点」——被负向逼出来的结论

方案出于习惯写了 `close()` → `_edit.release_focus()`，并把它描述成"不能省的第二层保险"。
负向 N-2 按这个写的第一版注入是**删掉那一行**，结果：

```
N-2 删掉 close() 的焦点释放 → ❌ 仍绿（断言无效）
```

不是断言写错，是**这行代码什么都不做**：Godot 的 `Control` 在
`NOTIFICATION_VISIBILITY_CHANGED` 里已经把 `visible = false` 的控件焦点释放掉了。
`world_controls_blocked()` 里那句 `focus.is_visible_in_tree()` 本来就是为这个场景兜底的。

处理方式：**删掉 `close()` 里的 `release_focus()`**，并把负向改成「删 `popup()` 的 `grab_focus()`」——
那才是真正有后果的一行（删了玩家敲的数字会全变成快捷栏操作）。

> 这也是「无效防御」的判定标准：**如果删掉它没有任何测试能红，又不产生任何行为差异，
> 那它不是保险，是一句会让后人不敢删的谎。**

### 10.3 实施中抓到的一个真 bug

弹框首次跑 `--quit` 时冒出：

```
WARNING: 3 RIDs of type "CanvasItem" were leaked.
WARNING: 69 ObjectDB instances were leaked at exit
ERROR: 2 resources still in use at exit
```

取改前基线（`git stash -u` 后复跑）确认是**本次改动引入**的。根因：

```gdscript
_cost_label = _make_preview_line(PanelChrome.MUTED)   # 建了
_got_label = _make_preview_line(PanelChrome.GOLD_LIGHT)
_hint = _make_preview_line(PanelChrome.DANGER)
content.add_child(_make_actions())                    # 只把 actions 加进去了
```

**用工厂函数 `_make_xxx()` 建控件时，"创建"和"add_child"分成了两行，漏了后者。**
表现极其隐蔽：不报错、不崩溃、日志干净，只是三行预览永远不显示；唯一的痕迹是进程退出时的
RID / ObjectDB 泄漏告警。三步定位：① `--quit` 输出里的 leak 告警；② `git stash -u` 取基线
确认是新增；③ 逐个对账 `new()` 与 `add_child()`。

> 04 教训：**「泄漏告警」是这类 bug 唯一的自动化痕迹**，所以 `--quit` 那一层不能只看
> 「配置校验通过 ✅」，还要看它下面有没有 WARNING / ERROR。
