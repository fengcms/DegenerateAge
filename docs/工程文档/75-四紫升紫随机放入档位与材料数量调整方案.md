## 零、一句话结论

你说的两件事，一件是**改策略**（随机放入应吃最低档），一件是**改规则**（材料 2—4 件可变 + 成功率阶梯）。

- **随机放入**：现状是所有「够 4 件」的档**等概率抽一个**，注释写明是故意的（"避免容量大的档独占选择机会"）。这与你「从最低级紫色开始合成」的本意**正好相反**，改起来很小，但会把这条注释一起推翻 —— 需要你确认这个策略反转。
- **材料数量**：现在是**硬编码 4 件、7 处**。放开到 2—4 件技术上不难，真正的岔路口是 **「失败时材料怎么处理」** —— 这个你没说，但它决定了整个功能的性质（§3）。我推荐**失败全损**，并且可以证明它**不会让玩家更亏**：3 件 75% 与 2 件 50% 的**期望消耗都精确等于 4 件**。

## 一、现状核对（代码事实，不是印象）

### 1.1 随机放入：等概率抽档，不是最低档

`scripts/systems/equipment_fusion.gd:85-119` 的 `random_materials()` 分三步：

1. 遍历背包，筛出「装备 + 未收藏 + **0 星** + 品质匹配 + 有效档 + 有效部位 + （升紫）档+10 不超上限」的候选，按 `tier_start()` 分桶（:90-105）；
2. **只保留桶内 ≥ 4 件的档**（`if (groups[tier] as Array).size() >= 4`，:108）；
3. 对这些档**等概率抽一个**（`randi_range(0, tiers.size() - 1)`，:113），再在该档内无放回抽 4 件（:115-118）。

函数上方注释（:83-84）原话：

> 先等概率抽合格档，再在该档无放回抽四件，**避免容量大的档独占选择机会**。

**所以：不是最低档优先。** 背包里 51 档堆 40 件、71 档留着 5 件，随机放入有 50% 概率去吃你那 5 件 71 档。

### 1.2 「必须 4 件」的 7 处硬编码

| # | 位置 | 代码 | 作用 |
|---|---|---|---|
| 1 | `equipment_fusion.gd:46` | `items.size() != 4` | 规则层直接拒绝 |
| 2 | `equipment_fusion.gd:108` | `size() >= 4` | 随机放入的档位门槛 |
| 3 | `game_state.gd:996` | `needed := 2 if STAR_TRANSFER else 4` | 交易层数量白名单 |
| 4 | `equipment_fusion_panel.gd:291` | `row >= (2 if STAR_TRANSFER else 4)` | 单格合法性 |
| 5 | `equipment_fusion_panel.gd:311` | `for i in range(4)` | 同档检查遍历 |
| 6 | `equipment_fusion_panel.gd:365` | `picked.size() != 4` | 随机按钮判空 |
| 7 | `equipment_fusion_panel.gd:413` | 任一空格即 `return []` | **真正的"必须 4 件"门禁** |

第 7 条是核心：`_material_snapshots()` 只要碰到一个空格就返回空数组，确认按钮永久禁用。**只改规则层不改这里，UI 上依然放不进 2 件。**

### 1.3 现在的「失败」只有一种含义

产品 05 §5.13 写的是「确认时重新核对……**失败不消耗资源**」。这是说**校验失败**（材料变了 / 金币不足 / 背包满 / 产物生成失败）不扣东西。

引入概率失败后，这句话会变成**误导**：掷骰失败是**要扣材料**的。这是对既有产品承诺的语义扩展，必须同步改写文档，否则将来有人按"失败不消耗"去改代码（§4.4、§7 有专门一条防这个）。

### 1.4 升紫不收金币

`plan_four()` 不返回 `cost`，`forge_equipment` 里 `cost = 0`。**升紫的唯一成本是材料本身**。这一点决定了 §3 的验算很干净。

### 1.5 「时限」：不存在

`random_materials()` 是纯函数，调用即返回，没有排队、冷却、次数限制或每日上限。`forge_equipment()` 同理。当前**没有任何时间维度的限制**。

## 三、🔴 需要你先拍板：失败时材料怎么处理

### 3.1 三种可能，只有一种成立

| 做法 | 后果 | 判断 |
|---|---|---|
| A. **失败全损**（4 件 100% / 3 件 75% / 2 件 50%） | 用数量换方差，期望不变 | ✅ **推荐** |
| B. 失败退还部分材料 | 逻辑复杂、玩家算不清，且失去"赌"的手感 | ❌ |
| C. 失败不扣（等价于免费重试） | **2 件也能 100%**，概率形同虚设，直接击穿经济 | ❌ 绝对不可 |

C 是最容易误选的一条：听起来"人性化"，实际是把「2 件换 1 件高档」变成白嫖。必须排除。

### 3.2 全损不是变贵：期望消耗**恒等于 4 件**

升紫不收金币，成本只有材料。设每次尝试投入 `n` 件、成功率 `p`，材料为独立同分布、失败全损：

```
期望尝试次数 = 1 / p        期望材料消耗 = n × (1 / p)
```

| 投入 | 成功率 p | 期望尝试次数 | **期望材料消耗** |
|---|---|---|---|
| 4 件 | 100% | 1.000 | **4.00 件** |
| 3 件 | 75% | 1.333 | **4.00 件** |
| 2 件 | 50% | 2.000 | **4.00 件** |

**三档完全相同。** 这不是巧合 —— `p = n / 4` 时 `n / p ≡ 4`。所以这个设计**在经济上是完全中性的**，它卖的不是"更便宜"，是"更高方差 + 更快出手"。

### 3.3 方差才是玩家能感知到的差别

消耗件数服从「`n` × 几何分布」，标准差 `SD = n × √((1−p) / p²)`：

| 投入 | 期望消耗 | 标准差 | 中位数 | 90 分位（最倒霉 10% 要烧多少） |
|---|---|---|---|---|
| 4 件 | 4.00 | **0.00** | 4 | 4 |
| 3 件 | 4.00 | **2.00** | 3 | **5.5 件** |
| 2 件 | 4.00 | **2.83** | 2 | **6.6 件** |

一次成功率 / 累计成功率：

| 投入 | 1 次 | 2 次 | 3 次 | 4 次 |
|---|---|---|---|---|
| 3 件 75% | 75% | 93.75% | 98.44% | — |
| 2 件 50% | 50% | 75% | 87.5% | 93.75% |

**结论：**
- 4 件档必须保留，它是方差锚 —— 不想赌的玩家永远有 100% 的路。
- 2 件档有 10% 的人会烧 6.6 件才成一次，这股体感必须靠**明确的成功率预告**来对冲，不能藏在暗处（§4.3 UI）。

## 四、方案设计

### 4.1 随机放入：改「最低档优先」

**推荐 R1 —— 严格最低档：**

```
按档升序遍历，取第一个「件数 ≥ 2」的档
  → 填 min(4, 该档件数) 格
  → 1 件的档跳过（凑不成一次合成）
```

优点：完全贴合你的本意；低档料永远先被当肥料，高档紫装（准备穿 / 准备保星的）**不会被随机按钮误吃**。

副作用（必须知道）：如果背包最低档只剩 2—3 件，随机按钮就会给出一个 50% / 75% 的赌局。**这个副作用可接受**，因为预览会显示成功率，玩家看见 50% 可以选择不点、手动从别处拿料。

**备选 R2 —— 可满优先：** 先找「件数 ≥ 4 的最低档」填满；全都不满 4 件时才退到「件数 ≥ 2 的最低档」。
优点：随机按钮永不主动把玩家推进赌局。缺点：51 档 3 件 + 61 档 10 件时，会跳过 51 档去吃 61 档的 4 件，与"从最低级开始"的字面意思有偏差，容易让人困惑。

**我的建议：R1。** 理由：随机放入的定位是"帮我清垃圾"，清垃圾就该从最烂的开始；赌局由玩家手动决定。

> 同一个改动会**顺带修掉四金与四紫定向的一个体验问题**：`random_materials()` 被三个模式共用，而四金的产物档 = 材料最低档，随机抽到高档史诗就等于"用高档料产低档货"。统一改成最低档优先对三个模式都更合理。
> 若你只想改升紫，可以加模式分支，但那会让"同样一个按钮、三种行为"，我不推荐。

**注释要一起改**：`equipment_fusion.gd:83-84` 那句"避免容量大的档独占选择机会"是旧策略的辩护词，改完必须重写，否则下一个人会照着它改回去。

### 4.2 材料数量：2—4 件

| 位置 | 改法 |
|---|---|
| `plan_four()` | `items.size() < 2 or items.size() > 4` 才拒；函数名保留（改名要动 7 处调用含测试，收益不值），注释写明 2—4 件 |
| `random_materials()` | 档位门槛 `>= 4` 改 `>= 2`，抽出件数 `min(4, 该档件数)` |
| `forge_equipment()` | `needed` 从定值改为范围：`STAR_TRANSFER` 恒 2，其余 `2..4` |
| `_material_snapshots()` | 收集非空件；**空数组才算"材料不足"**；返回 2—4 件 |
| `_material_error()` | row 范围不变（仍是 4 格）；同档遍历改 `range(_selected.size())` |
| `_on_random_fill()` | `picked.size() < 2` 才判空 |
| `_on_confirm()` | `items.size() < 4` 时**强制走一次 `_risk_confirmed`**（复用现有机制），文案说明成功率与失败全损 |

**同档约束保持不变**：2 件也必须同档。否则「2 件低档 + 高档」会按最低档出产物，等于坑玩家。

### 4.3 成功率阶梯

新增纯函数（放规则层，可单测、不碰 RNG）：

```gdscript
## 投入件数决定成功率：4 件必成，3 件 75%，2 件 50%。
## 期望材料消耗恒为 4 件（n / (n/4)），这是设计约束，不是巧合。
static func success_rate(count: int) -> float:
    return clampf(float(count) / 4.0, 0.0, 1.0)
```

**UI 预告（必须做，不可省）：**
- 预览 `_summary` 追加一行：`成功率 100%` / `成功率 75%`（橙）/ `成功率 50%`（红）
- `< 100%` 时追加一行红字：`失败将消耗全部材料，产物不会生成。`
- 确认按钮文案在 `< 100%` 时保持现有 `_risk_confirmed` 二次确认流程（第一次点击只出警告）

### 4.4 结算顺序（最容易写错的地方）

引入概率后，`forge_equipment()` 的返回语义要分成两类：

- `ok:false` + **无 `lost` 字段** → 校验失败，**一件不扣**（材料变了 / 金币不足 / 背包满 / 产物生成失败）
- `ok:false` + `lost:true` + `consumed:n` → 掷骰失败，**材料已扣，无产物**
- `ok:true` → 材料已扣，产物已入包

**必须的步骤顺序：**

```
1. 快照重核 + 材料校验（同档 / 品质 / 星级 / 收藏 / 升紫只用背包件）
2. plan_four → 得到 output_tier
3. 金币判定（升紫恒 0，不影响，但保星/其他模式共用此函数，不能跳）
4. ★ 掷骰（rng.randf() < success_rate(n)）
   ├─ 失败 → 扣材料 → 广播 → return {ok:false, lost:true, consumed:n, reason:...}
   └─ 成功 → 继续
5. 选部位 → make_output → _valid_item
6. 背包落点判定
7. 扣材料 + 产物入包 + add_gold(-cost)
```

🔴 **第 4 步必须在第 5、6 步之前**。理由：如果先造产物再掷骰，失败时产物已生成却被丢弃，`make_output()` 白白吃掉一段 RNG 序列，且"失败却生成过产物"这个中间态会在日志与测试里制造歧义。
🔴 **第 5、6 步的失败仍然一件不扣**。这是 1.3 那条既有承诺的唯一残存地盘，不能因为引入了概率就顺手扩大到"反正都要扣"。

### 4.5 开放范围：只升紫，还是三种全开

从 §3.2 可知，**三种全开也不会破坏经济**（期望恒定）。所以这是**产品口味**问题，不是数值红线：

| 模式 | 允许 2/3 件？ | 理由 |
|---|---|---|
| 四金（epic→legendary） | ❌ 建议保持 4 件 | 品质跃迁；金装本身是过渡装备，赌输 2 件金装体感极差 |
| 四紫定向（指定部位） | ❌ 建议保持 4 件 | **指定部位是额外价值**，打折会让"补缺槽位"变成连烧 8 件的赌局 |
| 四紫升紫（随机部位） | ✅ 开放 | 产物部位随机、纯档位推进，三种里最"垃圾回收"，最适合做实验场 |

**我的建议：只开升紫。** 若你想三种全开，规则层加个 `mode` 分支即可，但我不会硬拦 —— 代价只是四金/定向的体感变赌。

**本期不做（可选后续）：** 连续失败保底（N 次必成）。它需要跨会话计数 → 要落档 → 违反"派生值不落档"的简洁性，且会破坏 §3.2 的期望恒等式。不建议。
