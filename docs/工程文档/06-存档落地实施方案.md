## 2. 存档 Schema（本次落定）

```jsonc
{
  "schemaVersion": 1,
  "slotId": 1,
  "savedAt": "2026-10-12T00:34:38",       // 系统时间字符串，展示时把 T 换成空格
  "player":      { "name", "level", "xp", "hp", "mp", "attack", "defense",
                   "criticalChance", "criticalMultiplier", "attackInterval",
                   "movementSpeed", "dodge", "block", "cdr" },
  "gold":        1280,
  "currentMap":  "camp",                   // 10.3「当前地图与坐标」
  "playerPos":   [400.0, -400.0],          // 世界像素坐标，数组形式（JSON 无 Vector2）
  "inventory":   [ null, { …实例… }, … ],  // 定长 40（5.8）
  "equipment":   { "weapon": { …实例… }, "ring_1": null, … },   // 14 槽（5.1）
  "questStates": { "Q001": "done" },        // M2 起有内容
  "firstClear":  { "boss_corrupt_beast": true },                // M3 起有内容
  "settings":    { "autoBattleDefault", "autoPickupDefault", "potionThreshold",
                   "searchRadius", "allowBoss", "masterVolume", "sfxVolume", "uiScale" }
}
```

**不入档**：运行态自动战斗 / 自动拾取开关（`auto_battle_on` / `auto_pickup_on`）。10.3 明确"重启后自动战斗默认关闭"，
存档中的 `settings.autoBattleDefault` 是**设置面板里的默认值**，与 F / G 打开的运行态开关是两件事（见产品文档 10.3 补充说明）。

槽位与旁文件：

```
user://saves/
  slot_1.json          主档（原子写入的最终产物）
  slot_1.json.bak      最近一份**有效**备份
  slot_1.json.tmp      写入中的临时文件（正常情况不残留）
  slot_1.json.corrupt  损坏现场（仅在触发过备份恢复后出现）
  last_slot.json       {"slot": N} —— 上次使用的槽，供启动续档（10.3「继续」）
```

## 3. 保存策略（何时写盘）

| 触发 | 实现 | 说明 |
|---|---|---|
| 手动存 | 存档面板「保存」 | 弹「已保存到槽 N」提示；该槽成为**活动槽** |
| 关键事件 | 升级 / 穿戴变更 / 交易完成 / 切图 / 任务完成 → `request_autosave()` | **0.6s 去抖**合并连续变更，避免频繁写盘 |
| 定时 | 每 **120 秒**（10.3） | 静默保存，成功不打扰 |
| 退出 | `NOTIFICATION_WM_CLOSE_REQUEST` → `save_on_quit()` | 同步写盘后再退出 |

**活动槽（`active_slot`）规则**：默认 `-1`（新游戏未开档）→ **不做任何自动写盘**，避免新游戏覆盖玩家旧档；
玩家手动保存 / 读取某槽后该槽成为活动槽，此后所有自动保存都写它。启动时读 `last_slot.json` **自动续档**，
因此「存 → 退 → 进」自然一致，无需手动读档。

自动保存只在**失败时**弹提示（成功静默），避免每 120 秒刷一条 toast。

## 4. 损坏恢复（T16）

```
read_slot(slot)
  ├─ 主档不存在                 → {ok:false, "槽 N 还没有存档"}
  ├─ 主档解析成功且含 player    → {ok:true, source:"main"}
  └─ 主档不可用（坏 JSON / 缺 player 字段）
       ├─ 备份可用              → 坏档改名 .corrupt（保留现场）+ 备份内容写回主档（自愈）
       │                          → {ok:true, source:"backup", message:"…已从备份恢复"}
       └─ 备份也不可用          → {ok:false, message:"…损坏且备份不可用（现场文件已保留）"}
```

两个关键加固：

1. **只有"有效主档"才被备份覆盖**（`save_slot` 中 `_is_valid_save` 前置判断）。
   否则第二次保存会用一个损坏的主档把可用的 `.bak` 覆盖掉，T16 就再也救不回来。
2. **恢复即自愈**：备份内容写回主档，下一次保存照常建立新备份；坏档不删除而是改名 `.corrupt`，便于复盘。

## 5. 读档与场景重载

```
存档面板「读取」→ SaveManager.load_into_game(slot)
                    ├─ read_slot（含 T16 回退）
                    ├─ apply_to_game_state（写入 GameState，含 active_slot / last_slot）
                    └─ GameState.emit_all()（HUD 刷新）
                  → 关闭面板 → get_tree().reload_current_scene()
                  → Game._ready 读 GameState.save_pos → 出生在存档坐标（clamp 到地图内）→ 消费一次即清空
```

- **为什么要重载场景**：读档必须清掉旧怪物 / 地面掉落 / 未结算的出售托盘 / 面板状态。
  M1 用"重载当前场景"这一最简实现达成（10.5「读档清旧实体」）；M3 引入多图后改为地图级加载（T15 正式覆盖）。
- **坐标容错**：`IsoGround.clamp_to_map()` 把越界 / 坏档坐标夹回地图可用范围，避免把玩家扔到边界墙外。
- **HP / MP 收敛**：读档后按当前总属性重算上限，超出则收敛到上限（不补满、不按比例），
  与 `_after_equip_change` 口径一致。

## 7. 关键决策与取舍

| 决策 | 原因 |
|---|---|
| 坐标存成 `[x, y]` 数组 | JSON 无 Vector2；数组比 `{x,y}` 更省字节且解构简单 |
| 读档后**重载场景**而非增量同步 | 读档是低频操作；重载天然清干净旧实体与面板态，避免"漏清一处"的隐性 bug |
| 自动存**不弹成功提示** | 120 秒级频率，弹提示会刷屏；失败必提示（10.3 不静默） |
| 新游戏（`active_slot = -1`）不自动写盘 | 防止玩家"随便玩玩就退出"覆盖已选槽的旧档 |
| `.bak` 只由**有效**主档覆盖 | 否则损坏档会把备份一起带走，T16 失效 |
| `_deep_int` 统一把整数值 float 回落 int | Godot JSON 解析所有数字为 float；不回落则读档后 1 变 1.0，属性比较 / 显示会漂移 |

**两个实测踩坑（记入备查）**：

1. **JSON 往返会改变字典的键顺序**（解析后按键排序）。因此断言"实例属性一致"必须做**键集 + 逐键深比较**，
   不能用 `str(dict)` 比较——否则数据全对却报失败（本次即由此发现并补上 `_deep_equal`）。
2. 项目开启了**警告视为错误**：`var x := <Variant 推断>` 会直接编译失败，读取 `Variant` 的辅助函数（如 `_read_file`）
   返回值必须显式标注 `: Variant`。
