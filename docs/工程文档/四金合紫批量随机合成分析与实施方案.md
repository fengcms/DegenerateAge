# 四金合紫批量随机合成分析与实施方案

日期：2026-10-31。状态：方案，尚未修改运行代码。

## 1. 目标与现状

四金合紫页新增「批量合成」按钮，将背包中符合条件的金装一次批量合成为随机部位紫装，减少反复选料与点击。

已静态核对：EquipmentFusion.plan_four允许epic（金装）0—12星、排除收藏，四件可不同档，输出取最低十级档；make_output生成该档随机部位legendary、0星基础四词条。GameState.forge_equipment会重核实例快照并在校验后消耗材料。当前单次随机选料入口按最低合格档取四件，不能直接反复调用它代表全背包批量策略。

仓库与已穿戴物品不应参与批量，只处理背包。现有手动四金合紫维持原行为；无金币费用、无概率失败、不投如意。产物不自动穿戴，也不继续作为下一轮材料。本分析基于源码，没有运行游戏或性能测试。

## 2. 推荐选料规则

- 只读取有效背包装备实例，品质epic、未收藏、instanceId唯一且材料规则合法。
- 默认只取0星。批量确认面板提供「包含带星金装」复选框，默认关闭且每次打开重置；勾选后纳入所有合法0—12星金装，明确列出将消失的星级与件数。
- 不额外套用“评分比身上低”之类隐藏筛选，否则无法解释哪些装备为何没被合成。想保留的未穿金装应收藏；确认页允许查看和排除具体材料。
- 勾选/排除后重算整份计划。所有符合当前选择规则的装备，按四件一组合成到不足四件；剩余0—3件留在背包。

“全部”指本次确认计划内的合格池；不是无条件烧掉收藏或身上装备。默认保护带星属于推荐取舍，用户也可以要求批量默认包含带星；实施前应冻结这个口径。

## 3. 分组：同档优先，再跨档凑余数

每组产物按最低档生成，所以“随机”应落在产物部位与词条上，不应随机选择材料档位。

1. 按十级档分桶，每档优先组成尽可能多的四件组。
2. 收集各档剩余0—3件，按档位从低到高排序，再每四件组成跨档组。
3. 同档内按实例ID稳定排序，保证预览与确认一致；玩家看到确认计划后，不因重新刷新而换料。
4. 总合成次数=floor(本次合格件数/4)，消耗=次数×4，保留=件数%4。

例：51档1件、61档7件→先用4件61档产1件61档紫装，再用1件51档＋3件61档产1件51档紫装。禁止把低档材料拆散混入多个高档组。

例：51档3件、61档3件→跨档合成1组，产51档紫装，余下2件61档保留。

确认页必须高亮「跨档组数、因混合而降档的高档材料件数、各输出档数量」。跨档不可逆；若玩家不想降档，可排除低档材料后重算。首版不建议增加第二套隐含分组模式，减少按钮语义歧义。

## 4. 操作流程

仅在四金合紫页显示「批量合成」，与现有操作按钮使用PanelChrome样式，不挤占四个材料格。点击打开独立批量确认层，不立即消耗。

确认层显示：候选数量、预计消耗/保留、产物数量和按等级档分布；未参与的收藏/带星数量；跨档降档告警；带星开关；按组折叠的材料详情与排除操作。底部「取消」「确认批量合成 N 次」。没有可合组时禁用并解释原因。

批量计划独立于当前四个手动预选格，不从预选格偷偷追加或排除。打开时保留手动预选，取消不改变它；成功后沿用物品变化重新核对预选，只清除真正被消耗的实例。只有一个批量会话，可见时禁止重复打开。

确认后一次提交，成功显示「合成N次，消耗4N件金装，获得N件紫装，剩余R件」，产物在背包高亮即可，不逐件刷toast。保留单次合成入口。

## 5. 后台战斗与快照边界

随身工作台可能边战斗边拾取、出售、整理。计划必须固定一组instanceId与内容快照：

- 新拾取金装不自动加入已经确认的计划，避免确认后扩大消耗；提示「新物品下次批量处理」。
- 背包整理只改下标，按ID重新定位，不导致计划失败。
- 已选装备被收藏、穿戴、移仓、出售、升星或改词条，则计划失效，要求刷新并再次确认；不能悄悄换入另一件材料。
- 勾选或排除材料使原确认失效，重建计划；金币变化不影响免费合成。
- 提交无await，按钮立即防重复；成功后旧会话失效，重复提交不得再发奖。会话不落存档。

不要通过while循环不停扫描实时背包，自动吃掉战斗中新捡到的金装。这会使操作没有明确终点，也可能持续吞掉玩家尚未看过的物品。

## 6. 工程分工与原子结算

推荐给EquipmentFusion增加纯批量分组计划，复用plan_four校验每组；产物生成复用make_output和既有随机部位选择。单次与批量共用组级产物生成函数，避免两套掉落/词条规则；旧单次路径的随机序列要保持不变。

GameState新增唯一批量提交门面：校验会话、重定位全部ID、核对仍在背包和完整材料快照、验证全部组，之后在仓库之外的背包副本执行“移除全部输入→生成并验证全部输出→放入全部输出”。全部成功才一次替换真实背包，发一次inventory_changed和批量摘要。任务/自动存档等观察者统一接收提交后状态，必要统计提供聚合次数事件，不逐组重建UI。

不要循环调用现有forge_equipment：它每组都直接写真实背包并发信号，会造成中途失败的半批完成态、重复刷新和大量通知。

正常情况下每组四件不可堆叠装备换一件，会释放三个格，满背包也可合成。仍在副本中检查最终落点：模板缺失、产物校验或入包失败时整批不提交，材料不消失，产物不丢地、不进入未领取战利品。所有输出都是新实例，不能重复ID，不继承星级、收藏或第五词条解锁标记。

生成发生在确认校验之后，不在每次预览时抽词条。预览只承诺档位/件数，随机部位与词条以成功结果为准。失败副本不写存档；若需要失败重试复现随机，应使用批量会话独立RNG并固定种子，不能在预览中消耗战斗全局随机流。读档不会恢复未执行会话。

## 7. 成本和性能

当前背包最多400格，最多100组合成、100件产物。只在打开、明确改选和确认时扫描/分组，复杂度O(NlogN)，提交一次O(N)副本，候选和会话在关闭/成功后释放。没有逐帧扫描、世界物体或常驻计时器。

100次生成可能产生首个同步尖峰，实施时测量满400件、首次/热运行的CPU耗时和P50/P95/P99/峰值。若超过本机整帧预算，再考虑按帧准备候选并在最终重新校验后一次提交；不能分帧直接扣真实材料。先量再决定，不预先引入线程。验证目标仍为流畅60FPS，headless计时不能证明GPU帧率。

## 8. 实施节点与验收

1. 分组规则节点：0/3/4/5/7/8件、同档、混档、跨档余数、重复ID、收藏与带星过滤、排除后重算；固定输入分组稳定。单独commit。
2. 提交节点：满400件产100件、产物合法且唯一、全部0星4词条、失败背包不变、重复会话不发奖、整理重定位、拾取不扩大计划、移仓/穿戴/收藏导致重新确认；JSON保存读取一致。单独commit。
3. UI节点：只在四金页显示、批量详情和降档告警、带星开关默认关闭、取消保留手动格、成功聚合提示、窄窗口/大字号滚动及键鼠操作。单独commit。
4. 综合验收节点：原四金/四紫/保星、第五词条和耐久预选回归；满包实测与CPU采样；同步产品和交接文档。单独commit。

不调整单位材料比例、品质概率、价格、精炼或如意规则。所有测试隔离存档；共享测试扩展覆盖，不靠放宽既有断言通过。

## 9. 建议实施基线

推荐采用“默认0星、可明确包含带星；同档先组、跨档余数凑齐；预览后一次确认；点击时冻结材料范围、期间新拾取不加入；整批原子提交”。这个组合能覆盖全部可分组金装，同时让玩家看清会消耗哪些强化装备以及哪些材料会降档。
