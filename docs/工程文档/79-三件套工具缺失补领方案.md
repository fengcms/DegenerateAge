> 状态：**已落地**（Q1 读档自愈 / Q2 背包满走仓库 / Q3 修造档工具，均按建议采纳）｜2026-10-20
> 背景：slot_3 缺 60 级任务「轻装远行」（C6S07）发放的三件工具物品。该存档由

## 2. 根因（三层）

### 2.1 造档工具只置状态、不发物品
`tools/complete_all_quests.gd` 的边界声明是「只改任务与解锁相关字段，**不动等级 / 装备 / 金币 / 背包**」。
它把全部任务一键置 `rewarded` + 解锁键全开，但 `reward.items` **一件都没真正入包**。
凡是靠它造的档，C6S07 的三件工具必然缺失——这是设计边界，不是写坏。

### 2.2 正常游戏里三件工具**不可丢**
- 死亡惩罚只掉 `kind == "equip"`（`death_penalty.gd`），不碰 misc；
- 商店拒收 `questItem: true`（`shop.gd` 三重过滤之一）；
- 无「丢弃道具」操作（`remove_item_at` 的调用方只有消耗 / 出售 / 穿戴 / 死亡）。

⇒ **只要正常领过，就永远丢不了**。缺失 = 要么造档、要么旧档导入异常，属「发放链路断了」而非「物品消耗了」。

### 2.3 面板入口**只认物品、不认解锁键**
`PanelRouter.open()` 的唯一调用方是 `GameState._use_misc()`——即背包双击 `useType: "panel"` 道具。
`unlocks.tool_*` 三键**全库无人消费**（grep 零读取，只有 `quests.json` 写入）。
⇒ 解锁键形同虚设，背包没物品 = 三个面板永久锁死。

### 2.4 任务链不可逆
C6S07 状态 `rewarded` 后：`accept` 拒（「任务已完成」）、`deliver` 拒（要求 `completed`）。
前置 `prev: C6Q12` 也早已 rewarded，无法从上游重推。⇒ **「再领一次」在现规则下无路可走**。

## 3. 三个思路逐条分析

### 思路 1：直接在背包中增加（一次性修档）

**实现**：写小工具脚本（仿 `complete_all_quests.gd`）：读 slot_3 → `ItemFactory.make_any(id, 1)` ×3
→ 塞进背包空位 → `SaveManager.import_to_slot`（同套 `_is_valid_save` → 备份 → 原子写）。
不可手改 JSON（绕过 `_valid_item` 校验，下次读档可能整档判毁）。

| 优 | 劣 |
|---|---|
| 最快，10 分钟闭环；不动任何游戏代码 | 只救 slot_3 一个档（备份档、未来造档照样缺） |
| 零回归风险（不碰运行时逻辑） | 等于承认「造档工具的坑每次手工填」 |
| | 与 Q3 的机制诉求（防复发）无关 |

### 思路 2：复原领取任务，到 NPC 重新领

**实现**：把 `questStates.C6S07` 从 `rewarded` 改回 `available`（或直接删记录，由 `prev` 链推导），
玩家到 `c6_map00` 找 `c6_npc01` 接取（talk 类 + `talkOnAccept` → 接取即 completed）→ 交付领三件。

| 优 | 劣 |
|---|---|
| 走真实发放链路（`deliver` → `_reward_plan` → `add_item`），零新代码 | **仍是一次性修档**，下次造档复发 |
| 顺带补金币/经验/解锁（本任务 gold=0 xp=0，无重复收益） | 要跑一趟 c6_map00 找 NPC，操作成本高 |
| 可作为思路 3 的「降级手动版」 | 改任务状态仍是手改存档，得走 import 工具 |

⚠ 若选此路，**必须只改 C6S07 一条**，不能动其它 `rewarded` 记录——`unlocks` 白名单与 `firstClear`
联动校验会把大面积状态回退判成脏档。

### 思路 3：机制上解决——缺失就可补领（防复发）

**实现**：新增「工具补领」判据 + 两个可选触发点（见 Q1）。
判据（唯一，纯函数，测试与 UI 共用）：

```
missing_tools() -> Array[String]
  = 对每个 useType=="panel" 的 miscItem：
      若 GameState.unlocks.get(id) == true            # 任务链说「发过」
      且 背包与仓库都找不到该 itemId                    # 但物品真不在
      ⇒ 列为缺失
```

| 优 | 劣 |
|---|---|
| **根治**：造档、旧档、未来任何断发场景全部自愈 | 要写代码 + 测试 + 负向，工作量最大 |
| 三件套是「永久工具」语义，补领无重复收益漏洞 | 判据必须精确（见 🔴 风险），误伤面在存档层 |
| 与思路 2 不冲突：机制落地后 slot_3 直接被机制覆盖 | |

## 4. 推荐组合

**思路 3 为主 + 思路 1 作过渡（可选）**：

- **R1**：`missing_tools()` 判据 + 补领入口（Q1 拍板触发点）—— 根治，覆盖 slot_3 / 两份备份档 / 未来造档；
- **R2**（仅当想立即上手 slot_3 而机制还没好）：一次性注入工具，机制落地后可删；
- 思路 2 不单独推荐——它和思路 1 同是一次性修档，且要跑图，**被思路 3 完全覆盖**。

**为什么思路 3 安全**（对照 §2.2）：三件工具不可卖、不可丢、不可消耗（`panel` 类不消耗），
正常玩家**永远不会触发补领**；只有「发放链路断了」的档才会命中——补的正是该有的，无刷道具面。

## 5. Q1—Q3 待拍板

**Q1 补领入口（触发点）**：
- **(a) 读档自愈**：`load_into_game` 末尾检测缺失 → 自动入包 + toast 提示。玩家零操作，最省事；
- **(b) NPC 处补领**：`c6_npc01` 对话里出「补领随身工具」按钮（仅缺失时显示），玩家主动领；
- **(c) a + b 都要**：自愈为主、NPC 按钮兜底（背包满导致自愈失败时走 NPC）。
→ **建议 (a)**。三件套是常驻工具，丢了就该回来，不需要仪式感；(b) 的交互价值低、还要出新文案。

**Q2 自愈失败的兜底（背包 170 格全满时 `add_item` 返 false）**：
- **(a) 放仓库**（仓库 40 格，先仓库后背包）；
- **(b) 只 toast 提示「背包已满，工具未能补发」**，等玩家清包再进档。
→ **建议 (a)**。工具是要双击用的，进仓库玩家自己会拿；(b) 等于把问题再还给玩家。

**Q3 是否顺手修造档工具 `complete_all_quests.gd`（根因 §2.1）**：
- **(a) 修**：造档时顺带把 `reward.items` 真发进背包（新档不缺件）；
- **(b) 不修**：机制上线后造档缺件会被自愈兜住，工具保持「只写状态」的纯粹边界。
→ **建议 (a)**。造出来的档应当自洽，不该靠事后补；两行改动（循环里 `make_any` + 塞背包）。

### 🔴 三条实现红线（后人改这里前必读）

1. **补领必须留在 `_suppress_autosave = false` 之前** —— 补发会广播 `inventory_changed`，
   放在抑制期内可避免「读档过程中额外落一次盘」。补发结果随下一次自然保存固化；
   即便没固化，下次读档仍会补（判据幂等）。
2. **判据不能脱离「不可消耗」这个前提** —— 三件工具现在丢不掉（死亡只掉装备、商店拒收
   `questItem`、无丢弃操作、`panel` 类双击不消耗），所以「解锁键说发过、物品却不在」只可能是
   **发放链路断了**。若将来它们变成可消耗 / 可交易 / 可丢弃，本判据立刻变成无限刷，
   届时必须先收紧判据（例如一次性标记字段），不能只加冷却。
3. **`unlocks` 条件是唯一的误伤闸门** —— 少了它，每个新档开局白送三件工具，
   把任务奖励变成赠品。这条由用例 4 与负向 N-1 双重看守。
