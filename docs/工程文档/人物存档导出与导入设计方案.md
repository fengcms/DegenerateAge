# 人物存档导出与导入设计方案

> 状态：**设计待评审（未实施）**。本文只做方案取舍与落地设计，不含实现代码。
> 需求来源：2026-10-17 用户提出——玩家可导出 / 导入人物存档，目的有三：
> ① 保存自己的游戏成果，换电脑可衔接；② 允许懂技术的玩家改档实现"作弊"（改坏自负）。
> 依据实现：产品文档 **10.3**（单机存档与数据可靠性）、**10.5**（退出重进一致 / 损坏恢复）、
> 工程文档 [06-存档落地实施方案.md](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/docs/工程文档/06-存档落地实施方案.md)（现有 schema 与旁文件约定）。

## 0. 结论摘要

推荐方案（**默认实现路径**）：

| 维度 | 结论 |
|---|---|
| 导出格式 | **明文 JSON 单文件**，与内部槽档**同一 schema**（无包装层、不加校验和、不加密） |
| 导出范围 | 仅**当前所选槽**的完整角色档（含 `settings`、含布局/版本字段）；**不含**本机显示偏好文件 |
| 导入落点 | 玩家在**哪张槽卡上点「导入」就写哪张槽**；目标槽已有有效档时先转 `.bak` |
| 跨设备衔接 | 玩家自选任意路径（默认桌面）导出文件 → 自行拷贝到新机器 → 新机器选槽导入 |
| 失败语义 | 校验通过**才**写盘；失败**不改动**目标槽任何字节，并给出字段级原因 |
| 作弊容忍度 | 沿用现有 `_is_valid_save` 校验，**不放松**（改坏不崩是需求的前置承诺） |

**需要用户拍板的 4 个点**见 §9（其中 D1「是否放松校验」与 D4「导入活动槽的处置」影响体验，建议优先确认）。

## 1. 需求拆解与验收判据

### 1.1 从玩家诉求到工程目标

| 玩家诉求 | 工程目标 | 说明 |
|---|---|---|
| 换电脑可衔接 | 单文件、自包含、可读回、跨版本可迁移 | 用文件承载，不放云、不做账号 |
| 保存游戏成果 | 导出物是**完整可玩的角色快照**，不是摘要 | 复用现有 `_collect` / schema，不新造精简格式 |
| 懂技术的玩家可改档 | 明文、结构可读、字段含义可文档化 | JSON 美化输出；不加签名/加密/校验和 |
| 改坏是他自己的事情 | 改坏**不能崩、不能静默毁掉本机原档** | 导入前全量校验 + 原子写入 + 失败不改动 |

### 1.2 验收判据

| 编号 | 判据 | 落地位置（预期） |
|---|---|---|
| A1 | 导出文件可被 `JSON.parse_string` 直接解析，顶层结构与槽档一致 | `SaveManager.export_slot` |
| A2 | 导出 → 导入到另一槽后，等级 / 经验 / 金币 / 背包 / 穿戴 / 任务 / 首杀 / 坐标 **逐字段一致** | `export_slot` + `import_from_file` |
| A3 | 导入非法文件（截断 / 非 JSON / 缺 `schemaVersion` / 结构非法）→ 明确报错，**目标槽字节不变** | `import_from_file` |
| A4 | 导入 `schemaVersion` 低于 11 与高于 `CURRENT_SCHEMA` → **分别给出可读理由**，不落盘 | 导入前置检查 + `_is_valid_save` |
| A5 | 导入覆盖已有有效档时，旧主档**自动留为 `.bak`** | 复用 `save_slot` 的备份策略 |
| A6 | 导入**不改变 `active_slot`**（避免导入内容被随后自动存覆盖） | `import_from_file` |
| A7 | 导出/导入为**一次性 I/O**，不进入 `_process` 热路径；实测单次耗时可忽略 | 设计约束 |
| A8 | 目标路径不可写 / 文件被占用 → 明确提示，不静默失败 | 写入返回码检查 |
| A9 | 新增文案全部走 `Localization.tr_key`，`python3 tools/check_localization.py` 通过 | [check_localization.py](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/tools/check_localization.py) |

**关键发现**：

1. 槽档本身就是**明文 JSON**（[save_manager.gd#L938](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L938) `JSON.stringify(data, "\t")`）。所谓"对玩家是黑盒"，只是**没有出口**，不是格式不可读——**导出几乎零转换成本**。

### 2.3 关键约束（影响方案的三件事）

1. **校验强度决定"作弊幅度"**（[save_manager.gd#L1038-L1063](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L1038-L1063)）：
   导入必然经过 `_is_valid_save`，其中已有多处上界——
   `gold ≤ GOLD_CAP(999,999,999)`（[game_state.gd#L10](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/game_state.gd#L10)）、
   `level ≤ PLAYER_LEVEL_CAP(999)`、`attack/defense/dodge/block ≤ PLAYER_STAT_CAP(999999)`、
   `cdr ≤ 0.5`、`movementSpeed ≤ 100`、背包/仓库长度必须等于扩容容量、装备词条数量与白名单受限。
   **但装备实例的 `rawBaseAttrs` 数值只有"非负"约束、没有上界**（[save_manager.gd#L1193-L1196](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L1193-L1196)）。
   实测口径：**改金币、等级、物品数量、装备基底数值、叠装备词条都改得进去；把 `player.attack` 改成 10^7 会被拒**。
2. **显示偏好与角色档已分离**：`uiScale / mapScale / textScale / displayScaleMode / displayScale / fullscreen / resolution`
   单独存 `user://display_preferences.json`（[settings_runtime.gd#L22-L24](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/settings_runtime.gd#L22-L24)），

   → 导出**不需要**打包显示偏好；跨设备时应保持本机屏幕设置，这正是现状行为。
3. **导入会沿用读档迁移的副作用**：旧档缺 `mapLayoutVersion` 时会触发坐标重映射与营地迷雾重置
   （[save_manager.gd#L401-L410](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L401-L410)）→
   导入老版本导出文件后，玩家可能被搬到营地出生点、迷雾被重置。这是既有读档语义，须在 UI 上提示，不能当作 bug。

## 3. 方案取舍

### 3.1 导出格式

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 明文 JSON，与内部 schema 完全一致** | 复用校验/迁移零成本；玩家看到的就是文档化 schema；diff 可读 | 文件无"防伪"，与内部槽档不可区分 | ✅ 推荐 |
| B. 明文 JSON + 包装头（`{"kind":"...","exportVersion":1,"data":{...}}`） | 可识别来源、可加人类可读头部 | 多一层嵌套；玩家编辑要多剥一层；包装字段一旦改动又需版本治理 | ❌ |
| C. 二进制 / 压缩 / 加密 | 体积小、防改 | 与"允许改档"诉求直接冲突 | ❌ |
| D. 明文 JSON + 校验和签名 | 可提示"文件被改过" | 用户明确接受改档；签名只增加维护成本 | ❌ |
| E. 自定义扩展名 `.dgsave`（内容仍是 JSON） | 文件对话框中不易与其他 JSON 混淆 | 玩家改档前要先改名，多一步；不符合"技术玩家直接编辑" | ⚠️ 备选 |

**推荐 A**：`JSON.stringify(read_slot 迁移后数据, "\t")`，扩名 `.json`，UTF-8。
理由：用户的第 2 条诉求（可改档）与 A 完全对齐；A 同时让"导出文件 → 导入"与"本机槽档 → 读档"走**同一条校验/迁移链**，
避免出现两套校验导致"导出能读、导入不能读"的分裂。

### 3.2 导出范围

| 内容 | 是否包含 | 理由 |
|---|---|---|
| 角色/背包/装备/仓库/任务/首杀/解锁/迷雾/坐骑/快捷栏/世界时钟/刷新状态/未领取战利品 | ✅ | 由 `_collect`（[save_manager.gd#L139-L173](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L139-L173)）整体提供，无可裁剪项 |
| `settings`（音量、喝药阈值、键位、自动战斗默认值…） | ✅ | 换机衔接需要键位与习惯；已在槽档内，无需额外处理 |
| 本机显示偏好（`uiScale/mapScale/textScale/fullscreen/resolution`…） | ❌ | 跨设备屏幕与密度不同，强行套用会得到错误的 UI 缩放；现状读档已按"本机优先"处理（§2.3-2） |
| 运行态开关（`auto_battle_on` / `auto_pickup_on` / 技能与药水冷却） | ❌ | 10.3 明确不入档，导出自然也不含 |
| `slotId` / `savedAt` | ✅ 原样保留 | `slotId` 导入时按目标槽改写；`savedAt` 保留原值（表"这份进度是在何时被采集的"） |

### 3.3 导入落点与覆盖策略

| 方案 | 说明 | 结论 |
|---|---|---|
| **每张槽卡上各有一个「导入」按钮，写本槽** | 与现有"保存/读取/删除"的按槽操作惯例一致；无额外"选目标槽"弹层 | ✅ 推荐 |
| 面板级一个「导入」按钮 + 二级选择目标槽 | 需新增一个 3 选 1 弹层，多一步 | ❌ |
| 导入到上次使用的槽 | 玩家无法预期，易误覆盖 | ❌ |
| 导入即自动读取并进游戏 | 少一步，但会**立刻销毁当前会话进度**，且中途状态切换风险大 | ❌（列为可选增强） |

覆盖策略：**校验通过后才写**；目标槽已有**有效**主档时先复制为 `.bak`（照搬 [save_manager.gd#L209-L214](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L209-L214)）→ 原子写入。
若目标槽存在但内容无效（损坏），则**不覆盖它的 `.corrupt` 现场**，直接写新主档（与 `new_game` 语义一致）。

### 3.4 跨设备衔接方式

| 方案 | 结论 |
|---|---|
| **文件导出（玩家自选路径，默认桌面） → 玩家用 U 盘/网盘/邮件搬运** | ✅ 推荐。唯一不需要任何服务端、账号与网络的功能 |
| Base64 分享码 / 剪贴板 | ❌ 实测 221 KB → Base64 约 295 KB，作为文本分享体验极差 |
| 云同步 / 账号绑定 | ❌ 超出单机范围，涉及服务与合规 |

### 3.5 是否放松校验（作弊幅度）

这是本需求最需要用户拍板的地方：

| 选项 | 后果 |
|---|---|
| **保持现状（推荐）** | 越界值被拒。玩家能改：金币、等级、物品与装备实例、装备基底数值、任务状态、解锁等；不能改：超上界的 `attack/defense/dodge/block`（>999999）、`cdr`（>0.5）、`movementSpeed`（>100）、超长背包、装备词条数量/白名单外词条 |
| 导入时放宽/跳过校验 | 直接违反"改坏不崩"的前置承诺：非法档一旦 `apply_to_game_state` 就会污染运行态、写坏自动存档，且崩溃点难以预判 |

**推荐保持现状**。理由：需求的原话是"改坏了是他自己的事情"，其成立前提是**改坏只影响他自己那份导入文件**；
一旦放松校验，坏档会经自动存写回本机槽位，损害就扩散到"本机存档"这个玩家没打算牺牲的东西上。
现有校验已经拦下最危险的一类（数值越界），而"能改"的空间（金币/等级/装备数值）依然充足。

## 4. 推荐方案（详细）

### 4.1 数据流

```
导出：槽卡「导出」→（若该槽=活动槽且已开档：先静默 save_slot 落盘）
        → 只读读盘取该槽内容（主档有效用主档，否则用有效 .bak；不触发自愈写回）
        → _is_valid_save 通过 → _migrate 归一化到 CURRENT_SCHEMA
        → JSON.stringify(data, "\t") 写到玩家选定路径
        → toast「已导出…」

导入：槽卡「导入」→ FileDialog 选文件 → 读文件 → JSON.parse_string
        → 失败：明确原因，不写盘（原档字节不变）
        → 版本前置检查（<11 拒绝 / >CURRENT_SCHEMA 拒绝并提示升级）
        → _is_valid_save（固有校验，含字段级原因 _last_invalid_reason）
        → _migrate 归一化 → 覆盖 slotId = 目标槽 → name 归一化（截断 16 字，见 §4.5）
        → 原有效主档 → .bak；原子写入主档
        → 刷新槽卡，toast「已导入到槽 N；点『读取』进入该角色」
```

### 4.2 SaveManager 新增 API（设计签名）

```gdscript
## 导出某槽为可移植的明文 JSON 文件。
## 返回 {ok: bool, message: String, path: String}；失败不产生半截文件。
func export_slot(slot: int, path: String) -> Dictionary

## 只读获取待导出内容：主档有效用主档，否则用有效备份（**不**触发 _restore_backup 的自愈写回，
## 导出不应改动本机存档）。两者皆无效 → ok=false + 原因。
func _read_for_export(slot: int) -> Dictionary

## 从外部文件导入到指定槽。校验通过才写入；不改变 active_slot。
## 返回 {ok: bool, message: String, pruned: int}。
func import_from_file(slot: int, path: String) -> Dictionary

## 把已校验的存档数据写入某槽（供 import_from_file 与自动化测试直接调用）。
func import_to_slot(slot: int, data: Dictionary) -> Dictionary

## 导出文件名清洗与生成：清洗非法字符、截断角色名，返回 "…json"。
func export_file_name(data: Dictionary) -> String
```

设计要点：
- `import_to_slot` **不复用 `save_slot`**：`save_slot` 会 `_collect()` 采集**当前运行态**并改写 `active_slot`
  （[save_manager.gd#L183-L234](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L183-L234)），
  两者都正是导入不能要的行为；只复用其"校验 → 备份 → `_write_json_atomic`"的**步骤顺序**。
- 与 `new_game` 的差异：`new_game` 会重置坐标并清空 `.bak/.corrupt`（[save_manager.gd#L220-L225](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L220-L225)），导入**不清**旧 `.corrupt`，保留现场。

## 5. 边界与异常处理

| 场景 | 预期行为 |
|---|---|
| 导出目标目录只读 / 磁盘满 | 写入失败 → toast「导出失败：…」，不留半截文件（先写 `.tmp` 再改名，或失败即删） |
| 导出文件名含角色名非法字符（`/ \ : * ? " < > \|`、控制字符） | 导出前清洗；空名回退 `character` |
| 导出时该槽主档损坏但备份有效 | 导出**备份内容**并提示"（来自备份）"；不改动本机存档 |
| 导入文件不是 JSON / 被截断 | 「存档文件无效」；目标槽字节不变 |
| 导入 `schemaVersion < 11` | 「版本过旧，不支持导入」；目标槽不变 |
| 导入 `schemaVersion > CURRENT_SCHEMA` | 「来自更新版本的游戏，请升级后再导入」；目标槽不变 |
| 导入 `schemaVersion` 合法但字段被改坏（如背包长度与扩容不符） | `_is_valid_save` 拒绝并回**字段级**原因（`_last_invalid_reason`，[save_manager.gd#L1117-L1121](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L1117-L1121)）；目标槽不变 |
| 导入旧版档触发坐标/迷雾迁移 | 沿用读档语义（§2.3-3）；成功后提示可能被重置 |
| 导入含无法识别的旧装备 | 逐件丢弃并复用 `_pruned_notice` 计数提示（[save_manager.gd#L342-L347](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/autoload/save_manager.gd#L342-L347)） |
| 目标槽 = 当前活动槽（游戏中） | 「导入」置灰 + 提示（§4.3）。否则自动存会在 120 秒内或关键事件时把导入内容覆盖掉 |
| 导入后未点「读取」 | 允许。卡面立即刷新为新内容，提示一句「点『读取』进入该角色」 |
| 同一文件重复导入 | 允许（幂等覆盖）；第二次覆盖时 `.bak` 变成上一次导入的内容 |
| 文件路径在 `user://` 内（玩家误选） | 允许，不特殊处理 |

## 8. 不做的事项

- 不加密、不签名、不写校验和（与"允许改档"直接冲突）。
- 不做云同步、账号绑定、Base64 分享码（体积与范围都不合适，§3.4）。

- 不做导入后自动读取进入世界（列为可选增强，需单独确认）。
- 不因本功能提升 `schemaVersion`，不新增槽位。
- 不引入原生系统文件对话框（`use_native_dialog`）——列为后续可选增强。
- 不新增任何内联样式；新增 UI 全部走 `PanelChrome` 与文案表。
