# NPC 头顶可接任务提示实现分析

> 2026-10-17。本文只分析方案和验收口径，不修改游戏行为或制作美术。目标是让玩家在场景中看见“这个 NPC 现在可以发布任务”，而不必逐个打开对话框。

## 1. 现象、结论与边界

当前任务官面板能显示“接受任务”，主线追踪也能提示下一位发布人，但**场景里的 NPC 只有名称和靠近后出现的 `[E] 交谈`**。玩家走过 NPC 时无法直接判断是否有任务可接，尤其是发布人分散在不同地图、且并非所有发布人都配置为 `role=quest` 时。

建议在符合条件的 NPC 名称上方增加一个轻量提示标记，首版用占位符 `!` 验证功能，具体图标与动画留给美术。**标记只表达“此刻能在这个 NPC 接取至少一项任务”**，不代表任务已完成、可交付或仅有尚未解锁的任务。点击标记按点击 NPC 处理：接近后打开原有对话/任务面板，不自动接受任务。

## 2. 代码与数据核查

| 事实 | 现有证据 | 对方案的含义 |
|---|---|---|
| NPC 已有头顶显示层 | `scenes/entities/Npc.tscn` 有 `NameLabel`、`HintLabel`；`scripts/entities/npc.gd::_ready()` 设置头顶位置并把文字加入 `world_text` 组 | 标记可作为 NPC 的子节点，不需另建全屏 HUD 投影层；应复用文字/地图倍率补偿 |
| NPC 按地图配置生成 | `scripts/world/game.gd::_spawn_npcs()` 遍历 `MapService.current_npcs()`；配置含稳定 `npcId`、名称和 `role` | 标记应按 `npcId` 与任务的 `giver` 关联，不能按名称或 `role` 判断 |
| 任务状态已有事实源 | `scripts/systems/quest.gd::state_of()` 根据前置任务和存档推导 `available` 等状态；`accept()` 还检查同时进行中的任务数量上限 5 | 不增加地图或 NPC JSON 的“有任务”布尔字段，避免与进度脱节 |
| 现有快捷判断语义过宽 | `Quest.has_actionable_at_npc()` 同时把 `available` 和 `completed` 视为可操作，且未检查接取上限 | 不能直接用它驱动“可接”标记，否则待交付任务或满任务栏会出现误导 |
| 任务事件不完整 | `EventBus` 有 `quest_accepted`、`quest_completed`、`quest_rewarded`，但 `Quest.abandon()` 目前未发任务状态变化事件 | 标记若只监听现有三个事件，放弃任务后无法即时重新出现 |
| 放弃态现有 UI 有缺口 | `Quest.abandon()` 写入 `abandoned`，`accept()` 允许重接；但 `QuestPanel._make_action_button()` 未给 `abandoned` 配接受按钮，落到禁用的默认分支 | 若要兑现“放弃后可重接”，先要让任务面板真正可重接，再让标记与之保持一致 |
| 当前内容规模有限 | 实测配置为 **100** 项任务、**35** 张地图、**64** 个 NPC 配置；同图最多 **8** 个 NPC（沉井镇） | 一次事件扫描任务表和本图 NPC 足够，不需要每帧轮询或复杂空间索引 |

上表是代码与配置核查结果。用户所述“走过 NPC 看不出有任务”与场景当前仅有名称/交谈提示的实现一致；具体视觉可读性仍须在原生窗口实测。

## 3. 显示规则

| 任务状态 / 条件 | 首版“可接”标记 | 理由 |
|---|---|---|
| `available`，发布人是该 NPC，进行中数量 `< 5` | 显示 | 玩家现在可以接取 |
| `abandoned`，发布人是该 NPC，任务面板已支持重接，且数量 `< 5` | 显示 | 放弃后立即可重新接取；须先修复当前禁用按钮 |
| `available` 但进行中数量已达 5 | 隐藏 | 点击后会被接取上限拒绝，不能称为“可接” |
| `locked`、`active`、`rewarded` | 隐藏 | 分别是未解锁、已接、已领奖 |
| `completed`，该 NPC 是 `turnIn` | 隐藏 | 这是“可交付”，不是“可接”；若以后要提示，使用另一种明确标记，不复用本标记 |
| NPC 同时发布多项任务 | 只显示一个标记 | 标记表达是否存在可接任务，不在场景里列任务数量 |

任务发布人只看模板 `giver`；交付人 `turnIn`、NPC 的 `role` 和 NPC 名称都不能替代它。主线与支线采用同一判定。当前 `state_of()` 不依赖玩家等级；将来若接取规则增加等级等条件，标记必须复用与 `accept()` 相同的只读可接判定，不能继续只查状态。

## 4. 推荐实现

1. **统一只读判定。** 在 `Quest` 增加面向 NPC 的可接查询，例如 `available_givers_on_map(map_id)`。它遍历任务模板一次，按 `state_of()`、`giver`、`active_count()` 和当前地图实际 NPC ID 过滤，返回可显示标记的 NPC ID 集合。`Quest.accept()` 与查询应复用接取条件的纯判断部分；失败提示及写状态仍留在 `accept()`。不要改变 `has_actionable_at_npc()` 的既有对话分流语义。
2. **修复放弃重接口径。** 给任务面板的 `abandoned` 状态提供与 `available` 相同的“接受任务”入口，确认 `Quest.accept()` 重接后计数归零。随后把 `abandoned` 纳入可接查询；若本轮只做 `available`，必须先明确地暂不对放弃任务显示标记，避免标记与不可操作的按钮冲突。
3. **把稳定 ID 交给 NPC 实体。** `Game._spawn_npcs()` 将配置中的 `npcId` 写入 `Npc.npc_id`，标记和点击交互都使用该 ID。当前 `_interact_with()` 通过 `npcName` 反查 ID，存在同名误配风险；实现时应改为使用实体 ID，不改变玩家交互方式。
4. **在 NPC 头顶呈现。** 在 `Npc.tscn` 的 `NameLabel` 上方增加默认隐藏的标记节点；`mouse_filter=IGNORE`，并将标记区域纳入 `Npc.contains_screen_point()`，使点击标记与点击 NPC 一样走现有接近和对话流程。标记不遮挡 NPC 立绘或名称，不参与碰撞。随 NPC 入组 `world_text` 或复用相同的地图/文字倍率补偿；在 100%、150%、200% 文字和不同地图倍率下核对间距。
5. **事件驱动刷新。** `Game` 在 NPC 生成后统一计算一次本图 ID 集合，并在任务状态变化后重算；建议增设单一 `quest_state_changed` 信号，在 `Quest` 的成功接取、完成、交付、放弃提交状态后发出，现有细分信号保留供 HUD 与任务面板使用。读档/重置若复用当前世界，不经过重新生成 NPC，也要显式触发一次刷新。切图重建世界时由生成后的初始计算覆盖，不保存标记状态。

标记为纯表现状态，数据来源是已有任务模板与 `GameState.quest_states`；**无需新增存档字段、地图参数或任务配置字段**。每次状态事件最多扫描当前 100 项任务并更新本图最多 8 个 NPC；平时不做 `_process()` 查询。缓存仅保留本图当前可显示的 NPC ID 集合，切图或数据重载时失效；标记节点跟随 NPC/世界释放。

## 5. 验收清单

- 新角色进入幸存者营地时，确实有可接任务的发布人头上出现标记；无可接任务的货郎、车夫等不因 `role` 或名字相似而误亮。
- 接取一项后：若同一 NPC 还有其他可接任务，标记保留；否则立即消失。任务上限满时隐藏，腾出名额后重新出现。
- 完成任务但尚未交付时不出现“可接”标记；交付领奖后，若解锁了该 NPC 或另一 NPC 的后续任务，对应标记立即出现。跨图读档后也与真实任务状态一致。
- 支线放弃后，任务面板能够再次接取，标记立即重现；重接后消失或按剩余可接任务保留。
- 点击 NPC 人物、名称或标记均走同一个接近/对话入口；标记不直接改变任务状态，不穿透到地面造成误走路。
- 原生窗口检查 NPC 密集区、视口顶端、相机缩放以及 100%/150%/200% 文字设置；标记与名称、立绘保持间隔，不揭示迷雾外 NPC。隔离测试覆盖状态切换和同名 NPC 的 ID 关联，冒烟测试确认旧的 NPC 对话、任务接取与交付流程不回退。

## 6. 实施顺序与风险

建议一次功能提交完成：先补齐可接判定与放弃重接，再接入 NPC 稳定 ID 和标记，最后做事件刷新、隔离测试及窗口验收，并同步更新 `docs/产品文档/08-任务系统.md`、`09-UI与交互规范.md`。采用 `feat(quest): 增加NPC头顶可接任务提示` 一类提交信息。

主要风险不是图标绘制，而是**提示与真实按钮状态不一致**。为此应把“能否接取”集中到任务逻辑层，用任务状态事件驱动显示，而不是在每个 NPC 脚本里复制判定或按角色类型写死标记。
