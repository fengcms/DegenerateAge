# 存档导出文件选择器高分屏缩放修正

日期：2026-10-17。状态：**已修正并通过隔离回归**。范围：存档面板「导出 / 导入」的内置文件选择器（`FileDialog`）。

## 1. 现象

玩家在**高分屏**上把设置里的「界面大小」调到 100% 以上（80/100/125/150/175/200%）后实测导出：
面板、按钮、文字都按倍率放大了，但**存文件用的那个窗口没跟着放大**——尺寸仍与 100% 时一样，
相对其余面板"小一圈"，窗口内的文字、列表行高也偏小。

## 2. 根因

界面轴（09-A / 工程文档 17 号 §3）的载体是 **`UI` CanvasLayer 的 `transform`**：

- [settings_runtime.gd](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/settings_runtime.gd#L255-L270) `apply_ui_scale_to()`：把 UI 层 `transform` 设为 `scale(界面倍率)`，同时把 UI 下根控件尺寸设为 `视口尺寸 ÷ 界面倍率`（即"设计空间"）。
- 根窗口渲染策略为 `CONTENT_SCALE_MODE_DISABLED`（[apply_display_strategy](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/settings_runtime.gd#L217-L223)），逻辑视口＝窗口尺寸；元素**物理尺寸 = 设计尺寸 × 界面倍率**。

**`transform` 只作用于 `CanvasItem`**，而 `FileDialog` 是 `Window`（`Viewport` 派生），
落在**视口像素坐标系**、由父视口的嵌入式子窗口通道合成，**不经过 CanvasLayer 变换**。
因此它拿到的 `popup_centered(760, 520)` 是 760×520 个**视口像素**，与界面倍率无关：
界面 200% 时，面板设计空间已收缩到 640×400、一个 760 设计单位的元素会渲染成 1520 像素，
而弹层仍只有 760 像素——**相对其余 UI 恰好小一半**，这就是"显得较小"的量化口径。

## 3. 实测证据（临时探针，已删除）

Godot 4.7.2，真窗口 1280×800，`DisplayServer.screen_get_scale() = 2.0`（Retina）。

| 场景 | 弹层像素尺寸 | 弹层内可用设计空间 | 内容倍率 |
|---|---|---|---|
| 修正前 × 界面 200%（只给尺寸、不补内容缩放） | 760×520 | 760×520 | 1.00 |
| 修正后 × 界面 100% | 760×520 | 760×520 | 1.00 |
| 修正后 × 界面 200% | 1229×768 | 614×384 | 2.00 |

- 修正后弹层像素尺寸始终 = 设计尺寸 × 界面倍率，被窗口钳制后仍落在窗口内（1229×768 ≤ 1280×800）；
- 修正后弹层**内**可用设计空间（`get_visible_rect().size`）与同倍率下面板的设计空间同口径
  （200% 时面板设计空间 640×400，弹层 614×384 落在其内）：弹层的**相对观感与 100% 时一致**。
- 界面 100% 时三列数值与修正前完全相同 ⇒ **默认档位零行为变化**。

### 3.1 附带结论：回答 17 号文档 U2

17 号文档 §6 U2 曾留问"`disabled` 模式下 `Window.content_scale_factor` 是否仍生效"。实测结论：

- 根窗口 `content_scale_mode = DISABLED` 时，**子窗口自身**设
  `content_scale_mode = CANVAS_ITEMS` + `content_scale_factor = f` 仍然生效，
  且 `content_scale_size` 留 `(0,0)` 时为**纯倍率**语义：`弹层内可用设计空间 = 尺寸 ÷ f`
  （实测 1520×1040 → 760×520）。
- 这正是 Window 类弹层唯一可用的缩放途径（它们吃不到 CanvasLayer 变换），故本次采用。
  **这不违背 17 号 §4 M5-9c"不引入 `Window.content_scale_factor`"**：那条约束针对**主画布**
  （避免与 CanvasLayer 口径重复乘一次），主画布口径未变。

### 3.2 为什么不乘 `DisplayServer.screen_get_scale()`

Retina 下 `screen_get_scale()` 回报 2.0，但它**不能**再乘一次：工程口径是
"系统密度补偿由引擎/系统在逻辑单位层完成，游戏内只应用一次"（17 号 §3、`displayScaleMode = auto`
注释）。实测亦如此：`screen_scale = 2.0` 时界面 100% 下弹层 760×520 与其余面板比例已经正确，
再乘 2 会让弹层比面板大一倍，制造新的不一致。

## 4. 修正方案

### 4.1 缩放口径（属于界面轴的 owner 模块）

[settings_runtime.gd](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/settings_runtime.gd#L275-L297) 新增：

- `apply_ui_scale_to_window(dialog)`：给弹层（及其**内部子弹层**）设
  `content_scale_mode = CANVAS_ITEMS` + `content_scale_factor = 界面倍率`。
  子弹层必须一并处理：实测一个 `FileDialog` 自带 3 个 `ConfirmationDialog`、2 个 `AcceptDialog`、
  4 个 `PopupMenu`（覆盖确认、收藏夹菜单等），它们同属独立视口，不补就仍会偏小。
- `dialog_popup_size(viewport_size, design_size)`：返回
  `设计尺寸 × 界面倍率`，并按**可用设计空间**（`视口尺寸 ÷ 界面倍率`）收缩、
  上限 `DIALOG_FIT_RATIO = 0.96`。界面倍率越高，窗口能容纳的设计空间越小；
  不做收缩会出现"弹层大过游戏窗口、确认按钮落到屏幕外"的硬伤。

### 4.2 调用点

[save_panel.gd](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/ui/save_panel.gd#L219-L224) ：

- `FILE_DIALOG_SIZE`（760×520）语义明确为**设计尺寸**（与面板同处设计坐标系）；
- 新增 `_popup_file_dialog(dialog)`：先补内容缩放，再按换算尺寸弹出；
- 「导出」「导入」两处 `popup_centered(FILE_DIALOG_SIZE)` 改走该入口。

## 6. 验收口径

- `tests/settings_test.gd` 新增 `_check_dialog_scale()`（M5-9g）：
  100% 时尺寸等于设计尺寸；150% / 200% 时严格放大且不超窗口；弹层内设计空间不超过设计尺寸；
  小窗口高倍率下不溢出；`apply_ui_scale_to_window` 对弹层与子弹层都写入
  `CANVAS_ITEMS` + 界面倍率。
- 定向复核：`SettingsTest`、`PanelChromeCoverageTest`、`SaveTransferTest` 通过；
  默认隔离回归 **29 项全通过**。
- 真窗口实测（探针，用后已删）：界面 100% → 760×520 / 倍率 1.00；
  界面 200% → 1229×768 / 倍率 2.00，弹层内设计空间 614×384（窗口 1280×800）。

**待玩家实机确认**：在自己常用的界面倍率下导出一次，确认弹层与面板观感一致。
最终观感需在实际窗口目视，代码侧只能证明倍率口径正确。
