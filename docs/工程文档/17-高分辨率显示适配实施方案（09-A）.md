# 17 高分辨率显示适配实施方案（09-A）

日期：2026-10-12。状态：**M5-9a～M5-9f 已完成；2026-10-13 增补 4K 试玩修订**。本文既是方案也是执行记录。

> **2026-10-13 4K 试玩修订**：原实现让 `CanvasLayer` 的界面倍率与字体字号倍率相乘，界面/文字同设 150% 时字形变为约 225%，固定尺寸 HUD 发生重叠。修订后“文字大小”表示最终字形倍率：UI 字号覆盖值取 `textScale / uiScale`，再由 CanvasLayer 只放大一次；手动显示系数也只应用一次。世界文字取 `textScale / mapScale`，动态 UI 文字入树后补应用。设置页长说明换行、各页纵向滚动，并按逻辑视口限制面板尺寸。原存档设置键和值沿用，无 schema 变化；旧档首次显示采用新语义。

> **2026-10-13 追加**：4K 试玩认为三轴 150% 仍偏小，地图与文字档位各增加 175% / 200%，界面原有 200% 保持不变。`MAP_SCALE_MAX` / `TEXT_SCALE_MAX` 升至 2.0；当前默认值、手动显示适配与存档结构不变。旧档 150% 原样读取，新档选择 200% 后立即应用。

依据：创意 `09`（v1.0，§9 三判断已确认）· 工程 `16`（D1 纳入 M5、D2 出规格）· 产品 `09` §9.11。
范围：**09-A 基础适配（必做）**；09-B 高级项（175/200% 跨屏热重算、低配渲染清晰度）不在本文内。
归属：**M5 收口，排在 M5-8 打包之前**（15 §2 新增批次 ②B）。

## 1. 目标

已确认的三条判断（创意 09 §9）：

| # | 目标行为 |
|---|---|
| 1 | 放大窗口 = **增加地图视野与排版空间**，人物不随窗口同比变大 |
| 2 | 高分辨率屏幕 = **自动保持清晰与可读**，避免一律 200% 密度补偿 |
| 3 | **UI 大小与地图显示大小分开**；人物小可单独放大地图，字小可单独放大 UI / 文字 |

对应验收（创意 09 §8）：六条，见本文 §7。

---

## 2. 根因（现状核对，2026-10-12）

| 层 | 现状 | 后果 |
|---|---|---|
| `project.godot` `[display]` | `window/stretch/mode="canvas_items"` + `aspect="expand"`，基准 1280×800 | 窗口放大 ⇒ **整块画布按比例放大**，元素一起变大、**视野不增**（＝用户"4K 太小 / 放大后全体变大"的直接原因） |
| `Player.tscn` `Camera2D` | **无 `zoom`**，仅 `position_smoothing` | 没有"地图显示大小"入口 |
| `game.gd` 装配相机 | `limit_left/top/right/bottom` = 地图包围盒 | 与缩放配合需复验（见 §6 RK-4） |
| `settings_runtime.gd` | UI 缩放（CanvasLayer 变换，clamp 0.8–1.5）、文字缩放（font_size 覆盖，clamp 0.8–1.5）、窗口 3 档 | 有 UI/文字双入口，但**无地图倍率**、无密度口径 |
| `main.gd` | 已接 `get_viewport().size_changed` → `_apply_ui_scale()` | 窗口变化的重算**已有接线**，可直接复用 |

> 结论：**不是"缺功能"，是渲染策略与产品意图不符** + 缺一个相机倍率入口。

---

## 3. 总体设计：三条独立轴

```
最终视觉 = 地图显示大小(Camera2D.zoom) × 界面大小(CanvasLayer 变换) × 文字大小(font_size 覆盖)
           三者互不影响；各自独立设置项，各自独立默认值
系统密度补偿：由引擎/系统在「逻辑单位」层完成，游戏内**只应用一次**（不重复乘）
```

| 轴 | 载体 | 档位（建议） | 默认 | 影响 |
|---|---|---|---|---|
| **地图显示大小** | `Camera2D.zoom` | 80 / 100 / 125 / 150 / 175 / 200% | 100% | 人物、地形、技能范围形状、可见怪 |
| **界面大小** | `UI` CanvasLayer `transform` | 80 / 100 / 125 / 150 / **175 / 200%** | 100% | HUD、面板、按钮 |
| **文字大小** | 逐控件 `font_size` 覆盖 | 100 / 110 / 125 / 150 / 175 / 200% | 100% | Label / Button / LineEdit / TabBar 文本 |
| **显示适配** | 全局系数（见 M5-9c） | 自动 / 手动（75–150%） | **自动** | 三轴同时乘一次，用于平台信息不可靠时 |

> `zoom = 0.8` ⇒ 等比例可见宽高 ×1.25、面积 ×1.56，**不改变**碰撞、射程、怪物数量、拾取距离（创意 09 §4）。

## 4. 分步实施

### M5-9a 渲染策略切换（核心）✅ 已执行（2026-10-13）

**⚠ 与原方案的一处必要偏离（实测驱动，非口味问题）**：策略**没有写进 `project.godot`**，而是由
`main.gd::_ready()` 调用 **`SettingsRuntime.apply_display_strategy()`** 在**运行时**应用（无头时跳过）。

原因（实测）：`disabled` 下根视口尺寸**源自窗口**，而无头运行时 dummy 显示驱动报告窗口尺寸 **0×0**
⇒ 根视口塌成 **64×64** ⇒ `Game.visible_enemies()`（用 `get_viewport_rect()` 判定画面内可见怪）
看不到任何怪 ⇒ **冒烟 T 系列误判失败**（实测：`自动战斗应锁定半径内目标` 等 2 项稳定失败）。
无头没有显示器、渲染策略无意义，故无头回退项目默认的 `canvas_items`（视口取
`display/window/size/viewport_*` 的 1280×800），**测试网零改动、零风险**。

同时实测否定掉两条替代路径（写在 §5 U 系列里备用）：`window/stretch/mode.headless`
特性覆盖**不生效**；`--resolution` 在无头下**无效**。

**交付证据**（`tests/DisplayProbe.tscn`，同一位置同倍率、玩家固定不动）：

| 策略 | 窗口 1280×800 | 窗口 1920×1200 | 结论 |
|---|---|---|---|
| 旧 `canvas_items`（对照） | 玩家 **24px** / 可见世界 **1280×800** | 玩家 **36px（1.5×）** / 可见世界 **1280×800** | 元素跟着放大、**视野不增**（原缺陷） |
| 新 `disabled` | 玩家 **24px** / 可见世界 **1280×800** | 玩家 **24px（1.0×）** / 可见世界 **1920×1200（1.5×）** | **元素不变、视野 +50%** ✅ |

- 无头下窗口尺寸 0×0 → 视口 64×64，所以 **`disabled` 绝不能写进 `project.godot`**（见上）。
- `window/stretch/aspect="expand"` 保留不删（`disabled` 下失效，仅为便于回退；已在 `project.godot` 注释注明）。
- `display/window/dpi/allow_hidpi` 未显式设置 → 默认 **true**（实测确认），Retina 清晰度依赖它。
- `project.godot` 中 `window/stretch/mode` **保持 `canvas_items`**，并已加注释指向运行时策略。
- ⚠ **`OS.has_feature("headless")` 实测恒为 false**（无头下也返回 false）→ 判断无头只能用
  `DisplayServer.get_name() == "headless"`。`settings_runtime.gd::_apply_window()` 里原有的该判断
  因此实际失效（属既有隐患，本轮未动它，仅记录）。

### M5-9b 地图显示大小（相机倍率）✅ 已执行（2026-10-13）

- 新设置键 `mapScale`（float，0.8–1.5，默认 1.0），入 `GameState.default_settings()`。
- `SettingsRuntime` 新增三件：`_apply_map_scale()`（从 `current_scene` 找相机，供 `apply_all()` 末尾调用）、
  `apply_map_scale_to(camera)`（**直接传相机**）、`map_scale_value()`（读取 + clamp 0.8–1.5）。
  - ⚠ 为何拆出 `apply_map_scale_to()`：`game.gd` 里 `Game.tscn` **未必是 `current_scene`**（测试直接
    加载 `Game.tscn` 时不是），按路径查会落空 —— 与既有 `apply_ui_scale_to(ui)` 同一模式。
- **切图 reload 会重建 Player/Camera2D** ⇒ 在 `game.gd` 装配相机段（四行 limit 与 `reset_smoothing()` 之间）
  **补应用一次**。
- 与 limit 的配合：`zoom < 1` 可见范围更大，相机被 limit 夹住后**地图外围出现底色空白** —— 属
  "地图真实边界外仍受相机限制"的预期行为（创意 09 §4），**不视为缺陷**；边界外装饰留 M6。
- **实测**（`tests/DisplayProbe.tscn -- --map-scale=X`，固定 1280×800，玩家不动）：

| mapScale | 相机 zoom | 可见世界 | 玩家像素高 | 校验 |
|---|---|---|---|---|
| 0.8 | (0.8, 0.8) | **1600×1000** | 19.2 | 可见世界 = 视口/zoom（1280/0.8=1600）✅ |
| 1.0 | (1.0, 1.0) | 1280×800 | 24.0 | 基准 ✅ |
| 1.5 | (1.5, 1.5) | **853×533** | 36.0 | 可见世界 = 视口/zoom（1280/1.5=853）✅ |

- 截图 `/tmp/degenerateage_m59b_map{0p8,1p0,1p5}_1280x800.png`：**HUD / 小地图 / 快捷栏三档完全同尺寸同位置**
  （三轴解耦成立）；同时可见 **NPC 头顶名"车夫"随 zoom 一同变大变小** ⇒ 直接印证 **M5-9e 反向补偿的必要性**。
- 无头回归：冒烟新增 `_test_map_scale` —— ①取值 / clamp / 缺键默认；②`apply_map_scale_to` 使 `zoom == 倍率`；
  ③加载 `Game.tscn` 后相机 `zoom == 0.8`（证明世界装配确实补应用）。
- **无需 schema 升级**（缺键取默认 1.0）。

### M5-9c 窗口尺寸变化与「显示适配」✅（2026-10-13，提交 `029743d`）

**窗口尺寸变化**：
- `main.gd` 的 `size_changed` → `SettingsRuntime.reapply_for_viewport()`（内部即 `_apply_ui_scale()`）：
  - `canvas_items` 下窗口变化不改逻辑尺寸，此前几乎不触发；`disabled` 后**每次拖窗口都触发**。
  - 处置：`call_deferred` **同帧合并**（不用时间去抖 —— 拖动中面板滞后于窗口属可见劣化）。
- 🔴 **实测事故（修复见下）**：真窗口探针 `--resize-check` 发现 HUD 根尺寸全程不随倍率生效，
  根因是探针把 `Main` 挂在探针节点下，`set_current_scene` 被引擎拒绝（要求根直接子节点），
  `_apply_ui_scale()` 找不到 "UI" 全程空转。探针已改挂 `SceneTree` 根（`add_child.call_deferred`）。
- 实测（1280×800 @ uiScale=1.5）：初始 HUD 根 = 853.33×533.33；拖到 1920×1200 后跟随为
  1280×800（= 视口/1.5）✅；截图 `degenerateage_m59c_resize_*.png`：四角锚定正确、元素像素尺寸不变。

**「显示适配 自动 / 手动」**：
- **自动（默认）**：不额外补偿。macOS 上系统缩放已把物理像素换算成逻辑单位，引擎完成密度补偿 ⇒ **游戏内不得再乘一次**（`display_scale_factor()` 恒 1.0）。
- **手动（P1）**：新设置键 `displayScaleMode`（"auto"/"manual"）+ `displayScale`（clamp 0.75–1.5，默认 1.0，仅手动模式生效），作为**统一系数**乘到三轴最终值上：
  ```
  生效值 = (界面/地图/文字 各自倍率) × (手动 ? displayScale : 1.0)
  ```
- 实现**不引入** `Window.content_scale_factor`：口径可预测、可无头断言（见 §5 U2）。
- 实测（真窗口 1280×800，手动 1.25）：界面轴 transform=1.25｜地图轴 zoom=(1.25,1.25)｜
  文字轴 16→20｜HUD 根 1024×640 ✅（截图 `degenerateage_m59c_m59c_1280x800.png`）。

🔴 **同批次修复的存档回归（根因与教训见 08 交接文档）**：`_migrate` 原先只在

### 2026-10-13 高倍率面板补丁

4K 试玩反馈推动了面板实测：在 2280×1425、界面/地图/文字均 150% 时，常用面板可完整显示；在 1280×800、界面 150% 时，任务列表与大地图的固定高度、仓库双栏的固定宽度会越过可见区域。任务列表按剩余高度设滚动区，大地图缩放绘图区并允许说明换行，仓库按可用宽度调整列数及滚动区尺寸。设置变更和视口尺寸变更均触发重排。`SettingsTest` 在 1280×800 与 2280×1425、界面 80%～200% 的矩阵中复验这三个面板的外框。

| 编号 | 待验问题 | 影响 | 验证方式 |
|---|---|---|---|
| **U1** | macOS Retina 下 `Viewport.get_visible_rect().size` 返回**逻辑点**还是物理像素 | 决定密度补偿是否要额外处理（若返回物理像素，需除以 `screen_get_scale()`） | **✅ 已实测**：本机外接屏 2560×1440 且 `UI Looks like 2560×1440` ⇒ `screen_get_scale() = 1.0`、`get_visible_rect().size == window.size == 1280×800` ⇒ **返回逻辑点**、无额外换算。⚠ 本机**无 HiDPI 屏**，`scale ≠ 1` 的分支**未能实测**（须在有 Retina 屏时复验：期望 `get_visible_rect()` 仍为逻辑点、`screen_get_scale()` 为 2） |
| **U2** | `disabled` 模式下 `Window.content_scale_factor` 是否仍生效 | 若生效，「显示适配手动」可直接用它，实现更短 | **⏸ 本轮不需要**：M5-9a 已改为运行时切 `content_scale_mode`，且 §4 M5-9c 已定"不引入 `content_scale_factor`"（口径可无头断言）。留待 09-B 若需跨屏热重算再验 |
| **U3** | 切到 `disabled` 后现有 15 个面板的锚点/硬编码尺寸是否仍成立 | 决定 M5-9f 的工作量 | ⏳ M5-9f；M5-9a 已目视确认 HUD / 小地图 / 快捷栏在新策略下正常（截图见 `/tmp/degenerateage_m59a_after_*.png`） |
| **U4** | 漂字 / 头顶名称是否已有自身 `scale` 动画 | 决定 M5-9e 的反向缩放挂哪一层 | ⏳ M5-9e |

> U1 是**最关键**的一项：结论直接决定"手动显示适配"是否必要。
