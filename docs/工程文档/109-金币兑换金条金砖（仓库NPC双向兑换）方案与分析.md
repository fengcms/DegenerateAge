## 1. 需求原文与我的理解

> 「100 万金币换一块金条，10 块金条换一个金砖，金条和金砖可以叠加，最多叠加 99 块。玩家多余的金币可以换成金条和金砖存到仓库。兑换 NPC 就选仓库的 NPC。同样，这个 NPC 也可以把金条或金砖换回金币。」

拆成 6 条可执行约束：

| # | 约束 | 含义 |
|---|---|---|
| 1 | 100 万 → 1 金条 | `1 金条 = 1,000,000 金币` |
| 2 | 10 金条 → 1 金砖 | `1 金砖 = 10 金条 = 10,000,000 金币` |
| 3 | 两种都可堆叠，上限 99 | 每格最多 99 块；超出自动开新格 |
| 4 | 产出落仓库 | 兑换结果**直接写入仓库栏**（已拍板，不走「先进背包」） |
| 5 | NPC = 仓库 NPC | 六个 hub 的仓库 NPC 通用，不新增 NPC |
| 6 | 反向可兑回金币 | 金条→金币、金砖→金币，**金砖可直兑 1000 万**、**双向 1:1 无手续费**（均已拍板） |

**这个功能真正的价值不是「收纳」，是价值密度。** 金币上限 `GOLD_CAP = 999,999,999`（约 9.99 亿，`autoload/game_state.gd:10`）。一格金砖 = 99 × 1000 万 = **9.9 亿**，几乎等于金币全局上限；同样价值若用金币表示，永远突破不了上限。所以它是「满级玩家把溢出金币固化成一格资产」的通道，顺带解决仓库格位（40 格起、扩容很贵）的稀缺问题。

## 3. 方案设计

### 3.1 数据层

**① 两个物品（`data/miscItems.json` 追加）**

```json
{ "id": "gold_ingot", "name": "金条", "price": 0, "noDrop": true,
  "desc": "熔铸成条的金子，一块值一百万金币。可在仓库管理员处兑回金币。" },
{ "id": "gold_brick", "name": "金砖", "price": 0, "noDrop": true,
  "desc": "十块金条的合铸，一块值一千万金币。可在仓库管理员处兑回金币。" }
```

- **不写 `useType`** ⇒ 双击走 `use_item` 的兜底分支「该物品无法使用」，行为正确不用改。
- **不写 `questItem: true`** ⇒ 不会污染任务物品语义（`Shop.is_quest_item` 还会连带影响丢弃提示文案，见 §5 风险 5）。
- **`price: 0`** ⇒ `can_sell` 直接拒；`Shop.sell_price() == 0`。
- **`noDrop: true`** 是**新增字段**（当前 miscItems 无此字段，全库无消费点）⇒ 需在 `GameState.can_drop_item()` 增加一条守卫（排在 tool 之后、quest_item 之前）+ 新 reason `"no_drop"` + 文案「贵重物品不可丢弃」。理由：100 万一枚的资产掉地上，若地面物品会消失，等于让玩家自己删钱。**新增 reason 必须登记文案**（08 §15 坑 64）。

**② 汇率表（新建 `data/exchange.json`，注册进 `DataLoader.TABLES`）**

```json
{ "pairs": [
  { "id": "gold_to_ingot",  "from": "gold",       "to": "gold_ingot", "fromCount": 1000000,  "toCount": 1 },
  { "id": "ingot_to_brick", "from": "gold_ingot", "to": "gold_brick", "fromCount": 10,       "toCount": 1 },
  { "id": "ingot_to_gold",  "from": "gold_ingot", "to": "gold",       "fromCount": 1,        "toCount": 1000000 },
  { "id": "brick_to_gold",  "from": "gold_brick", "to": "gold",       "fromCount": 1,        "toCount": 10000000 }
] }
```

- **四条显式写出，不做汇率推导**：将来若要做「回收折价 5%」，改数据不改代码，也不会出现「砖靠条推导、条靠常量、常量又改了一处」的漂移。
- `gold` 是特殊源/目标（不是物品，是 `GameState.gold`），逻辑层里显式分支处理。
- 校验项：`from`/`to` 必须在 `{gold, 已知 miscItems id}` 之内、`fromCount/toCount > 0`、每条 `id` 唯一。

### 3.2 逻辑层

**新建 `scripts/systems/gold_exchange.gd`（纯静态，与 `Shop`/`Warehouse` 同构）**

```gdscript
static func pairs() -> Array              # 读 exchange.json，非法返回 []
static func pair(id: String) -> Dictionary
static func max_affordable(id: String) -> int    # 当前状态下最多能换几次（受金币/仓库格/堆叠限制）
static func check(id: String, times: int) -> Dictionary   # {ok, reason} 只判不写
static func apply(id: String, times: int) -> Dictionary   # 真正的原子提交（在 GameState）
```

**`GameState.exchange(id, times)` 提交顺序（原子性是这个功能的命门）**

```
1. 查 pair；times ≥ 1
2. 试算：srcCost = fromCount * times；dstTotal = toCount * times
3. 源校验
   - from == "gold"  → gold >= srcCost（否则「金币不足」）
   - from 是物品      → 仓库内该 itemId 累计 count >= srcCost（否则「金条/金砖不足」）
4. 目标校验（不写，先试算副本）
   - to == "gold"    → 🔴 gold + dstTotal <= GOLD_CAP（超了直接拒绝，**不夹取**）
   - to 是物品        → 在 warehouse 的 duplicate 上 Inventory.add(...) 必须成功
                        （仓库满 / 堆叠 99 开新格失败 ⇒ 拒绝，且**一分金币都不扣**）
5. 提交：扣源 → 加目标 → emit gold_changed / warehouse_changed → toast
```

🔴 **第 3—4 步全部通过前一行都不写**。这是本项目的老坑（工程 56 出售口径、108 的费用同源）：先扣后判 = 「扣了钱没给货」，先给后判 = 「白送」。

**关于「直接进仓库」的源物位置（需要你点头的一条）**：

- 反向兑换（条/砖→金币）**只认仓库里的金条/金砖**，不动背包；
- 正向链条（金币→条、条→砖）产出**直接进仓库**。

因此玩家若背包里有金条想合砖，需要先双击/拖放进仓库（一步，现有流程）。**我认为这是对的**：兑换台在仓库 NPC 身上，语义就是「只处理库存资产」，否则要同时处理背包扣物 + 仓库产出两套落点，边界会翻倍。代价是文案要说清楚（按钮提示与 toast 都带「仓库」字样）。

### 3.3 UI（仓库面板内新增兑换区）

插在 footer **上方**一行，四个按钮 + 一个状态标签：

```
┌ 仓库 · 杜仓 ─────────────────────────────────────────┐
│  背包 [40]                        仓库 [40]           │
│  ┌────────┐                      ┌────────┐          │
│  └────────┘                      └────────┘          │
│  详情：……                                             │
│  兑换（双向 1:1，无手续费）                            │
│  [金币→金条 100万] [金条→金砖 10块] [金条→金币] [金砖→金币] │
│  金币 12,345,678                        [扩容 40→50]  │
└──────────────────────────────────────────────────────┘
```

交互规则：

| 操作 | 效果 |
|---|---|
| 单击按钮 | 换 **1 次**（金条↔金砖 1 次 = 10 条→1 砖） |
| Shift + 单击 | 换到上限（`max_affordable`），按钮 tooltip 明示这层操作 |
| 不可执行 | 按钮禁用 + 置灰；禁用原因走 `check()` 的文案，不用另一套判断 |

按钮文案动态化，带可兑换次数（例：`金币→金条 100万（可换 12 块）`），玩家不用自己算。四按钮宽度有限，文字压到最短：`→金条`、`→金砖`、`条→金币`、`砖→金币`，tooltip 补全。

**布局影响**：新增约 32—36px 竖向高度 ⇒ `WAREHOUSE_VERTICAL_CHROME_BUDGET` 230 → **266**，并在 1280×720 / 1024×768 / 900 高下各看一眼滚动区是否仍 ≥ 100px（该常量就是给滚动区让位的下限，`warehouse_panel.gd:178`）。

## 4. 边界与拒绝理由（逐条写清，避免「点了没反应」）

| 场景 | 期望行为 | 文案方向 |
|---|---|---|
| 金币 < 100 万 | 按钮禁用 | 「金币不足（需 100 万）」 |
| 仓库金条 < 10 想合砖 | 禁用 | 「仓库金条不足（需 10 块）」 |
| 仓库只剩 1 格、已有 90 块条、要换 2 砖（20 条） | 允许：同格叠到 99 后另开 1 格（若放不下则整单拒绝） | — |
| 仓库满且无可合并堆 | 拒绝，**不扣任何源物** | 「仓库已满，先腾出空位」 |
| 反向兑回时 `gold + 1000万 > 999,999,999` | 拒绝 | 「金币已达上限，先花掉一些或换成金条」 |
| 一次全兑 99 砖（9.9 亿）且金币为 0 | 允许（9.9 亿 < 上限） | — |
| 金条/金砖尝试丢地 | 拒绝 | 「贵重物品不可丢弃」 |
| 金条/金砖尝试卖给货郎 | 拒绝（`price: 0` 已有行为） | 现有「该物品无法出售」 |

## 5. 🔴 风险清单

1. **🔴 金币上限夹取 = 资产蒸发。** 反向兑换若图省事直接 `add_gold(dst)`，`clampi` 会把 1000 万截成上限内余额，多出的价值**静默消失且无提示**。必须在第 4 步前置拒绝。**这条与工程 56「出售不因上限被拒」刻意不同**：出售是清库存行为，夹取可接受；兑换是玩家主动把储值换回现金，夹取等于偷钱。
2. **🔴 原子性。** 先扣后判 / 先给后判都会产生刷物品或丢金币的窗口。四步校验通过才提交，提交段不允许任何 `return` 提前退出。
3. **🔴 仓库满必须校验「含堆叠合并」的空间。** 只看 `has_space_for(item)` 不够：一次要 150 块时得算「现有 90 块那格补 9 + 新开 1 格」，直接用 `Inventory.add` 在**副本**上试算，跑通再提交。
4. **🔴 图标白名单。** 新增 `assets/sprites/items/gold_ingot.png` / `gold_brick.png` 并登记 `SampleArt.ICONS`。漏登记的表现是「格子有数量有名字，图标空白」——不报错、不崩，只有肉眼能发现（坑 61）。**且 preload 路径必须真实存在且有 `.ctex`**，否则运行时才炸。
5. **🔴 不要复用 `questItem: true` 来禁丢。** 它的提示语是「任务物品不能丢弃」，语义错位（坑 64 同类问题）；且 `questItem` 会进 `Shop.is_quest_item` 判定、影响任务物袋与补领判据。用独立 `noDrop` + 独立 reason。
6. **🔴 本地化 key 撞号。** 静默后者胜出，且现有测试**不会**替你发现。落键前先 `grep -c` 总量并断言新键解析出的正文是预期文本。
7. **⚠ 布局挤压。** 加一行后 720p 下滚动区可能被压到 100px 下限，`_update_layout` 会 `maxf(100, ...)` 兜住但不保证格子可读。改常量后必须量三个分辨率下的实际高度，并遵守「两侧夹逼」断言习惯（只断「≤ 可用高」会被塌陷骗过，坑 45）。
8. **⚠ 存档无迁移，但要注意大数。** 仓库里会出现 `count: 99` 的 `misc` 物品，`_is_valid_save` 只校验非负数，无风险；**不要**给金条加 `count > 99` 的可能性（堆叠上限由 `stack_max` 统一给 99，别在兑换代码里手写 99 常量）。

## 8. 我建议但你可以否决的三处

1. **「只认仓库里的金条/金砖」**（背包里有还得先存一步）。理由见 §3.2；若你要「背包里的也能兑」，我加一条「源优先取仓库、其次背包」的取物顺序，成本约 +40 行和 2 条测试。
2. **`noDrop` 新字段**（金条金砖不可丢地）。若你认为「可丢，玩家自己负责」，我删掉这条守卫和 1 条测试。
3. **图标先用程序生成的像素占位**（金条长条 + 金砖方块的纯色块 + 少量高光），美术阶段再换正式图。这样不阻塞功能落地。

| 建议 | 结论 | 落地 |
|---|---|---|
| 反向只认仓库里的金条/金砖 | ✅ 采纳 | `GoldExchange.plan()` 只读 `GameState.warehouse`，背包不参与 |

### 10.2 落地时的口径修正：`noDrop` → `bound`

方案里写的是新增 `noDrop`（仅禁丢）。实际动手时撞到一条既有硬约束：

> `DataLoader._validate_sellable_prices()` 要求**所有非 `questItem` 的 misc 必须 `price > 0`**
> （工程 39 D-7，防「卖出去静默拿 0 金币」）。

金条/金砖是「零价、非任务物」，直接写 `price: 0` 会让**启动校验报错**。两条路：
① 标 `questItem: true` 混过去 —— 但丢弃提示会变成「任务物品不能丢弃」，玩家会以为任务链出问题（坑 64 同类）；
② 扩校验，给一个显式标记。

选 ②，并把「不可售」与「不可丢」合并成**一个字段 `bound`**（绑定物 = 既不能卖也不能丢）：

- `miscItems` 新增 `bound: true`；校验器要求 `bound` 是布尔、且 `price` 必须为 0。
- `Shop.is_bound()` 唯一判据；`can_sell()` 显式拒绝（不只靠 `base_value <= 0` 的副作用）。
- `GameState.can_drop_item()` 新增 reason `"bound"`（排在 tool 之后、quest_item 之前）。
- `world_drop_zone._fail()` 新增 `bound` 文案 `msg.drop_to_ground.p008`「贵重物品不能丢弃」。

### 10.3 落账方式：target-state 而不是分步扣加

`GoldExchange.plan()` 直接返回**目标状态**（`{store, gold}`），`GameState.exchange()` 只做
`gold = ... / warehouse = ...` 两次赋值。这比方案 §3.2 的「四步校验 → 扣源 → 加目标」更彻底：
中间态根本不存在，所以「扣钱不给货 / 给货不扣钱」不是靠顺序小心，而是结构上不可能。
`check()` 与 `max_times()` 都复用 `plan()`/`room_in()`，UI 的「可换 N 次」与真实提交同源。
