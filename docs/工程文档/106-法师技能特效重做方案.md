> 起因：105 落地后玩家反馈「雷电术特效特别好，其他几个技能是不是也能重新设计」。

> **批 2 待开工**（火焰喷发 / 冰咆哮 / 魔法盾）。§一—§九 是确认前的方案（保留原文便于对照），

## 一、现状取证：改前到底是什么样

### 1.1 法师 6 个技能的视觉实现一览

| 技能 | shape / range | 现有视觉 | 判定 |
|---|---|---|---|
| 火球术（普攻） | `single` / 6 | `player_projectile`：**6px 圆点 + 一圈细弧**，固定 0.14s 飞完 | ⚠️ **最常见的画面，却最简陋** |
| 雷电术 | `single` / 6.5 | `thunder_fx`：三阶段天降落雷 | ✅ 105 已完成 |
| 火焰喷发 | `circle` / 3.5 | 地面半透明盘 + 描边，飞一颗球 | ⚠️ 像「脚下摊了一块水」 |
| 魔法盾 | `self` / buff | `magic_shield_aura`：椭圆线框 + 极淡填充 | ⚠️ 静态、无生命感 |
| 冰咆哮 | `cone` / 4.5 | 地面扇形楔子 + 描边，飞一颗球 | ⚠️ 像「贴了一张扇形贴纸」 |
| 陨石术 | `circle` / 7 | 地面半透明盘 + 描边，飞一颗球 | 🔴 **与 105 同款的巨型椭圆** |

### 1.2 三个攻击类 AoE 的实际尺寸（按 `data/skills.json` 真实 range 计算）

`Iso.TILE_W = 64`（`scripts/systems/iso.gd:11`），`Iso.GROUND_SQUASH = 0.5`（`:59`）。

| 技能 | range | 地面半径 | 屏幕横向直径 | 占视口宽 1280 | CD |
|---|---|---|---|---|---|
| 火焰喷发 | 3.5 格 | 224px | 448px | 35% | 3.2s |
| 冰咆哮 | 4.5 格 | 288px（90° 扇形） | 弧长半径 288px | 22%（单边） | 2.8s |
| **陨石术** | 7 格 | **448px** | **896px** | **70%** | 3.8s |

`tools/mage_fx_before_preview.tscn` 按真实半径渲染的三张图（`/tmp/mage_fx_before/`）证实：
**放一次陨石术，屏幕上出现一块横向占 70%、纵向占 56% 的静态半透明椭圆，淡入淡出 0.3 秒。**

这正是 105 里雷电术被判「不合适」的同一种画面 —— 只是这次它的**范围语义是对的**（陨石术确实是半径 7 格的真 AoE），所以**不能删，只能重做成「陨石砸下来」**。

### 1.3 火球术：为什么它最该改，却最容易被忽略

`player_projectile.gd:18` 的 `setup()` 里 `_duration` 默认 `0.14`，**与距离无关**：

| 量 | 值 |
|---|---|
| 普攻射程 | 6 格 = 384px |
| 飞行时长 | 0.14s（固定） |
| 等效速度 | **2743 px/s** |
| 60fps 下每帧位移 | **45.7px** |
| 球体直径 | **6px** |

每帧位移是球体直径的 **7.6 倍**。所以玩家看到的不是「一颗火球飞过去」，而是**一帧一闪的抖动**。

而它又是**全法师最高频的视觉**：技能 CD 有 2.8—3.8 秒，普攻间隔 `Combat.MIN_ATTACK_INTERVAL = 0.2`（`combat.gd:11`）到 1.7 秒左右。**玩家 80% 以上的攻击动作都是它。**

> 结论：这次重做的第一优先级不是最丑的陨石术，而是**最高频的火球术**。

### 1.4 结构性问题：三个原因叠在一起

1. **范围提示只有「一块静态盘」这一种表达**（`skill_range_fx.gd:52`）。
   `GroundFx.fill` + `GroundFx.outline` + 线性淡出，画完就不动了。它承担了「告诉玩家打哪」的职责，
   但表现力为零 —— 所以玩家看到的是「地上浮出一块颜色」，而不是「技能正在发生」。
2. **所有非雷电技能共用一颗无身份的球**（`player.gd:782` 的 `_spawn_cast_fx` 只有 `thunder` 一个分支）。
   陨石术、冰咆哮、火焰喷发都用同一颗 6px 小球，**技能身份完全丢失** —— 这正是 105 里玩家说
   「雷电是单体攻击却画个圈」的同一类问题：**视觉没有跟上技能的语义**。
3. **淡出是线性的，没有「发生感」**。真实技能有三个节拍：预警 → 爆发 → 余韵。现在只有一个节拍。

## 二、设计原则（与 105 保持同一套语汇）

本作美术是**程序化绘制**的简约等距风，不是贴图动画。雷电术之所以效果好，是因为它踩对了四条：

| 原则 | 雷电术的做法 | 推广到本次 |
|---|---|---|
| **P1 靠线条与分段明暗，不靠大块填充** | 三层描边（16/8/3）+ 折线 | 火焰用「舌」不用「盘」，寒潮用「片」不用「楔」 |
| **P2 三节拍** | 预兆 0.05s → 劈下 0.09s → 余电 0.12s | 每个技能都要有 预警 / 爆发 / 余韵 |
| **P3 从上到下读得出方向** | 天降，起点在画面外 | 陨石从天降、火焰从脚下起、寒潮向前推 |
| **P4 形状由数据算，不写死** | 高度随射程重新评估 | 半径一律读 `skills.json` 的 `range`，**不在 fx 里另写一份** |

再加一条 105 没写、但这次必须写死的：

| **P5 特效不得盖住被击中的怪** | 105 踩过：落点光斑 24px 把目标整只吞掉（§3.5）。地面系 fx 一律 `z_index = -1`（在怪之下），只有「从天而降」允许 `z_index = 1` |

## 三、逐技能设计

### 3.1 火球术（`basic_fireball`）—— 升级 `player_projectile.gd`

**现状**：6px 点 + 细弧，固定 0.14s。

**新设计**：三层结构 + 彗尾 + 命中爆点。

| 元素 | 做法 | 参数 |
|---|---|---|
| 核心 | 全亮白芯 | `radius × 0.55`，`#fff3d6` |
| 主体 | 技能色实心球 | `radius`，`#ffb347` |
| 辉光 | 外层大而淡 | `radius × 2.2`，alpha 0.28 |
| **彗尾** | 沿飞行反方向 6 个递减小圆，越远越淡越小 | 间距 `radius × 1.6`，末个 alpha 0.06 |
| 缩放呼吸 | 球体随飞行轻微收缩（飞出去会「散」） | `1.0 → 0.85` |
| **命中爆点** | 到达后原地炸开：短弧外扩 + 中心闪白 | 0.10s，半径 `radius → radius × 3.2` |
| 飞行时长 | **改为按距离算**：`0.10 + dist / 384 × 0.10` ⇒ 近 0.10s、满射程 0.20s | 见 §五 R3 |

**为什么彗尾用「沿反方向画圆」而不是「记录历史位置」**：弹道是直线，方向恒定，反方向画圆与历史位置**等价**，
但不需要保存历史数组、不需要每帧 append。代价是 6 次 `draw_circle`（104 已实测 `draw_circle` 极便宜，
贵的是抗锯齿折线）。

🔴 **本节风险最高**：它是全法师最高频的视觉。改完必须按 104 的口径实测「同时实例数 × 每帧 draw 命令数」，
不接受「看着还行」。预算见 §六。

### 3.2 火焰喷发（`flame_burst`）—— 新建 `flame_burst_fx.gd`

**现状**：脚下 448×224 半透明椭圆 + 一颗球飞向首个目标（**完全看不出这是「以自身为中心」的技能** —— 球飞出去这件事本身就在撒谎）。

**新设计**：**从脚下向外喷的火舌**，射程语义由范围环承担。

| 阶段 | 时长 | 内容 |
|---|---|---|
| 预兆 | 0—0.10s | 脚下亮起一圈细橙环（`GroundFx.outline`，半径 224），轻微收缩 |
| 爆发 | 0.10—0.22s | **14 道火舌**从脚下向外生长至半径 224，每道由 3 段折线构成、向斜上方（`y` 负）偏移 |
| 余韵 | 0.22—0.50s | 火舌上飘 + 渐隐，颜色由 `#ffd9a0` 转 `#ff8a4c` |
| 三段脉冲 | 爆发期 | 因为 `hits: 3` 是**同一帧内瞬时结算**，视觉上做 3 次间隔 0.09s 的亮度脉冲（**纯视觉，不改结算**） |

**关键参数**：`TONGUES = 14`；火舌张角在 `±12°` 内随抖动（不是均匀分布 —— 均匀会像齿轮）；
每道火舌的**长度随机 0.75—1.0 倍**（等长会像围栏）。

**范围提示归属**：保留 `skill_range_fx` 的圆形提示（真 AoE 语义正确），但由 §四 的通用升级改成「动起来的环」。

🔴 **`z_index = -1`**：怪物会站在 3.5 格内（近战怪），火舌若盖在怪身上就变成「怪在火里看不见」。

### 3.3 冰咆哮（`frost_roar`）—— 新建 `frost_roar_fx.gd`

**现状**：一个平面扇形楔子（288px，90°）+ 一颗球。

**新设计**：**三段向前推进的寒潮弧 + 冰晶碎片**。

| 阶段 | 时长 | 内容 |
|---|---|---|
| 预兆 | 0—0.08s | 前方扇形边缘亮起（保留扇形范围提示） |
| 推进 | 0.08—0.30s | **3 道弧**从近到远依次铺开（半径 96 → 176 → 288），每道是 90° 弧上的**断续冰棱**（不用连续弧线，用 11 段短折线，间隔留白） |
| 冰晶 | 0.12—0.55s | **18 片小菱形**（`draw_colored_polygon` 4 点）沿扇形向外飘，逐片旋转、渐隐 |
| 余韵 | 0.30—0.55s | 地面残留一层薄霜（半透明扇形，alpha ≤ 0.06） |

**关键参数**：`WAVES = 3`；`SHARDS = 18`；菱形尺寸 3—6px。

🔴 **朝向必须与命中方向一致**：`cone` 的 `facing` 由 `player.gd:670` 用「到锁定目标的方向」算出来。
fx 若自己取 `Vector2.RIGHT` 或自己找最近怪，就会出现「冰往左喷、右边怪掉血」。**必须由调用点传进来同一份 facing。**

🔴 **2 段 `hits` 同样是瞬时结算**，视觉上做 2 次脉冲，不做分批。（同 3.2）

### 3.4 陨石术（`meteor`）—— 新建 `meteor_fx.gd`

**现状**：`896 × 448` 的静态半透明椭圆，CD 3.8s。这是本次最丑的一个，也是 §1.2 里唯一 🔴。

**新设计**：**天降陨石 + 冲击波扩散**，用「冲击波扫过」代替「静态大盘」表达 7 格半径。

| 阶段 | 时长 | 内容 |
|---|---|---|
| 预警 | 0—0.45s | 落点地面画**一圈细金环**（半径 7 格 = 448px，不是填充盘）+ 中心十字标记 + 环内极淡填充（alpha ≤ 0.05），环边有 2px 的亮度流动（沿弧长偏移的高亮段） |
| 落下 | 0.45—0.60s | 一颗**带熔岩拖尾的球**从落点上方 360px 斜 15° 砸下（拖尾同 3.1 的彗尾做法，但粒子更大、更不规则） |
| 命中 | 0.60—0.70s | 中心白光 + **冲击环**从 0 快速外扩到 448px（0.10s 内），环身 3 层（粗淡 / 中 / 亮细） |
| 余韵 | 0.70—0.95s | 冲击环外扩到 520px 后淡出，地面留下一圈焦痕（暗红环，2.5s 慢慢消失——可选项，见 R6） |

**为什么这样比静态盘好**：静态盘是「地上有一块颜色」，玩家要靠想象补上「陨石砸下来」；
冲击波是**把「7 格内全部命中」这件事本身演出来** —— 环扫到哪里，哪里就该掉血。语义与观感一致。

**关键参数**：`METEOR_HEIGHT = 360`（比雷电的 320 略高，因为它还要砸出一个平面冲击波）；
`RING_GROW = 0.10s` 从 0 到 448px；三层线宽 10 / 5 / 2。

🔴 **预警时长 0.45s 是设计决策，不是配错**：它是**给玩家看的**，不是给敌人躲避用的（敌人不会躲）。
如果嫌慢，改 `WARN` 一个数即可，但**不要压到 0.2s 以下** —— 那样预警环会与雷电的「一闪而落」撞成同一种节奏，
玩家会分不清「我要挨打」和「我在打人」。风格上必须拉开：雷电是瞬发低伤，陨石是延迟高伤。

🔴 **`skill_range_fx` 的圆形提示与陨石 fx 的预警环会重叠**（都是 448px 圈）。
必须二选一 —— 见 §四，由 `skills.json` 的 `fx` 字段决定「范围提示交给专属 fx」。

### 3.5 魔法盾（`magic_shield`）—— 升级 `magic_shield_aura.gd`

**现状**：椭圆线框 + 极淡填充，30 秒内完全静止。它是一个**持续 30 秒**的状态，却没有任何「活着」的迹象 ——
玩家只能靠 UI 图标判断盾还在不在。

**新设计**：**呼吸 + 能量网**，不改变外形尺寸。

| 元素 | 做法 |
|---|---|
| 呼吸 | 外轮廓整体 alpha 在 0.55—0.85 之间以 1.8s 周期起伏 |
| 能量网 | 轮廓内侧画 6 段纵向弧（像笼子），缓慢绕中心旋转（30s 转一圈 = 察觉不到但不呆板） |
| 受击反馈 | `damageToManaPct` 生效时，护罩闪亮一帧（可选，见 R6） |
| 法力见底 | 法力 < 20% 时护罩转红警示（**这是产品向增强，需确认**，见 R6） |

🔴 **不得改 `outline_bounds()`**：`tests/` 里有场景回归检查护罩上沿与脚底锚点（`magic_shield_aura.gd:22`）。
只改 `_draw` 里的画法，尺寸一分不动。

## 四、架构改动：从「一颗球通吃」到「表驱动分派」

### 4.1 现状

```gdscript
# scripts/entities/player.gd:782
func _spawn_cast_fx(skill: Dictionary, skill_id: String, target: Node2D) -> void:
	if String(skill.get("fx", "")) == "thunder":
		_spawn_thunder(target.global_position)
		return
	_spawn_projectile(skill_id, target.global_position)
```

加 4 个技能要加 4 个 `if`，且每个 fx 的构造上下文不同（挂玩家 / 挂目标 / 要朝向 / 要半径）。
继续堆 `if` 就是 105 判过的「`else` 兜底承担语义分派」（坑清单第 69 条）的翻版。

### 4.2 目标结构

```gdscript
## 施法视觉分派表：key = skills.json 的 fx 字段，value = fx 脚本。
## 🔴 新增技能特效 = 在表里加一行 + 在数据里写 fx，不改任何 if。
const CAST_FX := {
	"thunder": preload("res://scripts/systems/thunder_fx.gd"),
	"flame_burst": preload("res://scripts/systems/flame_burst_fx.gd"),
	"frost_roar": preload("res://scripts/systems/frost_roar_fx.gd"),
	"meteor": preload("res://scripts/systems/meteor_fx.gd"),
}
```

统一上下文通过一个 `setup(ctx: Dictionary)` 传入，所有 fx 脚本实现同一个可选接口：

| 键 | 含义 | 谁需要 |
|---|---|---|
| `origin` | 施法者位置 | 火焰喷发（以自身为中心） |
| `target` | 首个命中目标位置 | 陨石术（落点）、雷电（已在用） |
| `facing` | 施法朝向（与命中筛选同一份） | 冰咆哮 |
| `radius` | 地面半径 = `range × TILE_W` | 全部（**从数据算，不写死**） |

**三个必须写死的规矩**：

1. 🔴 **未知 fx key 必须报警 + 回落投射物**，不能静默 —— 反之，删掉某个 fx 脚本必须让测试变红。
   这需要测试遍历 `skills.json` 里所有 `fx` 值，断言表里有同名 key、脚本能 `preload` 成功。
2. 🔴 **`fx` 字段 = 「这个技能的视觉全权由专属脚本负责」**。所以 `player.cast_skill` 里：
   **有 `fx` ⇒ 不 spawn `skill_range_fx`**（否则陨石术会同时出现预警环 + 448px 静态盘，两份提示互相对不上）。
   无 `fx` ⇒ 照旧 spawn（武士 5 个技能全部走这条，行为逐位不变）。
3. 🔴 **`fx` 脚本不得参与伤害结算**。伤害在 `player.cast_skill` 调用点已结算（105 §契约，`player_projectile.gd:1-8`）。

### 4.3 通用范围提示升级（`skill_range_fx.gd`）

这是**一处改动、全部 AoE 受益**的部分。武士的裂地斩 / 旋风斩 / 灵刃风暴也吃这个升级。

| 现状 | 改后 |
|---|---|
| 填充 alpha 0.10 线性淡出 | 填充 alpha 从 0.10 **先升到 0.14 再降**（0.3s 内），前 20% 有一个「亮起来」的起手 |
| 边缘一圈实线 | 边缘一圈实线 + **沿弧长流动的高亮段**（2px 亮线，0.3s 内绕一圈的 1/4） |
| 半径恒定 | 填充半径从 `0.92R` 扩到 `1.0R`（爆发感），描边半径恒定（**范围边界必须稳**） |
| 线性淡出 | 用 `pow(1 - t, 1.6)` 收尾（先慢后快，末尾不会拖一条淡影） |

🔴 **描边半径绝不能动**：它是玩家判断「我站这里会不会被打」的唯一依据。只有填充可以「生长」。
这一条 105 已经用「单体不画范围」的代价换来过教训 —— **提示的几何正确性 > 好看**。

| # | 事项 | 风险 | 处置 |

## 六、性能预算（按 104 的口径，不接受「看着还行」）

工程 104 的口径是 **「同时实例数 × 每帧 draw 命令数」**，不是「单次 draw 贵不贵」。按此逐项估：

| 特效 | 同时实例数（上限） | 每帧 draw 命令 | 合计 | 判定 |
|---|---|---|---|---|
| 火球术（普攻） | 攻击间隔 0.2s、飞行 0.20s ⇒ **最多 2** | 圆 3 + 尾 6 + 弧 1 = **10** | **20** | ✅ 可接受（104 的坑是 2400 件 × 4 条折线） |
| 火焰喷发 | CD 3.2s、寿命 0.5s ⇒ **1** | 火舌 14 × 3 段折线 = 42 + 环 2 | **44** | ⚠️ 需实测 |
| 冰咆哮 | CD 2.8s、寿命 0.55s ⇒ **1** | 弧 3 × 11 段 = 33 + 冰晶 18 = 51 | **51** | ⚠️ 需实测 |
| 陨石术 | CD 3.8s、寿命 0.95s ⇒ **1** | 预警 3 + 陨石 9 + 冲击波 3 + 焦痕 1 = 16 | **16** | ✅ 可接受 |
| 魔法盾 | **常驻 1** | 呼吸 2 + 能量网 6 + 弧 1 = 9 | **9** | ✅ 可接受（已常驻，仅 +7） |

🔴 **火焰喷发与冰咆哮是唯一两个 ⚠️ 的**：它们每帧要发 40—50 条抗锯齿折线。
104 的教训是「折线不坏，是**数量 × 频率**坏」，这两个都是「1 个实例、寿命 0.5s」，
量级比 104 的 2400 件低两个数量级，理论上安全 —— 但**必须实测确认**，不能靠推理。

**测法**：复用 `tools/ground_loot_perf_probe` 的墙钟差值口径（`Performance.TIME_PROCESS` 在
`await physics_frame` 后读数会偏移，104 §6 已踩过，不要再用）。

### 10.4 性能实测（`tools/mage_fx_perf_probe.tscn`，窗口模式、vsync 关、1280×800）

首跑的数字是自相矛盾的（基线 2.54ms，而「加了特效」反而 0.97—1.87ms）。补了预热 + 首尾基线 + 敏感性校验之后：

| 场景 | 实测 |
|---|---|
| baseline 空场景 | 0.92 ms/帧（1088 fps） |
| fireball ×2 同屏 | +0.32 ms |
| meteor ×1（预警期，本 fx 最重段） | −0.14 ms（落在噪声内） |
| **标定** fireball ×200 | **+11.70 ms** ⇒ 单价 **0.0585 ms/帧/个** |
| **标定** meteor ×200 | **+7.30 ms** ⇒ 单价 **0.0365 ms/帧/个** |

> **换算**：真实峰值（2 投射物 + 1 陨石）≈ **0.15 ms/帧**，占 60fps 预算（16.7ms）的 **0.9%**。
> 单个/两个的差值落在探针噪声里（±0.3ms），所以结论取自「200 个差值反推单价」而不是「和基线比」。

⚠ 本机在探针末尾出现过基线从 0.92 跳到 **6.9ms** 的抖动（后台负载），因此只采用 min 取样、且结论只用**数量级**。

1. 🔴 **多边形顶点顺序自交 ⇒ 整片消失**。第一版火苗写成
   `base-side → mid+side → tip → mid-side → base+side`，左右两个底点被拆到首尾、中间跨着上半圈。
   Godot 三角化后**什么都不画**，而 `_draw` 里其余部分（范围环）照常输出 ——
   表现是「范围提示画出来了、火苗一个都没有」，日志零错误。
2. 🔴 **`_ready()` 在 `setup()` 之前**。`host.add_child(fx)` 触发 `_ready`，`setup(ctx)` 是之后才调的，
   所以 `_ready` 里拿不到 `_radius` —— 随机参数只能存**比例**（`dist` / `height`），不能存像素值。

### 11.4 性能实测（`tools/mage_fx_perf_probe.tscn`，窗口模式、vsync 关、1280×800）

批 2 的三个特效比批 1 重得多（火焰每帧 20 道 × 3 层多边形 + 20 个着火点，冰咆哮 3 道弧 + 14 片冰晶），
所以必须实量，不能沿用批 1 的「0.15 ms」估算。

**先撞了一次测量事故** —— 首轮扩展探针跑出来：

| 场景 | 读数 |
|---|---|
| flame ×1 | 6.898 ms |
| frost ×1 | 6.899 ms |
| shield ×1 | 6.899 ms |
| 全部同时 | 6.900 ms |

四个 draw 量差十倍以上的场景**读数一模一样**，且两个独立进程都复现、都从启动约 10 秒后开始
（首个基线还是 0.67—2.01 ms）。这不是物理，是 macOS 在窗口失焦 / 降频时把帧时间压到的一个**地板**：
低于地板的场景全部读成同一个数 ⇒「相对基线」会算出 +0.001 ms 甚至负数，顺手就会写成「特效免费」。
**处置**：给探针加 `-- --one=<场景>` 单场景模式（一个进程只测一个场景，2—3 秒跑完，落在地板出现之前），
并让长跑模式自带地板检出（尾测基线 > 首测 ×2 且两个工作量天差地别的场景读数几乎相同 ⇒ 直接喊「本次差值不可用」）。
记为坑 77。

**单场景实测**（每项 3 个独立进程，列出最小—最大）：

| 场景 | 实测（3 次） | 占 16.7 ms 预算 |
|---|---|---|
| fireball ×2 同屏 | +0.22 / +0.23 / +0.40 ms | 1.3—2.4% |
| meteor ×1 预警期 | +0.11 / +0.25 / **−0.27** ms | ≤1.5%（出现负值 ⇒ 已低于分辨率） |
| frost ×1 推进期 | +0.27 / +0.47 / +0.62 ms | 1.6—3.7% |
| **flame ×1 爆发期** | **+0.62 / +1.00 / +1.09 ms** | **3.7—6.5%** |
| shield ×1（**常驻**） | +0.08 / +0.31 ms | 0.5—1.9% |
| 全部同时（合成最坏） | +2.07 / +2.13 / +2.31 ms | 12.4—13.8% |

**标定反推单价**（×100 / ×200，两个独立长跑互相印证）：

| fx | 单价 | 备注 |
|---|---|---|
| fireball | 0.038—0.040 ms/帧/个 | 批 1 测得 0.0585，同量级 |
| meteor | 0.037 ms/帧/个 | 批 1 |
| frost | 0.19—0.20 ms/帧/个 | ×100 |
| flame | 0.48—0.49 ms/帧/个 | ×100，**多份重叠过绘 ⇒ 只能当上界** |
| shield | 0.064 ms/帧/个 | ×200 |

**结论**：

1. 最重的是**火焰喷发**（单体 0.6—1.1 ms/帧），但它是 0.5 秒的一次性特效，占预算 3.7—6.5%；
   魔法盾虽然**常驻**，但只有 0.08—0.31 ms（0.5—1.9%）。
2. 「全部同时 +2.3 ms」是**合成出来的**最坏值 —— 火焰与冰咆哮共用攻击槽位，实战不可能同帧存在，
   而且探针里两者还被摆在同一个格子上（过绘翻倍）。真实峰值 ≈ 火焰 + 护盾 + 2 投射物
   ≈ **1.0—1.4 ms（6—8%）**。
3. 与工程 104 的 **66 ms/帧（2400 件积压掉落）**差两个数量级 ⇒ **施法特效不是性能风险**；
   104 的距离门控与装饰圈预渲染仍然是唯一需要守的热点。

### 11.6 🔴 顺手修掉一个**更危险**的问题：负向脚本会把偶发故障误报成「牙齿不存在」

首轮完整跑 `verify_106_negative.py` 时出现过诡异现象：同一条用例**单独跑稳定红、
连跑时偶发「仍然全绿」**，而且每次报错的条目都不一样。

根因：`run_isolated_tests.py` 在导入阶段失败时**只往 stderr 打「资源导入失败」并 return 1，
stdout 里没有任何 FAIL 行**。而校验脚本原来的判据是「输出里有没有 FAIL」⇒
一次偶发的导入失败被读成「注入之后测试照样绿了」= **牙齿不存在**。

这个误报比没有验证更危险：它会让人误以为某条防线已经失效，进而去「修」一条本来好用的防线；
反过来，如果哪天它把真故障读成「全绿」，人就会去找根本不存在的 bug。

修法：**有效结果必须具备结论行**（`{Test}: PASS` 或 `{Test}: FAIL`），否则判定为
「本轮结果无效」并自动重试（`retries=2`），不再与「真的全绿」混为一谈。

### 11.7 实机点验清单（批 2，7 条）

1. 火焰喷发在**真实战场背景**（有地面砖）上，火苗的暗红外焰会不会糊成一团。
2. 20 道火苗 + 中心 5 道会不会**盖住站在 3.5 格内的近战怪**（理论上 `move_child` 已压到底层）。
3. 火焰的「三段脉冲」能不能被感知 —— 0.09s 间隔在 60fps 下只有 5—6 帧，可能太快。
4. 冰咆哮的**三道弧是否读得出「推进」**（预览是逐帧冻结的，动态下才看得出先后）。
5. 冰咆哮的扇形张角实机上是否与「怪掉血的范围」完全吻合（这条最关键，偏差就是「打不到/白打」）。

7. 魔法盾的能量网会不会在角色跑动时显得「跟着一起晃」（网是挂在玩家节点上的子节点，理应跟随）。
