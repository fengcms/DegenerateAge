# 104 · 地面掉落积压（背包满）卡顿分析与性能优化

> 现象：地图上爆了大量物品、玩家背包满捡不起时，整个界面非常卡；**百首禁域最明显**。
> 状态：**P1—P4 已落地**（2026-10-29）。P5（上限 2400）按方案保持不动。
> 探针：`tools/ground_loot_perf_probe.gd` / `.tscn`（只读，全程关闭 autosave，不碰真实档）。
> 守门：`tests/GroundLootPerfTest.tscn`（A—E 五组）+ `tools/verify_104_negative.py`（6 条负向）。

## 一、结论速览

| # | 根因 | 2400 件时 / 帧（改前） | 改后 |
|---|---|---|---|
| 1 | 每件每帧无条件 `queue_redraw()`，且 `_draw()` 里用 **抗锯齿折线** 画装饰圈 | **~54 ms** | ≈ 0 ms |
| 2 | 背包满 ⇒ `_find_loot()` 每物理帧全表重扫，每件还要扫 137 格背包 | **~10.5 ms** | ≈ 0.06 ms |
| 3 | 每件一个 `Area2D(monitoring=true)`，2400 个参与物理广相与重叠查询 | 未量化（结构性浪费） | 消除 |
| — | `GroundItem._physics_process` 自身 | 1.3 ms | 2.0 ms（+0.7，P3 的调度代价） |
| — | **合计** | **~66 ms/帧 ⇒ 15 fps** | **~2.1 ms/帧** |

真机还要叠加 GPU 与 2400 个 Area2D 的物理步进，所以体感比 15 fps 更差——与「非常卡」吻合。

**关键发现：卡的不是「物件多」这件事本身，而是「每件每帧都在重画几条抗锯齿折线圈」。**
同一批节点、同一份 `_draw` 结构，只把 4 条折线圈换成 4 次纹理 blit：
**每件 22.6 µs → 0.40 µs（受控对照实测，见 §二 PROBE D vs PROBE I）。**

## 二、探针实测（`--headless`，M1 Max）

同一次运行里同时给出**改前**（`mode = 0`，折线复刻）与**改后**（`mode = 5`，`GroundFx.ring` 照抄）两组，
跑同一批 1200 个节点，差值即本次收益：

```
PROBE 结构｜单件节点数=3｜Area2D monitoring=false monitorable=false input_pickable=true
PROBE A｜get_first_node_in_group("player") 单次：0.071–0.085 µs
PROBE A｜2400 件 × 每帧 1 次 ⇒ 0.17–0.20 ms/帧
PROBE B｜N=2400 ⇒ 1.95–2.49 ms/帧 ｜ 单件 0.81–1.04 µs
PROBE C｜拆解：只遍历组 0.11 ms ｜ 2400 次 has_space_for 6.98 ms
PROBE C｜_find_loot 等价全表扫描（2400 件）：背包满 9.5–10.5 ms ｜ 背包空 2.7 ms
PROBE C｜改后口径（背包满早退）：0.94 ms/次 ⇒ 相对旧口径 8.9%
PROBE D｜1200 节点：不重绘 6.92 ms/帧 ｜ 重绘（改前全套）33.0–34.2 ms/帧
PROBE E｜1200 节点最小绘制（1 个圆）：6.73 ms/帧 ⇒ 每件 ≈ 0
PROBE F｜1200 节点只画 4 条 outline（抗锯齿）：29.1–30.1 ms/帧 ⇒ 每件 18.5–19.3 µs
PROBE G｜1200 节点只画 4 条 outline（无抗锯齿）：25.5–25.8 ms/帧 ⇒ 每件 15.5–15.6 µs
PROBE H｜1200 节点画 2 张预渲染环纹理：6.7 ms/帧 ⇒ 每件 ≈ 0
PROBE I｜1200 节点 = 改后 GroundItem._draw 全套：6.89 ms/帧 ⇒ 每件 ≈ 0
PROBE J｜1200 节点只画光柱（rect + AA line）：6.9 ms/帧 ⇒ 每件 ≈ 0
```

读法（五条互不重叠的证据链）：

1. **`queue_redraw()` 本身不花钱**（PROBE E：只画 1 个圆时与完全不重绘一样），贵的全是 draw 命令。
2. **4 条 `GroundFx.outline()` ≈ 全套成本的 80%**（PROBE F 29.1 vs D 33.0）：
   `Iso.ground_ellipse()` 构造 28 点数组 + `draw_polyline(..., antialiased=true)`，每条 ≈ 4.6 µs。
   关抗锯齿只降 3.5 µs（PROBE G），**大头是折线几何本身，不是 AA**。
3. **换预渲染环纹理后归零**（PROBE H / I）⇒ 这是唯一有效的方向。
4. **`draw_string` 名字几乎免费**（PROBE D 的「含名字 / 无名字」差在 ±4% 噪声内）⇒ 不用动文字。
5. **短 AA 直线不贵**（PROBE J：光柱的 `draw_rect` + `draw_line` 归零）——贵的是**多段闭环折线**。
   这条决定了「保留光柱、只换圈」是正确的最小改动。

`_find_loot` 侧（PROBE C）：遍历组只 0.11 ms，**6.98 ms 全花在 2400 次
`Inventory.has_space_for()`**——背包满时每次都要从第 0 格扫到第 136 格才判定没空位。
而背包满时这个结果对**装备**恒为 false，扫 2400 遍等于什么都没换到。
改后口径 0.94 ms（8.9%），再叠加 0.25 s 节流 ⇒ 平均 **0.06 ms/帧**。

### 为什么只有百首禁域明显

| 地图 | `unclaimedLootCap` | `preserveUnclaimedLoot` | 单只掉落 | 一轮满图 |
|---|---|---|---|---|
| 百首禁域 `c7_boss_field` | **2400** | true | ≈ 17 件/只 | 100 席 ≈ **1710 件** |
| 无尽回廊 `c7_arena` | 200 | — | ≈ 8 件 | 20 席 ≈ 160 件 |
| 孤王绝域 `c7_solo_boss` | 600 | true | ≈ 86 件 | 1 席 |

只有百首禁域同时满足「**100 席 × 20 件掉落 × 不淡出 × 上限 2400**」。
工程 60 已埋了软阈值保护（`BOSS_LOOT_RESERVE = 32`，`auto_battle.gd:232`：到 2368 件自动停战），
**所以停战那一刻，地图里已经躺着 2368 件每帧重绘 4 条折线圈的物品**——挂机停了，卡顿不停。

## 三、根因（按贡献排序）

### 根因 1｜装饰圈用抗锯齿折线，且每帧重建（占 ~80%）

`ground_item.gd::_draw()` 对一件**静止的未认领 persistent 装备**每帧画：

| 来源 | 内容 | 条数 |
|---|---|---|
| `persistent and not _claimed` | 26 / 30 半径橙色边框 | 2 |
| `guard > 0`（仅出场 / 停驻期） | 20→38 半径渐隐高亮圈 | 0（落地后） |
| `_draw_quality_augment` `epic` | 16 / 23 底座双圈 | 2 |
| `_draw_quality_augment` `legendary` | 星形底座（polygon+polyline） | 1 |

→ 普通 / 稀有件 **2 条**、史诗件 **4 条**，每条 6.2 µs ⇒ **12—25 µs/件/帧**。

放大到 2400 件且大部分是稀有以上时：**35—42 ms/帧**。

### 根因 2｜背包满时 `_find_loot()` 每物理帧全表重扫（占 ~16%）

`auto_battle.gd::_tick_loot()` → `_loot == null` 时调 `_find_loot()`。
背包满 ⇒ `_can_pick()` 对每件装备都 `has_space_for()` 返回 false ⇒ `_loot` **恒为 null** ⇒
**下一个物理帧又全表重扫一遍**，60 次/秒 × 8.4 ms。

### 根因 3｜2400 个 `Area2D(monitoring = true)`

地面物只需要「左键点击」(`input_event`) 与「悬停」(mouse_entered/exited)，
但 `GroundItem.tscn` 里 `Area2D` 保持默认 `monitoring = true` + `monitorable = true`
⇒ 每件都进物理广相、参与 area/body 重叠查询。2400 件纯属浪费。
（本次未量化，属结构性正确的清理；若量化需要另写物理步进探针。）

### 根因 4｜产品口径：上限 2400 意味着「永远捡不完」

2368 件对玩家没有可操作性——不可能手动清完。这是**产品决策**，本方案不擅自改（见 P5）。

## 四、优化方案

### P1｜装饰圈改用预渲染环纹理（收益最大，零玩法变更）

给 `GroundFx` 增加一个**只给掉落物装饰圈用**的入口，用一张预生成的白色椭圆环纹理 +
`draw_texture_rect(..., modulate)` 着色，取代 `Iso.ground_ellipse + draw_polyline`：

```
GroundFx.ring(canvas, center, radius, color, alpha, width_scale)
```

- 纹理在首次使用时懒生成（`Image` 画椭圆环，64×64，带柔边），全项目共享一张。
- 颜色由 `modulate` 给，**不需要**为每个品质/状态各生成一张。
- 线宽随半径缩放（26/32 → 1.6px vs 原 2.0px；16/32 → 1px vs 原 1.8px）——像素级差异，
  且这些圈本来就是 1—2px 的装饰。
- **`GroundFx.outline()` 一律不动**（技能预警、玩家脚下圈、Boss 圈全部依赖它，
  改它的默认实现 = 全局视觉回归 + 高风险）。
- `legendary` 星形底座保留原样（0.05 概率，件数极少）。

预期：2400 件从 ~42 ms → ~0.1 ms（PROBE H 实测持平于「不重绘」）。

### P2｜拾取扫描：背包满早退 + 节流

1. `_tick_loot()` 每帧算一次 `_bag_full := Inventory.is_full(GameState.inventory)`（≈3 µs，可忽略）。
2. `_can_pick()`：`_bag_full` 时**装备恒不可拾取**，直接 false；金币照旧（不占背包）。
   → 全表扫描从 8.4 ms 降到 ≈0.09 ms。
3. `_find_loot()` 加 `LOOT_SCAN_INTERVAL = 0.25 s` 节流（仅 `_loot == null` 时生效）。
   → 发现新掉落最多延迟 0.25 s，玩家与挂机都无感；顺带把「装备不可拾取但仍要走位」的
   反复决策也降频。

### P3｜距离门控 + 低频重绘（把「屏幕外的静止物品」彻底停掉）

`_physics_process()` 里的无条件 `queue_redraw()` 改成有条件的：

| 状态 | 重绘策略 |
|---|---|
| 已认领（落地 / HOLD / FLY 动画中） | 每帧（1 秒内就消失，量有限） |
| 鼠标悬停中 | 每帧 |
| 出场 / 停驻保护期（`guard > 0`） | 每帧（要看出「刚掉的」） |
| 距玩家 ≤ `ANIM_RANGE`（22 格 ≈ 1408 px） | 10 Hz 低频（浮动 2px 看不出来） |
| 更远 | **不重绘**，距玩家变化每 0.3 s 检查一次，回到范围内自动恢复 |

`ANIM_RANGE` 取 22 格的理由：1 格 = 64 px，1920 宽半屏 = 15 格，2560 宽半屏 = 20 格；
22 格覆盖常见宽屏，保证「看得见的都在动」。

预期：百首禁域 2400 件里绝大多数在屏幕外 ⇒ 每帧重绘件数从 2400 降到同屏几十件。
即使 P1 没做，这一条也能把绘制成本压掉 90%+；两条叠加后为「彻底不卡」。

### P4｜`Area2D` 关掉重叠检测

`GroundItem.tscn`：`ClickArea.monitoring = false`、`monitorable = false`，
`input_pickable` 保持 `true`（点击与悬停仍工作）。

🔴 前置校验：全项目搜一遍是否有代码依赖地面物的 area 重叠（`get_overlapping_*` /
`area_entered`）。目前搜到 `monster.gd` / `player.gd` 的命中都不针对地面物，落地前再确认一次。

### P5｜（需你拍板，不建议本次动）上限 2400 → 更小

- 降到 800：超出部分按 FIFO 淘汰 = **丢奖励**，与工程 60/91「保全奖励」的定案冲突。
- 本方案 P1—P4 已把 2400 件压到可接受区间，**先不动 cap**。
- 如果你希望「几千件躺在地上」这件事本身不再出现，那是另一个产品命题
  （建议方向：超出 N 件后掉落只登记记录、不建地面节点），可单开工单。

## 五、实测收益（2400 件、背包满、百首禁域）

| 项 | 改前 | 改后 | 依据 |
|---|---|---|---|
| 装饰圈重绘 | **~54 ms**（1200 件 26.8 ms 线性外推） | **≈ 0 ms** | PROBE D vs I：22.6 µs → 0.4 µs/件 |
| `_find_loot` 全表扫描 | **~10.5 ms** | **≈ 0.06 ms**（0.94 × 1/15 帧） | PROBE C |
| `GroundItem._physics_process` | 1.3 ms | **2.0 ms**（+0.7） | PROBE B |
| Area2D 物理广相 | 未量化 | 消除 | 结构断言 |
| **合计（CPU）** | **~66 ms/帧 ≈ 15 fps** | **~2.1 ms/帧** | — |

`_physics_process` 反而涨了 0.7 ms：`_tick_redraw` 每帧要递减两个计时器。
这是 P3 的**显式代价**，用 0.7 ms 换掉 50 ms 的重绘，值得；已写进 §六 便于以后核算。

真机额外收益还没算进来：GPU 侧从「每次 `_draw` 上传 28 点折线 + 抗锯齿几何」变成「一次纹理 quad」，
2400 件 × 4 条圈的顶点量差了三个数量级。

## 六、风险

- 🔴 **P1 动了「唯一允许画地面环的入口」`GroundFx`**：新增 `ring()` 与保留 `outline()`
  必须在文档注释里写清楚分工（装饰环走 `ring`，玩法相关圈走 `outline`），否则下一个人
  随手把 `outline` 也改成纹理，技能预警圈的观感会连带变。
- 🔴 **P1 的线宽会随半径缩放**：26 半径圈从 2.0px 变 1.6px、16 半径从 1.8px 变 1px。
  这是像素级差异，但**必须实机确认**「史诗双圈是否还看得出双层」；如果太细，就把纹理基础
  线宽从 2px 调到 2.5px 再缩放。
- 🔴 **P2 的 0.25 s 节流会让「刚掉落的物品」最多晚 0.25 s 才被顺路拾取**。
  需要跑一遍 `AutoControlAcceptance` / `panel_auto_battle_test` /
  `quest_target_respawn_hint_test` 等有关时序的行为测试，确认没有断言依赖「掉落当帧就去捡」。
- 🔴 **P3 的「远处不重绘」会让屏幕边缘的物品浮动动画停住**。判定范围必须留余量
  （22 格），且**地图倍率设置变化时**要么跟着缩放、要么把范围取足够大；
  否则玩家把地图缩到最小（视野最大）时会看到边缘物品「冻住」。
- 🔴 **P3 与 `_fade_out()` 的交互**：`_fade_out` 用 tween 改 `modulate.a`，CanvasItem 属性
  变化不需要 `queue_redraw`，但**必须实测**远处物品淡出是否真的消失（若 Godot 需要重绘才更新
  modulate，会出现「幽灵物件」）。验证方式：把 `ANIM_RANGE` 临时设为 0，跑到 60 s 看物品是否消失。
- 🔴 **P4 关 `monitoring` 可能影响 `mouse_entered/exited`**：需实机确认悬停名字仍然出现
  （Godot 的 `mouse_entered` 由 `input_pickable` + 鼠标 picking 驱动，理论上与 `monitoring`
  无关，但这条必须实测，不能只靠推断）。
- ⚠ 本方案**不改任何数值平衡**，不影响战斗、掉落、存档格式。

### 落地时发现的三处偏差（与方案不同）

1. **节流范围收窄**：方案里写「`_loot == null` 就节流」，实际跑测试时 `SmokeTest`
   的 T10「有怪物目标时也应先走向可拾取的地面装备」直接红了 —— 它手动调一次 `_tick_loot`
   就断言进入 `PATH_TO_LOOT`。改成**只在 `_bag_full` 为真时节流**：
   背包未满保持原行为（掉落一出现就能走），背包满才享受节流。痛点场景收益不变。
2. **`RedrawProbe` 需要 `TEXTURE_FILTER_NEAREST`**：探针替身一开始没设，`ring()` 的
   纹理 blit 与真实 `GroundItem` 不同源；补上后才和 `mode = 5` 对齐。
3. **端到端 `Performance` 探针不可靠**：`Performance.TIME_PROCESS` /
   `TIME_PHYSICS_PROCESS` 在 `await physics_frame` 之后读到的值有明显偏移
   （测出过「停跑后物理时间反而从 2.9 ms 涨到 19.6 ms」）。改用**同批节点的受控对照**
   （PROBE D vs I），只信墙钟差值，不信绝对读数。
