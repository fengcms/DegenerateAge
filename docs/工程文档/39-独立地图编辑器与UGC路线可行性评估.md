# 39 独立地图编辑器与「网友共建地图」：可行性评估与路线建议

本文回答你这次提出的三件事：**①继续丰富地图设计资源 → ②可视化选材质、自己造地图 → ③把编辑能力做成一款独立软件，并让网友用它帮你做地图，产出能顺利导入 Godot 成为游戏地图**。

本文是**评估文档**（现状 + 差距 + 路线 + 裁决点），不含实现代码，不修改任何地图数据。相关既有文档：[22-可视化地图编辑工作流建议](../素材设计/22-可视化地图编辑工作流建议.md)（工作流方案，成稿于编辑器实现之前）、[24-地图素材丰富化需求分析与制作路径](../素材设计/24-地图素材丰富化需求分析与制作路径.md)（七层素材体系）、[35-幸存者营地可视化编辑器首版验收](35-幸存者营地可视化编辑器首版验收.md)、[36-幸存者营地地面与碰撞可视化编辑扩展](36-幸存者营地地面与碰撞可视化编辑扩展.md)、[37-地图可视化编辑技术构成与通用化评估](37-地图可视化编辑技术构成与通用化评估.md)。

## 一、结论摘要

1. **完全可行，而且不是从零开始。** 仓库里已经有一个**可运行的营地地图编辑器**（`addons/camp_map_editor/`，提交 `12274cc3` / `ae1af09a` / `ffac8dcd`）：能画地面装饰、编辑碰撞轮廓、移动整体物件、拖动道路控制点，并带「保存草稿 → 校验 → 重建正式数据 → 失败回滚」的完整导出链。你想要的「可视化编辑地图」在营地这一张图上**已经跑通**。
2. **「独立软件」与「Godot 插件」不是两条路，是同一个核心的两个外壳。** 编辑器的数据层（`camp_map_document.gd`）与画布层（`camp_map_canvas.gd`）是普通 `RefCounted` / `Control`，**只有 3 处依赖编辑器专属 API**（`plugin.gd:13`、`plugin.gd:31`、`camp_map_panel.gd:178`）。换壳成本远低于重写。
3. **独立化真正的账单不在界面，在「校验与编译必须脱离 Python 与工程树」。** 目前的「应用到游戏」是调 `tools/apply_camp_map_editor.py`（`camp_map_panel.gd:171`），由它再调两个 Python 生成器。网友机器上没有 Python、没有这份工程源码。**这笔账必须先算清，否则独立软件做出来只能自己用。**
4. **「选择不同材质造地图」的前置条件目前只满足了一小块。** 现可选的「材质」只有营地那 4 种 128 像素装饰笔刷；第一章三图的地面是**程序按加权哈希算出来的**（`ground.gd` 的 `_pick_theme_tile()`），而 [24 号](../素材设计/24-地图素材丰富化需求分析与制作路径.md) 七层体系里的 **L1 过渡边缘、L3 贴地装饰、L4 立体小物件、L6 地形边界基本还没有素材**。没有素材就没有可选的材质库。
5. **UGC（网友共建）在技术上可行，但需要一套现在还不存在的东西**：稳定的**地图包格式**、**运行时从 `user://` 装载地图的通道**（当前 `DataLoader` 只读 `res://`，见 `data_loader.gd:31` 与 `:120`）、**只允许使用发行素材**的授权边界，以及分发/审核渠道。这些是独立软件之外的**第二批工作量**。
6. **建议的推进次序**：素材体系（进行中）→ 创作源统一 + 编译器自包含 → 编辑器核心泛化（营地以外的地图）→ 导出为独立应用 → 地图包契约与 UGC 通道。**先把编辑器做给自己用，再谈给网友用。**

## 三、关键结论一：编辑器核心已经存在，缺的是「壳」

### 3.1 现状：一个已跑通的营地编辑器

`addons/camp_map_editor/` 的四种模式与边界（详见该目录的 `README.md` 与 [37 号](37-地图可视化编辑技术构成与通用化评估.md) §四）：

| 模式 | 能做什么 | 边界 |
| --- | --- | --- |
| 绘制地面 | 128 像素格点涂／拖涂 4 种笔刷，擦除恢复底纹 | 不改通行；不能换基底循环地纹 |
| 编辑碰撞 | 拖顶点改整体碰撞轮廓，Shift 加点、右键删点 | 不能越界、自交、挡 NPC、切断通路 |
| 移动整体物件 | 拖动 7 实体 + 4 围栏，整体带美术/脚底层级/碰撞 | 不能新增／删除物件 |
| 调整道路节点 | 拖动主路与支路控制点，应用后重建道路贴图 | 不能改控制点数量 |

导出机制：草稿写 `data/map_art/camp_editor_draft.json`（游戏不加载）→「应用到游戏」校验源哈希（`base_hash`）+ 连通性 → 调 `tools/apply_camp_map_editor.py` 重建 → 失败保留正式文件、成功后删草稿。

### 3.2 三种「壳」的对比

| 壳 | 用户需要装什么 | 复用程度 | 主要新增工作量 | 与 UGC 的关系 |
| --- | --- | --- | --- | --- |
| **A. Godot 编辑器插件**（现状） | 装 Godot + 拿到工程源码 | 100% | 无 | 只适合你自己与协作者，**不适合网友** |
| **B. 用 Godot 导出独立应用**（推荐） | 只要 app（exe/dmg） | 渲染/素材/坐标/画布**全部复用**；只需剥离 3 处编辑器 API | 校验与编译自包含（见第四节）+ 地图包的打开/保存/导出 UI | **可达性足够**：下载 app 就能做图，导出的地图包可直接发布 |
| **C. Web 端编辑器** | 只要浏览器 | 渲染层需**重写**（等距投影、图集合批、像素级对齐要重新实现） | 最大 | 门槛最低、传播最好，但**等于另起一套渲染器**，且与「编辑器里看到的 = 游戏里出现的」这条验收纪律冲突风险最高 |

**建议路线 B。** 理由不是「B 比 C 省事」，而是 B 能让「编辑器所见」和「游戏所见」**物理上共用同一套渲染代码** —— 这正是 22 号与 35 号反复强调的验收标准（画面里改一个对象，游戏里以相同位置、层次和通行结果出现）。Web 端要把这条纪律重新证明一遍。

## 四、关键结论二：独立化最大的账单是「校验与编译自包含」

这是本文最重要的一条，也是很容易被低估的一条。

**现状链条**（证据）：

```
编辑器草稿 data/map_art/camp_editor_draft.json
   └─ camp_map_panel.gd:171  →  tools/apply_camp_map_editor.py（Python 校验 + 调用生成器）
                                   ├─ tools/build_camp_whitebox.py      → data/layouts/*.json
                                   └─ tools/build_camp_style_full_b_v2.py → assets/maps/<style>/*
```

**独立软件会撞上的三堵墙**：

1. **没有 Python**：网友机器上不会装 Python，更不会拿到 `tools/` 这堆脚本。
2. **没有工程树**：`res://` 是导出后的只读包，写不进也读不出「源工程文件」；生成器输出到 `assets/maps/...` 这条路径在导出版里不存在。
3. **没有 Godot 编辑器**：`EditorInterface.get_resource_filesystem().scan()`（`camp_map_panel.gd:178`）在导出版里不可用；素材导入缓存（`.import` / `.ctex`）也由编辑器管线生成，导出版需要预导入。

**对策（三条，必须至少选一条）**：

| 方案 | 做法 | 代价 | 备注 |
| --- | --- | --- | --- |
| **B1 校验/编译改写成 GDScript** | 把 `apply_camp_map_editor.py` + 两个生成器的**确定性逻辑**搬进 GDScript，编辑器与游戏共用一份 | 中等，但一次到位 | 最干净：独立应用与游戏运行时用同一份编译器，也顺带解决「游戏内加载网友地图」 |
| **B2 随 app 打包 Python 运行时** | 把 `tools/*.py` 与解释器一起塞进导出包 | 体积大、平台适配（win/mac 各一份）、macOS 公证麻烦 | 只适合自己用，不适合分发 |
| **B3 双格式 + 官方离线编译** | 编辑器只产「创作源」，编译由你（或 CI）在仓库里跑 | 网友无法自检 | 可作为过渡：先让网友做草稿，你统一编译 |

**建议 B1**：它同时解决了独立应用与 UGC 运行时两件事（游戏端要从 `user://` 加载网友地图，也需要一个能跑的校验器）。B3 可作为 UGC 早期的过渡策略。

## 五、关键结论三：先统一「创作源」，再做界面

**现在一张地图的事实源分散在 4 处、跨 2 套坐标系**（以营地为例）：

| 文件 | 内容 | 坐标系 |
| --- | --- | --- |
| `data/maps/ch01/camp/map.json` | 尺寸、出入口格、NPC 格、刷新点、`layoutPath` | 逻辑格 |
| `data/layouts/camp.json` | `walkable_rows` 掩码、命名逻辑点 | 逻辑格 |
| `data/map_art/camp_whitebox_v2.json` | 参考画布 1672×941、`world_rect` 3200×1800、道路控制点、7 实体 + 4 围栏的轮廓 | **屏幕画布像素** |
| `assets/maps/camp_style_full_b_v2/manifest.json` | 地纹、道路层、11 个实体的分层矩形与 `foot_y` | 画布像素 + 世界像素 |

第一章三图又是第三种形态：`data/layouts/<id>.json`（掩码）+ `data/map_art/chapter1_v2/<id>.json`（`road_rows` + `entities[]`，含 `visual_cells` / `blocking` / `collision_polygon` / `visual_assets`）+ `data/maps/ch01/<id>/map.json`，地面由程序哈希生成。

**目标态应该是三层**：

```
① 创作源（一张地图一个文件，人/编辑器只改这一份）
      ↓  编译器（确定性、可回滚、带校验）
② 运行时产物（layout 掩码 / 图集 / 分层清单 / 逻辑配置）
      ↓
③ 游戏加载
```

编辑器只读写 ①。**先把 ① 的格式定下来，再决定界面长什么样**；格式定不下来，壳换成什么都不解决问题。附带收益：地图包（UGC 的分发单位）就是 ① 加素材引用清单。

**两套地图形态需要抽象**：营地是「矩形屏画布 + 世界矩形 + 128 像素装饰格」；章一三图是「等距逻辑格 + 64×32 图集 + 程序散列 + 道路掩码」。编辑器的画布层需要抽出一个「画布驱动」接口，让同一套文档/撤销/校验逻辑跑在两种形态上，而不是把营地画布硬编码复制一遍。

## 六、关键结论四：材质选择的前提是素材体系，且必须解决「程序生成 vs 手绘」冲突

1. **素材缺口**：24 号七层体系里，L0 与 L2（道路）已有产物，**L1 过渡边缘、L3 贴地装饰、L4 立体小物件、L6 地形边界**基本为零。没有这些，「选择不同材质」的库是空的，铺出来仍然只有单层地砖感、以及「拼接像棋盘」的老问题（24 号 §二根因 3）。
2. **冲突必须正面处理**：第一章三图地面每格贴图由程序算出（`ground.gd` 的 `_pick_theme_tile()`，加权九档散列）。如果编辑器改成逐格手绘，会立刻撞上两条纪律：
   - **必须保持整层合批**，不能退回逐格 Sprite/节点（`AGENT.md` 明文约束，[37 号](37-地图可视化编辑技术构成与通用化评估.md) §八重申）；
   - **既有地图画面不能跳变**（营地 4 变体的历史公式已被 `GroundTileThemeTest` 锁死，就是这条纪律的产物）。
3. **推荐的数据模型：分区，不逐格覆写。**
   - 新增「材质分区层」：以矩形/多边形区域为单位指定材质族与强度，**分区内仍由程序按加权散列铺变体**；缺省回退到现有哈希逻辑 → 既有地图零变化，新地图获得可编辑性，合批不受影响。
   - 只有需要精确表达的地方（道路、特殊地标、L1 过渡）才允许显式覆写，且覆写层与程序层**优先级必须写死并可在编辑器里可视化**（[37 号](37-地图可视化编辑技术构成与通用化评估.md) §七.2 已提出「逐格贴图数据化、缺省回退哈希」的同类思路，分区是在它之上更省的一步）。
   - L1 过渡边缘**不手绘，由编译器从分区边界自动派生**——这与 24 号 §四.1「模块化连接件 + autotile」的构成方式一致，也避免了手摆过渡件的高维护成本。

## 七、关键结论五：UGC 的前置清单（技术 + 产品）

技术上，让「网友做图 → 你在游戏里玩到」跑通，至少需要：

| 前置件 | 现状 | 需要做什么 |
| --- | --- | --- |
| **运行时地图装载通道** | `DataLoader` 只读 `res://data/maps/`（`data_loader.gd:31`、`:120`） | 新增 `user://` 下的地图包目录 + 与内置地图同构的加载路径 |
| **地图包格式** | 无 | = 创作源 JSON + `manifest`（目标 `layoutVersion`、素材 ID 清单、作者、版本号）+ 封面图；**不含图片**（素材只引用游戏内 ID） |
| **版本门禁** | 只有 `layoutVersion` 一致性断言（`ground.gd` 对营地白盒有显式断言） | 地图包声明所需游戏版本/素材集版本，不匹配即拒绝加载并给出可读提示（沿用「坏档逐件丢弃、不整份损坏」的思路） |
| **校验器** | 在 Python 里（`tools/apply_camp_map_editor.py`） | 必须能随游戏一起运行（见第四节 B1）：掩码尺寸、越界、连通性、素材 ID 存在性、阻挡逻辑点、包体积上限 |
| **素材授权边界** | 项目已确立纪律：无明确授权的转卖资源不得使用 | 地图包**只允许引用发行版自带素材 ID**；网友不能往包里塞图片。这既避免侵权，也让包体积极小 |
| **分发与审核** | 无 | 早期可用「网友上传地图包文件 + 你人工跑校验器 → 通过则随更新内置或置于可下载目录」；后期才考虑 Workshop 类平台 |

产品层面要诚实面对一件事：**UGC 的价值前提是「有人愿意玩玩家做的图」**。因此建议把 UGC 放在 P4 之后，先用 P0–P3 把编辑器做成你自己能高效产图的工具；那时素材库与编译链都已稳定，再做对外的包格式与通道，成本最低、返工最少。

## 八、分期路线与验收门槛

| 期 | 目标 | 验收门槛（每期一句话） |
| --- | --- | --- |
| **P0 素材（进行中）** | 按 24 号推进 B 批新材质族 + L1 过渡边缘，补齐 L3/L4/L6 首批 | 每族/每层第 1 张先确认；通过 35 号校准的质量判据；等距铺装无棋盘感 |
| **P1 创作源统一** | 定义「一张地图一个创作源」格式；写编译器和校验（先 GDScript 或先 Python 都行） | 用现有营地做往返：源 → 编译产物与当前正式文件逐字段等价，游戏画面零变化 |
| **P2 编辑器泛化** | 抽出画布驱动接口，把现有营地工具扩到章一三图（先只读回显，再开放编辑） | 只读回显与正式运行截图逐物件对齐；再开放「材质分区 + 实体摆放 + 道路」 |
| **P3 换壳为独立应用** | 剥离 3 处编辑器 API，用 Godot 导出 app；打开/保存/导出地图包 UI | 独立 app 里完成「改一处 → 导出 → 放回游戏 → 位置/层次/通行一致」 |
| **P4 地图包与 UGC 通道** | 包格式 + `user://` 装载 + 校验器 + 版本门禁 | 一份网友包在你的正式游戏里加载成功且失败时给出可读拒绝理由 |
| **P5 分发与审核** | 提交/审核/更新流程 | 至少一条端到端的人工审核路径跑通 |

P1 之前**不要**动 `ground.gd` 的选砖逻辑与营地 128 像素笔刷层——它们是 P1/P2 的对照基线。

## 九、需要你拍板的六件事

1. **壳的选择**：接受「先做 Godot 导出的独立应用（路线 B）」，还是坚持从零写一个与引擎无关的独立软件？（后者需重写渲染，成本数倍）
2. **编译与校验的落点**：B1 改写为 GDScript（一次到位、UGC 也用得上）／B2 打包 Python／B3 先只产创作源、编译留在你这边？
3. **材质编辑粒度**：接受「分区 + 程序变体」的推荐模型，还是坚持逐逻辑格手绘？（后者与合批纪律、既有画面不变两条有直接冲突，需要单独评估）
4. **手绘不可走区**：[37 号](37-地图可视化编辑技术构成与通用化评估.md) §十遗留问题——继续沿用「实体碰撞编译出掩码」，还是新增可手绘的掩码叠加层？
5. **泛化顺序**：先做营地工具做扎实，还是直接铺章一三图（等距格形态）的资产库与画布适配？
6. **UGC 节奏**：现在就排入计划，还是按建议等到 P4？

## 十、明确不做（承接 [37 号](37-地图可视化编辑技术构成与通用化评估.md) §八）

- 不逐格建 Sprite／节点／刚体，地面必须保持整层合批（`AGENT.md` §2/§4）。
- 不让游戏长期维护两套地图事实源（Tiled JSON 只能作体验验证，不能成为第二套正式数据）。
- 不让编辑器绕过校验直接写正式文件，「草稿 + 源哈希 + 失败回滚」机制保留。
- 不为编辑方便降低碰撞正确性、连通性或遮挡关系。
- 地图包不含图片素材，网友作品只引用发行版素材 ID。
