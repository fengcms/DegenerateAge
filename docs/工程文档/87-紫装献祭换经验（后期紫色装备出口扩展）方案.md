## 1. 结论摘要

1. **想法成立，而且闭环比你说的更紧。** 你点出的「升级 → 又需要紫装」不是修辞，是既有机制：循环图掉落 `levelFromBoss`，**每升 10 级整代装备贬值一次**。升级本身就在批量制造「过时紫装」，你的方案是把这条既有规律从惩罚改成资源。
2. **但溢出的主源不是「Boss 爆紫」。** 百首禁域每小时产 11.7 件直掉紫 + **30 件由 120 件金装合成的紫**——**71% 的紫装来自四金合紫**。这决定了数值不能只按「紫装掉率」算。
3. 推荐兑换率：**1 件紫装 = 1 只同级循环 Boss 的经验**（锚 `Balance.boss_xp(装备需求等级)`）。文案能一句话说完，数值落在「值得换、但不替代刷图」的区间。
4. **代价必须说清**：整体经验增幅约 **26%—35%**（含金装链二阶通道）。这是本方案唯一真正动节奏的地方。
5. **与 86 号的关系**：86 的「重铸精炼」与本方案抢同一个材料池。建议**献祭升 P1、精炼降 P2 观察项**（§4.3）。

## 2. 术语与现状

### 2.1 本作的「紫」= 传说 `legendary`

品质配色是 **白 / 蓝 / 绿 / 黄 / 紫**（`ItemUtil.QUALITY_COLOR`）：紫 = `legendary`（最高档）、黄 = `epic`。后文统一：**紫装 = `legendary`，金装 = `epic`**。

### 2.2 三条产出通道（百首禁域口径）

循环图 Boss 全部 `respawnTime = 600`，按「30 秒清一只 + 重生补位」的流水线口径 ≈ **120 只/h**（工程 67 / 86 同口径）。

| 通道 | 单只期望 | 每小时 | 占比 |
|---|---|---|---|
| Boss 直掉 `legendary` | 0.0975 件（2 组独立 5%） | 11.7 件 | **29%** |
| 金装 → 四金合紫 | 1.0 件 `epic` ÷ 4 | 30.0 件 | **71%** |
| 四紫升紫 | 4 件进 1 件出（净 −3 件） | 负 | — |
| **合计** | | **41.7 件/h** | 100% |

> 回廊（`c7_arena`，20 席）是同口径的约一半：5.9 + 15 = 20.9 件/h。

### 2.3 现有四个出口，各有硬闸门

| 出口 | 单次消耗 | 闸门 | 实际容量 |
|---|---|---|---|
| 四紫定向 | 4 件同档 | 拿到目标部位后需求骤降 | 一次性 |
| 四紫升紫 | 2—4 件同档（期望恒 4） | 产物档 +1，要先升级才穿得上 | 每代一次 |
| 保星升级 | 2 件（低档 12★ + 高档 0★） | 128,747 金币 + 12★ 底件 | 件/周级 |
| 出售 | 无限 | 60% 折价，玩家觉得亏 | 心理上不可用 |

**没有任何出口能承接「任意档、任意星、件数零散、每小时 42 件」。** 这是溢出的结构原因，与掉率高低无关。

### 2.4 溢出测算（一代 = 10 级，L80→L90）

| 项 | 数量 |
|---|---|
| 一代 Boss 数 `ΣK(80..89)` | 165 只 |
| 一代产出紫装 | 16.1（直掉）+ 41.3（合成）= **57.4 件** |
| 一代需要穿 | 14 件 |
| **净盈余** | **43.4 件/代**（旧代那 14 件换下来后也是 57.4 件） |

结论：**每代 43 件紫装没有任何去处**。玩家不是贪心，是系统没给出口。

## 3. 你的想法：对在哪里

### 3.1 它解决的是「心理」，不是「格子」

背包能扩到 400 格、仓库 400 格，**纯容量从来不是瓶颈**。真正的痛点是「这些是最高品质，卖了心疼，留着没用」。给它们一个「换进度」的去处，等于把垃圾重新定义为燃料——这比再加 200 格有效得多。

### 3.2 「升级 = 装备贬值」是唯一真正的发动机

```text
L80 穿 71—80 档
L81 → 掉落档跳到 81—90，旧代 14 件全部变成「次一档」
```

**升级本身就在批量制造过时紫装。** 你的方案把这条既有规律从「惩罚」改成「资源」：过时件不再只能卖 60% 折价，而是能折成进度。这是本方案最有价值的部分，也是它比「再加一个合成服务」更聪明的地方——合成服务只会继续消耗「同档材料」，解决不了「跨档碎片」。

### 3.3 为什么它比重铸精炼更对症

| 维度 | 重铸精炼（86） | 紫装献祭（本方案） |
|---|---|---|
| 需求性质 | **有限**（词条满意后不再重铸） | **无限**（等级上限 9999） |
| 挑不挑材料 | 挑（还要劝退高档料） | 不挑（任意档、任意星） |
| 操作负担 | 每次重铸手动投 4 件 | 一键全投 |
| 改随机流 | **要**（`reroll_affixes` 加 `floor_ratio`） | 不要 |
| 存档 | 零字段 | 零字段 |
| 战力影响 | 词条质量（间接） | 等级（直接） |

**关键差异**：精炼的需求会毕业，献祭的需求不会。紫装产出是永续的，出口也必须永续。

## 4. 四个必须回答的硬问题

### 4.1 等级是全局乘性基底（最危险的一处）

`Balance.base_attack / base_defense` 是曲线，`max_hp / max_mp` 在其上再乘套装与词条。所以「紫装 → 经验 → 等级」是**用可再生资源买永久战力**，且有正反馈（战力↑ → 击杀↑ → 紫装↑）。

三条护栏：

1. **不动 `Balance` 任何一条曲线**（`PaceTest` 三条护栏零回退）；
2. 兑换率锚在 `boss_xp(L)` 上 —— 比例恒定，不随等级漂移；
3. 增幅封在 35% 以内（§5.2 实测）。

### 4.2 金装链二阶通道：4 金 → 1 紫 → 经验

这是本方案**最大的一处未预期放大**：

```text
120 件金装/h ÷ 4 = 30 件紫/h（四金合紫）
30 × boss_xp ≈ 2.5 倍于紫装直掉的贡献
```

即使你只想处理紫装，玩家也会把**全部金装合成紫装再献祭**，因为：

- 4 件金装卖钱 = 10,080 金币（L80、0★）
- 合紫后献祭 = 11,375 经验 = 2 只 Boss
- 对「不缺金币、缺进度」的玩家，后者更优

⇒ **必须把这条通道算进总量，否则数值会低估 2.5 倍。** 处理选项见 Q3。

### 4.3 与 86 号已拍板方案抢同一个池子

86 v4 已拍板「重铸精炼」（紫装作精炼材料、抬词条下限），**目前未落地**（代码里零 `refine_count` / `floor_ratio`）。

| | 容量 | 需求会毕业吗 |
|---|---|---|
| 精炼 | 20—36 件/h（4 件 × 5—9 次） | 会 |
| 献祭 | 无上限 | 不会 |

**建议：献祭升 P1，精炼降 P2 观察项。** 理由：

1. 献祭改动面小得多（不动 `reroll_affixes` 随机流，`PaceTest` 与随机快照零风险）；
2. 献祭解决「舍不得扔」，精炼解决「词条不够好」——后者已有重铸金币这条路反复试；
3. 两者并存时，理性玩家会先献祭（清空即收益）再精炼（有目标才用），精炼的可用料会被吃掉七成。

> 若坚持两个都上，建议把精炼单次上限从 4 件降到 2 件，把池子留出来。

### 4.4 低级图套利？已被 `respawnTime = 600` 挡住

直觉上「回 L61 图秒杀刷紫装换经验」应该更快。实际上：

- 循环图 Boss 全部 `respawnTime = 600`，**每小时可持续击杀上限约 120 只，与等级无关**；
- L61 档一件只值 `boss_xp(61) = 6,077`，L80 档值 11,375；
- ⇒ 回低级图刷，单位时间经验只有 54%。

**但这有前提**：兑换必须按**装备需求等级**计价，不能按玩家当前等级。按玩家等级计价，低级图立刻变成最优解。这条写进红线（§8.4）。

## 5. 主方案：紫装献祭

### 5.1 兑换公式

```text
xp_per_item = round( boss_xp(requiredLevel) × RATIO × (1 + star × 0.08) )
```

- `requiredLevel` = 该件装备的需求等级（`Equipment.level_req`）
- `boss_xp(L)` = `Balance.boss_xp(L)`，与循环 Boss 同一口径，**不新增曲线**
- `RATIO = 1.0` ⇒ 文案直接写「**一件紫装 = 一只同级 Boss 的经验**」
- `star × 0.08` 与卖价公式（`Shop.STAR_SELL_BONUS`）**同构**，玩家不必记第二套规则

### 5.2 数值表（**按装备需求等级**口径，v1 口径错误已订正）

> ⚠ **v1 这张表原来按「玩家等级」列 `boss_xp(L)`，落地时发现错了**：十级一套口径下，L80 玩家的武器
> 实例 `requiredLevel` 是 **71**（`ItemFactory.dynamic_tier_start(80) = 71` + 武器偏移 0），
> 所以一件换的是 `boss_xp(71) = 8,717`，**不是** `boss_xp(80) = 11,375`。差 30%，
> 而「按玩家等级计价」正是 §4.4 划红线要防的那个 bug。下表已改用**档位起点**（与测试断言同源）。

| 装备档 `requiredLevel` | `boss_xp(档)` | 1 件 0★ | 12★（×1.96） |
|---|---|---|---|
| 61 | 6,077 | 6,077 | 11,911 |
| 71 | 8,717 | 8,717 | 17,085 |
| 81 | 11,686 | 11,686 | 22,905 |
| 91 | 14,963 | 14,963 | 29,327 |
| 101 | 18,530 | 18,530 | 36,319 |
| 111 | 22,372 | 22,372 | 43,849 |

**每小时贡献**（百首 41.7 件/h）—— 玩家的档位 `T = 61 + ⌊(L−61)/10⌋×10`：

| 玩家等级 | 档 T | 献祭 经验/h | 献祭 级/h | 刷图 经验/h（120 只） | 刷图 级/h | 占比 |
|---|---|---|---|---|---|---|
| 70 | 61 | 253,411 | 2.18 | 729,240 | 6.26 | **34.8%** |
| 80 | 71 | 363,499 | 2.05 | 1,046,040 | 5.90 | **34.8%** |
| 100 | 91 | 623,957 | 1.79 | 1,795,560 | 5.15 | **34.8%** |
| 120 | 111 | 932,912 | 1.57 | 2,684,640 | 4.52 | **34.8%** |

> **占比恒 34.8% 不是巧合，是结构性的**：打图经验同样走 `boss_xp(同一档)`（怪物按档生成、掉落
> `levelFromBoss`），所以占比就退化成**件数比** `41.7 / 120 = 34.75%`，与曲线完全无关。
> 这一条比 v1 的「分子分母同源所以恒定」更强：改曲线、改等级都不会动它。
>
> 也就是说：**献祭永远只值「多打 42 只 Boss」，而这一小时玩家本来打了 120 只。**
> 它替代不了刷图，只是让清包有回报。

### 5.3 不可献祭的白名单

| 条件 | 处理 | 理由 |
|---|---|---|
| 非 `legendary` | 拒绝 | 本方案只做紫装；金装有四金合紫出口 |
| `favorite == true` | 跳过 | 收藏即「我要留」 |
| 穿戴中（`equipment[slot]`） | 跳过 | 不能把身上的喂掉 |
| 任务物品 | 跳过 | 既有约束 |
| `star == 12` | **默认不勾，手动勾选时警告** | 12★ 是保星底料；四紫合成同样拒绝 12★ |
| 玩家 < 61 级 | 入口不开放 | 保护 D-20 的「一章 500—700 只」前 60 级锚点 |

### 5.4 操作与 UX

**入口**：铁匠 → 合成组 → 新增整行按钮「紫装献祭」。

**面板**（复用 `equipment_fusion_panel.gd` 的 mode 骨架，新增 `SACRIFICE` 模式）：

```text
┌ 紫装献祭 ──────────────────────────────┐
│ 可献祭 43 件（0—11★ / 未收藏 / 未穿戴）    │
│ ├ 61—70 档 × 12 件  →    72,924 经验     │
│ ├ 71—80 档 × 28 件  →   318,500 经验     │
│ └ 12★ × 3 件（未选中）                    │
│ 合计 391,424 经验 ≈ 升 2.20 级（L80）      │
│                        [ 全部献祭 ]       │
└────────────────────────────────────────┘
```

- **只给一个「全部献祭」按钮**，不做逐件勾选：42 件/h 的产出，逐件点等于劝退；
- 汇总按档位分组，让玩家看得见「我在喂什么」；
- 二次确认弹窗写明「将消耗 43 件紫装，获得 391,424 经验」。

### 5.5 批量与多级连升

`GameState.add_xp()` 内部是 `while` 连升。一次喂 200 件会连升 20+ 级、刷 20 条 toast。

**建议单次上限 20 件**（20 × 11,375 = 227,500 ≈ L80 的 1.28 级）。玩家有 200 件就点 10 次，每次 1—2 级，反馈清晰。

> 替代方案「允许全量 + 合并 toast」需要改 toast 合并逻辑，风险高，不推荐。

### 5.6 存档

**零新增字段。** 献祭 = 「扣背包实例 + `add_xp`」，两者都是既有事务语义：

- 任一件不合规 ⇒ **整批不扣**（不做部分成功）；
- 成功后逐件删除 + 一次 `add_xp`；
- `schema` 恒 **14**，`_is_valid_save` 零改动。

## 8. 验收要点（✅ 已全部执行，实测结果见 §10.4）

1. **公式**：`xp_of` 对 **61 / 71 / 91** 三个套起点逐值断言（含 `requiredLevel == 套起点` 显式判据）；12★ = 1.96 倍。
2. **白名单**：收藏 / 穿戴 / 任务 / 非紫装 / 星级越界 / 空字典全部被拒，且**整批不扣**。
3. **守恒**：献祭 N 件 ⇒ 背包少 N 件、经验 + Σ`xp_of`，无其他增减；重复 id 必拒。
4. **红线**：兑换按**装备需求等级**计价（防低级图套利）；单次 ≤ 20 件；不越过 `PLAYER_LEVEL_CAP`；`PaceTest` 三条护栏逐值不变。
5. **回归**：`--import` 0 报错、隔离集 59 → **63**（新增 `PurpleSacrificeTest`，并把长期不在默认集的 `EquipmentFusionUiTest` 一并收回）、`--quit` 配置校验通过、`md5(slot_1)` 不变、本地化零重复键、schema 恒 14。
6. **负向**：六条注入逐条变红（`tools/verify_87_negative.py`），且与隔离集**串行**执行。
