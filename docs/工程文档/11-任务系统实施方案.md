## 0. 一句话方案

**把「任务」做成一条纯数据的状态机流水线**：`scripts/systems/quest.gd`（静态纯逻辑层，与 `Loot` / `Shop` / `Equipment` 同构）负责状态推导与推进，状态落 `GameState.quest_states`（**存档链已现成**），推进信号复用**已有的** `EventBus.monster_died` / `EventBus.item_picked`，表现层新增一个任务面板 + HUD 任务列表。

**但**：数据侧有 **4 个必须先补的缺口**（灵能碎片无产出路径、无任务官 NPC、地图范围对不上、无精英/Boss 测试怪点）—— 这些是本方案的核心决策点，见 §3。

## 4. 核心设计

### 4.1 任务状态机（6 态，推导 + 存储分离）

08 §8.1 定义了 6 态，施工图 M2-1 描述为 4 态 UI 语义。**两者不冲突**：内部用 6 态，UI 映射为 4 种按钮态。

```
locked ──→ available ──→ active ──→ completed ──→ rewarded
                              ↘ abandoned（可立即重接，计数清零重做）
```

**关键设计：`locked` / `available` 不落档，由 `prev` 链推导。**

```
state_of(id):
    若 quest_states 有该 id  → 取其存储值（active / completed / rewarded / abandoned）
    否则若 prev 为空         → available
    否则若 prev 已 rewarded  → available
    否则                     → locked
```

好处：存档只存"玩家做过什么"，不存"推导得出来的东西" —— 减少状态不一致的可能。

**存储结构升级（F2）**：

```gdscript
# 旧（当前注释所写，实际恒为空 {}）
quest_states = { "Q001": "rewarded" }

# 新
quest_states = { "Q002": { "state": "active", "progress": 2 } }
```

- 读档时做**防御性迁移**：若值 `is String` → 包成 `{state: 值, progress: 0}`（当前档为空，无实际负担，但防止 `bak/` 旧档或跨版本串档）
- `SaveManager` **无需改动**（`duplicate(true)` 已能处理嵌套字典）

### 4.2 推进机制（复用现成信号）

```
EventBus.monster_died(monster_id) ─┐
EventBus.item_picked(item_id)    ─┴─→ Quest.on_event(kind, target_id)
                                          │
                                          ├─ 过滤：仅 active 状态的任务
                                          ├─ 匹配：objective.kind == kind 且 targetId == target_id
                                          ├─ 地图：current_map ∈ mapScope（D3）
                                          ├─ progress += 1（封顶 count）
                                          ├─ 达标 → state = completed + emit quest_completed
                                          └─ emit quest_progressed(id, cur, need)
```

**"同一次击杀只记一次"**（08 §8.1）：达标后立即置 `completed`，不再接受该任务的计数（`state != active` 自然挡住）。

**同时接取上限 5**（08 §8.4）：`accept()` 前检查 `active` 数量。

**主线不可放弃**（08 §8.2）：`abandonable == false` 时拒绝放弃并提示。

### 4.3 奖励结算与升级结转（M2-5）

```
Quest.deliver(id):
    1) 校验 state == completed（否则拒绝 + 明确提示，不静默）
    2) reward.gold  → GameState.add_gold(n)
    3) reward.xp    → GameState.add_xp(n)      # 已含多级连升 + 结转
    4) reward.item  → 构造实例 → GameState.add_item(item)   # 背包满 → 明确提示（不静默丢奖）
    5) reward.unlock→ GameState.unlocks[键] = true          # 新增字段（F3）
    6) state = rewarded → emit quest_completed → 自动存（已挂）
```

**F1 的解法（装备实例构造去重）**：

现有 4 处各自造装备实例。建议**抽一个公共静态工厂** `scripts/systems/item_factory.gd`：

```gdscript
class_name ItemFactory extends RefCounted
static func make_equip(item_id: String, level: int) -> Dictionary   # 读 equipments 模板 → 实例
static func make_any(item_id: String, count: int) -> Dictionary     # 装备/药水/杂项/如意 自动判类
```

- `Quest` 用它构造奖励装备
- `game.gd._make_debug_equip()` 改为调它（行为等价，`debug` 模板不走掉落池的逻辑不变）
- `Shop.make_item()` 保留（差异仅是"按 id 反查品类"），或同样收敛到 `ItemFactory.make_any()`

> ⚠ **这是 M2 里唯一的"重构既有代码"动作**。若想降低风险，也可选择**不重构**，仅在 `Quest` 内写私有构造（约 20 行重复）。**见 §7 拍板项 Q5。**

**T05 升级结转**：`GameState._level_up()` 已按 4.3 保留 HP/MP **百分比**。M2 **不做逻辑改动**，只**补冒烟断言**锁死行为（当前无任何测试覆盖升级结转）。
