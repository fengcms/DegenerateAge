## 1. 一页结论

| 项 | 结论 |
|---|---|
| 改动文件 | **3 个既有文件 + 1 个新文件**：`autoload/game_state.gd`、`autoload/save_manager.gd`、`tools/run_isolated_tests.py`、新增 `scripts/systems/balance.gd` + `tests/BalanceTest.*` |
| 净增代码 | ≈ 130 行（其中 `balance.gd` 约 60 行，测试约 70 行） |
| schema | **不变（仍 14）**——不新增任何存档字段 |
| 1–60 影响 | **逐位不变**（§4.4 给了形式化证明，不是"应该不会变"） |

**三句话**

1. `E(L)` 在 `L ≤ 60` 时因子恒为 `1.0`，浮点乘法精确 ⇒ 存量经验表一个数字都不动。
2. `base_attack(L) ≡ 12 + 2(L−1)` 在 `L ≤ 60` 成立，而升级用 `maxi(cur+2, base_attack(L))` ⇒ **与原逻辑逐位等价**。
3. 对齐**不用标记位**：曲线值只由等级决定，读档时做一次 `maxi` 即可，幂等、可重复、不碰 `unlocks` 白名单。

## 3. 三个前置硬点的处置

### 3.1 P-14：`PLAYER_LEVEL_CAP` 999 → 9999

```gdscript
# autoload/game_state.gd:17
-const PLAYER_LEVEL_CAP := 999
+const PLAYER_LEVEL_CAP := 9999
```

**为什么是 9999 而不是"更大"**：

| 等级 | 每级经验 `E(L)` | 每级击杀数 `K(L)` | 判断 |
|---|---|---|---|
| 1,000 | 1.84×10⁸ | 181 | 已远超实际可达 |
| 9,999 | 7.51×10¹⁰ | 1,801 | 仍在 `int64`（9.22×10¹⁸）与 JSON 双精度（2⁵³）内，余量 7 个数量级 |

再往上没有工程收益，反而要考虑 `pow` 返回 float 的精度：
`E(10⁶) ≈ 4.7×10¹⁵`（开始贴近双精度整数的精确上限），`E(10⁷) ≈ 7.5×10¹⁸`（逼近 `int64`）。
**所以「无限」在产品口径上写作「无内容硬顶」，在工程上是 9999 级护栏**（产品 13 §9.3 Q-9）。

> ⚠ 这一条是**产品决策**（Q-9）。本方案按建议值 9999 / 99,999,999 写；
> 若你希望换一个数字，只需改这两个常量 + 同步测试断言，其余代码不动。

### 3.2 P-16：`PLAYER_STAT_CAP` 999,999 → 99,999,999

```gdscript
# autoload/game_state.gd:18
-const PLAYER_STAT_CAP := 999999.0
+const PLAYER_STAT_CAP := 99999999.0
```

**为什么必须同步抬**（实算）：

| 等级 | `base_attack(L)` | 相对 999,999 |
|---|---|---|
| 1,000 | 261,093 | 余量 3.8 倍 |
| **1,915** | **999,999 +** | **开始撞破**（二分求得首个越界等级） |
| 9,999 | 28,339,142 | 需 ≥ 2,834 万 |

⇒ 若只抬等级上限而不抬属性上限，**1915 级**会从另一个口子把存档判坏。
两条必须同批改，且加一条钉死关系的断言：

```gdscript
_expect(Balance.base_attack(GameState.PLAYER_LEVEL_CAP) < int(GameState.PLAYER_STAT_CAP),
	"等级上限处的基础攻必须低于属性上限（否则 1915 级会撞 cap）")
```

### 3.3 P-15：对齐**不用** `unlocks` 标记

原方案（产品 13 §10 R-3）写的是 `unlocks["endgame_aligned"] = true`。
但 `save_manager.gd:1263-1271` 会校验 `unlocks` 的每个键都在 `_known_unlock_ids` 里
（该集合只由**任务奖励的 `unlocks` 数组**与**首杀记录的 `unlock`** 构建，`:1321-1339`），
自造键 ⇒ `_reject("unlocks 含未登记键：…")` ⇒ **存档读不进去**。

**改成幂等校正**（不存任何标记）：

```gdscript
GameState.player.attack  = maxi(int(GameState.player.attack),  Balance.base_attack(...))
GameState.player.defense = maxi(int(GameState.player.defense), Balance.base_defense(...))
```

理由三条：
1. 曲线值**只由 level 决定**，不存在"需要记住做过没做"的状态；
2. `maxi` 只升不降 ⇒ 对本来正确的档是恒等操作，可无限次重复；
3. 旧档 / 新档 / 手改档走同一条路径，不会出现"标记丢了永远不对齐"。

## 4. 落地设计

### 4.1 新增 `scripts/systems/balance.gd`

```gdscript
class_name Balance
extends RefCounted
## M10-0：满级后数值地基（产品 13 §2）。三条曲线 + 两个基线推导，全部纯静态、无状态。
## 口径约束：L ≤ 60 时所有函数必须与既有实现**逐位一致**，任何改动都要过 tests/BalanceTest。

## 60 级及以下沿用 4.4 的逐级成长；> 60 改走曲线。
const SOFTCAP_LEVEL := 60
## L60 的基线值（= 12 + 59×2 / 5 + 59×1），是曲线的锚点。
const BASE_ATTACK_60 := 130
const BASE_DEFENSE_60 := 64

## 缩放曲线 S(d) = 1 + 0.12·d + 0.0022·max(0, d−12)²，d = level − 60。
## 线性段即既有 M_HP_PER_LV = 0.12；二次段从 d=13 起，故存量（最大 d=9）不受影响。
static func scale(delta_level: int) -> float:
	var d := maxi(0, delta_level)
	var quadratic := 0.0022 * pow(float(maxi(0, d - 12)), 2.0)
	return 1.0 + 0.12 * float(d) + quadratic

## 经验曲线 E(L) = round(100·L^1.6·(1 + 0.03·max(0, L−60)))。
## L ≤ 60 时因子恒 1.0 —— 与旧的 round(100·L^1.6) 完全等价。
static func xp_to_next(level: int) -> int:
	var l := maxi(1, level)
	var boost := 1.0 + 0.03 * float(maxi(0, l - SOFTCAP_LEVEL))
	return int(round(100.0 * pow(float(l), 1.6) * boost))

## 难度旋钮：每级期望击杀 Boss 数 K(L) = 12 + 0.18·max(0, L−60)。
static func kills_per_level(level: int) -> float:
	return 12.0 + 0.18 * float(maxi(0, level - SOFTCAP_LEVEL))

## 循环 Boss 的单只经验 = E / K（掉落表不再手填经验，改由此反推，保证「打 K 只升一级」）。
static func boss_xp(level: int) -> int:
	return int(round(float(xp_to_next(level)) / maxf(1.0, kills_per_level(level))))

## 基线攻击：L ≤ 60 = 12 + 2(L−1)；L > 60 = round(130 · S(L−60))。
static func base_attack(level: int) -> int:
	var l := maxi(1, level)
	if l <= SOFTCAP_LEVEL:
		return 12 + (l - 1) * 2
	return int(round(float(BASE_ATTACK_60) * scale(l - SOFTCAP_LEVEL)))

## 基线防御：L ≤ 60 = 5 + (L−1)；L > 60 = round(64 · S(L−60))。
static func base_defense(level: int) -> int:
	var l := maxi(1, level)
	if l <= SOFTCAP_LEVEL:
		return 5 + (l - 1)
	return int(round(float(BASE_DEFENSE_60) * scale(l - SOFTCAP_LEVEL)))
```

**设计取舍说明**

| 取舍 | 选择 | 理由 |
|---|---|---|
| 是否引用 `GameState` | **不引用** | 静态类被 `--check-only` 单脚本检查时 autoload 不可见，会出假阳性；clamp 交给调用方 |
| 曲线值 vs 逐级乘算 | **曲线绝对值** | 逐级 `×S(d)/S(d−1)` 每级要 `round` 一次，1000 级累计漂移 < 0.4%（产品 13 R-2）；绝对值**零漂移** |
| 一个类 vs 散落常量 | **一个 `Balance`** | 后续 M10-2/3/8/10 都要读同一条曲线，单一来源避免"两处公式各写一遍" |

**④ 新增 `align_baseline_stats()`（紧跟 `_level_up` 之后）**

```gdscript
## M10-0：把基础攻防抬到曲线基线（幂等）。用于读档后对齐「旧档（线性成长）」与「新档（曲线）」。
## 不写任何标记位 —— 曲线值只由等级决定，可重复执行。
func align_baseline_stats() -> void:
	var prev_max := max_hp()
	var ratio := float(player.hp) / float(maxi(1, prev_max))
	player.attack = maxi(int(player.attack), Balance.base_attack(int(player.level)))
	player.defense = maxi(int(player.defense), Balance.base_defense(int(player.level)))
	player.hp = clampi(int(round(float(max_hp()) * ratio)), 0, max_hp())
```

> HP 按比例结转而不是补满：读档时玩家可能正在残血，补满等于白送一次治疗。
> `max_mp` 不依赖攻防（F-12），无需处理。

**⑤ `add_xp` 的 `while` 加等级护栏（落地时新增，方案原稿遗漏）**

```gdscript
	# M10-0：等级护栏。`PLAYER_LEVEL_CAP` 同时是读档校验上界，若这里不拦，
	# 一旦越过（改档 / 极端经验注入）就会写出「自己读不回来」的存档（P-14）。
	while int(player.level) < PLAYER_LEVEL_CAP and int(player.xp) >= xp_to_next(int(player.level)):
```

`PLAYER_LEVEL_CAP` 在方案里被称作「9999 级护栏」，但 F-2 已经写明 `while` **无封顶** ——
不补这一条，常量就只是校验用的数字，玩家仍然能越过它把自己写死。到顶后**经验照常累积、不再升级**
（不丢 xp，只是不再成长），行为对 `L < 9999` 逐位不变。

### 4.4 为什么「1–60 逐位不变」是**证明**而不是**期望**

```
命题：对任意 1 ≤ L ≤ 60，若玩家按正常路径升级，maxi(cur+2, base_attack(L)) == cur+2。

证明：正常路径下 cur = 12 + 2(L−2)（上一级的值），故 cur+2 = 12 + 2(L−1)。
      而 base_attack(L) = 12 + (L−1)×2 （L ≤ 60 分支）= 12 + 2(L−1)。
      两者恒等 ⇒ maxi 取任一，结果与旧代码完全相同。∎
```

防御同理（`cur+1 = 5 + (L−1) = base_defense(L)`）。
经验同理（`1 + 0.03×max(0, L−60)` 在 `L ≤ 60` 时精确等于 `1.0`，IEEE754 下 `x × 1.0 == x`）。

⇒ 因此 §6 的回归要求「跑的是一份 L≤60 的旧档，前后 `xp_to_next` 与 `max_hp` 逐值一致」，
它可以被**直接验证**，不需要依赖"应该没问题"的判断。

## 10. 一句话总结

**M10-0 不是"改两个公式"，而是"给等级找一条不会毁档的路"。**

三件事按顺序做：先抬两个上限（否则 1000 级整档作废），
再把三条曲线收进 `Balance`（否则后面 5 个批次各写一遍），
最后用**幂等对齐**替代标记位（否则撞上 `unlocks` 白名单）。
做完之后 1–60 一个数字都不变，而 61 级以上第一次有了可复算的成长曲线。
