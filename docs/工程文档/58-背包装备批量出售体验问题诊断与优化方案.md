## 0. 一句话结论

现行「预设 + 逐件清单」不是坏设计，但它把「**日常清包这个高频、低风险的动作**」交给了「**为防误卖珍贵装备而设计的四层保护规则**」，结果默认勾选集在实战中趋近空集（绿装更是被硬性排除），玩家不得不逐件手勾、还要再点一次「再次确认珍贵装备」——用户感知到的「无法快速卖出」「新界面看不懂」，正是这两件事的直接后果。

根因**不是**界面文案写得不清楚（预设选项文案其实已经写明「仅普通、零星、低至少 10 级」），而是**默认规则过窄 + 批量操作缺失 + 单件快卖路径被移除**三者叠加。

### 1.3 `upgrade` 的判定特别值得注意

[ equipment.gd#L134-L140](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/equipment.gd#L134-L140)：

```gd
var worn: Dictionary = slots[target] if slots[target] is Dictionary else {}
var candidate_score := score(item)
var worn_score := score(worn)          # 空槽 = score({}) = 0
var score_delta := candidate_score - worn_score
var score_increase := score_delta > 0.0 and not is_zero_approx(score_delta)
```

**空槽时 `worn_score = 0`**，因此**任何评分大于 0 的装备在「目标是空槽」时都算「评分可提升」**，也就必然落入 `upgrade` 保护、不被任何预设默认勾选。这一段在产品方案 §3 中是**有意为之**（"槽位为空也按现有评分预览计为可提升"），但它的实际后果是：**空槽越多的角色，能自动卖掉的装备越少**。

## 2. 问题归因

### P1（主因）四层保护叠加 ⇒ 默认勾选集趋近空集

一条装备要被默认勾选，必须**同时**满足：

1. **不收藏**；
2. **无有效替换槽之外……** 即 `preview.ok == true`（有合法目标槽）；
3. **评分不超过目标槽**（含空槽 ⇒ 只要评分 > 0 就被排除）；
4. **零星**；
5. **品质 ≤ 预设上限**（最高只到 `uncommon` 优秀即蓝装）；
6. **`requiredLevel ≤ 玩家等级 − gap`**（gap 为 10/10/5）。

逐条对照用户的三类装备：

| 装备 | 关卡 | 结论 |
|---|---|---|
| **白装（common）** | 3/4/5/6 关可通过 | 只要**等级差 ≥ 10** 且**零星**且**不优于目标槽**才自动勾选。当前章节同档装备（装备为「十级一套」）几乎全部倒在「等级接近当前角色」上；空槽/低评分槽位不足时又倒在「评分可提升」上 |
| **蓝装（uncommon）** | 仅「标准 / 积极」可过 | **默认预设「谨慎」直接排除**；切到标准/积极后仍要过等级差 10/5 与评分保护 |
| **绿装（rare 稀有）** | **任何预设都不通过** | `max_quality` 最高只到 `uncommon` ⇒ 绿装**100% 落入「必须逐件手选 + 二次确认」路径** |

> 这就是用户观察到「大量白装、蓝装、绿装无法快速卖出」的**直接机制原因**。绿装不是"漏配"，是设计上就排除；白/蓝装不是"不能卖"，是**默认不勾**（且默认预设还把蓝装排除）。

叠加放大效应：装备是「十级一套」模型（见《53-装备十级一套改造分析与方案》），玩家在某一章节停留时，背包里绝大多数装备的 `requiredLevel` 都落在当前档内 ⇒ `level` 理由命中率极高 ⇒ **默认勾选数常年为个位数**。

### P2（主因）「快」被两次确认与逐件勾选吃掉

- 由于 P1，玩家想清包只能**手勾**。手勾即 `risky` ⇒ 确认按钮变成「再次确认珍贵装备」⇒ **每一次批量清包至少两次点击**，且中间没有任何"这是最后确认"的独立弹窗，容易点错。
- 清单**没有任何批量操作**：没有全选 / 全不选 / 按品质分段全选 / 反选 / 排序 / 搜索。
- 结论：清 40 件绿装 = 40 次勾选 + 2 次确认。这已经不是"批量出售"，是"逐件出售"。

### P3 「搞不清楚」的界面归因（用户原话）

1. **入口语义与结果不一致**：按钮叫「出售装备」，点开却是"预设 + 清单 + 后续还要确认"。旧设计里「一键卖出低级装备」的字面语义（点一下=卖掉）被破坏，但按钮位置和风格没变 ⇒ 玩家第一反应是"点了怎么没卖"。
2. **清单把不卖的也列出来**：全部装备 + 每行一行灰色原因。信息密度高，且**没有一句全局说明**"下面打勾的才会卖，灰色行是没被预选的原因"。要理解 7 种底层 reason 的 AND 关系才能明白为什么"一件都没勾"。
3. **勾选框两种"未勾"含义**：
   - `disabled`（收藏 / 不可出售）= 灰框、点不动；
   - 被 `quality`/`level`/`upgrade`/`starred` 排除 = **框是亮的，但没勾**。
   玩家分不清"不能卖"与"我没选它"，很容易误以为"这些也都不能卖"。
4. **同一个确认按钮文字会跳变**（`确认出售` → `再次确认珍贵装备`），且风险详情挤在页脚一行小字里（`ui.sale_preview.risk`「珍贵装备：%s。再次点击确认后才会处理。」）。
5. **「收藏」完全不可发现**：背包底部提示只写"左键查看 · 与人物面板并开时可拖放装备"（[inventory_panel.gd#L239](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/ui/inventory_panel.gd#L239)），格内金色 ★ 标记（[item_slot.gd#L205-L209](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/ui/item_slot.gd#L205-L209)）没有图例。玩家不知道有右键收藏，也不知道为什么某些格子卖不掉（原因文案只写"已收藏，先取消收藏才能出售"）。
6. **浮窗叠层**：无遮罩可拖动浮窗 z_index 3000，与背包面板并存，初始位置在视口上方 18% 处，可能同时压住背包格；且没有"这是独立于背包的窗口"的视觉暗示。
7. **清单条目形态**：每件一个 `VBoxContainer` + `HSeparator`，100+ 装备时列表极长，只有滚动条，没有品质色彩分组/折叠，没有搜索。

### P4 单件快卖路径缺失

背包格现有的 4 种操作：左键双击=穿戴、左键拖放=移动/穿戴、右键=收藏、（面板按钮）整理/扩容/出售。

**没有任何"卖掉这一件"的快捷操作。** 以前靠「筛选阈值 + 一键卖出」，现在只剩"打开清单勾选"或"去货郎拖进托盘"。对"我只想卖掉手上这一件蓝装"这个极高频动作，步数反而变多了。

## 3. 优化方向

### 方向 A：先修默认规则（不改交互，改动最小，见效最快）

| 编号 | 改动 | 效果 | 代价 / 风险 |
|---|---|---|---|
| **A1** | 品质上限从 `uncommon` 提到 `rare`，或新增第 4 预设「清仓：稀有及以下、零星、低至少 N 级」 | 绿装进入默认勾选候选 | 稀有装可能含好词条 ⇒ 但仍有 `upgrade` + 零星保护兜底；且收藏可手动排除 |
| **A2** | 等级判据从固定的「低 10 / 5 级」改为**「套起点低于玩家当前套起点」**（`ItemFactory.tier_start_for_template(itemId) < ItemFactory.dynamic_tier_start(playerLevel)`） | 与「十级一套」模型对齐，语义可解释为"旧套装"，当前档装备不再被无意义排除 | 需要处理**循环套**（`tier_start_for_template` 恒为 51，见 [item_factory.gd#L43-L67](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/item_factory.gd#L43-L67)）：满级循环装备必须按 `dynamic_tier_start(level)` 口径，否则会全部被判为"当前档" |
| **A3** | `upgrade` 保护改为**只在与「已穿戴」比较时生效**（`preview.empty` 时不算 `score_increase`） | 空槽/低评分槽位不再全灭，新号与空槽多的角色恢复可用 | **这是本次最有争议的一条**：产品 14 §3 明确要求空槽也保护。若采纳 A3，需接受"可能卖掉本可穿上空槽的装备"；缓解手段是保留 `preview.ok` 与收藏 |
| **A4** | 预设项文案追加实时数字：`谨慎（将售出 37 件 / 4,120 金币）` | 点预设即见效果，解决"点了没反应" | `OptionButton` 改文案需在 `_refresh_footer` 或重建时同步，纯展示层 |

> A3 若被否决，至少应保留 A1 + A4：**绿装可自动卖 + 默认勾选数可见**，这两条就能消掉用户最大的挫败感。

### 方向 B：把「逐件勾」降成「几次点击」（中等改动）

| 编号 | 改动 | 效果 |
|---|---|---|
| **B1** | 清单顶部加「全选 / 全不选 / 仅选符合预设的 / 反选」 | 清包从 N 次勾选降为 1–2 次 |
| **B2** | 清单按品质分段（白 / 蓝 / 绿 / 黄 / 紫）分组 + 每段「全选本段」 | 直击"我有大量白/蓝/绿装"的场景 |
| **B3** | 排序（售价 / 品质 / 等级）+ 搜索 | 长列表可用性 |
| **B4** | 把「逐次累加的二次确认」改为**确认时一次性风险弹窗**（列出全部预设外装备名称与总价，只需一次确认） | 去掉"按钮文字跳变"与"点两次"的困惑 |
| **B5** | 背包格右键改为**上下文菜单**（收藏 / 出售 / 移入仓库），或 `Shift+左键` = 快速出售单件 | 补回 P4 缺失的单件快卖 |
| **B6** | 背包提示行补一句"右键装备可收藏（★），收藏不会被批量出售" | 补回收藏可发现性 |

### 方向 C：重做入口语义（较大改动，长期）

| 编号 | 改动 | 说明 |
|---|---|---|
| **C1** | 把一个「出售装备」拆成两个明确动作：**「一键清包」**（按预设直接结算，1 次点击）+ **「挑选装备」**（打开清单精修） | 恢复"字面语义 = 行为"的一致性，最贴合用户"快速卖出"的原话 |
| **C2** | 玩家自定义保留规则以**可视化面板**暴露（收藏 / 星级门槛 / 品质门槛 / 套装档门槛），预设只是其快捷组合 | 回到"规则可见"，但用可视化替代旧的两个数字 SpinBox，与产品 14 §7"不同时保留两套可见配置"不冲突 |
| **C3** | 清单改为**反选思路**：默认全部勾选，玩家取消要留的 | 契合"清包"心智（"我要扔掉的比我要留的多"，这是背包爆仓时的真实分布） |

## 4. 推荐组合与 trade-off

**建议分两步，先小后大：**

**第一步（推荐先做，改动集中在一个策略文件 + 文案）**
- A1（绿装纳入默认）+ A4（预设项显示实测件数与金额）+ B6（收藏提示）
- 结论：不动交互骨架，就能把"一件都勾不上"变成"一眼看到会卖多少、一键确认"。

**第二步（体验层补齐）**
- B1 + B2（全选 / 按品质分段全选）→ B4（一次确认）→ B5（右键菜单补单件快卖）
- A2（套装档判据替代等级差）建议与第一步同批评估，因为它直接决定"当前档装备能不能卖"，是 P1 的第二个大头。

## 7. 「积极」预设重定义分析（追加，针对「不管等级、白蓝绿都能快卖」的诉求）

### 7.1 诉求与现行定义的差距不止一处

用户诉求：**选定「积极」时，不限制装备等级，白 / 蓝 / 绿装都要能快速卖出。**

现行「积极」= `{level_gap: 5, max_quality: "uncommon"}`（[sell_gear_policy.gd#L13](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/sell_gear_policy.gd#L13)）。逐项对照：

| 诉求 | 现行规则是否满足 | 需要改的键 |
|---|---|---|
| 不看装备等级 | ✗（`level_gap = 5`） | `level_gap` |
| **绿装（稀有 rare）可卖** | **✗ 被硬性排除** | `max_quality` → `rare` |
| 白装（普通）可卖 | ◜ 受等级与评分保护双重限制 | 见下 |
| 蓝装（优秀）可卖 | ◜ 同上 | 见下 |

> **关键提醒**：用户在反馈里点名了"绿装"，但**绿装被挡的原因不是等级，而是 `max_quality` 只到 `uncommon`**（[sell_gear_policy.gd#L42-L43](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/sell_gear_policy.gd#L42-L43)）。因此**只删掉等级条件，绿装仍然一件都卖不掉**——两项必须同批改。

### 7.2 技术根源：等级差规则与「十级一套」装备模型语义错配

装备是**十级一套**模型（《53-装备十级一套改造分析与方案》）：型号 `tierBases` 以 1 / 11 / 21 / … / 51 为套起点，而**同一套内各实例的 `requiredLevel` 分布在 `[套起点, 套起点 + 9]`**（[item_factory.gd#L105](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/item_factory.gd#L105) 校验 `required_level >= tier_start and required_level < tier_start + 10`）。

现行判据却是"**等级差**"（`requiredLevel ≤ playerLevel − gap`，gap = 10 / 10 / 5），两者语义不匹配：

- 玩家 Lv60、装备属 51 套（`requiredLevel ∈ 51…60`）时，`gap = 10` 要求 `requiredLevel ≤ 50` ⇒ **整个当前套被全数排除**；
- `gap = 5` 要求 `requiredLevel ≤ 55` ⇒ 在**同一个套内按等级线性切一刀**："同套里等级低的那几件能卖、高几级的那几件不能卖"。

这就是"等级限制不合理"的技术根源：**它并没有在表达"旧套装可以卖"这个有意义的规则，而是在同一套装内部按数字切一半。** 正确的表达应该是「套起点是否低于玩家当前套起点」，或者对该预设**直接不设等级条件**。

附带记录一处口径不一致：《14-背包装备批量出售预设与本次勾选产品方案》§3 写「负阈值自然匹配不到装备」，但按实现公式 `放行 ⟺ requiredLevel ≤ playerLevel − gap`，**负 gap 反而会放行高于角色等级的装备**，与该表述相反。修正文档时需一并澄清（实现层未见对负 gap 的额外兜底）。

### 7.3 关键耦合：空槽会把 `upgrade` 保护放大成"全灭"

[equipment.gd#L93-L100](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/equipment.gd#L93-L100)：

```gd
static func auto_slot_for(slots: Dictionary, item: Dictionary) -> String:
	...
	for sid in ids:
		if slots.get(sid) == null:
			return sid          # ← 只要有一个兼容空槽，就优先返回该空槽
```

配合 [equipment.gd#L134-L140](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/equipment.gd#L134-L140) 的 `worn_score = score({}) = 0`：**任何评分 > 0 的装备，只要它有任何一个兼容槽位是空的，就会被判 `score_increase = true`，落入 `upgrade` 保护、不被任何预设默认勾选。**

后果：**只要某类槽位存在空位，该类装备就 100% 无法自动批量出售。** 双槽类（戒指 / 护腕 / 护膝 / 手镯）是重灾区——玩家只戴一只戒指、另一只空着，则背包里**所有戒指**都被 `upgrade` 挡住。

⇒ 结论：**去掉等级门槛若要真正生效，必须同时决定空槽语义**（即本文 §3 的 A3 / §7.6）。二者不是并列可选项：不同时处理，改动在有空槽的角色上等于没改。

### 7.4 建议的「积极」精确定义

| 条件 | 现定义 | 建议定义 | 说明 |
|---|---|---|---|
| 品质 | ≤ 优秀（蓝） | **≤ 稀有（绿）** | 用户点名绿装，必须放开 |
| 等级 | 低至少 5 级 | **不限等级** | 诉求核心；用"不含 `level_gap` 键"显式表达，而非哨兵数字 |
| 星级 | `star > 0` 排除 | **保留** | 06 §6.2 升星是主要金币消耗，误卖 = 烧掉已投入金币 |
| 收藏 | 排除 | 保留 | 玩家自治的最后一道闸 |
| 不可出售 | 排除 | 保留 | 规则边界 |
| 评分保护 | 优于默认替换槽则不勾 | **保留**（空槽取舍见 §7.6） | 见 §7.5 说明 |

**实现形状建议**：把 `level_gap` 改为**可选键**——`RULES[preset]` 不含该键即表示"不限等级"，`entry()` 中改为 `if rule.has("level_gap")` 才附加 `level` 理由。这样"积极 = 无等级门槛"由数据层显式声明，而不是靠 `gap = 9999` 或负 gap 之类的哨兵值去表达。

### 7.5 三个预设的建议重定义（对照）

| 预设 | 现定义 | 建议定义 | 理由 |
|---|---|---|---|
| 谨慎（默认） | 低 10 级 + 白装 | **不变** | 首发期防误卖，保持保守 |
| 标准 | 低 10 级 + 白/蓝 | **旧套档（`tier_start < 当前套档`）+ 白/蓝/绿** | 用"旧套"替代"低 10 级"，与十级一套模型对齐，语义可解释 |
| 积极 | 低 5 级 + 白/蓝 | **不限等级 + 白/蓝/绿** | 玩家已明确表达清包意图，等级门槛在此纯属干扰 |

> 注意：保留 `upgrade` 保护后，"积极"的实际语义是「**卖掉所有不优于现有穿戴的白 / 蓝 / 绿装，不看等级**」。这正是安全且符合直觉的定义——真正该留的（比身上强的）仍会被挡住，等级这层是冗余的。

### 7.6 空槽语义的两个候选（需拍板）

| 候选 | 规则 | 效果 | 风险 |
|---|---|---|---|
| **V1（推荐）空槽不计入保护** | `stronger = not preview.empty and score_increase` | 有空槽的槽类恢复正常批量出售 | 可能卖掉"本可填进空槽"的装备；但这类装备相对空槽(0 分)只是微弱为正，且可用收藏排除 |
| **V2 空槽仍保护，仅补文案** | 保持现行为，清单对该类行写"可用于空槽，未默认勾选（可手动勾选）" | 只解决"看不懂"，**不解决"卖不掉"** | 用户核心诉求落空 |

> 倾向 V1。空槽保护的本意是"别把你还没穿上的好东西卖了"，但当背包里同槽装备成堆时，它的实际效果是"该槽类什么都卖不掉"。折中方案 V1′（"该槽类背包内候选 ≥ N 件时才关闭保护"）会引入更难向玩家解释的参数，不如 V1 直白。

### 7.7 预期效果（Lv60 举例）

场景：14 槽全满，背包 120 件本套（51 套）白 / 蓝 / 绿，星级 0、未收藏。

| 预设 | 现行为默认勾选 | 按 §7.4/§7.5 建议后 |
|---|---|---|
| 谨慎 | 极少（gap=10 排除整档） | 不变 |
| 标准 | 极少 | 约"旧套"部分（具体数值待定） |
| 积极 | 个位数 | **接近全部**（仅剩 `upgrade` 拦下的少数高评分件 + 已升星件） |

若存在空槽（例如未戴第二只戒指）：按 **V1** 该槽类同样恢复正常；按 **V2** 仍为 0 件。

### 7.8 结论

1. 用户对"等级限制不合理"的判断**成立**——该规则与十级一套模型语义错配，无法用数字阈值表达"旧套可以卖"；
2. 「积极」应当**不限等级**，但**必须同时**把 `max_quality` 提到 `rare`，否则绿装仍然卖不掉；
3. 空槽语义（§7.6）是本次改动的**必要伴随项**，不处理则改动在多空槽角色上无效；
4. 星级保护建议保留，它是防止烧掉升星投入的最低成本护栏。

#### 锁定的三预设参数

| 预设 | 品质上限 | 等级条件 | 星级 | 收藏 | 不可售 | 评分保护 |
|---|---|---|---|---|---|---|
| 谨慎（默认） | common | `requiredLevel ≤ playerLevel − 10` | 排除 | 排除 | 排除 | 仅与**已穿戴**比较 |
| 标准 | **rare** | **`suit(item) < current_suit(playerLevel)`** | 排除 | 排除 | 排除 | 仅与**已穿戴**比较 |
| 积极 | **rare** | **无** | 排除 | 排除 | 排除 | 仅与**已穿戴**比较 |

#### 套档判据的精确定义（本次最关键的技术口径）

**不要用 `ItemFactory.dynamic_tier_start()` 做这个判据。** 它在 `level ≤ 60` 时返回的是**等级本身**（[item_factory.gd#L43-L48](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/item_factory.gd#L43-L48)：`if level <= SOFTCAP_LEVEL: return level`），拿它当"当前套档"会让 L60 玩家的 `current_suit = 60`，从而把**当前的第 51 套**误判成"旧套"默认出售 —— 正好卖错东西。

正确的计算方式是**按十级带宽取套起点**（`EquipmentFusion.tier_start` 已经在用，[equipment_fusion.gd#L11-L15](file:///Users/fungleo/Sites/GameProjects/DegenerateAge/scripts/systems/equipment_fusion.gd#L11-L15)）：

```
suit(requiredLevel)   = floor((requiredLevel − 1) / 10) * 10 + 1     # 实例所属套起点
current_suit(level)   = floor((level − 1) / 10) * 10 + 1             # 玩家当前套起点
标准默认出售 ⟺ suit(item) < current_suit(playerLevel)
```

逐档验算：

| 玩家等级 | `current_suit` | 第 51 套装备（`suit = 51`）是否被"标准"默认出售 | 是否正确 |
|---|---|---|---|
| L50 | 41 | 否（51 > 41） | ✓ 高于当前的装备不卖 |
| L55 | 51 | **否**（51 = 51） | ✓ 当前套不卖 |
| L60 | 51 | **否** | ✓ 当前套不卖（这正是 `gap=10` 会卖错的场景） |
| L70（循环） | 61 | 是（51 < 61） | ✓ 上一档可卖 |
| L1000（循环） | 991 | 是 | ✓ 循环套逐档正确 |

该公式对**循环套**同样成立（L1000 的装备 `requiredLevel ∈ 991…1000` ⇒ `suit = 991`），因为它只依赖实例的 `requiredLevel`，不依赖 `tierBases` 的静态键。

> **工程建议**：把上述公式从 `EquipmentFusion.tier_start()` 提升为**共享方法**（放 `ItemFactory` 或 `Equipment`），由铁匠合成与出售策略共用同一入口，避免两处公式日后各自漂移。跨系统直接调用 `EquipmentFusion` 不合适（它是铁匠私有规则层）。
