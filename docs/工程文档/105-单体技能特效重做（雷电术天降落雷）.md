# 105 · 单体技能特效重做：雷电术改「天降折线落雷」

> 现象：玩家报「雷电术的特效是画一个圆圈，但这是单体攻击，看着不合适」。
> 状态：**方案 A 已落地**（2026-10-29）。本文 §一 是代码路径推导（每条都给了文件行号，可复核），
> §三 是实际实现口径，§七 是落地后的验证结果。

---

## 一、根因：`else` 兜底把「单体」当成了「圆形 AoE」

### 1.1 代码路径

`player.cast_skill()` 把技能的 `shape` 原样传给提示特效：

```gdscript
# scripts/entities/player.gd:666-670
var range_fx := preload("res://scripts/systems/skill_range_fx.gd").new() as Node2D
range_fx.shape = String(skill.get("shape", "circle"))
range_fx.radius = float(skill.get("range", 1.0)) * Iso.TILE_W
```

而 `skill_range_fx.gd` 的绘制**只有一种具名形状**，其余全部落进 `else`：

```gdscript
# scripts/systems/skill_range_fx.gd:22-32
func _draw() -> void:
	var alpha := 1.0 - age / 0.3
	var ink := Color(0.46, 0.91, 0.88, 0.6 * alpha)
	if shape == "cone":
		... 扇形
	else:                                    # ← single / circle / 未知形状 全走这里
		GroundFx.fill(self, Vector2.ZERO, radius, Color(0.46, 0.91, 0.88, 0.10 * alpha))
		GroundFx.outline(self, Vector2.ZERO, radius, ink, 2.0, 40)
```

`lightning` 的 `shape` 是 `"single"`（`data/skills.json`），于是它被画成一个**地面圆盘**。

### 1.2 这个圆盘有多大

| 量 | 值 | 依据 |
|---|---|---|
| `range` | 6.5 格 | `data/skills.json` |
| `Iso.TILE_W` | 64 px | `scripts/systems/iso.gd:11` |
| 地面半径 | **416 px** | 6.5 × 64 |
| 屏幕横向直径 | **832 px** | 视口宽 1280 的 **65%** |
| 屏幕纵向直径 | **416 px** | `GROUND_SQUASH = 0.5`，视口高 800 的 **52%** |

也就是说：放一次雷电术，屏幕上有**一块占横向 65%、纵向 52% 的半透明椭圆**淡入淡出 0.3 秒。这就是玩家看到的「圆圈」。

### 1.3 语义为什么是错的

`skill_range_fx` 的 `radius` 参数被赋成 `range × TILE_W`，但 `range` 这个字段在两种技能上含义不同：

| shape | `range` 的真实含义 | 当半径画是否正确 |
|---|---|---|
| `circle`（火焰喷发 3.5 / 陨石术 7 / 旋风斩 2.0） | **AoE 半径**，以自身为中心 | ✅ 正确 |
| `cone`（冰咆哮 4.5 / 裂地斩 2.5） | **扇形半径**（射程） | ✅ 正确 |
| **`single`（雷电术 6.5 / 破甲重击 1.5）** | **到目标的距离上限** | ❌ **荒谬** —— 单体没有「范围」可提示 |

单体技能画范围圈，等于告诉玩家「这一片都会被打」，实际只打一只。这是**误导性提示**，不是「画得不好看」。

### 1.4 影响面：不止雷电术

| 技能 | 职业 | shape | range | 现状 | 判断 |
|---|---|---|---|---|---|
| `lightning` 雷电术 | 法师 | single | 6.5 | 416px 圆盘 | 🔴 玩家报障的就是它 |
| `armor_break` 破甲重击 | 武士 | single | 1.5 | **96px 圆盘** | 🔴 同根因，只是小到没被注意 |
| `flame_burst` 火焰喷发 | 法师 | circle | 3.5 | 224px 圆盘 | ✅ 真 AoE，正确 |
| `meteor` 陨石术 | 法师 | circle | 7 | 448px 圆盘 | ✅ 真 AoE，正确 |
| `whirlwind` / `spirit_storm` | 武士 | circle | 2.0 / 4.0 | 圆盘 | ✅ 真 AoE，正确 |
| `frost_roar` / `earth_cleave` | — | cone | 4.5 / 2.5 | 扇形 | ✅ 正确 |
| `basic_fireball` / `basic_slash` | — | single | — | 不进 `cast_skill` | ✅ 不受影响（见下） |

`basic_fireball` 是法师普攻、`basic_slash` 是武士普攻，都在 `cast_skill` 第 637 行被 `skill_id == PlayerClass.basic_skill()` 提前挡掉，走的是 `perform_attack()` —— 因此**普攻从来没画过圈**，只有技能画了。这也解释了为什么玩家是先注意到雷电术，而不是火球。

### 1.5 现在的雷电术一共画了什么

| 层 | 实现 | 时长 | 评价 |
|---|---|---|---|
| 地面大圆盘 | `skill_range_fx`（本文 §1.1） | 0.3s | ❌ 语义错误 |
| 飞行小蓝球 | `player_projectile.gd`，半径 6px | 0.14s | ⚠️ 「扔一颗球」不像雷 |
| 角色攻击动作 | `sample_art.attack()` | — | ✅ 保留 |
| 目标锁定环 | `monster.gd:1293`，青色环 radius+7 | 持续 | ✅ **已经有了**，单体不缺「打谁」的提示 |

最后一行是关键：**锁定的怪脚下本来就有一圈 2.5px 的青色环**。所以单体技能完全不需要另画范围，玩家已经知道打哪一只。

## 二、设计原则

1. **单体不画范围。** 范围提示的语义是「这一片都会被打」。单体画它 = 骗玩家。
2. **雷电要有「雷」的身份。** 雷电是**瞬时天降**，不是「扔一颗球」。现在的飞行小球是通用远程实现，对火球合适，对雷电不合适。
3. **落点必须看得见，但不是范围。** 用**落点光斑**（半径约 18px ≈ 1/4 格）表达「打在这一只身上」，与 416px 的圈是两个数量级。
4. **数据驱动，不硬编码技能 id。** 遵循项目既有口径：技能归属读 `skills.json` 的 `class`，判普攻读 `basic: true` 标记。本次引入 `fx` 字段。

## 三、新特效：天降折线落雷（方案 A 详设）

### 3.1 时间轴（总 0.26 s）

| 阶段 | 时间 | 画面 |
|---|---|---|
| **预兆** | 0—0.05 s | 目标头顶一道**细竖光柱**：宽 2px，从 `y = -150` 垂到 `y = -40`，蓝白 `#9ad8ff`，alpha 0.22。给玩家「要劈了」的预告 |
| **主雷** | 0.05—0.14 s | 从 `y ≈ -170` 到目标身体中心（`y ≈ -12`）画 **3 条锯齿折线**：主路宽 3px 白芯 + 两条副路（横向偏移 ±11px、宽 1.5px、淡蓝），**每帧重算锯齿横向偏移** ⇒ 噼啪抖动。落点同时炸开：地面光斑（`GroundFx.fill` 半径 18px）+ 一圈快速外扩冲击环（`GroundFx.outline` 18→34px，2 帧内消失） |
| **余电** | 0.14—0.26 s | 折线变细变淡；向两侧甩出 2 条短分叉弧；落点留一颗光点渐隐 |

### 3.2 几何要点

- **起点**固定在目标上方，不是固定屏幕高度：`target.global_position + Vector2(0, -170)`。跟角色走，玩家移动时不脱节。
- **终点**取 `target.global_position + Vector2(0, -12)`（怪物绘制中心在 `-radius * 0.6`，见 `monster.gd:1353`，radius 17—22 ⇒ 约 -10 ~ -13）。闪电**穿过身体**而不是停在头顶。
- **落点光斑**在 `target.global_position + Vector2(0, 8)`（脚下地面，与怪物的阴影同高），走 `GroundFx` 的椭圆口径。
- **锯齿生成**：把起点到终点按 8 段等分，每段横向偏移 `randf_range(-7, 7)`，两端点偏移为 0（保证首尾精确贴合）。

### 3.3 颜色

| 元素 | 颜色 | 说明 |
|---|---|---|
| 主路芯 | `#f2fbff` | 近白，最亮的 1px |
| 主路外光 | `#9ad8ff` | 与 `SPELL_COLORS["lightning"]` 一致 |
| 副路 | `#9ad8ff` alpha 0.45 | 比主路淡 |
| 落点光斑 | `#e8f8ff` alpha 0.30 | 地面，压扁 |
| 冲击环 | `#9ad8ff` alpha 0.55 | 快速外扩 |

### 3.4 跳过飞行投射物

雷电术**不再生成 `player_projectile`**，改由 `thunder_fx` 直接表现。

- 伤害仍在调用点即时结算（`player.cast_skill` 第 677—692 行），**一行不动**。
- `player_projectile.gd` 顶端注释写死了「纯视觉、不参与结算」，本次改动不触碰这条契约。
- `mage_ranged_test.gd:129` 断言的是**普攻**产生 1 个投射物（走 `perform_attack`），不受影响；技能侧目前零断言。

### 3.5 为什么这次可以用折线，而工程 104 说折线是坑

工程 104 的结论是「**2400 件 × 每帧** 重画抗锯齿折线 = 54 ms/帧」。本处的量级完全不同：

| | 工程 104（掉落物装饰圈） | 本次（雷电术） |
|---|---|---|
| 同时存在的节点数 | 最多 2400 | **最多 1**（寿命 0.26s < CD 0.6s） |
| 每帧折线数 | 2400 × 4 = 9600 条 | 3 条（每条 9 点） |
| 单次预算 | 22.6 µs × 2400 | 约 3—5 µs |

结论：**这里用折线是对的**，因为闪电的形状每帧都在变，无法预渲染。但必须在 `thunder_fx.gd` 顶端写死这条判据，防止以后有人照抄到高频路径上。

## 四、三个方案

| | 做法 | 改动面 | 效果 | 风险 |
|---|---|---|---|---|
| **A｜去圈 + 天降落雷（推荐）** | 新增 `thunder_fx.gd`；`single` 分支不再画范围；雷电跳过飞行投射物；`skills.json` 加 `fx` 字段 | 新增 1 文件 + 改 3 处 | 「雷」的身份确立，语义正确 | 折线抖动观感需实机确认 |
| **B｜只去圈** | `single` 分支直接返回，什么都不画 | 1 个分支 | 圈子消失，但雷电术变成「一颗小蓝球飞过去」+ 无落点反馈 | 最省事，但「雷」感仍缺失 |
| **C｜去圈 + 落点爆闪** | 新增落点光斑 + 冲击环（0.18 s），不做空中折线 | 1 个分支 + 1 个小文件 | 有落点确认，比 B 强 | 玩家看不出这是「雷」，仍像一颗球 |

三个方案都会顺手修掉 `armor_break` 的 96px 圆盘（同根因，一行分支的差别）。

## 五、风险

- 🔴 **`else` 兜底会复活**。方案 A 不能只加一个 `if shape == "single": return`，必须把 `else` 改成**只画 `circle`**，未知形状画什么都不画 + `push_warning`。否则以后新增形状（如 `line`）会继续被静默画成圆 —— 这与坑清单第 64 条「过宽防线在前提消失后静默变成新 bug」同构。
- 🔴 **`radius` 字段对 `single` 无意义**。`skill_range_fx.radius` 对 `single` 仍会被赋 416，若将来有人「顺手」拿它做别的提示就会重现本 bug。`single` 分支必须显式不读 `radius`。
- 🔴 **数据驱动不能退成硬编码**。`player.gd` 里若写 `if skill_id == "lightning"`，以后新增瞬发技能又得改代码。必须读 `skill.get("fx", "")`。
- ⚠ **视觉一致性**：改完雷电后，火焰喷发 / 陨石术仍是**大圆盘**（224 / 448px）。那不是 bug —— 它们是真 AoE，圆盘就是它的正确语义。玩家若问「为什么火圈还在」，属于预期。
- ⚠ **抖动的可读性**：每帧完全随机重算会像「噪点闪烁」。建议用「每 2 帧重算一次」而不是每帧，肉眼更接近电弧的持续放电。
- ⚠ **`sample_art.attack()` 的方向参数**：现在传的是 `目标位置 - 自身位置`。落雷不改变这一行，但改完后角色仍会「朝目标挥一下」，属正常施法动作，保留。

### R1 相对原方案的一处改进（必须记下来）

原方案写的是「拆出 `single` 分支」。落地时改成**抽纯函数 `draws_ground()` 作为唯一判据**，原因：

> 如果 `draws_ground()` 只给测试用、`_draw` 里另写一份 `if shape == "single": return`，
> 那么**测试守的是测试**，把生产代码那一段删掉照样绿 —— 这正是坑清单第 37 条
> 「期望值复用被测常量 ⇒ 常数改坏照样绿」的变体。

现在 `_draw` 第一行就是 `if not draws_ground(shape)`，改坏这个函数会同时让逻辑层与行为层红。

同时 `_draw` 里**刻意不写 `else`**：`cone` 分支之后直接是 `circle` 的绘制，注释写明「到这里只可能是 circle」。
兜底分支承担语义分派正是本次 bug 的成因，不能在新代码里留同款。
