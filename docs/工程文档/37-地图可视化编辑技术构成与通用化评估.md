# 地图可视化编辑：技术构成、能力现状与通用化评估

本文回答两件事：① 当前游戏地图在工程上是怎么构成的；② 「让策划自己在画面里编地图、再交给工程转换成游戏可用数据」这个想法是否成立、缺什么、下一步该做什么。

本文是**评估文档**（现状 + 差距 + 建议）。工作流方案见 `docs/素材设计/22-可视化地图编辑工作流建议.md`；编辑器自身的交付验收见 `docs/工程文档/35-幸存者营地可视化编辑器首版验收.md` 与 `36-幸存者营地地面与碰撞可视化编辑扩展.md`。本文不含实现代码，也不改变任何地图数据。

---

## 一、结论摘要

1. **你的想法方向是对的，而且项目已经按这条路线走了一段**：仓库里已有一个内嵌 Godot 编辑器的营地专用地图工具（`addons/camp_map_editor/`），支持画地面装饰、编辑碰撞轮廓、移动整体物件、调整道路控制点，并带「保存草稿 → 校验 → 重建正式数据」的导出链。
2. **你直觉里那句「编辑结果不能直接用、需要 AI 转换」需要修正**：需要的是**编译器**，不是 AI。这条编译链项目里已经存在；AI 只在「要产出新素材 / 新增物件类型」时才需要介入。
3. **四条诉求对现状的符合度**：摆放物件＝部分支持（只能移动，不能增删）；改不可走＝只能通过改实体碰撞间接影响，不能直接手绘；改每格贴图＝营地上已有 128 像素装饰层可编辑，但逻辑格贴图与基底循环地纹仍不可编辑；改地图网格尺寸＝不支持。
4. **最大结构性约束**：**可行走掩码不是画出来的，是从几何多边形编译出来的**。这决定了「直接涂不可走区」的诉求需要单独设计，不能顺手加。

## 二、地图的技术构成（三层 + 一条编译链）

### 2.1 逻辑层：地图事实源

| 文件 | 关键字段 | 用途 | 证据 |
| --- | --- | --- | --- |
| `data/maps.json` | `size{w,h}`、`exits[].cell`、`entrances{}`、`spawnPoints[].cells`、`npcs[].cell`、`carterArrival`、`worldRect`、`layoutPath`、`layoutVersion` | 地图注册表；格子坐标表达出入口、刷怪点、NPC、落点 | `data/maps.json` camp 条目 |
| `data/layouts/<id>.json` | `grid_size`、`points{}`、`walkable_rows[]` | 逐格可行走掩码（`1`=可走，`0`=不可走）与命名逻辑点 | `data/layouts/camp.json`（110×110，`0` 共 7206、`1` 共 4894） |

`scripts/world/ground.gd:192` 的 `_load_map()` 从 `maps.json` 读 `size` 决定 `grid_size`；`ground.gd:93-95` 断言 `CaveLayout.size == grid_size`，即**地图尺寸、布局掩码、运行时网格三者必须一致**。

### 2.2 美术层：画布坐标与运行素材

- `data/map_art/camp_whitebox_v2.json`：`reference_canvas [1672,941]`（屏幕画布像素）、`world_rect [-1600,-2660,3200,1800]`（游戏世界像素）、`grid_size [110,110]`、`spawn`、`main_road`/`branches`（道路控制点）、`entities[7]`（含 `footprint` 碰撞多边形、`visual` 轮廓、`art_rect`、`art_foot_y`）、`fences[4]`、`targets{}`。
- `assets/maps/camp_style_full_b_v2/manifest.json`：`ground_tile`、`road_overlay`、`objects[11]`（每项 `rect`/`foot_y`/`back`/`front`/`pixel_art`）。
- `data/map_art/camp_ground_palette.json`：`cell_size: 128` + 4 种地面笔刷（草簇／碎石／石板／土纹，各带 `source_rect` 与运行资源路径）。对应编辑的上限是 **14×8＝112 个 128 像素装饰格**。

### 2.3 运行时渲染：两条并行路径

`scripts/world/ground.gd`（`IsoGround`）按地图类型分叉：

- **营地路径**（`_load_camp_whitebox()` / `_load_camp_final_art()`，`ground.gd:112-178`）：一张 2048×2048 循环地纹 + 可选可编辑覆盖层 + 纯道路层 + 11 个整体实体按 `back`/`front` 分层，`front` 用 `foot_y` 换算世界 Y 作为 `z_index` 参与遮挡排序。
- **其他地图路径**（`_draw_tile_floor()`，`ground.gd:460-499`）：64×32 图集，**每格贴图由程序算出**——`variation := posmod(col*73 + row*37 + col*row*11, 19)`（`ground.gd:479-480`），道路格另有数据来源 `_chapter_one_road_tile_index()`（`ground.gd:511`，四邻位掩码选边缘／转角纹理）。整层一次性 `draw_mesh` 合批。

### 2.4 编译链：白盒 → 正式数据

```
data/map_art/*.json（白盒，人/工具编辑）
   ├─ tools/build_camp_whitebox.py   → data/layouts/*.json（walkable_rows）、maps.json 坐标
   └─ tools/build_camp_style_full_b_v2.py → assets/maps/<style>/（地纹、道路层、实体分层、manifest）
                                  ↓
                     scripts/world/ground.gd（加载装配）
```

`tools/apply_camp_map_editor.py:195-213` 的 `compiled_rows()` 说明了**可行走的来源**：对每个格子判断是否在世界矩形内缩 `CLEARANCE` 之内、是否贴近任一 `footprint`/`fence` 多边形，落在多边形邻近范围即为不可走。

## 三、关键事实：可行走是「编译出来的」

这是全文最重要的一条，直接决定「我要涂哪里不能走」这个诉求的实现方式。

- 你在编辑器里拖动一栋房子或改它的碰撞轮廓，`compiled_rows()` 会重算整张 110×110 掩码，并校验 NPC 格、出入口格、出生格、刷怪格与**从出生点到各服务点的连通性**（`apply_camp_map_editor.py:216-260`），任何一项被破坏就整次拒绝。
- 也就是说：**目前不存在「直接编辑 walkable_rows」的入口**。不可走区是实体碰撞的副产品。想要「手绘不可走区」，需要新增一层与几何编译并存/叠加的掩码来源，并明确两者的优先关系与冲突处理——这是一次架构决定，不是加个画笔。

## 四、现有可视化编辑器的能力与边界

`addons/camp_map_editor/`（Godot 编辑器插件，`project.godot` 已启用；主屏幕标签「营地地图」）：

| 4 种模式 | 能做什么 | 边界 |
| --- | --- | --- |
| 绘制地面 | 在 128 像素格上点涂／拖涂四种笔刷，擦除恢复底纹；只改外观 | 不改通行；不能换基底循环地纹；上限 112 格 |
| 编辑碰撞 | 拖顶点改整体碰撞轮廓，Shift 加点、右键删点，最少 3 点；改碰撞不拉伸贴图 | 不能超出画布、不能自交、不能挡 NPC／切断通路 |
| 移动整体物件 | 拖动 7 个实体、4 段围栏，整体移动美术 + 脚底层级 + 碰撞 | **不能新增／删除物件** |
| 调整道路节点 | 拖动主路与支路控制点，应用后重建道路贴图 | 不能改控制点数量 |

共用能力：撤销／重做、保存草稿、应用到游戏、重新载入；滚轮缩放、中键平移。

导出机制（值得保留的设计）：草稿写 `data/map_art/camp_editor_draft.json`，**游戏不加载它**；「应用到游戏」校验正式源哈希（`base_hash`）后调用两套编译器重建，任何失败回滚原文件，成功后删除草稿。别的任务在编辑期间改了正式布局则拒绝应用（`apply_camp_map_editor.py:263-293`）。

## 五、你的四条诉求 vs 现状

| 你的诉求 | 现状 | 差距 |
| --- | --- | --- |
| 修改地图的网格 | 网格尺寸写死在 `maps.json.size` / 白盒 `grid_size`；编辑器明确不支持改尺寸 | 需改尺寸则牵动 `maps.json`、`layoutPath`、`worldRect`、三处一致性断言与存档 `layoutVersion` 迁移 |
| 修改哪里不能走 | **只能通过移动实体／改碰撞轮廓间接影响**，掩码由 `compiled_rows()` 重算 | 缺「直接手绘不可走区」入口；需设计掩码叠加来源与优先级 |
| 修改每一个方格的贴图 | 营地已有 128 像素装饰覆盖层（`ground_patches` + `camp_ground_palette.json`）可编辑；**逻辑格贴图不可编辑**，其他地图的格贴图是程序按 `variation` 哈希算的 | 缺「逐逻辑格贴图」数据。若要做，须把 tile 选择从程序哈希改为可编辑数据，且必须保持整层合批 |
| 在上面摆放物件 | 只能移动现有 7 实体 + 4 围栏 | 缺「新增／删除物件」与配套素材库（稳定 ID、锚点、碰撞、前后分层规范） |

覆盖度大致是：**摆放类有了骨架，贴图类有了粗粒度版本，网格与不可走区还是空白。**

## 六、「需要 AI 转换」这句要修正

你的判断是「编辑器产出的东西不能直接用，要 AI 分析转换」。实际情况是：

- **转换工作已经工程化，且比 AI 更可靠**：草稿经过校验后由 `build_camp_whitebox.py` + `build_camp_style_full_b_v2.py` 编译成 `walkable_rows`、地纹、道路层、实体清单。这条链是确定性的、可重复的、失败可回滚的——这正是你想要的「转换」。
- **AI 的位置应该收窄到两件事**：① 产出并重排**新素材**（你明确说过自己没有美术天赋）；② 新增**物件类型**时的接库工作（锚点、碰撞轮廓、分层切图与规范登记）。
- 把「编辑器产物 → 游戏数据」交给 AI 逐次转换，等于放弃现有的确定性编译与校验（`base_hash`、连通性检查、回滚），是**降级**，不建议。

**判断**：你的真实需求不是「AI 转换」，而是「一个受校验约束的确定性编译入口」——它已经存在了。

## 七、通用化路线建议（按性价比排序）

1. **先固化现有营地工具，不要急着泛化**。让一次「画面里改 → 应用到游戏 → 实走验收」闭环真正跑顺；营地是最复杂的样板（9 个实体 + 4 段围栏 + 道路），跑通后其他地图反而更简单。
2. **把逐格贴图数据化**（收益最高）：把 `_draw_tile_floor()` 的 `variation` 哈希改成读取「每格 tile id」数据，缺省时回退到现有哈希，保证既有地图表现不变。这是「改每一个方格贴图」的正解，且不破坏合批。
3. **再加新增／删除物件**：需要先定素材库规范（稳定 ID、参考画布尺寸、允许旋转／翻转、脚底锚点、碰撞多边形、前沿分层），然后开放「从库拖入 → 自动生成 footprint → 重算掩码」。
4. **最后才是改地图尺寸**：这是改动面最大的一项（数据三处一致性 + 存档版本迁移），建议等 1–3 稳定后单独排期。
5. **手绘不可走区**单独作为一次架构决定来评估：明确它是与几何编译「二选一」还是「叠加」，叠加时谁优先级更高、如何提示冲突。

## 八、明确不建议的做法

- **不要逐格建 Sprite／节点／刚体**。`AGENT.md` §2、§4 明令禁止退回逐格节点与逐瓦片切换纹理；地面必须保持整层合批。
- **不要让游戏长期维护两套地图事实源**（例如 Tiled JSON 与白盒并存）。转换器只能作为体验验证，不能成为第二套正式数据。
- **不要让编辑器绕过校验直接写正式文件**。现有「草稿 + 源哈希 + 失败回滚」机制请保留。
- **不要为了编辑方便降低碰撞正确性、连通性或遮挡关系**。
