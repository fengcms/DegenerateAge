# 仓库「合成如意」功能实现方案

日期：2026-10-30。状态：已实施并完成定向验收。用户追加要求：钻石如意堆叠上限改为 999，其余如意保留 99。

## 1. 需求与现状

仓库增加「合成如意」按钮，一次点击自动合成仓库中的如意。比例固定为：4 铁→1 玉、4 玉→1 金、40 金→1 钻石。仅向上合成，无失败概率、无额外金币费用、不提供拆解。城镇仓库和超级随身令牌打开的仓库使用同一个入口和规则。

已核对的实现依据：

- `scripts/ui/warehouse_panel.gd` 已有双栏仓库、整理、金币兑换区，按钮使用 PanelChrome；新增入口可复用该面板。
- `autoload/game_state.gd::exchange` 与 `scripts/systems/gold_exchange.gd::plan` 已采用副本预结算、成功后提交的结构，可沿用这一分工。
- `Inventory.add` 会先检查整批容量，再合并已有堆叠并利用空格；上限通过 ItemUtil.stack_max 获取，不能硬编码 99。
- `RuneCharge.inventory_counts` 可按如意 ID 汇总跨堆叠数量。正式 ID 为 rune_iron、rune_jade、rune_gold、rune_diamond。
- 仓库容量配置为初始 40、上限 400 格（data/warehouse.json）；如意现有单价和重掷权重来自 data/runes.json。

设计依据为源码与配置分析；实施后的逻辑和窗口验收见第8节。性能成本为结构估计，未进行整帧性能对照。

## 2. 玩家规则

### 连续合成与余数

一次点击执行全量连续合成，而非每种只合一次。先把铁的可合成数量转成玉，再把原有玉和新玉一起转成金，最后把原有金和新金一起转成钻石。原有钻石原样保留。只读取和改动仓库；背包、穿戴如意均不参与。

设仓库原数量分别为 I、J、G、D，使用整数除法计算：

```text
玉产出 a = I / 4
铁剩余   = I % 4
金产出 b = (J + a) / 4
玉剩余   = (J + a) % 4
钻产出 c = (G + b) / 40
金剩余   = (G + b) % 40
钻最终   = D + c
```

如完全合成，铁剩余 0—3、玉剩余 0—3、金剩余 0—39。任何不足比例的余数都保留。

例：640 铁→160 玉→40 金→1 钻石；最终只有 1 钻石。

例：仓库 19 铁、3 玉、39 金、2 钻石：先产出 4 玉，再产出 1 金，最后产出 1 钻石；最终为 3 铁、3 玉、0 金、3 钻石。提示不能把过程中已继续消耗的玉、金误报为最终获得物。

### 生效与失败

按钮点击立即执行，无数量输入和额外确认，符合一键自动合成的需求。按钮 tooltip 常驻说明比例、仅仓库、连续合成、余数保留和不可逆。没有足够材料时置灰；即使直接调用业务接口，也返回明确失败原因。

仓库满不等于必然失败：合成可能释放格位，必须根据最终产物是否能放入判断。若最终状态无法容纳，整笔不执行，所有原物品保持不变；不部分合成、不移到背包、不自动出售、不生成地面掉落。

原材料被扣掉却未完全腾空的情况尤其需要检查：满仓时某个铁堆从 5 变为 1，并未释放格位，若玉没有可合并的堆和空位，就应拒绝。

## 3. 界面设计

按钮放在仓库栏标题操作区，与「整理」相邻，明确作用于右侧仓库。复用 PanelChrome.style_action 和现有字号、悬停、焦点样式，不另造原生按钮风格。两枚按钮在窄窗口和大字体下若撑宽标题行，则统一放进仓库栏下方操作行，不扩大物品网格设计宽度。

文案「合成如意」。tooltip 示例：

> 仅使用仓库中的如意，按 4 铁→1 玉、4 玉→1 金、40 金→1 钻石连续合成，余数保留。点击立即执行，不可撤销。背包如意需先存入仓库。

可用态与真正执行都调用同一个计划函数。失败时显示「没有足够的如意可合成」或「仓库空间不足，请腾出空位」。成功后在详情区给出数量前后对照，例如「合成完成：铁 19→3，玉 3→3，金 39→0，钻石 2→3」，toast 使用简短摘要，避免误报中间产物。

成功时批量发出一次 warehouse_changed，沿用仓库刷新和自动存档链路。不得逐枚刷新。弹框或其他模态界面打开时沿用当前输入拦截规则。

## 4. 工程结构

### 配置

建议在现有 data/warehouse.json 添加 runeSynthesis 配方数组，依次登记 sourceId、sourceCount、targetId、targetCount（目前均为 1）。保留既有仓库扩容字段。配方归仓库管理，不改全局 runes.json 的价格、掉落和效果，不混入 GoldExchange 的金币兑换对。

DataLoader 增加校验：配方恰好覆盖本次约定的三条升档关系；ID 必须引用如意模板；数量必须是正整数；无重复、无自环、无逆向边，顺序可连续处理；报告错误而非跳过错误配方。显示比例与执行计算读取同一配置。

### 纯计划层

新增 `scripts/systems/rune_synthesis.gd`，提供 `plan(store: Array) -> Dictionary`。不读写 GameState，不发信号、不保存。返回 ok、reason、store（成功后的容器副本）、before、after、每档转换次数。

计算流程：

1. 校验配置和容器相关如意数量，汇总跨堆叠数量。
2. 按三条配方做三轮整数运算，得出每种最终数量。无任何转换就返回不可合成。
3. 深拷贝仓库，先完成各档净减少的扣除；按仓库格序扣堆叠，耗尽置 null。
4. 全部扣除完成后，使用标准如意物品工厂和 Inventory.add 放入各档净增加量。这样不必为会继续升级的中间产物寻找格位，也可利用所有实际释放的空格。
5. 任一产物放不下就丢弃副本，返回失败；全部成功返回计划。

不清空重建全部如意堆，不自动整理仓库：未参与扣除的堆叠和其他物品保持原位置；新增量按现有合堆和空格规则放入。对受影响堆叠必须保留既有物品结构，不修改原始字典。

### 唯一提交入口

新增 `GameState.synthesize_warehouse_runes()`：同步重新生成计划，成功后一次替换 warehouse，再广播一次变更和结果提示。UI 不缓存可直接写回的旧仓库副本，不自己扣物品。

操作同步、无 await；每次点击重新计算，连续点击第一次合完后第二次自然不可合成，不重复发奖。若未来加入确认框，确认时必须重新计划，不能提交打开确认框时的快照。

### UI 接线与存档

warehouse_panel 新增按钮、刷新可用态和点击回调。初始化、仓库变化、打开面板时刷新；复用现有信号生命周期，不增加 _process 扫描。所有文本进入 localization.json。

不新增存档字段，不改 schema。仍保存原仓库物品数组；旧存档照常加载。运行成功后使用既有自动存档事件路径，不自行写文件。

## 5. 经济与效果影响

这是将多枚低档消耗品压缩成更强单枚的选择，不是总价值守恒兑换。按当前 runes.json：

| 转换 | 模板总价变化 | 重掷权重总和变化 |
|---|---:|---:|
| 4 铁→1 玉 | 1200→800 | 2→1 |
| 4 玉→1 金 | 3200→2000 | 4→2 |
| 40 金→1 钻石 | 80000→60000 | 80→4 |

实际售卖同样按六折计算，方向一致。高档如意能在四格限制下提供更高单次重掷收益，但连续合成会降低库存的累计用途和售价。按用户给定比例实施，不额外调整售价或掉落补偿；界面不宣称保值或总收益增加。本期不增加“保留若干低档”“只合某一档”选项。

## 6. 成本与生命周期

数据为三条配方，容器最多 400 格。点击/仓库变化时做有限次 O(N) 扫描、四类堆叠插入和一次 O(N) 深拷贝；不得按每四枚材料逐次循环，批量数量一次计算。只存在一个同步计划，无后台任务、计时器或资源缓存。副本在失败或提交后离开局部作用域释放。UI 只新增一个按钮，不新增逐帧工作。

## 7. 验收与实施节点

节点一：配置校验与纯计划层。覆盖 0、3、4、5 铁；3/4 玉；39/40/41 金；640 铁贯通；混合余数；多堆叠；已有钻石保留。确认失败不修改输入。完成并通过后单独 commit。

节点二：GameState 和 UI。覆盖成功只广播一次、重复点击无重复收益、背包不参与、无材料置灰、库存变化更新、城镇和随身入口一致、无装备/其他物品被扣。完成并通过后单独 commit。

节点三：容量、存档与窗口验收。覆盖满仓可合堆成功、扣除释放位置后成功、余数占位导致产物放不下整笔失败、跨多个输出堆、保存读档数量一致。窗口检查默认尺寸、大字号/高 UI 缩放、窄窗口、tooltip 和成功提示遮挡。同步产品基线与交接记录，单独 commit；共享测试新增覆盖，不放宽已有断言。

逻辑测试采用隔离存档环境，不覆盖玩家真实存档；headless 不能作为视觉或帧率验收依据。正式数值采用用户明确给出的三种比例与钻石堆叠上限。
