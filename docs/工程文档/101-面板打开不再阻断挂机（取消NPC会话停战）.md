# 101 · 面板打开不再阻断挂机（取消「NPC 会话停战」）

> 关联：工程 45（随身三件套）｜工程 74（面板互斥）｜工程 71（面板打开时快捷栏失效）｜08 坑清单第 66 条
> 状态：**已落地**（R1—R7 全部完成，见 §九 落地记录）

## 〇、需求变更（初版方案作废）

初版问题描述是「打开**随身商队**会停止战斗」，据此出的方案是「只让随身形态不算 NPC 会话」。
现需求升级为：**任何面板打开都不影响背后的挂机**，类似网络游戏，玩家自己评估风险；不做透明面板。

初版方案因此作废——它只治了「随身三件套」一个口子，而实测表明同一现象覆盖 8 类面板。
本版改为**拆掉整层判据**，一次解决全部面板，并同步改产品规格。

## 一、现状实测：面板对挂机的影响是**三档**，不是一档

探针 `tools/panel_auto_battle_probe.tscn`（只读，不写档）：`camp` 图开 F，逐面板打开后等 5 个物理帧取样。

|---|---|---|---|---|---|

| 存档 `save`（单独打开） | **false** | false | 接近目标 | 走动 | ① |
| **Esc 暂停菜单 `menu`** | **true** | false | （引擎冻结） | — | ③ 真暂停 |

三条结论：

1. **现状不是「面板都停战」，而是「有一批面板停战」**。背包、人物、技能、坐骑、大地图、追猎令牌
   本来就照常挂机——玩家日常用得最多的那批是好的，所以问题不刺眼、也没人系统报过。
2. 会停战的是 **8 类功能面板**，判据只有一条：`GameState.npc_dialog_open()`。
3. **设置 / 存档单独打开时并不暂停**——它们自己从不设 `get_tree().paused`，能不能冻结世界
   取决于是不是从菜单进的（菜单已暂停）。所以它们本来就属于①档，不需要为本次改动做任何处理。

## 二、根因：中间档就是 `NPC_DIALOG_PANEL_IDS` 这一层

`autoload/game_state.gd:1894`：

```gdscript
## NPC 会话面板：打开期间暂停自动战斗挂机（普通可并开的信息面板不影响自动决策）。
const NPC_DIALOG_PANEL_IDS := ["shop", "quest", "carter", "blacksmith",
        "warehouse", "upgrade", "reforge", "equipment_fusion"]

func npc_dialog_open() -> bool:
    for panel_id in NPC_DIALOG_PANEL_IDS:
        if _open_panels.has(panel_id):
            return true
    return false
```

三个消费点：

| # | 位置 | 后果 |
|---|---|---|
| 1 | `auto_battle.gd:236` | 挂机 `_set_state(RECOVER, ui.auto.npc_dialog)` + `set_auto_move(ZERO)` + `clear_travel_intent()` |
| 2 | `ground_item.gd:132`（生成即认领） | G 开着也不自动拾取 |
| 3 | `ground_item.gd:182`（靠近拾取） | 同上 |
| 4 | `hud.gd:191` | 挂机图标打叉 + 文案「对话中暂停」 |

**关键发现（影响方案设计）**：`auto_battle.gd:251` 那段 `if get_tree().paused:` 分支**实际不可达**——
`AutoBattle` 没设 `PROCESS_MODE_ALWAYS`，世界暂停时 `_physics_process` 根本不会被调用。
探针里 Esc 菜单 `paused=true` 时 phase 仍停在「接近目标」而不是「已暂停」，就是证据。

所以拆掉中间档之后，挂机侧**不再需要任何「面板」概念**：
世界在跑就继续挂机，世界停了引擎替它停。一个判据、两种状态，没有第三档。

## 三、方案：拆掉中间档，只保留「不阻断」与「真暂停」

### 3.1 删除清单（4 处生产代码）

| 文件 | 改动 |
|---|---|
| `autoload/game_state.gd` | 删 `NPC_DIALOG_PANEL_IDS` + `npc_dialog_open()` |
| `scripts/systems/auto_battle.gd` | 删 `:236—248` 的 npc 分支 + `_npc_dialog_suspended` 字段 |
| `scripts/entities/ground_item.gd` | 删 `:132` / `:182` 的 `or GameState.npc_dialog_open()` |
| `scripts/ui/hud.gd` | `paused` 判定去掉 `ui.auto.npc_dialog`（保留 `ui.auto.paused`） |

删完 `auto_battle._physics_process` 的分支顺序变成：
关闭 → 死亡 → 未领取战利品上限 → 打坐 → 真暂停 → 手动接管 → 正常决策。

**没有新增状态、没有新增判据、没有新增开关**——这是纯减法。

### 3.2 为什么不做「加开关让玩家选」

用户要求是默认行为变更，不是可配项。加一个「面板内是否继续挂机」设置项会带来：
两套分支都要长期维护、存档要加字段（撞坑清单第 60 条：给 `default_settings()` 加键会让存量档判损坏）、
UI 还要加一行说明。收益为零，风险不小。

### 3.3 保留的三个真暂停点（不动）

| 面板 | 暂停来源 | 保留理由 |
|---|---|---|
| `death`（死亡选择） | `death_panel.gd:69` | 玩家已死，`auto_battle` 的 `is_dead` 分支本来就会关挂机；死亡面板必须冻结世界 |
| `menu`（Esc 暂停菜单） | `menu_panel.gd:65` | 它叫「暂停菜单」，玩家按 Esc 就是要停下来；且退出主菜单/读档都在这里 |
| `equipment_confirm`（换装二次确认） | `equipment_confirmation.gd:135` | 这是**弹窗**不是面板，用途就是让玩家停下来看清「换掉的是哪件」；世界在动会让确认框变成赌博 |

`settings` / `save` 不改：它们自己从不 `paused`，靠菜单上下文；单独打开时按①档走，正合本次语义。

如果你希望连 `equipment_confirm` 也不暂停，代价是：确认框弹出时背景继续战斗，
玩家在读「当前 / 将要装备」的两行属性时随时可能被怪打断，且它自己有一套
`_pause_before` 恢复逻辑（`:148`）需要跟着改。**建议保留**，实机觉得别扭再单独处理。

## 四、连带影响与风险

| 编号 | 影响 | 处置 |
|---|---|---|
| 🔴 R-1 | **不再有「安全暂停」**：玩家整理装备/卖东西时角色一直在挨打，可能当场死亡 | 这是需求本身要的（「由玩家自己评估」）。死亡时 `panel_opened("death")` 会关掉所有面板，`ShopPanel` 走 `_return_tray()` 把托盘物品退回背包，**不丢件**；需实机验证一次 |
| 🔴 R-2 | 自动拾取同时放开 ⇒ 交易中 `inventory_changed` 频繁触发 `InventoryPanel._refresh()` | 已核：`_refresh()` 复用现有 slot 节点（`_ensure_bag_slots()`），不重建；拖拽 payload 是快照。风险低，实机拖一件确认 |
| 🔴 R-3 | 挂机继续 ⇒ 角色会走开，而面板是全屏 UI 不跟随 | 这是正确行为（网游同样如此）；玩家关面板时人在别处，属预期 |
| ⚠ R-4 | 自动喝药会消耗「还没拖进托盘」的药水 | 既有行为（开 F + 手动开背包整理时一样），非本次新增 |
| ⚠ R-5 | 挂机打怪产出的掉落会在地上堆积（G 开着就会捡；关着则堆积） | 既有行为，与面板无关 |
| ⚠ R-6 | `ui.auto.npc_dialog`（「对话中暂停」）文案变成孤儿键 | **保留不删**：删除会动本地化条数（919），且它无副作用。在本文档标注「已无消费点，留待文案清理批次统一回收」 |
| ⚠ R-7 | `ui.auto.paused` 分支实测不可达（世界暂停时 UI 也冻结） | 既有问题，**本次不修**；如需「暂停中」可见反馈，要另开一单把 Hud 设为 `PROCESS_MODE_ALWAYS` |

**数值、掉率、装备、存档结构、刷怪：零改动。**

## 八、一句话结论

**挂机停不停，应该由「世界在不在跑」决定，而不是由「哪个面板开着」决定。**
现状多出来的那一档（`npc_dialog_open`）正是问题所在，拆掉它，8 类面板一次全部解决，
且不需要新增任何开关、字段或配置。

### 9.3 与方案的两处偏离（都是踩出来才发现的，记在这里防复发）

1. **B 组判据从「30 帧内 `auto_move != ZERO`」改为「90 帧内 掉血 **或** 位移」**。
   原判据在真实战场会假红：玩家贴身站桩输出时 `auto_move` 恒为零（攻击不移动），
   连续打两三只怪就能让前几个面板全部报错。**「在打」也是挂机在跑**，所以判据必须是
   「掉血或位移」二选一；两者都不发生才说明决策链被跳过。
2. **掉血判据必须用「全场总血量」而不是「第一个敌人」**。第一版取 `enemies` 组的第一个，
   而挂机锁定的往往不是它 —— 明明在打第三只，却盯着没挨打的第一只报「没推进」。
   这类「取样对象搞错」的假红，比假绿更难发现，因为报错方向看着完全合理。

另外一条**测试环境**的坑：本测试节点设了 `PROCESS_MODE_ALWAYS`（C 组要在暂停中继续推进协程），
而 `process_mode` 会**向下继承** —— 不显式把 `Main` 压回 `PROCESS_MODE_PAUSABLE`，
整棵场景树都会跟着 ALWAYS，`paused = true` 变成空操作，C 组静默假绿。

### 9.4 负向验证（`tools/verify_101_negative.py`，4/4 红在预期断言上）

| 编号 | 改坏方式 | 结果 |
