## 1. 一页结论

| 项 | 结论 |
|---|---|
| 改动文件 | **4 个既有 + 1 个新测试场景**：`autoload/data_loader.gd`、`scripts/systems/loot.gd`、`scripts/entities/monster.gd`、`data/dropTables.json`、新增 `tests/arena_drop_test.gd` + `.tscn` |
| 净增代码 | ≈ 90 行（`data_loader` ≈ 25、`loot` ≈ 22、`monster` 1 行、`dropTables.json` ≈ 45 行、测试 ≈ 70 行） |
| schema | **不变（仍 14）** |
| 1–60 影响 | **零**：`Loot.roll` 新增参数有默认值；静态条目（有 `tierStart`）走原分支，随机调用顺序不动 |
| 数据文件 | `dropTables.json` **只增不改**（新增 `DT_C7_Arena_Boss`，既有 26 张一字不动） |
| 最大风险 | 把「`levelFromBoss` 与 `tierStart` 互斥」写成「两个都可选」⇒ 一张同时带两者的坏表能静默跑错分支 |

**三句话**

1. **`levelFromBoss` 不是新档位，是新的取等级方式**：套固定 loop 51（`ItemFactory.DYNAMIC_BASE_TIER`），等级由击杀那一刻的 `Monster.level` 决定；`levelRange` / `tierStart` 对这类条目**必须缺席**。
2. **等级要一路传下来**：`Loot.roll` 现在只认「表 id + 怪物 id」，不认识怪物等级。必须加 `source_level` 并透传到 `_roll_equip`，否则 61+ 动态条目永远拿不到等级（只能兜底 60 档，等于循环图不掉新装）。
3. **P-3 已在 M10-1 解决，本批不重复改**：`make_equip_dynamic` 是独立门面，固定走 51 套，绕开了 `make_equip_roll` 的「穿戴等级与所属套不符」断言。

## 3. `data_loader` 校验：按 `levelFromBoss` 分支

### 3.1 判定表

| 校验项 | 静态档（现状） | 动态档（`levelFromBoss: true`） |
|---|---|---|
| `requiredLevel` | **禁止** | **禁止**（不变） |
| `levelRange` | **必须**（`[lo,hi]`、`lo ≥ 1`、`lo ≤ hi`） | **禁止**（等级由击杀目标决定，写了会误导） |
| `tierStart` | **必须**且命中六档 | **禁止**（套由 `ItemFactory.DYNAMIC_BASE_TIER` 锚定） |
| `levelFromBoss` | 必须是 `false` 或缺席 | 必须是 **`true` 布尔**（写 `"true"` 字符串直接报错） |
| `countRange` / `templatePool` / `qualityWeight` | 照旧 | **照旧**（品质合计 100、池必须存在） |

> **为什么是「互斥」而不是「二选一优先」**：两种取等级方式同时存在时，运行期必须挑一个，
> 而「挑哪个」没有任何数据可以表达 —— 早晚会有人写出 `{"levelFromBoss": true, "tierStart": 51, "levelRange": [51,60]}`
> 然后困惑「为什么 100 级还是掉 51 级装」。**启动期直接拒**比运行期猜要便宜得多。

### 3.2 代码草案（`data_loader.gd:612-630` 整体替换）

```gdscript
				"equip":
					# M10-2：两套互斥口径——静态档靠 levelRange + tierStart，
					# 动态档（levelFromBoss）靠击杀目标的实际等级，套由 ItemFactory 锚定 51。
					var dynamic_flag: Variant = en.get("levelFromBoss", false)
					if not (dynamic_flag is bool):
						report.append("[dropTables] %s 的 levelFromBoss 必须为布尔值" % did)
						dynamic_flag = false
					var dynamic := bool(dynamic_flag)
					if en.has("requiredLevel"):
						report.append("[dropTables] %s equip 不能用 requiredLevel" % did)
					if dynamic:
						if en.has("tierStart"):
							report.append("[dropTables] %s equip 的 levelFromBoss 与 tierStart 互斥" % did)
						if en.has("levelRange"):
							report.append("[dropTables] %s equip 的 levelFromBoss 条目不应带 levelRange" % did)
					else:
						var level_range: Variant = en.get("levelRange", null)
						if not level_range is Array or level_range.size() != 2 \
								or not _is_whole_level(level_range[0]) or not _is_whole_level(level_range[1]) \
								or int(level_range[0]) < 1 or int(level_range[1]) < int(level_range[0]):
							report.append("[dropTables] %s equip 条目缺少 levelRange" % did)
						if not en.has("tierStart"):
							report.append("[dropTables] %s equip 必须使用 tierStart，不能用 requiredLevel" % did)
						if en.has("tierStart"):
							var required: Variant = en.get("tierStart")
							var cfg: Variant = tables.get("equipmentRules")
							var legal := false
							if cfg is Dictionary and _is_whole_level(required):
								for configured in cfg.get("tiers", []):
									if int(configured) == int(required):
										legal = true
							if not legal:
								report.append("[dropTables] %s 的 tierStart 未在装备套起点表中" % did)
					# countRange / templatePool / qualityWeight：两种口径共用，保持原样
```

> ⚠ `var dynamic_flag: Variant = en.get(...)` 必须显式标 `Variant` —— `warnings_as_errors` 开启时
> `var x := <Variant 来源>` 直接编译失败（交接 08 §7 第 7 条）。
> 原代码 `if en.has("requiredLevel") or not en.has("tierStart")` 把两个错误合并成一句，这里拆开，
> 否则动态档会一直带着「必须使用 tierStart」的误报。

## 4. `Loot`：加 `source_level` 并在 `_roll_equip` 分岔

### 4.1 签名变化（三处，全部带默认值）

```gdscript
static func roll(drop_table_id: String, rng: RandomNumberGenerator = null,
		source_monster_id: String = "", source_level: int = 0) -> Array:
static func _roll_entry(e: Dictionary, r: RandomNumberGenerator,
		source_monster_id: String = "", source_level: int = 0) -> Dictionary:
static func _roll_equip(e: Dictionary, r: RandomNumberGenerator, source_level: int = 0) -> Dictionary:
```

### 4.2 `_roll_equip` 分岔位置（**品质抽取之后、静态等级抽取之前**）

```gdscript
static func _roll_equip(e: Dictionary, r: RandomNumberGenerator, source_level: int = 0) -> Dictionary:
	var pool := String(e.get("templatePool", ""))
	var quality: String = _weighted_quality(e.get("qualityWeight", {}), r)
	# M10-2：动态档的等级来自击杀目标的实际等级；未提供时兜底 60（=既有最高档，不产生 v5）。
	if bool(e.get("levelFromBoss", false)):
		var boss_level := source_level if source_level > 0 else Balance.SOFTCAP_LEVEL
		var dynamic_tpl := _pick_equip_template(ItemFactory.DYNAMIC_BASE_TIER, r, pool)
		if dynamic_tpl.is_empty():
			return {}
		return ItemFactory.make_equip_dynamic(
			String(dynamic_tpl.get("id", "")), boss_level, quality, r, "drop")
	var lr = e.get("levelRange", [1, 1])
	var lo := int(lr[0]) if lr is Array and lr.size() >= 1 else 1
	var hi := int(lr[1]) if lr is Array and lr.size() >= 2 else lo
	var source_level_roll := r.randi_range(lo, maxi(lo, hi))
	var tier_start := int(e.get("tierStart", ItemFactory.tier_for_level(source_level_roll)))
	var tpl := _pick_equip_template(tier_start, r, pool)
	if tpl.is_empty():
		return {}
	return ItemFactory.make_equip_roll(String(tpl.get("id", "")), tier_start, quality, r, "drop")
```

**随机流分析（这是「1–60 零影响」的证明）**

| 场景 | 随机调用序列 | 与改动前比 |
|---|---|---|
| 静态条目（`levelFromBoss` 缺席） | `randf`（品质）→ `randi_range`（等级）→ `randi_range`（型号）→ `make_equip_roll` 内部 | **逐字相同**（`if` 不进，`randi_range` 位置不变） |
| 动态条目（新表才用） | `randf`（品质）→ `randi_range`（型号）→ `make_equip_roll` 内部 | 新路径，无历史包袱 |

> 局部变量名 `source_level_roll` 是为了不和参数 `source_level` 撞名（GDScript 同作用域重名直接编译错）。

### 4.3 `monster.gd:827` 一行

```gdscript
	var rolled := Loot.roll(table_id, null, monster_id, level)
```

`level` 是 `Monster` 的实例实际等级（F-8）。对 1–60 的怪，`level` 与模板等级同值，静态条目根本不读它 ⇒ 既有 26 张表零影响。

## 7. 数值验算（本机实跑口径）

| 条目 | 件数 | 期望 |
|---|---|---|
| 普通（common 70 / uncommon 30） | `randi(5,8)` = 5–8 | 6.5 |

### 7.2 一轮（10 只全清）

| 项 | 值 |
|---|---|
| 件数 | **70–100**（期望 85.5） |
| 回收总额（60 级档） | 单件 300–480 ⇒ **21,000–48,000**，期望 ≈ 33,000 |
| 背包压力 | `INVENTORY_SIZE = 40` ⇒ **打 4–5 只就满**（产品 §4.6 的「4–6 只」节奏成立） |

> ⚠ **产品 13 §8 写的是「60 级档一轮 50–80 件」，与本表的 70–100 不符**。
> 复算：「50–80」只算了普通组的 `5–8 × 10`，漏掉「好装 2 件/只」（+20）。
> **验收以本表的 70–100 为准**（因为它严格来自 `DT_C6_Boss` 的既有结构）。

### 7.3 各等级档的实际取值

| source_level | 版本 | `requiredLevel` | 武器基底 atk | 单件回收 |
|---|---|---|---|---|
| 60 | **4** | 51（模板值） | **75** | 300–480 |
| 61 | 5 | 61 | **84** | 300–480 |
| 70 | 5 | 70 | **165** | 300–480 |
| 100 | 5 | 100 | **564** | 300–480 |
| 1000 | 5 | 1000 | **150,630** | 300–480 |

> 100 级武器基底 = `round(75 × S(40)) = round(75 × 7.5248) = 564`。这里列的是**装备基底**，
> 不要和玩家的 `Balance.base_attack(100) = 978` 混为一谈（两者锚点不同）。
> 本批只保证「掉落装备的 `requiredLevel` 与 `rawBaseAttrs` 跟随 `source_level`」。

## 9. 风险与处置

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| **R1** | 把「互斥」写成「都允许」 | 坏表静默走错分支 | 校验**两个方向都报错**（有 `tierStart` 报、有 `levelRange` 也报）；测试的「表结构契约」用例直接断言三件套缺席 |

**方案外的一处必要改动：`EquipmentAxesTest` 契约更新**

原断言是「**所有**掉落表的 equip 条目都必须带与本档一致的 `tierStart` 且用本档型号池」——
这在「只有一种取等级方式」的时代成立，M10-2 引入第二种口径后它必然会红（实跑：`DT_C7_Arena_Boss` 报
「来源固定档位」+「使用本档型号池」各 3 次，导致该测试整体 FAIL）。

处置：**不是放宽，是换轨**——

- 动态条目（`levelFromBoss == true`）改判「**不得**同时带 `tierStart` / `levelRange`」后 `continue`，
  档位与型号池的契约交给 `ArenaDropTest` 的「表结构契约」用例；
- 静态条目仍逐条要求 `tierStart == 本档`、池必须命中 `pool_of[tier]`，**一个字没松**；
- `_tier_of` 补 `DT_C7_ → 51`（循环图复刻第六章套），供将来 C7 接静态表时直接可用。

> 这正是方案 §9 R1 想避免的事：如果当初把校验写成「两个都可选」，这里就不会红，
> 而是静默地让一张带齐两套字段的坏表跑错分支。**测试红了一下，反而是设计没走歪的证据。**

**实现与方案的一处偏差（收紧）**

- 方案草案里 `_roll_equip` 的静态分支变量名写的是 `source_level`，与新增的参数**同名**
  （GDScript 同作用域重名直接编译错）。落地改为 `source_level_roll`，随机流不受影响。
