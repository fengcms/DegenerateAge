## 2. 范围界定

### 2.1 M6-0 包含什么

创意 07 是自洽整体，其 §13 明确"未领取保护未完成前，不应作为完整产品包发布"，故：

| 子域 | 创意 07 章节 | 交付 |
|---|---|---|
| 敌人外观层次 + Boss 顶部血条 | §4 | 三档视觉规格 + Boss 独立血条 |
| 分组掉落（精英 3–4 / Boss 7–10 + 传说） | §5 §6 | 掉落表结构扩展 + 结算分组 |
| 传说池与固定属性 | §7 | 新模板 `weapon_legendary_vein_guard` + 固定属性路径 |
| 奖励结算与入包规则 | §8 | 批次 ID + 品质优先入包 + 溢出保护 |
| 装备雨展示时序 | §9 | 分类出场 + 批次散布 + 光柱 / 名称 |
| 汇总提示与设置 | §10 | 批次摘要 + 传说提示 + `dropFlyAnim` 兼容 |
| 未领取持久化 | §11 | **GameState + 存档 schema 8** |
| 启动校验 | §12 | 分组 / 传说池 / 概率合计校验 |

### 2.2 M6-0 不包含什么

- 创意 08（步行 / 车夫 / 集群拓扑）→ 属 M6-1~M6-4。
- 创意 07 §7 的"独特被动执行器"——本版无被动（§7 明确）。
- 正式美术素材——全占位图形（§4 明确）。
- 09-B 高级显示项。

### 2.3 与创意 08 的唯一接口

创意 08 §8 要求"未领取战利品按 07 持久化，出行不丢失"。因此 **M6-0c（未领取持久化）是 08 的硬前置**；M6-0a/b/d/e 与 08 无依赖。若希望尽快解锁 08，可**先做 M6-0b + 0c**（分组掉落 + 持久化），把外观 / 装备雨后置。

## 4. 落地方案

### 4.1 数据配置：`dropTables.json` 结构扩展

现有 entry 是"单条 = 单件"，扩展为**分组**（旧字段向后兼容）：

```jsonc
{
  "kind": "equip",
  "chance": 1.0,
  "countRange": [2, 3],              // 新增：整数等概率件数（缺省 [1,1]）
  "qualityWeight": { "common": 70, "uncommon": 30 },
  "levelRange": [3, 5],
  "templatePool": "tier1_normal"     // 新增：可选命名池；缺省＝全表非 debug
}
```

> **落地（M6-0b）**：池定义落在新表 `data/lootPools.json`，仅两池 —— `normal`（排除传说）与 `legendary`（仅传说）。示例中的 `tier1_normal` 收敛为 `normal`（池**不绑定 tier**；tier 由生成等级动态决定）。**缺省池也排除传说**（比原注「全表非 debug」更严），以满足创意 07 §7「传说专属模板不得被抽成白装」。传说槽以 `templatePool: "legendary"` 表达；`qualityWeight` 写 `{legendary:100}` 以纳入「合计 100%」校验。

| 表 | 分组（创意 07 §5 / §6） |
|---|---|
| `DT_Elite_L1` | 基础装备 `countRange[2,3]`（common70/uncommon30）；好装备 1 件（uncommon70/rare27/epic3）；coin[48,72]；药水 small ×1（100%） |
| `DT_Boss_L1` | 基础装备 `countRange[5,8]`（common70/uncommon30）；好装备 2 件（rare75/epic25）；传说追加 1（chance0.05，池=legendary）；coin[720,880]；药水 large ×2（count=2）；如意 1 份（chance0.30，iron/jade 各 50%） |

> `countRange` / `chance` 语义（§12）：先判 `chance` 一次 → 再抽件数 → 各件独立抽品质与模板。

### 4.2 掉落结算：`Loot` 分组

- `Loot.roll` 增加"多件展开"：entry 含 `countRange` 时循环生成 N 件。
- `_roll_entry(KIND_EQUIP)` 支持 `templatePool` 过滤（`tier1_normal` / `legendary`）。
- **传说独立**：`templatePool="legendary"` 的 entry 强制 `quality=legendary` 且从传说池取模板（禁止"先抽品质再追加"）。
- **固定属性路径**：传说模板 `affixes` 视为**固定词条**；`_roll_equip` 对 legendary 一律取模板 `affixes`，不走 `AFFIX_COUNT`。
- **品质优先入包**：`Monster._settle_rewards` 生成批次后按 传说→史诗→稀有→优秀→普通 排序再逐件认领。

> **落地（M6-0c）**：`Monster._settle_rewards` 为整批生成唯一 `batchId`（`b_<ticks>_<seq>`，随机结果只抽一次）；
> 认领序由 `Monster._priority_order` 决定（分桶实现以保持**稳定次序**）：装备按品质降序
> （`_claim_rank` = 2+品质序）→ 药水 / 如意 / 杂项 → 金币（0）。该序**只影响背包空间分配**，
> 展示顺序由 M6-0d 负责（§8 明确「展示仍按基础 / 好装备 / 传说顺序」）。
> `_spawn_drop` 附带 `batch_id` 与 `persistent`（`kind ∈ {elite, boss}`）。

### 4.3 传说池与固定属性

- 新增模板 `weapon_legendary_vein_guard`（`equipments.json`）：`slot=weapon`、`tier=1`、`levelReq=9`、`quality=legendary`、`baseAttrs={atk:30}`、`affixes=[{atk,+6},{hp,+20}]`、`price=300`、`desc`（§7 原文）。
- `_pick_equip_template` 普通池**排除** `quality=legendary`（§7："不能被抽成白装"）。
- 等级缩放：Lv9 基准 30；Lv10 按既有 8% 得 32（复用 `_scale_base_attrs`）。

### 4.4 敌人外观 + Boss 顶部血条

- `Monster._draw` 按 `kind` 分支：普通（沿用）/ 精英（半径 19 + 高肩尖耳单爪 + 金色双描边 + 金色菱形地面标识 + 常显名）/ Boss（半径 36 + 双角双爪封印环 + 暗红四刻度环）。
- 头顶血条尺寸随 kind：34×4 / 64×6 / 100×8。
- **Boss 顶部血条**：新增 `BossHealthBar`（Control）挂 `Main.tscn` 的 `UI/Hud` 下（随 UI 轴缩放）。数据源＝EventBus 新增 `boss_hp_changed(name, hp, max, phase)`，由 Monster 在受击 / 阶段变更时广播。显隐：进入仇恨或玩家命中→显示；脱战 3s→隐藏；死亡 0.6s 后淡出（§4）。
- 阶段名：三阶段映射"封印束缚 / 封印开裂 / 腐化狂暴"（对应现 `bossSkill.phases` 0/1/2）。

### 4.5 装备雨展示

- 新增批次编排（`LootBurst` 节点，或 `GroundItem` 携带 `group` + `burst_id`）。
- 出场时序按 §9 表（精英 t=0.15 起每 0.05s；Boss t=0.45 起；好装备 / 传说追加间隔）。
- 散布：以死亡点为中心**分环**，精英 0.7–1.5 格、Boss 1.2–2.5 格，装备间距 ≥0.35 格，好装备 / 传说优先内侧。
- 光柱 / 底座 / 名称：按品质绘制（稀有 36 / 史诗 60 / 传说 90 世界像素）。
- 兼容 `dropFlyAnim`：关闭时结算不变，仅保留一帧品质提示 + 摘要。

### 4.6 未领取持久化（🔴 核心）+ 存档 schema 8

**GameState 新增**（镜像 `spawn_respawn` 的 encode / apply 模式）：

```gdscript
## 未领取战利品（工程 18 / 创意 07 §11）。key = map_id；
## value = [ { "uid": String, "batchId": String, "item": <item 实例>, "pos": Vector2 } ]
var unclaimed_loot: Dictionary = {}
```

> **落地（M6-0c）**：采用**扁平逐条记录 + 唯一 `uid`**（非方案原稿的「按批次分组」）——
> 每条一物一落点，直接支持「领取即注销对应记录」（§11.3），并允许同批物品分散在不同落点。
> `uid` 全局唯一，注销时跨图扫描即可，调用方无需记 `map_id`。配套 API：
> `add_unclaimed_loot / remove_unclaimed_loot / unclaimed_loot_for / unclaimed_count /
> encode_unclaimed_loot / apply_unclaimed_loot`。

- 精英 / Boss 入包失败的物品：`GroundItem` 标 `persistent=true` ⇒ **不走 60s 淡出**，留地可拾取，同时写入 `GameState.unclaimed_loot[map_id]`。
  - ⚠ 登记**延后一帧**（`call_deferred`）：掉落方在 `add_child` **之后**才设最终落点（`Monster._spawn_drop`），立即登记会记到默认位置（实测 `(0,0)`）。
- 领取成功（自动 / 点击）→ 移除记录 + `request_autosave()`；发 `item_picked`（§11.5：实际领取才发）。
- 切图 / 读档：`Game._ready` 装配地图时从 `GameState.unclaimed_loot[current_map]` 重建未领取地面物（重建物 `auto_claim=false` + `persistent=true`）。
- 落点不可达 → 移到驿站附近 + 提示（§11.4）。**当前仅做边界夹取**；完整可走网格校验待障碍系统落地后再补。
- 主动丢弃 → 二次确认（§11.6）。**未实现**（本版无丢弃未领取物入口）。

> **暂缓项（需产品确认）**：创意 07 §8「金币达上限时先入账可容纳部分、余额作同批未领取保留」——
> 当前沿既有语义（达上限**整份**留地并登记为未领取，不部分入账），不重复发整份金币；「部分入账 + 余额保留」留待后续批次收敛。

**存档字段**（`_collect` / `_migrate` / `_is_valid_save` 三处同步）：

```jsonc
"unclaimedLoot": { "<map_id>": [ { "batchId": "...", "items": [...], "pos": [x,y] } ] }
```

- `_migrate`：`if v < 8: data.unclaimedLoot = {}`（旧档默认空，§11）。
- `_is_valid_save`：校验字典结构 / map_id 合法（`DataLoader`）/ items 数组且每项 `_valid_item` / pos 长度 2 数对。

### 4.7 提示

- 批次摘要（§10）：最后一件出场完成时 `"<Boss> 掉落：装备 N 件（稀有 a、史诗 b）· 金币 G · 大型生命药水×2"`；含未领取追加 `"背包不足，N 件装备已保留"`。
- 传说：另发 `"传说 · 镇脉之刃"` 一次，3s。
- 沿用 `dropFlyAnim` 口径不变。

## 6. 启动校验扩展

`DataLoader` / 启动校验新增：

1. 掉落分组：`countRange` 为 `[lo,hi]` 且 `lo≥1`、`lo≤hi`；`qualityWeight` 合计 100（容差）。
2. 传说池：`legendary` 池非空、模板存在、非 debug、tier / 等级适配。
3. 引用：`templatePool` 指向的池存在；池内模板合法。
4. 空池 / 无效物品引用 → **启动明确报错**，不静默少发。
