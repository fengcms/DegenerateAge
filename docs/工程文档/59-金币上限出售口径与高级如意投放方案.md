## 一、先说结论

| 议题 | 现状核实 | 结论 |
|---|---|---|
| 金币接近上限卖不掉 | **是真的**，4 个出口全部「整单拒绝」 | 按你的口径改：照卖、入账截断到上限、返回实际入账额 |
| 金 / 钻石如意不能获得 | **半真**：Boss 掉落表里只有铁 / 玉（各 15%），**金与钻石确实为零投放**；但**随身商店能买**（金 2,400 / 钻 6,000，含 20% 溢价） | 加 Boss 投放，按章节递进解锁 |

## 二、议题一：金币上限下的出售

### 2.1 现在为什么会拒绝

`GOLD_CAP = 999,999,999`（`game_state.gd:10`），`add_gold()` 本身**已经会夹取**（`:378` `clampi(..., 0, GOLD_CAP)`，返回实际入账额）。
真正卡住的是 4 个出售出口在调用前就前置拒绝了：

| # | 函数 | 行 | 现在 |
|---|---|---|---|
| 1 | `shop_sell()`（单件卖给货郎） | `:1378` | `price > GOLD_CAP - gold` → 直接失败「金币已接近上限」 |
| 2 | `shop_sell_staged()`（托盘批量结算） | `:1400` | 同上，整批不收 |
| 3 | `sell_low_gear()`（一键卖低价值装备） | `:546` | 同上 |
| 4 | `sell_selected_equipment()`（背包勾选直卖） | `:606` | 同上 |

也就是说，**物品已经在手里、玩家也点了确认，却因为「钱包装不下」而整单退回**。
测试侧早就按正确口径写了（`review_regression_test.gd:152-167`，E-P3-2：挂牌 50、只剩 10 → 成功且入账 10），
**是实现没跟上**。这就是上一轮我报的 5 条既有红点。

### 2.2 改法（4 处同一模板）

```
删掉前置失败分支
gained := add_gold(挂牌总额)        # add_gold 内部已夹取并返回实际入账
返回值 gold/price = gained（实际入账，不是挂牌价）
gained < 挂牌总额 时追加一条「金币已达上限」提示
```

四个出口一次改齐。**只改一半就是脏状态**：单件能卖、托盘不能卖，玩家会以为是 bug。

### 2.3 连带要改的三处

| 位置 | 改什么 | 为什么 |
|---|---|---|
| `game_state.gd:1384`（`shop_sell` 内） | toast `p052`（「出售：%s（+%d 金币）」）用 `gained`；为 0 时追加新提示 | `gained` 本来就用返回值，但 0 会显示「+0 金币」 |
| `game_state.gd:553`（`sell_low_gear` 内） | toast `p009` 的第二个 `%d` 由 **挂牌总额 `total` 改成实际入账 `gained`** | 这里现在是硬编码 `total`，**不改就显示「+5 万金币」而实际进 0** |
| `shop_panel.gd:667` | `ok` 后 toast 用 `res.gold`（实际入账）；为 0 时改文案 | 现在会显示「出售 8 件（+0 金币）」，读起来像失败 |
| `equipment_sale_preview.gd:308` | 同上，`done_direct` 提示走实际入账 | 直卖走的是 `sell_selected_equipment` |
| `data/localization.json` | 新增 1 个 key（`msg.game_state.p054`）：**「金币已达上限，本次出售未获得金币」** | 现有 `p008`（「金币将超过上限，请先调整筛选」）语义已作废，但不删 key（保留不影响条数） |

⚠ 本地化当前 **735 条**、`msg.game_state.p001–p053` 连续无空洞。新增 `p054` 后必须核对总条数 = 736，
并且断言「该 key 解析出的正文确实是新文案」——`localization.json` 重复键后者胜出，这个坑已经踩过两次。

### 2.4 测试影响

| 文件:行 | 现有断言 | 处置 |
|---|---|---|
| `review_regression_test.gd:158-167` | 「靠近上限出售也应成功 / 入账 10 / 成批入账 1」 | **不动**，改完自然变绿（这 5 条就是验收标准） |
| `sell_gear_transaction_test.gd:44-46` | 「金币上限导致整批拒绝，不截断收入」 | **必须改**：改成「仍成功、金币封顶、`gold` 为实际入账」 |
| `sell_gear_transaction_test.gd:61` | 「货郎金币满时拒绝结算」 | **必须改**：改成「金币满时仍可结算，入账 0」 |

### 2.5 一个不公平点，需要你确认

「能卖出去但拿不到金币」意味着**物品被销毁、玩家零收益**。
在 `GOLD_CAP` 附近（9.99 亿）这个场景几乎不会自然发生，但如果玩家用改档 / 调试进了这个状态，
点一次「一键卖低价值装备」就会**把一背包装备清空且一分不拿**。

两个可选口径：

- **口径 A（严格照你说的）**：照卖，零收益，提示「金币已达上限」。
- **口径 B（推荐）**：照卖，但**当入账额为 0 时二次确认**（「金币已满，继续出售将不获得任何金币」），
  玩家确认后才执行。入账额 > 0 时直接成交不打扰。

我倾向 B —— 语义仍是「不限制卖出」，只是加一道防误触。**你定 A 还是 B。**

## 三、议题二：金如意 / 钻石如意的投放

### 3.1 现状：四张表的如意条目长一个样

7 张 Boss 表 + 1 张竞技场表，如意条目**逐字相同**：

```json
{"kind": "rune", "chance": 0.3, "itemIds": ["rune_iron", "rune_jade"]}
```

`Loot._roll_entry()` 用 `randi_range(0, size-1)` 在 `itemIds` 里等概率取一个 ⇒ 铁 15% / 玉 15%，金与钻石**恒为 0**。
`runes.json` 里金（+15%）、钻石（+20%）只是「配置文件里存在、升星界面认、商店有卖、Boss 不掉」。

### 3.2 投放节奏先说清楚（决定了概率给多少）

| 事实 | 数值 | 含义 |
|---|---|---|
| 主线 Boss | 17 只，**不进 `bossSpawns`、不重生** | 主线掉落只能是「章节惊喜」，不能当稳定供给 |
| `c7_arena` | **20 个 Boss 生成点**（10 种 × 2），全部 `respawnTime: 600` | 60 级后**唯一稳定刷点**，每 10 分钟一波 |
| 实测产出 | 按 10–15 只/小时估 | 高级如意的概率要按「每小时几枚」定，不是「每只几个百分点」定 |

### 3.3 方案：按章节追加独立条目（零代码改动）

`Loot._roll_entry()` 已经支持 `itemId` 单值（`loot.gd:80`），校验器也支持（`data_loader.gd:688`）。
所以**不动一行代码**，只往 Boss 表里追加独立条目，每条独立 `randf()` 判定、概率直接可读：

| 掉落表 | 来源 Boss | 基础如意（不变） | 金如意 | 钻石如意 |
|---|---|---|---|---|
| `DT_Boss_L1` | 腐化巨兽 L10 | 0.30 铁/玉 | — | — |
| `DT_C2_Boss` / `_Slag` / `_Final` | 二章三 Boss L15–20 | 0.30 铁/玉 | 3% | — |
| `DT_C3_Boss` | 三章三 Boss L25–30 | 0.30 铁/玉 | 5% | — |
| `DT_C4_Boss` | 四章三 Boss L35–40 | 0.30 铁/玉 | 5% | 2% |
| `DT_C5_Boss` | 五章三 Boss L45–50 | 0.30 铁/玉 | 6% | 4% |
| `DT_C6_Boss` | 六章三 Boss L55–60 | 0.30 铁/玉 | 8% | 6% |
| `DT_C7_Arena_Boss` | 无尽回廊（60+ 循环） | 0.30 铁/玉 | 10% | **8%** |

**为什么不用「权重」**：`itemIds` 是等概率，要做 5%/95% 就得靠重复列 id 造假权重 —— 后来人一「去重清理」权重就没了。
独立条目是显式的，概率就写在 `chance` 上，谁都改不坏。

**节奏核算（竞技场 10 只/小时）**：金 ≈ 1.0 枚/h、钻石 ≈ 0.8 枚/h ⇒ **攒 4 枚钻石约 5 小时**。
主线一整章 3 只 Boss，钻石期望 0.06–0.18 枚/章 —— 只够当惊喜，不构成供给。

### 3.4 这个概率的经济含义（必须一起看）

升星成功率 `[100,90,80,70,60,50,40,30,20,10,10,5]`（index = 当前星级），**只有 4 个如意格**，
所以高星段**永远无法满概率**（每格最多 +20%，4 格最多 +80%）：

| 段 | 基础 | 4 钻后 | 硬上期望金币 | 带 4 钻期望金币 | **每枚钻石的隐形价值** |
|---|---|---|---|---|---|
| 8→9 | 20% | **100%** | 64,070 | 12,814 | 12,814 |
| 9→10 | 10% | 90% | 192,220 | 21,358 | 42,715 |
| 10→11 | 10% | 90% | 288,330 | 32,037 | 64,073 |
| 11→12 | 5% | 85% | 864,980 | 50,881 | 203,525 |

🔴 **这里藏着一条既有的失衡（不是本轮引入，但加投放会放大）**：
钻石如意**商店卖 6,000 金，而它在 11→12 段的期望价值是 20 万金**。
也就是说「花钱买钻」在这个定价下是**碾压式划算**的杠杆。
本轮只加掉落、不动价格；但如果你希望升星是「真金消耗」，这个 6,000 迟早要重定价。**本轮建议先不动，只记录。**

### 7.3 关键实现

```gdscript
# autoload/game_state.gd
func _gold_gain(listed: int) -> int:      # 出售入账唯一门面
	return add_gold(listed)                # add_gold 内部已 clampi 并返回实际入账

func _notify_gold_gap(listed: int, gained: int) -> bool:
	if gained >= listed:
		return false
	EventBus.toast_requested.emit(Localization.tr_key("msg.game_state.p054"), "danger")
	return true
```

四个出口一律 `var gained := _gold_gain(total)`，返回值用 `gained` 并附 `capped: gained < total`。
