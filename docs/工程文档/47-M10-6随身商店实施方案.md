## 0.1 三件必须知道的事（方案期结论，实施后全部成立）

### C-1 🔴 **产品 §5.2 的数据源口径与真实数据不符：并集只有 9 种，不是 14 种**

产品 §5.2 写「数据源＝12 家店 `buyItems` 并集」，但**实测并集只有 9 种**（已逐店核对 `data/shops.json`）：

| 应上架的 14 种 | 在 12 家店并集里？ |
|---|---|
| 6 药水（红/蓝 × 小中大） | ✅ 全在（`potion_hp_small` 仅 1 家、`hp_mid` 11 家…） |
| `misc_random_ticket` / `misc_town_scroll` / `misc_revive_scroll` | ✅ 在 |
| **`misc_firework`（烟花，30 金）** | ❌ **12 家店全都不卖** |
| **4 如意（`rune_iron/jade/gold/diamond`）** | ❌ **12 家店全都不卖** |

⇒ 若严格照「并集」实现，随身商店只有 9 种，**与 §5.2 的「14 种」和 §8 验收「14 种齐备、价格逐项匹配 §5.2 表」直接冲突**。

**根因**：D-14 拍板的是「**全部在售品类**」，而「12 家店并集」只是当时的**举例式写法**，不是可执行口径——如意在现版本没有任何 NPC 出售（R-16 也提到如意「当前无消耗点」）。

**建议（Q-1）**：改为按**模板三表全品类**取货（`potions` + `miscItems` + `runes`），过滤条件写死为「有价 + 非任务物 + 非 `useType: quest`」。这样：① 结果恰好 14 种、与 §5.2 表逐项对齐；② 以后新增药水/如意**自动上架**，不需要改 `shops.json`；③ 不需要在数据里复制一份价格（价格权威仍是模板，避免「改模板忘了改随身店」）。
**不采纳的替代**：把 14 条写进 `shops.json` 新条目——会多出一份价格副本，且 `data_loader` 现有校验会把它当「无 NPC 引用的孤立商店」。

### C-2 🔴 `shop` 点亮后，`PortableToolsTest` 的「未点亮」锚点彻底消失

`tests/portable_tools_test.gd:101`（用例 4）与 `:135`（用例 6）现在**全靠 `shop` 未点亮**来断言「明确失败 + 有 toast + 不消耗」。M10-5 时是把锚点从 `boss_token` 挪到 `shop` 才保住覆盖；这次**三个面板全亮，没有下一个承接者了**。

**建议（Q-2）**：不新增假数据、也不删断言，而是把判定逻辑抽成纯函数：

```gdscript
# panel_router.gd
static func is_openable(entry: Variant) -> bool:
	return entry is Dictionary and bool((entry as Dictionary).get("ready", false))
static func is_ready(panel_id: String) -> bool:
	return is_openable(PANELS.get(panel_id, null))
```

用例 4 改为：① 合成数据断言 `is_openable({"ready": false}) == false`、`is_openable({"ready": true}) == true`、`is_openable(null) == false`（**分支覆盖不再依赖数据**）；② 遍历 `PANELS` 断言三项全部 `ready=true`；③ 保留「未登记 id → 报错且原因带 id」。用例 6 改为「双击随身商队 → 真广播 `shop_open_requested("portable_shop")` + 道具不消耗」。

### C-3 本批玩家**仍然拿不到道具**

`C6Q13`（发放三件套）按 Q-2 拍板顺延 M10-7。所以 M10-6 交付后，随身商店**只能通过测试/调试打开**，正常途径要等 M10-7。这与 M10-4a 处境相同，**不是缺陷**，但必须在交接文档里写明，避免「做完了却没人能用」的误判。

## 2. 设计

### 2.1 合成店铺 id（不写进 `shops.json`）

```gdscript
# scripts/systems/shop.gd
const PORTABLE_SHOP_ID := "portable_shop"
static func is_portable(shop_id: String) -> bool:
	return shop_id == PORTABLE_SHOP_ID
```

不进 `shops.json` 的三个理由：① `shops.json` 的每条都必须被某个 NPC 的 `shopId` 引用（`data_loader` 有反向校验），凭空多一条会被判孤立；② 价格权威在模板表，复制进 json 会双源；③ 只要 `entry()` 返回空，`sell_enabled()` 默认 true 正是我们要的（就地变现，R-18 依赖它）。

**配套契约（防撞名）**：`data_loader._validate_shops` 增加一条——任何店铺的 `npcId` **不得等于** `PORTABLE_SHOP_ID`，否则启动报错。

### 2.2 聚合规则（`aggregate_offers`）

| 项 | 口径 |
|---|---|
| 表顺序 | `potions` → `miscItems` → `runes`，**表内保持 json 原序**（结果稳定、可预期，不用排序算法） |
| 保留条件 | `price > 0` 且 `not questItem` 且 `useType != "quest"` |
| `kind` 映射 | `potions`→`potion`、`miscItems`→`misc`、`runes`→`rune` |
| 返回 | `[{itemId, kind, price, count: 1}]`，`price` 已是随身价 |
| 副作用 | **零**（不读写 GameState、不缓存） |

聚合结果（实测将得到的 14 条，与 §5.2 表逐项对齐）：

| itemId | 模板价 | 随身价（×1.2） |
|---|---|---|
| potion_hp_small / potion_mp_small | 20 | 24 |
| potion_hp_mid / potion_mp_mid | 60 | 72 |
| potion_hp_large / potion_mp_large | 150 | 180 |
| misc_firework | 30 | 36 |
| misc_random_ticket | 100 | 120 |
| misc_town_scroll | 80 | 96 |
| misc_revive_scroll | 120 | 144 |
| rune_iron / rune_jade / rune_gold / rune_diamond | 300 / 800 / 2,000 / 5,000 | 360 / 960 / 2,400 / 6,000 |

**被排除的**：`spirit_shard`（`price 16` 但 `useType: quest`，上架等于「花钱跳过收集」）、21 条 `questItem: true` 任务物、3 件 `tool_*`、**全部装备**（§5.2 已给理由：tier51 单件 300–480，×1.2 后能一次买穿 14 槽，打怪爆装动机当场消失）。

### 2.3 定价：整数向上取整，**不要写 `ceil(base * 1.2)`**

```gdscript
@warning_ignore("integer_division")
static func portable_price(base: int) -> int:
	if base <= 0:
		return 0
	return (base * 6 + 4) / 5     # = ceil(base × 1.2)，纯整数
```

两个坑叠在一起：① `warnings_as_errors` 开着，`int / int` 会触发 `INTEGER_DIVISION` 警告→编译失败，必须显式 `@warning_ignore`；② 反过来改用浮点 `ceil(base * 1.2)` 又踩 IEEE 表示误差（`1.2` 存的是 1.19999999999999996，某些基数下乘积会跨过整数边界多进 1）。整数式对任意 `base` 都精确，且**可被测试直接传任意 base 验证**（见 N-1）。

### 2.4 购买链路（零改造）

`buy_items` 分岔即可，购买侧一个字都不用改：

```gdscript
static func buy_items(shop_id: String) -> Array:
	if is_portable(shop_id):
		return aggregate_offers()
	var arr = entry(shop_id).get("buyItems", [])
	return arr if arr is Array else []
```

因为 `buy_price()` 本来就遍历 `buy_items()`，所以 `buy_price("portable_shop", x)`、`GameState.shop_buy("portable_shop", x)` 自动正确（扣金 / 背包满 / 金币不足 / toast 全部复用既有分支）。

### 2.5 打开链路

```gdscript
# panel_router.gd
"shop": {"ready": true, ...},
...
match panel_id:
	...
	"shop":
		EventBus.shop_open_requested.emit(Shop.PORTABLE_SHOP_ID)
		return {"ok": true, "reason": ""}
```

`shop_panel._on_shop_requested()` 收到合成 id 后，`_shop_id` 就是它，后续刷新全部走聚合列表。**面板本身零改动**，除了标题：

```gdscript
# shop_panel.gd:381 附近
var name := Localization.tr_key("ui.panel.portable_shop") if Shop.is_portable(_shop_id) \
	else Shop.display_name(_shop_id)
_title.text = PanelChrome.title_text(Localization.tr_key("ui.shop_panel.p010") % name)
```

标题因此显示「**随身商队　买卖**」。**刻意不让 `Shop` 引用 `Localization`**：`Shop` 目前在静态类层面零本地化依赖，保持它纯净，本地化留在 UI 层。

### 2.6 交易会话语义沿用

`set_open(true)` 会 `trade_mode_changed.emit(true)` 拉起背包并列——**随身商店也要这样**（野外清包正是要边看背包边卖）。「货郎不互斥、其它面板打开即关」的既有规则不需要例外处理。
