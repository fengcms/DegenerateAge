# 升星如意耗尽后预选未清空：原因与修复

> 2026-10-20 试玩反馈：点击“如意如意”后进行升星，最后一批如意被消耗；面板仍显示选中的“如意 ×0”，升星按钮无法继续使用。

## 现象与复现证据

在隔离 Godot 测试中，准备一件 8 星装备、四枚钻石如意及足够连续升两次的金币；自动选材后第一次升星必然成功（20% + 4×20% = 100%），四枚如意被消耗。修复前，`UpgradeAutoRuneUiTest` 新增的三条断言分别失败：库存从四枚降到一枚后未清空超额三格；四枚全耗尽后未切换为空；下一次无如意升星无法继续。隔离运行器输出这三条 `FAIL`，因此不是只凭界面截图推测。

代码链路也能直接解释：`autoload/game_state.gd` 的 `upgrade_equipment()` 成功结算后扣除如意并发出 `inventory_changed`；`scripts/ui/upgrade_panel.gd` 的 `_on_items_changed()` 会刷新选项，但修复前 `_refresh_runes()` 只重建“如意 ×数量”的下拉列表，并按旧 `_rune_choices[slot]` 恢复选中，即使数量已经是零。随后 `_refresh_details()` 调用 `Upgrade.rune_plan()` 核验旧 ID，库存不足使升星按钮禁用。

## 根因与影响

面板将“选中的如意 ID”和“背包里的可用数量”作为两份状态保存，但库存变化时只刷新了显示数量，没有同步核销预选。升星、出售、仓库转移等导致如意减少都可能触发该状态错位；全部耗尽最明显，部分耗尽则出现多格仍选中但总数不足。它不影响实际扣料安全性：`rune_plan()` 的终验正确拒绝超额请求；问题是玩家无法自然继续不放如意升星。

## 修复

- 在 `_refresh_runes()` 重建下拉选项之前，按 `kind == "rune"`、`itemId` 和正数 `count` 汇总背包库存，与实际扣料口径一致。
- 按四格顺序核销每个预选 ID：有库存就保留并占用一枚；库存不足、模板无效或数量为零时清空该格。随后重建下拉选项，使“空”与内部 `_rune_choices` 同步。
- 只处理现有预选的有效性，**不重新执行“如意如意”选材**，避免背包变化时擅自投入更高级的如意。`Upgrade.rune_plan()` 在点击升星时仍做最终校验；成功率和按钮状态由原有 `_refresh_details()` 更新。
- 四格核销是固定上限，额外成本仅为一次背包扫描，并随已有 `inventory_changed` / 面板刷新事件执行；不新增逐帧工作、不改存档结构。

## 复核结果与边界

修复后通过隔离 `UpgradeAutoRuneUiTest`、`UpgradeAutoRuneTest` 和 `SmokeTest`。新增用例验证：四枚缩到一枚时保留第一格、其余清空，成功率更新且按钮可用；实际升星消耗最后四枚后四格显示“空”，下一次可不放如意直接升星。测试使用随机独立项目名和 `user://`，不触碰正式存档。

本次只修正材料减少后的预选同步；“如意如意”的组合排序、升星概率、金币费用和失败规则未变。玩家仍可手动逐格选择；若点击升星瞬间背包发生变化，交易层终验仍负责拒绝不合法材料。
