## 0. 一句话结论

产品给的「`max(固定值, maxHp × pct)`，L60 百分比值 ≤ 固定值」在数学上**只在 `common` 品质满装时成立**。
实测 L60 穿 `rare` 满装 `maxHp = 5051`，20% = **1010**，是固定值 500 的 **2.0 倍** —— 直接违反「1–60 逐位不变」。

因此本方案在公式之外加一道**等级守护**（`level ≤ 60` 一律取固定值），用一行代码把「1–60 完全一致」从「靠数值巧合」变成「靠逻辑保证」。**这是本方案唯一与产品原文不同的地方，也是唯一需要拍板的地方。**

## 1. 产品依据（原文摘录）

| 编号 | 原文 |
|---|---|
| **R-15** | 药水系统在 60 级后整体失效。实测：大红一瓶 = L60 的 20.9% / L100 的 3.4% / L1000 的 **0.01%**。方案 `max(restoreAmount, maxHp × restorePercent)`，小 3% / 中 9% / 大 20%，**60 级时百分比值必须 ≤ 固定值**（3%×2390=72<80、9%×2390=215<220、20%×2390=478<500）⇒ 1–60 逐位不变 |
| **D-18** | 药水续航独立成批 M10-10，不并入 M10；用 `restorePercent` 且以 `max(固定值, 百分比)` 落地，保证 1–60 逐位不变 |
| **R-21** | 硬约束：L60 时 `maxHp × pct` 必须 ≤ 固定值（取值时留 4–5% 余量）；负向：把大红 pct 提到 0.25（=597>500）⇒ 「L60 恢复量仍为 500」必须失败 |
| **M10-10 验收** | L≤60 恢复量与现在**完全一致**；L100 大红由 500 → 2,969；L1000 → 748,736 |

产品把 `2390` 当作 L60 的 `maxHp` —— 这个数本身没错，但它对应的是 **`common` 品质满装**。

## 2. 实测事实（本次新测，探针已删）

`maxHp` 由 `BASE_HP + 8×L + 2×攻 + 4×防`，再乘 `(1 + hpPercent) + hp平值`。
同一等级下**品质不同，结果差 2.8 倍**：

### 2.1 L60 的 `maxHp` 随品质变化

| 品质 | 满装 maxHp | 3% | 9% | **20%** | vs 固定值 500 |
|---|---|---|---|---|---|
| 空装（无装备） | 1,046 | 31 | 94 | 209 | 0.42 ✓ |
| **common** | **2,390** | 71.7 | 215.1 | **478** | **0.96 ✓**（产品锚点） |
| uncommon | 2,657 | 79.7 | 239.1 | **531** | 1.06 ⚠ |
| rare | 5,051 | 151.5 | 454.6 | **1,010** | **2.02 ✗** |
| epic | 6,033 | 181.0 | 543.0 | **1,207** | **2.41 ✗** |
| legendary | 6,706 | 201.2 | 603.5 | **1,341** | **2.68 ✗** |

**产品验算的 2390 就是 `common` 这一行**，逐位吻合（71.7 / 215.1 / 478）。

### 2.2 各等级 `common` 满装的百分比值

| 等级 | maxHp | 20% | 3% | 9% |
|---|---|---|---|---|
| 60 | 2,390 | 478 | 71.7 | 215.1 |
| 61 | 2,622 | 524 | 78.7 | 236.0 |
| 70 | 4,713 | 943 | 141.4 | 424.2 |
| 100 | 14,839 | **2,968** | 445 | 1,336 |
| 1000 | 3,743,677 | **748,735** | 112,310 | 336,931 |

与产品验收的「L100 大红 2,969 / L1000 748,736」差 1，来自模板 `seed` 不同导致的 `maxHp` 尾数差，**取整方式是 `round`（不是 `floor`）**，这一点已确认。

### 2.3 前六章玩家实际会穿到什么品质

掉落表的品质权重（六章一致）：普通怪 `common 65 / uncommon 25 / rare 9 / epic 1`，
精英的第二组 `rare 90 / epic 10`，Boss 的第二组 `rare 75 / epic 25`。

⇒ **打过 Boss 的玩家在 60 级时身上至少有 2 件 `rare`**，其余多为 `common/uncommon`。
所以「只有 `common` 才不变」不是理论边角，是**大多数玩家的真实状态**。

### 2.4 蓝药（`max_mp`）的情况

`max_mp = 30 + 5×L + 装备 mp`，**没有攻击/防御那一层**，所以数值小得多：
L60 `common` = 444（20% = 89 < 500）、L60 `rare` = 501（20% = 100 < 500）。

⇒ 蓝药在 60 级**本来就够用**，它的问题只在高等级（L1000 `common` = 233,988，500 只回 0.21%）。
百分比化对蓝药同样有效，且 L60 天然不越界。

## 3. 两个方案（需拍板）

### 方案 A：纯公式（产品原文）

```gdscript
restore = max(restoreAmount, round(maxHp * pct))
```

- 优点：与产品原文逐字一致，无额外逻辑
- 缺点：**「1–60 逐位不变」不成立** —— L60 穿 `rare` 时大红从 500 变 1010（+102%），`epic` 变 1207（+141%）
- 玩家观感：60 级穿高品质装备的人突然觉得药变强了；61 级不会再有跳变

### 方案 B：公式 + 等级守护（**推荐**）

```gdscript
if level <= 60:
    return restoreAmount          # 1–60 一律取固定值
return max(restoreAmount, round(maxHp * pct))
```

- 优点：**「1–60 完全一致」由一行逻辑保证**，与装备品质无关；产品验收原文 100% 满足；负向可精确构造
- 缺点：60 级穿 `rare` 的玩家药水仍是 500（= 10% maxHp），要到 61 级才修好。但 60 级只是「刚满级」的过渡点，61 级立刻到位
- 「61 级跳变」的量级：`common` 500 → 524（+4.8%，无感）；`rare` 500 → 1056（翻倍，但此时怪物数值也在涨，且玩家刚换完循环装备）

### 为什么推荐 B

产品的三个验收点（`L≤60 完全一致` / `L100 = 2,969` / `L1000 = 748,736`）里，只有第一个会被 A 打破，且破得很彻底。
B 付出的代价只有「60 级这一年的一点点体验延迟」，而 A 付出的是**改掉一个已验收里程碑的战斗手感**。
R-21 立的规矩就是「这一批不许悄悄改 1–60」，B 是唯一能证明「没改」的实现方式。

> 如果选 A，则产品的 R-21 验收条款必须同步改成「`common` 品质下 1–60 不变」，
> 并在 §10 补一条「穿 `rare` 以上时 1–60 药水变强」的已知偏差 —— 也就是说 A 需要**改产品文档**才自洽。

### 4.2 代码：`scripts/systems/consumable.gd`

新增**纯函数**（三参数，不读 `GameState`，便于逐档回归）：

```gdscript
## 指定药水在「上限 cap、玩家等级 level」下的实际恢复量。
## 规则（M10-10 / R-15 / R-21）：
##   level <= PCT_FROM_LEVEL(60) → 恒为固定值（1–60 逐位不变，与装备品质无关）
##   level >  60                 → max(固定值, round(cap × pct))
static func restore_of(tpl: Dictionary, cap: int, level: int) -> int:
	var fixed := int(tpl.get("restoreAmount", 0))
	var pct := float(tpl.get("restorePercent", 0.0))
	if level <= PCT_FROM_LEVEL or pct <= 0.0 or cap <= 0:
		return fixed
	return maxi(fixed, int(round(float(cap) * pct)))
```

三处调用点改造：

| 位置 | 现状 | 改为 |
|---|---|---|
| `use()` L72 | `var restore := int(t.get("restoreAmount", 0))`（在 `cap` 之前算） | 调整顺序：先 `cap := max_of(kind)`，再 `var restore := restore_of(t, cap, int(GameState.player.level))` |
| `pick_index()` L119 | `var amount := int(t.get("restoreAmount", 0))` | `var amount := restore_of(t, cap, int(GameState.player.level))`（`cap` 提到循环外） |
| 新增 | — | `static func preview_restore(item_id: String) -> int`（供 UI，内部按当前 `max_of(kind)` + 当前等级算） |

> `mini(restore, cap - cur)` 的截断、`cur >= cap` 的「满值不浪费」、冷却表 **全部不动**。

### 4.3 UI：`scripts/ui/inventory_panel.gd`

## 9. 与 M10-9 的衔接

M10-9 的「可挨打次数 ≥ 6」是按**满血**算的，没算喝药。
本批落地后，`60 级以上`的续航实际上变强（大红从 4.8% → 20% maxHp），
`PaceTest` 的 `_hurt_count` 不受影响（它只算 `max_hp`，不涉及药水）。

⇒ **M10-9 的三条实测结论（123.1–123.8 击杀 / 135 只 / 5.19–8.84 次/h）一条都不用改**。
