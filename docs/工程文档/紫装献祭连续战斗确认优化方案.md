# 紫装献祭连续战斗确认优化方案

## 现象与原因

紫装献祭正常需要两次点击。第一次展示本批件数和经验，第二次扣装备并入账。当前 `scripts/ui/equipment_fusion_panel.gd:161` 在任何背包变更事件到达时同步撤销确认，即使变更仅涉及药品、未入选装备或背包排序。击杀磨损也经过 `autoload/game_state.gd:1279` 的装备收尾，广播背包变化，即使没有拾取物品。高倍速下两次点击之间很容易有新事件，使第二次点击再次变成第一次。

这是此前为避免献祭未确认装备加入的保护。`scripts/ui/equipment_fusion_panel.gd:859` 每次点击都会重新选出低档优先的前 20 件。如果只移除确认重置，新拾取装备可能进入排序并替换已确认的装备。现有 `tests/equipment_layout_regression_test.gd:64` 已覆盖同帧加入新紫装导致重新确认的行为。上述结论来自代码和现有测试核对，尚未测量用户存档中的事件频率。

## 方案

1. 第一次点击锁定本批实例 ID、每件经验、等级和星级等影响消耗意图的字段，并保留本批数量、分组和预计经验。最多 20 件，沿用低档优先、默认排除满星和收藏的规则。确认期间固定展示本批，提示新拾取的装备留到下一批。切换满星选项、退出或更换服务时清除快照。
2. 第二次点击只提交已锁定批次。普通拾取、穿戴磨损、整理、当前经验变化和无关装备变动时，仍可完成本批。按稳定实例 ID 从最新背包定位，复核资格、星级和经验；发现批内装备离开背包、被收藏或相关字段变化时，整批拒绝并提示重新预览。采用当前库存位置扣除，保留结算原子性及防重复提交。已经确认的件数不自动补齐，新的低档紫装也不替换旧件。
3. 保持现有库存事件按帧合并。未锁定时继续更新实时预览，锁定时跳过无关背包事件引起的全包重排。结算阶段一次扫描背包定位本批，复用现有 `Sacrifice.eligible` 和 `Sacrifice.xp_of`，不改变计价或自动拾取。

## 验收

- 在实际窗口用同帧新增低档紫装、叠加药品、整理背包和普通击杀磨损覆盖确认间隔。验证两次点击完成，扣除的实例和第一次确认一致。
- 覆盖批内收藏、移出、升星及切换满星选项，验证旧批次失效时库存与经验原样保留。覆盖超过 20 件、重复确认及结算后自动拾取回填。将原先“新增紫装撤销确认”的回归改为“新增紫装保留到下一批”，继续检查未授权物品不会被消耗。
- 在百首禁域的隔离存档对照记录确认次数、扣除 ID 和实得经验，并复测献祭后的背包回填。结算保护与界面接入分别验收并提交。

## 实施验证

隔离实际窗口在两次点击之间调用正式拾取入口、背包整理和击杀磨损入口，并增加 1 点战斗经验。第二次点击只扣第一次锁定的实例，新增的低档紫装仍在背包。批内收藏和升星分别在窗口与结算测试中验证为整批拒绝。紫装献祭、合成界面、保星自动穿戴、装备布局和拾取重试共五项回归通过。尚未在百首禁域连续实战中记录点击次数。
