## 1. 一句话结论

**M10-3b 不是「把血条画成三条」，而是把「这是谁的血」从信号里补回来。**

现在 `boss_hp_changed` 只有名字和数值，没有身份：

```gdscript
signal boss_hp_changed(boss_name: String, hp: int, max_hp: int, phase: int)
```

血条只有一组字段（`_boss_name / _hp / _max_hp / _phase`），谁最后发谁就是「当前 Boss」。`c7_arena` 五区各 2 只、同区两只同时进 `AGGRO_RANGE` 时，`_boss_beat` 每秒各发一次 ⇒ **血条以 1Hz 的频率在两只之间来回翻**，玩家看到的是「血条在跳，数字却一直不满」。

补 `boss_id` 之后，血条与音频都从「一个游标」变成「一张表」——这才是本批真正的结构变化。

## 3. 设计决策

### 3.1 P-7：信号带 `boss_id`，血条改成「表」

**新签名**：

```gdscript
signal boss_hp_changed(boss_id: int, boss_name: String, hp: int, max_hp: int, phase: int)
```

`boss_id` 取 `Monster.get_instance_id()`：

| 备选 | 为什么不行 |
|---|---|
| `monster_id`（配置 id） | `c7_arena` 10 只由 `endgame.json` 指定，同种模板可重复出现在不同区；同名同类正是**最需要区分**的场景 |
| `display_name` | 同上——10 只里有同名同族的，两条同名血条等于没区分 |
| 数组下标 / 点位 key | 要额外维护「实例 ↔ 点位」映射，且死亡重生后 key 会变；`instance_id` 天然随实例生灭 |

**表结构**（数组顺序即显示顺序，`index 0` = 最上）：

```gdscript
{ "id": int, "name": String, "hp": int, "max_hp": int, "phase": int,
  "since": float,      # 距上次更新的秒数，>= HIDE_AFTER 移除
  "dying_left": float, # >0 表示正在死亡淡出（0.6s 停留 + 0.3s 淡出）
  "alpha": float }
```

**四条行为规则**：

| 规则 | 实现 | 为什么这样定 |
|---|---|---|
| **插入** | 新 id 插到 `index 0` | 最新接战的在最上 = 产品说的「当前目标优先」 |
| **更新** | 命中已有 id → **原地更新，不重排** | 产品原建议是「最近受击置顶」，但两只同时挨打时会互相顶掉 ⇒ **仍然是跳位**。改成「首见置顶 + 原位更新」后，跳位从根上消失 |
| **过期** | 逐条 `since >= HIDE_AFTER(3.0)` 移除 | 等价于产品的「最近 3s 内受击才更新」，且**一条过期不带走另一条** |
| **死亡** | `hp<=0` → `dying_left = 0.6`，保留条目、0.3s 淡出，超时移除 | 单目标时代是「整个控件淡出」；多目标必须逐条，否则打死一只会把旁边那只的血条一起抹掉 |
| **上限** | `MAX_BARS = 3`，超限淘汰 `since` 最大的**非死亡**条目 | 同区 2 只 + 「刚打死一只、旁边又来一只」的过渡够用；再高就挡视野 |

**显隐**：`visible = not _bars.is_empty()`；`_dying` 保留原语义「非空且全部在死亡淡出」，`smoke_test` 的既有断言可继续用。

**布局**：`PITCH := 40.0`（名称 11px 在条上方 7px），第 `i` 条 `top = 22 + 40 × i`。
3 条占 22–140px；UI 轴缩放后仍在 4K / 720p 顶部安全区内；条宽维持 `BAR_W = 480`（与单目标时代一致，不做「主条宽 / 副条窄」的视觉分级——那是美术活，不在本批）。

**逐条 alpha**：`draw_rect` / `draw_string` 传带 alpha 的 `Color`，**不用 Control 级 `modulate`**（那是一条死亡全家变淡）。

**为测试留的两个只读入口**（避免测试伸手进内部结构）：

```gdscript
func bar_count() -> int
func bar_state(boss_id: int) -> Dictionary   # 空字典 = 没有这条
```

### 3.2 P-8：`current_bosses()` 只做配置层，**不做**运行态实例查询

产品 §7 P-8 的修法本身就是「数组化 + 兼容壳」，验收写的也是「旧 `current_boss()` 断言零改动通过」。而「返回带运行状态的实例」需要一个**跨场景注册表**，且目前**零调用方**：

- 血条由信号驱动，不需要主动拉取；
- 小地图 Boss 标点走 `Spawner.marker_points()`（`map_markers.gd:21`），不经过 `MapService`；
- 掉落 / 经验 / 刷新全部在 `Monster` 与 `Spawner` 内部闭合。

所以本批**只做配置层**。新增一个没人调用、还要跟着切图 / 重生 / 释放维护生命周期的 API，属于「先造坑再填」——真到 M10-4 令牌定位需要时再加，届时它的需求形态才清楚。

```gdscript
## 当前图全部 Boss 点规格：bossSpawns 优先，回退单点 bossSpawn，都没有 → 空数组。
func current_bosses() -> Array:
	var rows: Variant = current_data().get("bossSpawns", null)
	if rows is Array and not (rows as Array).is_empty():
		return rows
	var single: Variant = current_data().get("bossSpawn", null)
	return [single] if single is Dictionary else []

## ⚠ 仅兼容单点图；多 Boss 图请用 current_bosses()（本函数只给第 0 只）。
func current_boss() -> Dictionary:
	var rows := current_bosses()
	return rows[0] if not rows.is_empty() else {}
```

**语义变化（须知）**：`c7_arena` 上 `current_boss()` 会返回 10 只里的第 0 只。存量图（`bossSpawn` 单点）逐字等价，`smoke_test:3256/3258` 不受影响。给函数加注释标明「只用于单点图」，杜绝新代码误用。

### 4.4 `autoload/audio_cues.gd`

```gdscript
var _boss_seen: Dictionary = {}     # boss_id -> {"name": String, "phase": int}

func _on_boss_hp_changed(boss_id: int, name: String, hp: int, _maximum: int, phase: int) -> void:
	if hp <= 0:
		_boss_seen.erase(boss_id)
		return
	var prev: Dictionary = _boss_seen.get(boss_id, {})
	if String(prev.get("name", "")) != name or phase > int(prev.get("phase", -1)):
		play_cue("boss")
	_boss_seen[boss_id] = {"name": name, "phase": phase}
```

删掉 `_boss_name / _boss_phase`（已核对：`AudioCuesTest` 不引用这两个字段，只读 `cue_counts`）。这样「新 Boss 出现」与「升阶段」两种音效在多目标下语义仍然正确：同一只重复心跳不响，两只同名不同实例各响一次。

| # | 组 | 断言要点 |

## 9. 一句话总结

**血条多目标的本质是「信号补身份」**：补 `boss_id` 后，血条与音频各从「一个游标」变「一张表」，跳位问题从根上消失；`current_bosses()` 只是把单点配置数组化，**运行态实例查询留到真有调用方时再做**。
