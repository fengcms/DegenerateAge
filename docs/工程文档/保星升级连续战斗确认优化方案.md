# 保星升级连续战斗确认优化方案

保星升级正常需要两次点击。当前打怪或拾取期间，第一次风险确认会反复被清除，导致多次点击。以下结论来自当前代码核对，尚未采样玩家实战的事件频率。

`scripts/ui/equipment_fusion_panel.gd:184` 的材料重校验已允许同一装备的耐久变化，能够保留材料格。但是函数末尾无条件清除风险确认。因此击杀磨损触发装备和背包事件后，旧装备仍在格内，按钮却回到第一次确认。金币事件也无条件撤销确认，拾取金币或自动出售同样会触发。

此外，刷新如意下拉框会按库存自动清空不足的选项。如果只删除确认重置，可能出现第一次确认带四枚如意、最终却用较少如意结算的变化。必须锁定交易意图再允许无关事件通过。

建议第一次点击锁定旧装备和新装备的实例、除耐久外的材料内容、四格如意种类与数量、费用、产物等级和自动穿戴条件。第二次按稳定实例 ID 重定位材料，确认同一笔交易。

- 普通磨损更新当前材料快照；打怪涨经验、捡入无关物品、背包整理和金币余额变化，只要仍满足费用和材料要求，都保留确认。提交时沿用最新完整材料快照，匹配现有 `GameState.forge_equipment` 的严格校验。
- 更换任一材料、材料属性变化、手动调整如意、旧装备从穿戴变成背包或反向变化时，清除旧确认。重新选择后展示新的消耗和穿戴结果。
- 确认期间如意库存不足，不自动减少本单如意。保留已确认数量并显示缺少材料，提交时整笔拒绝。金币不足同样不扣装备或如意。恢复足额后仍按原交易提交。
- 玩家等级改变时重算产物穿戴条件。如果从暂不可穿变为可自动穿戴，展示更新后的结果并重新确认。普通同级经验变化不影响确认。
- 关闭窗口、更换服务或结算结束后清除确认快照。相同交易重复提交不得重复扣费。

实现上保星使用独立交易快照，复用现有材料定位、耐久兼容比较、如意计数与结算入口。库存事件按显示帧合并预览刷新，关键提交仍同步检查最新状态。

验收分两个节点。先验证确认条件和结算保护，再接面板反馈与分帧刷新。实际窗口在两次点击间注入击杀磨损、金币增长、自动拾取和整理，验证两次点击成功且消耗原装备、原数量如意和原费用。再验证批内材料变化、如意不足、金币不足、穿戴位置变化、跨级穿戴条件改变及连点。回归成功后自动穿戴、产物暂时穿不上和其他合成服务。每个节点验证后独立提交。


## 实施记录（2026-11-03）

已将保星风险确认改为面板会话内的交易条款快照。第二次点击先同步重定位两件材料、更新耐久并比较条款，再调用既有同步结算入口；两者之间没有异步等待。结算层原有完整快照、如意和金币校验保留，因此无需另建交易结算接口或修改存档。

保星库存、穿戴、金币与等级事件复用 `FrameLayoutScheduler`，每显示帧最多一次后台控件刷新。材料状态仍即时核对，点击时立即刷新并校验，不等待队列。快照仅持有两件材料与四格如意，关闭、切换服务、手动改料和结算后释放；调度器沿用宿主弱引用，关闭后的回调不更新界面。每次材料通知最多重定位两件已选装备；本轮没有增加全背包排序或逐物品节点创建。

稳定确认与预览保护共同构成一个修复节点：如意不足时必须保留选择并禁用提交，不能先单独上线“不撤销确认”。现有四金、四紫与紫装献祭流程不改变。

验证采用隔离存档的实际窗口测试。扩展 `EquipmentFusionUiTest`，覆盖磨损后一次追加点击结算、连续 32 轮库存及金币通知、金币不足再补回、旧料移入背包、等级跨过穿戴门槛、四枚钻石如意不足后补回。原有材料替换、非耐久属性比较、自动穿戴与等级不足返回背包断言继续保留。本轮未采样百首禁域 16 倍速实战帧率，不将按帧合并等同于已证明的 FPS 提升。

最终验收：`EquipmentFusionUiTest`、`StarTransferAutoEquipTest`、`StarTransferLevelHintTest`、`EquipmentLayoutRegressionTest` 四项 `--rendered` 全部通过；`git diff --check` 通过。
