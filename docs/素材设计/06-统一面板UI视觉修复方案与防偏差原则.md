# 统一面板 UI 视觉修复方案与防偏差原则（待确认）

日期：2026-10-15。本文承接[视觉还原偏差分析](05-统一面板UI视觉还原偏差分析.md)，以用户修订的 [背包与人物浮窗 SVG](样板/统一面板UI-v1/01-背包与人物浮窗.svg)和[组件细节 SVG](样板/统一面板UI-v1/04-组件细节.svg)为视觉基准。本阶段只提交修复方案与防偏差规则，**不改游戏 UI 或玩法**；待用户确认后才执行。

## 1. 修复目标和边界

目标是让游戏里的共用面板在实际尺寸下保留设计稿的轮廓、层级、金属质感和克制的线条数量，同时保持按钮文字、物品数值、页签等运行时内容可变。优先修复已确认的四处差异；顺带核对同一共用组件的其他明显遗漏，但不借此重排背包内容或改动交互流程。

以当前代码为基础：[共用外框与控件样式](../../scripts/ui/panel_chrome.gd)是主要修改点；[背包面板](../../scripts/ui/inventory_panel.gd)是首个验证场景。人物、技能、坐骑、设置、任务和 NPC 服务面板使用相同外框或样式，须检查复用效果。装备拖拽、窗口叠放、Esc、设置改键、背包容量和交易规则保持原样。

## 2. 逐项修复设计

| 部件 | 拟采用的实现 | 完成判据 |
|---|---|---|
| 帮助与关闭按钮 | 共用一个圆形标题按钮组件，分别提供图标和配色。明确**实际宽高相等**的尺寸约束，标题行中居中放置，不让容器纵向拉伸按钮；圆环、内衬和符号分层绘制，文字/符号保持清晰。悬停、按下、键盘焦点按同一外轮廓处理。 | 100% 时二者都是圆，不出现 26×40 或 30×40；80/150/200% UI 倍率及文字放大后仍为圆，图标居中且可点击区域足够。 |
| 四角金色刻线 | 从 SVG 提取四角的折线路径和相对边距，保留“短横—斜段—短竖”的切角结构。共用外框按实际宽高定位四个角；长边可伸缩，角件本身保持原始比例，不拉长斜段。外层八边形与内侧角饰分别核对。 | 四角均能看到折线的斜段；最小、常规和较大窗口宽高下，角件不变形、不穿出外框、不被内容覆盖。 |
| 常规操作按钮 | 建立按钮视觉规格：外边、深色内衬、渐变、高光细线、文字层；为普通/主要按钮规定默认、悬停、按下、禁用、键盘焦点状态。优先把 SVG 的装饰层拆成可复用的局部素材，以九宫格只拉伸中段；文字和可用状态继续由 Godot 控件管理。若局部素材在项目的显示缩放下不清晰，再以同一规格改用脚本绘制，不能直接退回纯色 `StyleBoxFlat`。 | 与 SVG 局部放大对照，按钮上沿高光、明暗过渡、边框层级可见；长度变化时端部不拉花，中文按钮文字不烘进图片；各状态仍易区分。 |
| 标题下的分隔线 | 指定共用外框为**唯一标题分隔线的绘制者**，按 SVG 保留视觉上“一条”的细亮线及其紧贴暗侧，不把暗侧当成第二条独立分隔线。逐面板辨别标题分隔和内容分组线，移除与标题重复的 `HSeparator`，保留真正用于内容分组的线。 | 标题下只出现一个连续分隔效果；背包、人物、技能、坐骑、设置及服务面板无重复线；内容区本来需要的分组线仍在。 |

这里选择“共用组件＋局部素材/精确绘制”的混合方式：框体长边与动态尺寸由代码控制，细节纹样保留设计稿结构，按钮文案保持运行时文本。正式制作前会记录每个组件的源稿区域、尺寸、可拉伸段、非拉伸角、层级与状态；不能直接把整张固定尺寸 SVG 当成面板背景。

## 3. 实施顺序与检查点

1. **建立组件对照表**：以用户修订 SVG 为准，标出四角、标题分隔、圆形按钮、常规按钮在源稿中的边界和层级；记下当前背包实机图对应区域。无源稿的 hover/pressed/focus/disabled 状态沿用同一金属语言补充，不假称它们已由 SVG 完整定义。
2. **先做独立组件预览**：在 Godot 中同时展示窄/宽面板、两种标题按钮、长短文字按钮及各交互状态。先检查几何和质感，再接业务面板，避免修改共用 `PanelChrome` 后把偏差传播到所有窗口。
3. **背包首验**：替换共用视觉部件并清理背包标题重复分隔；在正常游戏画面截图，与 SVG 按相同 UI 逻辑尺寸并排检查四处差异。核对背包打开、关闭、帮助提示、按钮操作、拖动与滚动。
4. **复用面板逐一核查**：人物、技能、坐骑、设置、任务、商店、车夫、铁匠等使用共用组件的面板逐个开窗确认。仅对存在重复标题线或局部排版冲突的调用方作针对性调整，不统一删除所有 `HSeparator`。
5. **缩放与交互回归**：按现有设计规划覆盖 1280×800 基准、常用较大分辨率、UI 80/100/150/200% 和文字 100/150/200% 的关键组合；检查窗口并排、长标题、按钮按下/禁用/键盘焦点与 Esc。运行相关现有功能测试；视觉通过必须来自实际渲染截图，headless 功能测试不能替代。

每一阶段保留对照截图或局部裁图，列出“设计稿—游戏—差异—处理结果”。若某个局部与已确认源稿仍明显不同，须明确记录原因并请用户判断，不能在交付描述中写成已完整还原。完成修复和验证后，按仓库规则独立提交该节点；本方案的确认不等于提前宣称修复通过。

## 4. 今后避免同类偏差的原则

1. **确认稿是视觉验收依据**：用户修改过的 SVG 优先级高于早期样稿、实现者印象和旧截图。先锁定对应版本及局部，再开发；内容和玩法依据现有产品规则，视觉不得自行省略。
2. **设计转实现必须有映射表**：每个可见层都标明“源稿位置/用途 → 游戏组件/资源 → 缩放行为 → 交互状态”。主动记录无法直接映射的项目，并提出等效方案；不能把未实现的高光、斜角称为“风格接近”。
3. **结构复用不等于视觉还原**：共用容器解决维护和布局，具体折线、明暗、高光仍需独立复核。共用组件先过预览，再被多面板复用，避免一次简化造成成批偏差。
4. **所有权唯一**：外框、标题分隔、内容分组线分别指定绘制者。同一位置只允许一个组件负责视觉效果，调用方不能再额外补一条“看似相同”的线。
5. **按实际尺寸验收**：`custom_minimum_size` 不是最终尺寸。要检查 Godot 布局后的真实矩形、不同 UI/文字倍率以及资源拉伸结果；圆形、切角、边框和触控区域以运行时表现为准。
6. **视觉与功能双轨验证**：功能测试检查操作和数据，实机截图检查形状、层级、间距、质感；至少有整窗、角饰/按钮/标题的局部放大对照。只通过其中一轨不能称为完成。
7. **明确偏差及决策**：若出于清晰度、性能或动态布局需要改变设计稿，先给出可见的替代预览和实测依据，请用户确认；未经确认不把省略当作默认优化。
