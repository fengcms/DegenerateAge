# 可视化地图编辑工作流建议：以幸存者营地为试点

这份文档回答「能否由美术提供素材、由策划在画面里摆地图」：**可以，而且适合本项目**。建议先做一个嵌入 Godot 的营地专用编辑器，沿用现有运行结构；等一次完整地图编辑、导出和实走验收跑通后，再考虑扩展为其他地图共用工具。本文是设计方案，尚未实现编辑器，也不改变当前营地地图数据。

## 现状与判断依据

营地当前画面是相对屏幕呈矩形的 **1672×941 参考画布**，运行世界矩形是 **3200×1800**，导航网格 **110×110**。`data/map_art/camp_whitebox_v2.json` 保存道路控制点、七个整体实体、四段围栏及碰撞轮廓；`tools/build_camp_whitebox.py` 编译通行布局；`tools/build_camp_style_full_b_v2.py` 生成地纹、道路与分层美术；`scripts/world/ground.gd` 按同一画布尺寸投影到世界、加载素材并建立整体碰撞。也就是说，底层已有「数据驱动」，缺的是把这些数据在**最终画面坐标**里直接编辑的界面。

这几轮制作暴露的问题有共同根因：地面、道路、实体、通行和遮挡分别在源图、生成器、JSON 与游戏窗口之间往返调整。只看源图不能发现草朝向、实装比例或玩家穿过物件；只改碰撞又无法预见画面的空隙。最近的地纹倒置尤其具体：生成器把 1024×1024 裁片的下半部分垂直镜像，视觉上草向下生长。本轮已改为同向循环，并在接缝窄带处理边缘；[更新后的全图](样板/幸存者营地B二版/camp_ground_upright_overview.png)与[200% 局部](样板/幸存者营地B二版/camp_ground_upright_200.png)可复核。它说明编辑器必须把最终合成预览和可行走层一起展示，而不能只显示素材库。

## 三种可视化方式

| 方式 | 你能直接做的事 | 与本工程的关系 | 判断 |
| --- | --- | --- | --- |
| Godot 原生 TileMapLayer | 画 64×32 小地块、地形边缘与局部装饰 | [官方 TileMap 文档](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)支持分层和地形绘制，但营地的大屋、树、马车、整体碰撞与自由形状道路不能只用单格画笔表达；场景瓦片过多也有实例开销 | 作为地表局部画笔，不作为整个地图的数据核心 |
| Tiled | 图层、瓦片和整体图像对象的拖放，物件属性、碰撞多边形 | [对象层](https://doc.mapeditor.org/en/stable/manual/objects/)和[分层](https://doc.mapeditor.org/en/stable/manual/layers/)能力现成；但等距对象坐标有它自己的投影约定，需编写并维护 Tiled JSON → 本工程画布／网格的转换器，验证坐标、脚底锚点和碰撞 | 适合快速体验编辑手感或做独立样板；不建议未经转换直接替换运行数据 |
| 项目内 Godot 编辑插件 | 在现有矩形画布上拖整体实体、画路、调整碰撞和预览玩家遮挡；一键按项目规则导出 | Godot [EditorPlugin](https://docs.godotengine.org/en/stable/tutorials/plugins/editor/making_plugins.html) 可在编辑器内扩展界面，[主屏幕插件](https://docs.godotengine.org/en/stable/tutorials/plugins/editor/making_main_screen_plugins.html)可提供完整编辑画布；可直接复用现有素材与校验逻辑 | **推荐作为正式流程**，前期需要做一次工具开发 |

推荐的关键不是换一套渲染系统，而是给**现有营地数据增加可视化编辑入口**。从当前正式地图开始建立样板，保证编辑前后运行图不跳变。Tiled 仍值得做短时体验验证，但不必让游戏长期同时维护两种地图事实源。

## 你实际使用的编辑界面

打开「营地地图编辑」后，主画布显示游戏中相同的矩形构图。左侧是我准备好的素材库，分为地面变化、道路段、草/碎石、小型装饰、建筑、树木、马车、灯和围栏。上方切换图层，右侧编辑所选物件属性。底部可切换 100%／200% 预览与玩家比例尺。

1. **地面层**：我先提供基底和同方向的草、土、碎石、石板变化。你可用适度大小的画笔局部点缀；有方向性的草和阴影默认禁止翻转，所有铺地边缘都在预览里显示接缝。大底纹仍批量或整体绘制，不生成上万个独立 Sprite 节点。
2. **道路层**：沿路拖控制点或铺短的转角、路口、边缘模块，实时显示实际碎石效果。道路可以单独隐藏，确认它是透明覆盖层，不会涂成大面积柔边色块。
3. **整体实体层**：从库里一次拖入一栋房子、一棵树或一辆马车。一个实体有稳定 ID、画面矩形、脚底锚点、完整背层、完整前沿层和**一个合并的碰撞多边形**；可以拖动和缩放，但不能把房屋拆成一堆 1×1 小瓦片。编辑器画出玩家前后遮挡线，并实时用人物剪影预览。
4. **逻辑叠加层**：用颜色显示不可走区、NPC/传送落点、入口、出口、推荐行走路线和玩家碰撞半径。拖动实体后先提示哪些通路会受影响，再由同一布局数据重算导航与碰撞；不允许单独改画面却留着旧碰撞。
5. **检查与导出**：按按钮生成游戏现用 JSON／贴图清单并运行营地测试。导出前校验尺寸、ID、越界、NPC 可达、入口连通、贴图存在、背层／前沿遮挡与实际碰撞。数据冲突直接指出地图上的位置。

编辑器画的是**屏幕画布坐标**，因为你希望地图在屏幕上呈矩形；它另画一层 64×32 等距投影辅助网格，以便检查角色移动。画布位置通过目前 `ground.gd` 的画布→世界映射转换，世界／网格位置由既有 `Iso` 逻辑转换。两套坐标必须同时可见，避免把视觉矩形误认为逻辑网格矩形。物件吸附默认关闭或使用画布辅助线；只有定位角色落点时才吸附导航格。

## 我需要先提供的素材包

最小可用包不追求数量，先保证每一类能组合：① 营地地面基底与少量同朝向、可混铺的草土石变化；② 道路直段、转角、路口、边沿的透明像素模块；③ 小型单格草、碎石、杂物；④ 当前已认可的房屋、树、马车、灯、围栏等整体实体，各自带清晰预览、运行图、脚底锚点、碰撞轮廓和前沿分层；⑤ 一个与角色尺寸一致的预览剪影。素材库记录稳定 ID、参考画布尺寸、允许旋转／翻转规则与运行资源路径。新增素材先在样板里看 100%／200% 效果，再进库。

你负责在地图里决定构图、道路、装饰密度和整体实体的位置；我负责制作可组合素材、维护生成与校验、处理遮挡／碰撞边界，并根据你的实走反馈补素材。这样你能快速试几种布局，我不必每次靠文字猜测位置，同时程序规则仍有明确验收入口。

## 实施顺序与验收门槛

1. **只读原样导入**：编辑器显示当前营地，与正式运行截图逐物件对齐。尺寸、NPC、道路、障碍和像素位置不能漂移；此阶段不写新数据。
2. **先开放整体物件和道路编辑**：支持拖动、撤销／重做、保存、重新打开、导出。选一棵树和一段路做往返测试：导出后视觉位置、碰撞、多条行走路线一致。冻结 NPC、出入口和世界尺寸。
3. **再开放地面画笔与小型点缀**：补少量高复用素材，检查方向、接缝、100%–200% 清晰度和重复纹理。对同一营地只改局部地表，不重做已满意的建筑。
4. **最后推广**：用户能在编辑器里完成一块营地局部，并在游戏里得到预期结果后，再为其他地图做资产库与坐标适配。每张地图保留自身视觉方向、锚点和碰撞清单。

每个阶段都要比较导出前后游戏截图，并运行现有 `CampFullArtAcceptanceTest`（实体、路线、NPC、地纹）、`MapTextureBatchTest` 和 `SmokeTest`。工具本身还需验证撤销／重做、重新打开后数据稳定、同一输入重复导出一致；窗口实测加载和帧时间，不能因编辑方便把地面变成逐格节点。编辑器阶段的验收点是「你在画面里改了一个对象，保存后游戏里以相同位置、层次和通行结果出现」，而不是编辑器窗口本身做得多复杂。

## 当前范围与下一步

目前还没有这个可视化编辑插件；正式营地仍由现有 JSON 和生成器驱动。下一项最有价值的开发是**原样导入当前营地的只读编辑画布**，先验证屏幕矩形、世界投影、图层顺序和可行走叠加完全吻合。该节点通过后，再开放拖动及导出，避免工具一开始就把已经满意的营地改坏。
