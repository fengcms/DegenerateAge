# 11—60 级怪物正式动画制作方案（执行中）

本方案接续[23 号美术计划](23-11至60级装备物品怪物美术开发计划.md)及[临时怪物接入验收](制作记录/11-60级/临时怪物接入验收.md)。目标是在保留当前可玩的临时外观、怪物 ID 和战斗规则的前提下，逐只把第二至六章 79 只怪物换成可信的八方向动画。F0 的包清单、地图级缓存、79 ID 制作矩阵和[分层源稿契约](41-怪物分层动画源稿与烘焙契约.md)已建立；F1 汲灵幼虫的[八向静态候选](制作记录/11-60级/正式动画F1方向样本复核.md)尚未通过方向结构与分层门槛，正式动画仍为 0/79。

## 1. 为什么重订生产方式

现在 **41 普通、22 精英、16 首领**均有独立概念稿与可用的单方向三格临时图，`appearanceId` 已稳定地指向各自档案；正式动画仍是 **0/79**。此前汲灵幼虫的[八向和待机图集试作](制作记录/11-60级/动画样本技术验收.md)实测失败：背向露出正面口器，多帧只发生像素抖动，脚底和附肢遮挡不能连续。因此，不再把“整张八向多帧图集”交给图像生成工具一次完成，也不把临时图放大、镜像、晃动后称为正式动画。

本机已具备 Godot 和 ImageMagick，未发现 Blender、Aseprite 或 LibreSprite。方案**不以新增商业软件为前提**：用逐方向的分层透明图作为可编辑源稿，在 Godot 中装配/预览，离线烘焙为现有 PNG 图集。图像生成可辅助产出造型和孤立部件草稿；背面、非对称结构、遮挡、接地和接触姿势必须由逐帧人工校正。若某个形体在分层变形后明显像纸片，应直接绘制该动作的关键帧，不强行套骨骼模板。

## 2. 交付标准和必须保留的玩法边界

| 对象 | 正式交付 | 允许复用 | 不允许代替 |
|---|---|---|---|
| 78 只可移动怪物 | 八个屏幕方向的 `idle/walk/attack/hit/death`，每个状态有实际姿势变化、统一脚底/悬浮锚点和元数据 | 同形体族的运动节拍、骨架结构、工具脚本 | 同一张概念图换色、水平镜像后不校正主光/非对称部件、整帧平移充当步行 |
| `c4_normal08` 哨塔寄藤 | 八向 `idle/attack/hit/death`；移动速度为 0，不制作无用途的走路画面 | 定点根系的收缩规律 | 用空白或重复帧凑 `walk`；先让加载器支持非移动状态清单 |
| 17 只远程怪 | 基础五状态中的 `attack` 需有清楚的起手和施放轮廓 | 现有投射物/法术效果 | 在动画回调中重复结算伤害 |
| 16 名首领 | 独立剪影、基础状态和逐只列出的技能/阶段姿势 | 共用预警绘制、技术渲染器和部件运动方法 | 用同一个首领图换色，或用通用攻击动作覆盖所有专属技能 |

方向顺序固定 `s, sw, w, nw, n, ne, e, se`。首轮样本按[01 规范](01-视觉与技术统一规范.md)的建议帧数检验：`idle 4 / walk 8 / attack 6 / hit 2 / death 6`，即移动怪 208 格；FPS、循环和接触帧逐状态登记。批量阶段可依动作质量和实测资源成本缩减某个形体族的**真实动作帧数**，但不得重复静图凑数量，且八方向与所有实际使用的状态不减。画布以普通 80×80、精英 112×112、首领 192×192 为起点；超出轮廓时按 ID 统一扩画布和脚底锚点，不逐帧裁切。游魂和特殊大型首领可另定固定帧尺寸，制作单写明偏离原因。

**战斗时序不改**：目前普通近战伤害在 `Monster._do_attack()` 调用时立即结算，`MonsterActorArt.attack()` 从 `contact` 帧开始播放后摇；不能在美术计划中承诺“先播放蓄势，到了画面接触帧才扣血”。远程起手、首领预警和章节二的特殊行为按各自现有回调做视觉同步。若未来希望近战也有真正的预备帧并延后伤害，那是单独的玩法时序变更，需另做设计与回归；本批先保持现有结算。

## 3. 可执行的生产线

1. **逐只做八向结构板**：以已通过的概念稿为造型参考，为 `s/sw/w/nw/n/ne/e/se` 建立真实的正面、侧面和背面轮廓。记录头、躯干、近/远侧腿或手、武器、尾/翼、光源、脚底及前后遮挡顺序；左右可在严格对称的虫兽上借用基础形状，但主光和身份部件必须重新校正。产物是可编辑的分层透明图，不能只保留一张扁平 PNG。
2. **按形体族制作动作母版**：先区分甲壳多足、蛇/蛭、四足兽、人形持械、翼兽、游魂悬浮、根系/定点七类。共用的是关节、步态、时间曲线与脚底规则；每个 ID 仍以自己的八向结构板装配和校正剪影。精英在相应母版上增真实结构件和专属攻击姿势；不能只改色或放大。
3. **离线烘焙，再像素修整**：Godot 制作工具在固定帧时刻渲染透明层；导出脚本按状态和方向排图，自动检查尺寸、透明边、锚点、方向顺序和元数据。人工在原生尺寸逐帧修补关节穿透、轮廓破碎、主光跳变与接触帧，并与当前临时图、玩家和地形同屏比较。烘焙工具不能直接把合格标志写进清单。
4. **按 ID 接入和回退**：正式图集存 `assets/sprites/monsters/<id>/`，源层与动作文件存 `art_source/chapters/chNN/monsters/<id>/animation/`。外观档案仍用原 `appearanceId=<id>`，仅把 `renderer` 从 `static_atlas` 改为 `animation_pack`。某 ID 没通过则继续使用其临时图，其他已合格 ID 可独立上线；存档、刷新、任务和掉落不迁移。

正式资源的状态图集采用 `MonsterActorArt` 的**列＝时间帧、行＝方向**契约，每状态一个 PNG 和一个 `animations.json`，记录 `frame_size/pivot/directions/frames/fps/loop/visual_contact_frame`。`SampleActorArt` 的“列＝方向”格式只供已有资源使用，不作为本批新图集输出格式。预览 GIF/视频、临时三格图和概念大图不进入正式运行依赖。

## 4. 三只样本先验证方法，再排期 79 只

| 样本 | 为什么选它 | 必须解决的难点 |
|---|---|---|
| `c2_spirit_larva` 汲灵幼虫 | 失败试作的原对象；普通多足形体 | 真背面、近远侧足遮挡、腹囊运动、八向步态与固定脚底 |
| `c2_elite_broken_inspector` 断链巡检长 | 非对称的人形持械精英 | 铁链/武器手的方向层序、攻击接触姿、装甲不穿模 |
| `c2_boss_hundred_arm_extractor` 百臂汲灵机 | 第二章结构最复杂的首领 | 核心与机械臂分层、汲灵/落锤/阶段姿势、技能预警不被遮挡 |

样本必须在 Godot 实窗中展示八向转身、全部实际状态、0.8/1/1.5 倍率、静止与战斗相邻帧；记录每只的实际制作耗时、返工点、源层数、PNG/导入后纹理大小和装配限制。**三只全部通过**后，再用实测工时计算余量：`41×普通单只工时 + 22×精英单只工时 + 16×首领单只工时 + 工具/复核成本`，按形体族修正复用收益。现在不给“几天完成 79 只”的未经样本验证承诺。

样本失败时暂停批量复制：先判断是八向结构稿、分层渲染、像素修整或运行时接入的问题。只有样本证明质量和成本可控，才扩大到 79 只；否则交付失败样本、耗时和替代路线供重新裁决，不用低质图凑齐数量。

## 5. 工程准备与资源预算

- **先改加载链路，再批量导出**：现有 `tools/build_monster_animation_assets.mjs` 只硬编码第一章 4 个包，`MonsterAnimationLibrary.PACKS` 是全局预载；`MonsterActorArt` 也把 `stomp/enrage_summon` 等第一章首领行为写在通用渲染器中。样本阶段要把生成器改为读取已审核的包清单、分离通用状态与首领专属状态，并验证导出包能加载。`c4_normal08` 必须允许无 `walk`。优先复用现有 `animation_pack` 档案，不开第二套正式数据身份。
- **明确资源释放**：若 79 只都按 208 格、普通 80²/精英 112²/首领 192² RGBA 计算，未压缩像素上界约 **895.2 MiB**，还不含技能图、导入副本与显存开销。当前地图配置静态统计为每图最多 **9 个不同怪物 ID**、约 **79.6 MiB** 基础图集像素量；这不是实际峰值。正式版不能像当前 `SimplifiedMonsterLibrary` 那样全局预载 79 套。按当前地图实际刷新和首领 ID 预取本图所需包，场景切换/无实例后释放，并实测缓存行为；退出正式图的 ID 同时从临时预载表移除。
- **热路径不做图集工作**：资源解码、方向排版和补帧只在离线工具或地图准备阶段发生；同一外观的多个实例共享纹理。`_process` 只推进帧索引，不读文件、不生成图片、不逐怪复制纹理。首次遭遇、跨图、满刷新、长时间挂机都计入性能验收。
- **动作事件适配**：现有 `Monster` 的命中、受击、死亡、首领预警与阶段仍是唯一结算事实源。表现层只消费事件。第二章 3 名首领的硬编码招式与第三至六章 `bossSkill` 的线/扇/圈共 13 名首领，要逐只列实际视觉动作与事件，不以相同形状推断相同姿势。

## 6. 批次、提交与验收门槛

| 批次 | 工作 | 准出及提交粒度 |
|---|---|---|
| F0 技术契约 | 冻结 79 ID 的形体族/可动性/远程/首领技能矩阵；做可编辑分层格式、通用状态/专属状态元数据、资源按图加载和导出验证工具；采集当前性能基线 | ID 双向校验、图集尺寸与状态验证、导出包实际可载；工具和契约分别提交 |
| F1 三样本 | 上表一普通、一精英、一复杂首领从八向结构稿做到实窗战斗 | 每只独立提交源层、五状态或实际所需状态、图集、测试、原尺寸预览、工时记录；三只均通过才批量化 |
| F2 普通怪 | 按七形体族复用运动母版，再按地图/章节接入 41 只 | 每 3—5 只一个可回退提交；原生尺寸、转向、移动、攻击与死亡逐只验收 |
| F3 精英 | 22 只在对应形体族上增加结构与身份姿势 | 每 2—3 只提交；与同族普通怪同屏可辨，不用纯颜色区分 |
| F4 首领 | 16 名首领分别制作独立技能、阶段和死亡关键姿势 | **一名首领一个提交**；预警/接触/阶段切换与现有逻辑逐项核对 |
| F5 全局验收 | 全 ID 资源、导出、章节战斗、长时间密集战斗、存档/切图、内存释放 | 79/79 的正式动画状态和实际接入均通过；更新清单并移除无用临时预载，另交实测报告 |

每个 ID 的制作记录至少保存：`data_id`、形体族、八向结构板/源层、使用的动作母版版本、状态帧数/FPS/循环/接触帧、固定锚点、特殊动作与事件、原尺寸预览、人工修整点、正式路径、源文件版本、授权来源、自动检查、实窗审查和接入状态。现有 `reviewed/temporary_static` 不覆盖；新增独立的正式动画进度字段，只有全状态审查及运行验收通过才改为正式接入。

验收分三层：①工具检查 ID、8 行方向序、帧格尺寸、透明边、锚点、状态与资源路径；②人工逐方向检查背面/非对称部件、真实运动、接触姿、死亡轮廓及 0.8/1/1.5 倍率；③Godot 隔离测试与实窗固定场景测试，比较同设备/同地图的冷加载、纹理峰值、帧时间中位数/P95/P99、抽样绘制调用和跨图释放。性能目标为不破坏 16.67ms 体验预算；具体允许增量以 F1 的**同场景前后基线**确认，不凭 PNG 文件大小或一次空场景截图宣布达标。现有全量测试的历史失败继续单列，不放宽旧断言制造“全绿”。

完成定义只有一个：正式动作及首领表现通过上述验收，79 个外观档案确实由游戏加载，`asset_manifest` 的正式动画状态为 79/79；这与目前的 79/79 **临时静态接入**明确分开。
