# 浮窗标题绘制、拖动与叠放命中问题分析

日期：2026-10-15。依据用户提供的技能＋背包重叠截图，检查当前[共用面板外框](../../scripts/ui/panel_chrome.gd)、[浮窗管理器](../../scripts/ui/floating_window.gd)、四个常驻面板及 `Main.tscn` 的节点顺序。本轮**只分析，不修改游戏代码或素材**。

## 结论

截图中的蓝圈、红框、黄框分别由三个边界不一致造成：标题渐变是未按切角裁剪的矩形，且盖住先画的内层轮廓；绘制出的标题带比真正接收拖动事件的控件更高；绘制前后由 `z_index` 决定，而鼠标命中仍受控件在场景树中的先后顺序影响。四个常驻浮窗共用后两套机制，因此背包、人物、技能、坐骑都有同类风险。

| 截图位置 | 代码证据与机制 | 影响 |
|---|---|---|
| 蓝圈：渐变背景压住转角 | [`PanelChrome._draw()`](../../scripts/ui/panel_chrome.gd)先画外框和内层切角线，再用 `draw_texture_rect(HEADER_STRIP, Rect2(7, 8, w-14, 49), false)` 画**完整矩形**标题渐变。矩形没有按内边框切角裁切，覆盖了内层斜角的一部分，还进入内框切角留白。后画的四个独立金色角饰仍在，但被覆盖的内层轮廓无法再显现。 | 角落出现线条突然消失或矩形底色压住折线的观感。问题来自绘制顺序与裁切区域，不是 SVG 素材缺失。 |
| 红框：上沿看得见却拖不动 | [`FloatingWindow.setup()`](../../scripts/ui/floating_window.gd)仅给 `header` 连接 `_on_header_input()`；`panel_box` 的 `_on_box_input()` 只负责置顶。各面板的 `header` 是有上内边距的 `HBoxContainer`，并非整块可见的渐变标题带。实测技能面板外框从局部 `y=0` 开始，标题行从约 `y=25` 才开始、高约 40；渐变本身从 `y=8` 延续到 `y=57`。 | 外框上沿及渐变上半部存在约 17–25 逻辑像素的视觉可拖、实际不可拖区域。缩放后屏幕上这段差距更显眼。 |
| 黄框：背包在前，点击激活技能 | [`FloatingWindow.bring_forward()`](../../scripts/ui/floating_window.gd)只重排四个宿主控件的 `z_index`，没有同步改变输入命中顺序。[`Main.tscn`](../../scenes/Main.tscn)里背包先于技能创建；两块面板重叠时，后创建的技能控件可以先收到 GUI 鼠标事件，即使 `z_index` 较低。技能面板的 `panel_box.gui_input` 收到按下后又调用 `bring_forward()`，于是原本在后的技能被抬到视觉前台。 | 点击视觉上属于前面板的背景、空白或非拦截区域，可能激活后面板；拖动和点击目标都可能与眼睛看到的层级不一致。 |

## 运行时复核

为排除仅凭截图判断的误差，使用当前 Godot 工程做了**临时运行探针**，没有把探针写进仓库：

1. 两个完全重叠的 `Control` 中，先加入树的控件 `z_index=10`、后加入的控件 `z_index=1`；向重叠处送入鼠标按下，收到事件的是**后加入、低 `z_index`**的控件。这验证了当前方案不能仅靠 `z_index` 对齐视觉和 GUI 命中。
2. 实例化真实背包与技能面板，令背包位于技能前方：`inventory.z_index=2`、`skill.z_index=1`。向两者重叠处连续送入点击，日志均为 `HIT skill_box`；首次点击后变成 `inventory.z_index=1`、`skill.z_index=2`。这与用户黄框所见一致。
3. 同一探针量到技能外框位置 `(40,80)`、尺寸 `(590,650)`；标题行位置 `(65,105)`、高度 `40`。标题行比外框上沿低 `25` 个逻辑像素，直接解释红框区域为何不触发拖动。

这些数值来自本次 1280×800、默认 UI 倍率的独立场景复核；面板内容和倍率变化会改变屏幕像素数，但不会改变“绘制区与命中区不一致”的结构性原因。

## 四个常驻面板的影响范围

背包、人物、技能、坐骑都以全屏 `Control` 为宿主，实际浮窗由 `FloatingWindow` 管理；四者均调用 `setup()` 将标题行设为拖动区，并调用 `bring_forward()` 改 `z_index`。它们在 `Main.tscn` 的相对创建顺序是**背包 → 坐骑 → 人物 → 技能**。当两个面板重叠且树顺序靠后的面板视觉上位于后方时，靠后的面板仍可能先命中；尤其是技能覆盖其他三者、人物覆盖背包/坐骑、坐骑覆盖背包的组合。是否在每个像素都发生，还取决于该点的子控件和 `mouse_filter`，不能把所有重叠区域都判成同一结果。

另一个连带问题是：Esc 所用的 [`is_top_window()`](../../scripts/ui/floating_window.gd)依据 `z_index` 判断“最上层”，鼠标却可能命中另一扇窗口。当前视觉、鼠标和键盘的“前台窗口”不是同一个事实源。模态面板、HUD、拖拽幽灵与商店并排窗口有各自层级语义；修复时不能简单把所有 UI 节点无条件移到场景树末尾。

## 后续修复必须满足的判据

- 标题渐变不得覆盖任何外框/角饰折线；切角外的留白仍透明，四角和不同宽高面板都要检查。
- 玩家看到的标题上沿至分隔线之间，除帮助/关闭等按钮外，空白区域应能开始拖动；按钮点击不能误触发拖动。
- 四个常驻面板中，鼠标点击重叠处始终归视觉最前的可交互面板；此时前后台、拖动对象、点击对象与 Esc 目标一致。至少复测背包＋技能、背包＋人物、人物＋坐骑及四窗叠放。
- 交易并排、模态弹窗、物品拖放和 HUD 的既有输入层级不得被浮窗置顶机制破坏。需要用实际 GUI 事件和渲染截图共同验收，不能只断言 `z_index` 数值。

以上是问题定位与验收边界，尚未选择或执行具体修复实现。
