# 高分辨率屏幕视野与UI自适应需求确认

日期：2026-10-12。版本：**v1.0（§9 三个判断已确认）**。

本文解释用户对2K、4K、5K屏幕的显示需求，提出产品方向与可观察的结果。本轮不改代码，不将候选倍率作为已经拍板的开发参数。

## 1. 对需求的理解

用户在当前2K屏幕上感觉正常，在4K上感觉内容太小；把窗口放大后所有内容一起变大，但没有相应获得更宽广的游戏视野。

建议将需求表述为：**窗口扩大时增加可见地图范围；高像素密度屏幕上保持人物、文字与按钮可辨认；界面大小与地图视野可以分别调整。**

“看到更多元素”首先理解为看到地图上更多已经存在的地形、怪物与掉落，以及有空间时显示更多界面内容。它不表示屏幕分辨率变高就生成更多怪物、扩大技能范围或增加背包容量。

尚不能从描述确定具体屏幕尺寸、macOS显示缩放、游戏窗口大小及是否在编辑器内运行，所以本文区分需求目标和设备上的具体倍率。最终参数应以用户觉得正常的2K体验为参照。

## 2. 当前实现与观察边界

| 来源 | 当前配置/实现 | 对需求的影响 |
|---|---|---|
| `project.godot` | 基础视口1280×800，canvas_items拉伸，expand宽高比策略 | 基础画布会随窗口拉伸；expand主要处理宽高比扩展，不能保证同宽高比的大窗口获得更多地图 |
| `scripts/systems/settings_runtime.gd` | UI单独通过CanvasLayer缩放，倍率限制0.8至1.5；文字另有0.8至1.5倍率 | 已有UI独立入口，但仍叠加整体画布拉伸；未看到按显示器像素密度自动选择的逻辑 |
| `scripts/ui/settings_panel.gd` | UI档位80/100/120/150%；窗口预设1280×800、1440×900、1600×900 | 不能仅靠现有档位表达完整4K/5K适配 |
| `scenes/entities/Player.tscn` | 相机无显式zoom设置 | 本轮所读配置未提供玩家可用的独立世界缩放入口 |
| 产品文档09 §9.11 | Retina清晰、自由窗口大小、UI缩放不影响逻辑坐标 | 有适配方向，但缺少可见地图与高密度补偿之间的规则 |

当前代码能解释整体放大的可能原因；“4K小”的具体原因仍需实际显示设置确认。没有读取用户屏幕或运行显示对比，不把推断当作实测。

Godot官方说明canvas_items会按窗口大小拉伸基础画布，HiDPI又会涉及高密度窗口与渲染行为。技术依据见[官方多分辨率说明](https://docs.godotengine.org/en/4.6/tutorials/rendering/multiple_resolutions.html)。本文只借此解释当前配置，后续实现需核对项目所用版本。

## 3. 分清四种大小

| 概念 | 例子 | 玩家感受 |
|---|---|---|
| 屏幕物理像素 | 常见4K为3840×2160，5K为5120×2880 | 决定清晰度潜力，不直接等于可用内容面积 |
| 系统显示缩放 | macOS可能把高密度屏幕显示为较小的逻辑桌面 | 字体与窗口不会小到难读 |
| 游戏窗口内容尺寸 | 游戏真正可绘制区域，排除标题栏等 | 决定当前窗口能容纳多少地图与UI |
| 游戏内缩放 | 地图视野、UI、文字各自的偏好 | 决定人物大小、按钮大小与字体大小 |

本文用“2K参照”暂指用户觉得正常的屏幕体验；计算例子采用2560×1440，实际设备可能是其他分辨率。不能仅按名称推算。

200%通常表示宽高各乘2，面积乘4。4K相对2560×1440是宽高各1.5倍、像素面积2.25倍；5K相对它是宽高各2倍、面积4倍。它们都不等于“必须把全部游戏放大200%”。

如果同尺寸高密度屏幕把人物和按钮用两倍像素绘制，可能只是保持原来的视觉大小和更清晰的边缘；如果同时把整个地图画布放大两倍，则会抵消新增视野。渲染密度补偿不能重复应用两次。

## 4. 推荐的产品行为

### A. 窗口扩大，世界视野扩大

同一显示器上拖大窗口，人物、普通怪、地面格子的显示尺寸保持基本稳定，新增区域显示在四周。人物不随窗口宽度从一倍变成两倍。

横向加宽主要增加左右地图，纵向加高主要增加上下地图；地图真实边界外仍受相机限制。比例不拉变形，不为凑满窗口把世界整体放大。

窗口尺寸变化不改变碰撞、怪物数量、仇恨、攻击射程、拾取距离或自动搜怪范围。可见敌人切换可以自然包含更多可见目标，但必须仍按既有射程判断攻击。

### B. UI保持可读，并利用额外空间

HUD贴窗口边缘，字体和按钮保持舒适尺寸。背包、商店等面板按内容排版，大窗口可容纳更多行或并列面板；不会把所有格子无限拉大。更多可见格子不增加实际背包容量。

小窗口下允许面板滚动或重新排布，避免按钮被裁切。长文本与放大字体应重新换行，不能只把字放大压到按钮上。

### C. 高密度自动适配，地图与UI独立调节

默认采用系统提供的显示缩放/密度信息并结合游戏实际渲染尺寸，保持清晰与可读。禁止仅凭“3840”或“5120”固定设200%。当平台信息不可靠时提供手动调节，避免猜测物理尺寸。

建议设置项为：

| 项目 | 候选选项 | 实际含义 |
|---|---|---|
| 显示适配 | 自动，手动 | 自动识别密度；手动允许用户指定显示补偿 |
| 界面大小 | 80、100、125、150、175、200% | 相对已经完成密度补偿的正常UI大小，仅改界面 |
| 地图显示大小 | 80、100、125、150、175、200% | 人物与地形相对正常大小；80%看得更远，200%看得更近 |
| 文字大小 | 100、110、125、150、175、200% | 最终字形大小独立于界面倍率，避免同为 200% 时重复叠乘 |

默认自动适配、界面100%、地图100%、文字100%。100%表示当前设备适配后的正常大小，不表示一个设计单位只能对应一个物理像素。界面和文字倍率按已适配结果应用一次，不重复乘系统缩放。

“地图显示大小”改变相机显示比例，既不改角色真实速度，也不改实际格子尺寸。用户把地图设80%后，等比例可见宽高约为原来的1.25倍，面积约1.56倍；不是多生成56%的怪物。

## 5. 4K与5K上的结果如何理解

以下只是假设窗口填满相同宽高比的显示区域、屏幕密度补偿相同、地图显示大小100%的数学例子，不是设备默认参数。

| 可绘制像素尺寸 | 相对2560×1440的可见宽高 | 可见地图面积 |
|---|---:|---:|
| 2560×1440 | 1.00倍 | 1.00倍 |
| 3840×2160 | 1.50倍 | 2.25倍 |
| 5120×2880 | 2.00倍 | 4.00倍 |

如果5K屏幕密度补偿为2倍，而2K参照补偿为1倍，则两者有效内容宽高相同：5120/2=2560。此时默认地图范围相同是合理结果，因为多出的像素用于清晰度与相同视觉大小。

同理，4K采用2倍补偿时有效宽度为1920，可能比上述2K参照还小。这并不意味着算法坏了，而说明分辨率、物理大小和系统缩放共同决定内容空间。用户若希望该设备显示更多地图，可单独降低地图显示大小，保留UI可读性。

可见世界宽高的概念关系为：`实际可绘制像素宽高 ÷ 有效密度补偿 ÷ 地图显示倍率`。有效密度补偿需统一口径，系统已转换为逻辑单位时不能再除一次。

因此本需求推荐的是“有效可用窗口更大时看到更多”，而不强制所有4K/5K设备都比所有2K设备看得更多。若用户坚持后者，需要另设按分辨率扩大视野的规则，但它可能让小尺寸高密屏上的人物过小，不建议作为默认。

## 6. 三种直观对比

| 操作 | 推荐预期 |
|---|---|
| 同一屏幕把游戏窗口宽高扩大50% | 人物与按钮基本不变大，四周地图增加；面板更有空间 |
| 将窗口移到同尺寸、像素更密的屏幕 | 人物与UI视觉大小接近原来，边缘更清晰；不强求视野增加 |
| 将窗口移到有效工作区更大的屏幕并最大化 | UI仍清楚，地图范围扩大；可再独立调地图或界面大小 |

推荐以第一个对比作为最先确认的核心需求。它直接回应用户“放大窗口不该所有元素一起放大”的反馈。

## 7. 关联体验与边界

跨显示器时自动重算适配，保持当前角色位置、游戏进度和玩家手动倍率；不得反复放大缩小或重置设置。窗口大小与适配更新不重载世界。

地图、HUD、人物头顶名称、飘字分别定义缩放归属：人物、地形和技能范围形状跟随地图；头顶名称、伤害数字与交互提示保持可读文字尺寸，但位置跟随世界坐标。不能为字更大而改变预警范围或点击目标判定。

所有点击、拖拽、地图标记和落点转换须与实际缩放一致，防止“看到一个位置却点到另一个位置”。背包双面板、出售托盘、Boss血条、技能栏与设置面板均需自适应。

更宽视野可能显示更多已有实体，需要性能检查；不得因为某玩家用5K屏幕就提高该图刷新数量。低配置设备后续可另设渲染清晰度选项，降低画面采样时仍保持UI清楚，不能用整体放大地图冒充性能优化。

保存的是显示适配偏好与用户倍率，不把显示器瞬时物理像素写进角色成长数据。显示设置宜作为设备偏好保留；跨存档切换不反复重置当前显示体验，具体迁移由开发方案确定。

## 8. 需求确认后的验收方向

1. 同屏同倍率下，扩大窗口前后角色显示尺寸基本一致，可见地图明显扩大。
2. UI大小变化不改变地图范围；地图显示大小变化不改变HUD字体和按钮大小。
3. 4K/5K高密度下字体清晰、按钮可点击，默认不小到难辨认；不重复应用200%补偿。
4. 不同宽高比、最大化、全屏、跨屏移动时画面不拉变形，关键UI不越界。
5. 点选怪物、拖装备、点击大地图与出口提示在所有倍率下位置一致。
6. 地图边界、怪物数量与战斗实际射程不因显示尺寸改变。

这些是后续验收目标，本轮没有测试或修改设置。

## 9. 三个判断（✅ 已确认 2026-10-12）

| 判断 | 结论 | 状态 |
|---|---|---|
| 1. 放大窗口的作用 | **增加地图视野与排版空间**，人物不随窗口同比变大 | ✅ 已确认 |
| 2. 高分辨率适配的作用 | **自动保持清晰与可读**，使用实际可用空间与系统密度，避免一律 200% | ✅ 已确认 |
| 3. 用户调整方式 | **UI 大小与地图显示大小分开**；人物小可单独放大地图，字小可单独放大 UI / 文字 | ✅ 已确认 |

三条**均按本文推荐值确认，无修改**。实现规格见 `docs/工程文档/17-高分辨率显示适配实施方案（09-A）.md`；落地归 **M5 收口、排在 M5-8 打包之前**（依据工程 16 的 D1）。

校准依据（未变）：以用户觉得正常的 2K 体验、4K/5K 的系统"看起来像"设置、窗口 / 全屏状态为基准，确定默认值与兼容档位。
