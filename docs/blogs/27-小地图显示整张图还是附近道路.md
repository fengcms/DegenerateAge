# 末法纪元·游戏开发27：右上角的小地图，该装下整个世界吗

### 前言

各位看官，地图还小时，把整张图缩进右上角，挺方便。道路、玩家和出口都在一块，基本不用额外设计。

等地图扩大，角色变成一个小点，附近岔路挤成一团。再加上NPC和任务标记，信息好像更多了，真正走路时却不太看得清。

《末法纪元》把小地图调整为跟随玩家的局部视野，大地图继续承担全局查看。这里不只是改一个缩放系数，还牵涉投影、边界、裁剪和已有底图缓存。

这一篇就拆开看看，一块小圆盘为什么会连到这些工程问题。

### 先决定玩家拿它回答什么问题

大地图适合问“整个区域是什么结构、下一张图往哪走”；小地图更适合问“我身边这条路怎么转、附近出口在什么方向”。

如果两者都只是整图缩放，小地图可能重复了全局信息，却没有足够空间表达局部。反过来，小地图只显示身边，也不能替代跨区域规划。

因此这是信息分工，不是哪个缩放值更漂亮。先明确用途，后面才知道哪些标记需要保留、哪些内容应交给打开大地图查看。

[第二十六篇]({{LINK:GAME-26}})讲交通拓扑，玩家需要在不同尺度上理解道路，地图窗口也应分别承接。

### 跟随视野改变的是观察中心

旧整图适配根据地图外框和控件尺寸计算比例，人物移动只改变标记。局部视野则要让观察中心跟随角色，周围地形看起来朝相反方向平移。

控件大小改变时，可以调整比例让设计视野仍有合理范围；世界地图本身并没有缩小，也不需要改寻路坐标。

当前源码根据圆盘半径、瓦片宽度和视野参数计算缩放。这里的参数有明确口径，不能简单称作所有方向都相同数量的地图格。

等距投影在不同轴上有压缩，[第十七篇]({{LINK:GAME-17}})的空间约定仍然适用。窗口直径、世界像素和网格跨度需要区分。

{{IMG:GAME-27-全局与局部}}

### 人走一步，不应该重建整张地形

局部视野最容易引入的退化，是每次玩家移动就重新绘制全部探索底图。地图越大，右上角这一小块反而越贵。

项目保留地形和动态叠加分层，把跟随位移应用到内容节点，已有底图几何继续复用。下面摘取实际更新中的关键部分：

```gdscript
_follow_offset = (_world_rect.get_center() - _view_center) * _scale
if is_instance_valid(_terrain):
    _terrain.position = _follow_offset
if is_instance_valid(_overlay):
    _overlay.position = _follow_offset
```

这不是完整刷新函数，视野中心和投影已在前面准备。它说明跟随位移可以通过节点变换表达，不必因此重造地形网格。

探索变化或布局变化仍需要更新底图。缓存复用只覆盖条件没变的结果，不能因为担心重建，就让新揭示的道路永远不显示。

### 走到地图边缘，人物不一定仍在圆心

如果始终把角色锁在圆心，走到地图边界，小地图就会露出大片空白。当前实现会把视野中心夹在地图外框内，减少无效区域。

这意味着边缘处玩家标记可能偏离圆心，是视口规则的结果，不一定是投影Bug。小地图显示的是有限地图的一块，不是无限平面。

地图比视野还小时，观察中心又应回到地图中心，不能用一个已经没有合法区间的夹取范围把画面推走。

测试要覆盖四边和角落，而不是只站出生点看着正常。矩形外框也不完全等同于真实可走轮廓，洞穴留白还要结合布局显示。

### 圆形边框，不等于内容真的被裁剪

画一个圆盘底色，再把地图放上去，圆外的线和标记可能仍然存在。控件矩形裁切也不能自动产生圆形边界。

项目给地形和叠加内容使用裁剪材质，圆盘本身保留独立绘制。片段在圆外被丢弃，才能让内容真正限制在视野里。

跟随时还要更新裁剪中心的坐标口径。内容节点在平移，材质使用的局部位置也随之变化；只改节点位置不改相关参数，圆形遮罩可能跟着内容跑偏。

这里的圆是UI窗口，不是地面攻击范围。不能因为等距地面圆应画椭圆，就把小地图窗口也强行压成椭圆。

{{IMG:GAME-27-跟随与裁剪}}

### 标记要按可见范围筛，不能挤在圆边

附近的NPC和出口应随真实位置投影。目标在视野外，如果没有明确边缘方向提示设计，就不应把它夹到圆边，制造“它就在这里”的错觉。

路线终点也一样。局部视野只看到一段经过的路径，不代表目标位于截断点。当前终点环要求真实终点仍在圆内，完整关系交给大地图看。

标记本身还有探索和任务可见规则。某个任务允许显示方向，不等于顺手显示周围所有未探索NPC。

因此可见性通常分为信息规则和视野范围两层：允许知道这件事，再判断这个窗口是否需要画它，不能只做一次距离判断。

### 共用投影，才能让路线和图标对齐

世界位置到画布位置的入口应包含跟随偏移，点击反向转换也要扣除同一份位移。否则图标看着对了，鼠标点到的位置却不对。

当前大小地图复用MapCanvas，但模式不同。大地图保持全局适配，局部跟随不应该无意改变它原来的点击导航。

世界相机倍率又是另一项设置。小地图可以维持自己的信息尺度，不能简单把主相机缩放直接乘进去，导致玩家调视野时附近道路也一起消失。

这些组合需要往返验证，不能只比较一张固定尺寸截图。

### 更新频率，也要按信息性质区分

玩家标记和路线需要及时变化，探索底图按探索事件更新，布局按版本失效。把所有内容放在同一轮全量刷新里，容易让便宜变化触发昂贵工作。

反过来，所有显示都统一低频，也可能让玩家标记明显落后或路线取消后仍残留。优化需要区分关键反馈与可合并工作。

隐藏后重开也要检查。窗口不显示时可以暂停某些绘制，但不能恢复后继续展示旧地图和旧探索集合。

[第二十篇]({{LINK:GAME-20}})的缓存条件，在地图控件里同样存在，只是变化来源更多了一个尺寸与模式。

### 怎样验证这次变化没有偷换功能

先固定一个世界点，检查大小地图投影与逆变换；再移动玩家，确认观察中心变化而底图不因普通移动重建。

之后看边缘夹取、圆外裁剪、目标环和大地图模式。地图比视野小、长宽比极端、隐藏重开，也应有明确结果。

项目已有局部视野、缓存和路线用例。本轮文章没有执行游戏测试，命令如下：

```sh
python3 tools/run_isolated_tests.py MinimapViewportTest MapCanvasCacheTest MapRouteOverlayTest
```

逻辑测试能检查坐标和重建计数，圆外像素、线条与文字遮挡仍要实际窗口复核。通过其中一类，不代表另一类自然成立。

### 别拿地图放大，掩盖信息设计问题

如果附近标记太拥挤，可以先看样式、分层和必要性。盲目减少可见范围，可能让玩家更频繁打开大图，也可能刚好看不到下一个路口。

视野参数因此适合作为明确设计值调试，固定路线比较不同窗口和角色速度，而不是某张截图上随手调到顺眼。

历史方案中的直径建议也有试玩待微调的说明。文章不能把设计起点写成所有设备的最佳结果，更不能从节点变换复用就推导整体游戏稳定帧率。

实际发布前，还可以让一位不了解地图的人只看小地图走到附近出口。记录他在哪个路口犹豫，再检查是比例、图例还是道路信息不清。这样的观察不能替代码验证，却能补上单纯坐标断言无法回答的可用性问题。

### 小结

局部小地图的关键，是观察中心、投影和内容边界一起变化，同时保留静态底图复用。

大地图回答全局，小地图解释附近；标记、路线和探索规则共用世界数据，但按窗口职责呈现。各位看官调整地图UI时，先确认它要帮助玩家做什么决定，再去选择尺度和刷新策略。
