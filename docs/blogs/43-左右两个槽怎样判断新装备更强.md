# 末法纪元·游戏开发43：左右两个槽，怎样判断新装备更强

### 前言

各位看官，角色戴着两枚戒指，左边一百分，右边三十分，新捡到一枚六十分的戒指。背包该不该提示它更强？双击以后应该换哪一边？

如果拿它和最强的戒指比较，答案是不如旧装备。如果习惯性替换第一个槽，又会把一百分换成六十分。两段程序各自看起来都说得通，连起来就成了一个很别扭的功能。

《末法纪元》有十四个装备槽，戒指之外，手镯、护腕、护膝也有双槽。这篇就讲这么一个小问题，怎样从一个判断条件，长成需要共同遵守的替换规则。

{{IMG:GAME-43-封面}}

### 先回答替换谁，再回答有没有提升

早期实现容易围绕物品类型写逻辑：它是戒指，就去找已经戴着的戒指。可同类型有两件，找到第一个与找到正确目标是两回事。

比较提示应该基于这次操作真正会替换的对象。目标尚未确定，先把所有同类装备的最高分拿出来比较，相当于替玩家发明了另一套换装过程。

[第四十二篇]({{LINK:GAME-42}})说过身份与位置的区别。这里还要再加一层：位置不仅是放装备的地方，也是本次操作的明确意图。戒指①与戒指②不能只在程序里有名字，确认框里却都显示一个模糊的“戒指”。

### 自动选择有顺序，不能靠遍历碰运气

当前自动选槽先找空位。有空戒指槽，就先把它填上，不必挤掉已经穿好的装备。

两个槽都满了，再找品质最低的一件；品质相同，选评分更低的一件；分数也相同，就保留固定槽序。这里有个容易讲错的地方：当前规则并不是无条件找最低分，品质排在评分之前。

下面是实际选择条件的节选，前面已经准备好了当前槽和已选槽的品质：

```gdscript
if rank < chosen_rank or (rank == chosen_rank and score(current) < score(chosen)
        and not is_equal_approx(score(current), score(chosen))):
    target = sid
```

固定顺序看似不起眼，却能避免相同条件下提示来回跳。玩家刚看完准备替换右边，界面刷新以后又变成左边，即使最后没损失，也会让人不敢相信按钮。

选择顺序是一项产品决定，应当写在共用入口里。若将来想改成最低评分优先，修改的是明确规则，还需要重新检查提示与确认，不能只改一个排序函数。

### 拖到哪里，就尊重哪个槽

自动选择服务于双击这类省操作的入口。玩家把新戒指明确拖到戒指①时，已经给出了目标，程序就不能觉得另一个槽更合适，偷偷替他换过去。

这也是为什么预览接口接受可选槽位。没有指定时调用自动选槽，指定以后核对类型是否合法，再围绕同一个目标计算变化。

自动操作可以提供默认选择，手工操作应该保留控制权。两者最后仍然走相同的穿戴资格、交换和属性刷新流程，否则拖放与双击很快就会出现一边能穿、一边不能穿的问题。

### 更强、降分、降品质，别挤成一个布尔值

装备等级、品质、星级分别承担什么职责，[第四十一篇]({{LINK:GAME-41}})已经拆过。本篇最直接的后果是：品质更低的装备，也可能因为等级、词条和星级而拥有更高评分。

因此预览分别返回评分差、是否更强、是否降分和是否降品质。它们不是一组非黑即白的同义词，也不能用一个“升级装备”的变量全部替代。

当前预览中的这两个字段就明确分开：

```gdscript
"stronger": not worn.is_empty() and score_increase,
"lower_quality": not worn.is_empty() and quality_rank(item) < quality_rank(worn)
```

注意空槽也单独处理。把一件装备穿进空槽可以增加属性，但没有旧装备被替换，“比原来这件更强”的卡片不必凭空造出一个对照对象。

降品质提醒的用途，是让玩家意识到自己正在放弃一档品质。它不是禁止降品质，更不能把评分下降一律拦死。玩家可能需要特定词条、套装条件，或者只是临时换上另一件东西。

### 一个六十分的教学算例

仍然用开头的数字说明比较对象。假设两枚戒指品质相同，评分分别是一百和三十，候选是六十，那么自动目标就是三十分的槽，差值是正三十。

如果玩家把同一件候选拖向一百分的槽，差值就成了负四十。物品没有变化，是替换意图变了。因此背包里一个孤立的绿色箭头，不能代替明确目标以后的完整预览。

这几个数只是解释选择顺序的教学算例，不是游戏里某套装备的实测成绩。真实评分按当前属性和权重计算，耐久等影响也要沿实际入口读取，不能直接比较模板上的裸数值。

还要留意评分的能力范围。当前公共权重主要覆盖攻击、防御、生命和法力，不能声称它已经准确估算所有流派收益。提示越简洁，说明越要克制，不能让一个辅助数字替玩家做全部判断。

### 让卡片、提示和操作共享一份预览

只把自动目标修好还不够。背包角标若继续和最强装备比，提示卡若继续拿第一个槽展示，玩家看到的仍然是三种答案。

比较需要统一到同一个预览结果，包括目标槽名、候选快照、旧装备快照与差值。界面可以按场景少显示几个字段，但不要各自重新发明替换算法。

快照在这里也有用途。绘制卡片时读到的旧装备，应该和这次比较是一份内容，不能标签来自上次刷新，属性来自这次读取。提交前仍要重新核对当前状态，预览本身不授予永久有效的操作资格。

警告选项同样只是交互偏好。玩家选择本次会话不再提示降品质，并不意味着后续操作可以跳过等级、槽位类型和实例有效性检查。

### 满背包替换，和脱下装备不是一件事

另一处值得顺手讲清的是容量。直接脱下装备，需要背包有空位；从背包拿一件换上去，拿走的新装备恰好腾出了自己的格子，可以让旧装备回到原位置。

如果把这两个操作都写成“先检查背包有没有空格”，满包时就会错误拒绝正常交换。反过来，若先脱旧装备再发现新装备不能穿，又容易留下半完成状态。

当前装备规则入口先验证来源、目标和等级，再执行交换。界面只负责提出请求，不应该为了视觉拖拽方便，先把真实背包挖空，失败以后再到处补回去。

这类交换最好用小状态例子推一遍：包满且目标合法、包满但等级不足、空槽穿戴、两个同分槽、显式拖向强槽。它们覆盖的是不同决定，不能只靠一段正常双击录像验收。

### 怎么检查，才不会只证明自己写对了一条分支

定位源码时，可以先沿这些共用入口找调用关系：

```sh
rg -n 'auto_slot_for|replacement_preview|slot_label' scripts/systems/equipment.gd scripts/ui autoload/game_state.gd
python3 tools/run_isolated_tests.py InventoryUpgradeBadgeTest EquipmentLayoutRegressionTest
```

这组命令用于后续复核，本文没有执行游戏测试。真正验收时，除了预览返回值，还应检查卡片上的槽号、拖放目标和最终背包里的旧装备是否一致。

品质相同且同分的用例尤其有价值，它能揭露不稳定遍历；高品质低分与低品质高分的交叉用例，则能揭露程序员有没有把两个概念混在一起。不要为了通过测试，反过来假定评分就是最终战斗收益。

还有一种回归要防：角标刷新后目标换了，已经打开的确认框却仍显示旧槽。确认框不是动态追着最优解跑的推荐器，它表达的是玩家刚刚准备执行的动作。状态变化以后，应重新校验或明确更新，不能悄悄换成另一笔操作。

### 小结

双槽换装的难处不是多了一个数组元素，而是自动选择、手工意图、提示比较和最终交换必须指向同一件旧装备。

先确定目标，再描述变化；把品质提醒与评分提示分开；允许玩家明确选择，也保证提交时资格仍成立。一个小小的绿色箭头背后，把这些边界讲清楚，才不会越做越让人困惑。
