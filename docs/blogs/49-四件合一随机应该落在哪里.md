# 末法纪元·游戏开发49：四件合一，随机应该落在哪里

### 前言

各位看官，背包里堆了一批金装，四件能够合成一件紫装。现在加一个批量按钮，自动分组，随机出结果，好像很快就能写完。

但随机二字，到底随机什么？随机挑四件材料，还是随机产物部位？高档与低档混在一起，按哪一档出装备？玩家点开面板以后新捡到的东西，要不要顺便吃掉？

《末法纪元》的批量四金合紫，把材料选择和产物随机分成了两件事。本篇先讨论分组规则，下一篇再讲整批结果怎样安全写进背包。

### 先说明金装与紫装的内部名字

界面里的金装，对应内部品质键epic；紫装对应legendary。写工程文章时若凭英文印象判断颜色，很容易把材料与产物讲反。

批量候选只从背包取，要求是合法装备、指定金装品质、未收藏，并有稳定实例身份。身上的装备不参与这项批量操作，不能因为全局查得到，就自动纳入。

[第四十二篇]({{LINK:GAME-42}})讨论过身份，到了批量操作更应当明确。候选是具体装备列表，不是某种型号的数量统计。两件同名同属性装备也各有归属，不能为了凑数把同一ID算两次。

收藏保护也应该在入口就生效。把收藏装先排进来，等到提交时再报错，虽然未必丢东西，却会让预览一直承诺一个根本不能执行的批次。

### 默认不吃带星装备，是给省事操作留边界

手动选择一件带星金装，和点击自动批量处理，表达的意图不一样。前者看得见具体物品，后者主要期待清理大量冗余材料。

因此默认排除带星装备，玩家明确开启选项以后才纳入。单件排除同样按实例ID记录，不要因为背包整理，就把原本保护的对象换成另一个格子。

预览需要说明有多少件因星级被保护，多少件实际进入分组，以及最后剩下多少不足一组。否则玩家只看到产物少了，很难判断是规则在保护投入，还是程序漏算材料。

允许加入带星装备，不代表产物继承这些星级。这个模式的产物规则与保星升级不同，不能共用一个含糊的“装备合成”说明就省掉关键差异。

### 同档先组，别让低档材料拖走整包高档

当前规则先按所属套分桶，档内按稳定身份排序，每四件成一组。各桶不足四件的余数，再按低档到高档合并。

这项顺序主要保护可以独立成组的高档材料。如果一开始把全部候选从低到高每四件切一刀，一件低档装备就可能带着三件高档一起落到低档产物。

下面是实际分桶循环里的节选，前面已经取出并排序了当前桶：

```gdscript
while rows.size() >= 4:
    groups.append(rows.slice(0, 4))
    rows = rows.slice(4)
leftovers.append_array(rows)
```

档内稳定排序不是为了提高装备收益，而是让同一批候选重复预览时结果可解释。若每次刷新都随机换一组材料，玩家排除某件以后，很难看懂剩余分组为何又变了。

{{IMG:GAME-49-同档优先}}

### 一件低档加七件高档，怎样分才说得清

用一个只演示分组的算例：五十一级档一件，六十一级档七件。先从高档里拿出四件，组成一组六十一级档产物。

余下的一件低档与三件高档，再组成混档组，按这一组最低档得到五十一级档产物。最终是两组，但两组档位不同。

这里高档余数确实发生了降档使用，系统不该把它藏在“预计获得两件紫装”这一句话后面。数量正确不等于价值说明充分。

[第四十四篇]({{LINK:GAME-44}})讲过套档与部位门槛，分组应调用共同分套规则。不能拿四件材料里最小的原始门槛，直接当成生成模板的档首，否则不同部位又会算出不同口径。

这个方案也不是宣称解决所有可能的收益优化。它采用明确、可说明的同档优先与余数策略，若产品以后改成禁止混档，应该直接调整规则与预览，而不是偷偷换一种算法。

### 混档提醒，要告诉玩家损失落在哪些材料上

当前规划结果分别记录混档组数、被降档使用的高档材料数量和参与的带星材料数量。它们回答不同问题，不能合成一个泛泛的风险标记。

混了一组，可能涉及一件高档材料，也可能涉及三件；带星材料可能同档，未必混档。玩家需要看见是哪一种代价，才知道应该排除某件，还是直接取消这一批。

警告应该出现于决策点，不能只放在很长的帮助文本里。尤其批量操作一次可能处理许多件，省掉点击的同时，也放大了误操作的规模。

但警告不能替代规则执行。玩家已经确认带星投入，程序仍需核对这些具体实例；玩家没确认的收藏装，也不能因为弹过一个总警告就顺手处理。

### 产物可以随机，投入不必跟着随机

这项合成允许产物部位与词条随机。材料分组则保持确定，让玩家知道具体拿哪些东西换哪个档位的机会。

如果把材料也随机化，玩家很可能反复开关预览，只为了避开某几件不想消耗的装备。这时随机没有增加乐趣，只是给控制投入增加了障碍。

产物随机也应发生在正式准备执行以后，预览只显示能够确定的组数与档位，不应在每次界面重绘时生成一批真装备。

[第三十篇]({{LINK:GAME-30}})说过随机序列，输入事件和界面刷新次数不该无缘无故改变结果路径。随机放在清楚的边界，后续重现问题也更容易。

{{IMG:GAME-49-随机边界}}

### 打开以后新掉落，留给下一批

批量面板打开时会冻结候选集合。之后拾取的新金装不自动补进本单，即使它正好能把余数凑成四件，也应该等下一轮。

这与[第四十八篇]({{LINK:GAME-48}})的固定确认批次是一条思路：省操作不能改变已经展示的消耗范围。

背包整理可以按ID重定位，但组内物品移走、内容改变或收藏，应让旧批次失效，不能找另一件同档装备补上。预览如果已经过期，也不该在后台默默重新选料，再把同一个确认按钮继续留给玩家。

冻结的是本次候选与意图，不是冻结整个背包。其他掉落仍能进入当前背包，游戏也不必为了等待玩家看完预览而暂停所有物品流转。

### 纯分组规则，适合单独推演

把候选收集、分组规划与最终提交拆开以后，分组器只需要读输入，返回组别与统计，不需要碰真实背包或界面。

这样可以用少量明确样本核对行为：恰好四件、七件余三、两个档位都能独立成组、多个档位只有余数，以及全部被保护的情况。

还要测试排除某件以后会不会重新形成混档组。排除本身是明确选择，但它引起的分组变化仍应该展示清楚，不能只从数量上减一就假定其他结果不变。

代码复核可以沿这些入口进行：

```sh
rg -n 'buckets|leftovers|downgraded|include_starred' scripts/systems/gold_batch_fusion.gd
python3 tools/run_isolated_tests.py GoldBatchFusionTest GoldBatchUiTest
```

本文没有执行游戏测试，也没有给出某次随机产物的收益统计。上述算例只证明分组顺序的含义，真实运行还需要检查面板风险提示与扣除实例是否一致。

另外，预览里的保护数不应与最终未消耗数混为一谈。被星级保护、玩家主动排除、余数不足四件，都会留下装备，但原因不同。将三类数量分别交代，玩家才能判断下一步是补材料、修改选项，还是保持当前保护。尤其没有任何完整组时，应明确说明不能提交，而不是摆出一个看起来能点的批量按钮。

### 小结

四金合紫的随机应该落在产物机会里，材料选择则尽量明确、稳定、可解释。同档先组，余数再混，降档与星级投入在确认前说清楚。

分组清楚以后，还有最后一个问题：一批准备出几十件装备，做到中间失败怎么办？下一篇继续讲批量提交，为什么不能简单循环调用单次合成。
