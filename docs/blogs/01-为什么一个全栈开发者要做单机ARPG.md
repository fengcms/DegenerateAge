# 末法纪元·游戏开发01：一个全栈开发者，开始做自己的单机ARPG

### 前言

各位看官，这次给大家换个口味，聊聊做游戏。

我最近在做一个叫《末法纪元：最后的守护者》的项目。2D等距视角，单机，实时战斗，打怪、掉装备、升级，再去挑战更强的怪。技术上用的是Godot和GDScript，最初的平台目标是macOS。

写到这篇文章的时候，游戏的程序和玩法逻辑已经比较完善，美术还有不少工作。我想趁这个阶段，把从立项到开发的过程整理下来。

毕竟，回头翻工程记录的时候，能写的东西还真不少：一件装备怎么生成，一笔奖励怎么落袋，角色为什么卡在墙角，挂机时打开背包怎么就卡了，还有一个查了三轮才找到根因的闪退。

这些问题单拎出来，都挺具体。连在一起，就成了一个全栈开发者做游戏的过程。

这一篇先聊开头：我做了一个什么样的游戏，过去的软件开发经验能带来什么，以及换到游戏这个场景之后，有哪些东西需要重新理解。

### 先把“我要做个游戏”说具体

“做游戏”三个字，范围太大了。

消消乐是游戏，开放世界也是游戏。脑子里只有这三个字，下一步很容易变成什么都想加：地图要大，技能要多，装备要丰富，剧情还得有点意思。光列功能，能列得自己热血沸腾。

真落到工程里，每一条后面都是活。

《末法纪元》的起点比较明确：玩家在斜着俯视的地图里探索，遇到怪物就战斗，打完获得经验和装备，再靠成长去挑战后面的区域。

这条循环说起来很普通：

```text
探索地图 → 战斗 → 获得掉落 → 提升角色 → 挑战更强的敌人
```

但我得把里面每个箭头都接起来。

怪物死了，要掉什么？装备掉下来，背包满了怎么办？换上新武器，攻击力什么时候更新？下一次打开游戏，上一次捡的东西还在不在？

玩家感受到的是“我打了一只怪，捡了一件装备”。程序要负责把这件事完整地办妥。

**把这样一条循环从头做到尾，本身就是一个足够扎实的项目。**

### 单机，让问题先落在游戏本身

这个项目从产品定位上就选择了单机，没有账号系统，没有多人服务器，也不做交易市场、抽卡和内购。

作为一个全栈开发者，账号、接口、数据库这些东西并不陌生。可熟悉某项技术，和这个项目需不需要它，是两回事。

一旦加上联网，角色数据由谁说了算，掉落怎么校验，断线怎么恢复，多人状态怎么同步，这些问题马上就进来了。还没把打怪做顺手，就得同时处理另一整套工程。

选择单机以后，我能先把注意力放在眼前：移动是否顺畅，战斗是否有反馈，装备是否值得捡，成长能不能让人感觉出来。

当然，单机也省不掉可靠性。

存档保存在本地，写坏了，玩家照样会丢进度；一件装备重复结算，经济照样会乱；角色走不过墙角，也不会因为没有服务器就自动找到路。

它只是让我可以按一个更集中的范围，把这些问题逐个解决。

### 全栈经验能带过来，而且还挺管用

刚看游戏工程，名词变了不少：场景、节点、碰撞、寻路、技能、掉落。

往里面多看一层，会发现很多老问题还在。

比如装备。做业务系统时，我们知道商品资料和订单里的成交记录不能混着用。到了游戏里，装备模板和玩家手里的那一件装备，也需要分开。

模板描述这种装备是什么；玩家手里的实例，还要记录它自己的星级、词条、耐久等状态。同一种武器可以有很多件，它们可不能共享一份会被随手改动的实例数据。

再比如交易。货郎面前卖一件东西，看起来只是点一下按钮，背后仍然要检查条件、修改物品、结算金币、通知界面。中间某一步失败，不能留下物品没了、钱也没到账的状态。

还有界面。背包、人物面板、商店、确认框，照样有数据更新、焦点、拖拽、遮挡和布局问题。做过前端的各位看官，看到这些应该已经有点熟悉的感觉了。

所以过去积累的建模、模块划分、状态管理和调试经验，都用得上。

**换一个产品形态，过去学会的东西会有新的落点。** 这也是这个项目值得拿来写专栏的地方：从熟悉的软件工程问题出发，看看它们到了游戏里，会长成什么样。

### 但游戏会把一些问题放大

能迁移经验，不等于照搬原来的习惯就够了。

游戏里的世界一直在动。

我打开一个装备面板的时候，角色可能还在打怪。怪物在掉东西，自动拾取在往背包里放东西，金币在增加，身上的装备还在掉耐久。

此时我选了几件材料，准备做一次合成。等我点确认，刚才选中的东西还在不在？背包整理过了，下标变了怎么办？新捡进来的装备，要不要算进这次操作？

这类问题让“点击确认”变得很有分量：程序得知道玩家确认的究竟是哪一笔操作。

性能也是一样。

一件地面掉落没什么感觉，积压到几千件，就得重新检查绘制、拾取判断和物理回调。一个控件刷新很快，整个背包在战斗中被反复重建，就可能成为卡顿来源。

甚至镜头跟随也有坑。正常速度下看着挺稳，开了高倍速，跟随计算的时间尺度不合适，镜头就可能越跟越晃。

这些都是后面会展开的真实问题。它们也提醒我：功能跑通以后，还得放到持续运行、密集战斗和连续操作里看看。

只站在出生点试两下，很容易觉得自己已经做完了。

### 自动战斗，也是一部分正经玩法

《末法纪元》支持手动操作，也有自动战斗和自动拾取。

别看“自动”两个字，做起来需要考虑的事情不少。找哪只怪，怎么走过去，路不通怎么办，打完以后继续去哪儿，玩家按了方向键又该怎么接管。

这些选择最后都会变成角色的行为。处理得不好，玩家看到的就是原地发呆、反复转身，或者明明旁边有怪，却跑去很远的地方。

这里的自动战斗发生在游戏运行期间，退出游戏后不继续打怪，也不计算离线收益。

它把一部分重复操作交给程序，也让程序必须承担更多判断。后面讲自动行为的时候，各位看官会看到，一个看起来很简单的开关，能牵出多少细节。

### 为什么现在开始写这个系列

项目做到这个阶段，已经积累了足够多可以拿出来讲的东西。

如果只展示现在的功能，很容易把过程压缩成一串名词：战斗系统、装备系统、任务系统、存档系统。每个名字都对，可到底怎么做出来的、为什么中途改过，反而看不见了。

我想保留的是这些过程。

有些方案在功能少的时候够用，内容一多就得调整；有些问题第一轮分析看着很合理，继续取证才发现方向错了；还有些优化在简单场景里效果很好，换成完整战斗场景，瓶颈又跑到了别处。

这些经历比一份最终目录更有意思，也更适合和各位看官交流。

系列会从立项和最小闭环开始，逐步讲到地图、战斗、装备、经济、交互，再到性能、测试和故障排查。具体的引擎用法会放进具体问题里讲，需要多少讲多少。

如果你也有软件开发经验，想试着做自己的游戏，希望这些记录能让你更容易判断：哪些能力已经具备，哪些地方需要补课，第一步应该先做多大。

### 小结

这就是《末法纪元》开发实录的开篇。

一个单机ARPG，从能走、能打、能捡东西开始，慢慢长出了后面的系统。全栈开发的经验帮得上忙，游戏持续运行的特点，也带来了新的功课。

接下来我会把这个过程一篇篇拆开。做过的讲做法，改过的讲原因，踩过的坑就把证据摆出来。

下一篇，先从产品目标说起：**打宝、成长、探索，这几个听着都对的词，怎样才能变成程序能实现、开发能验收的东西？**

各位看官如果对这个系列感兴趣，欢迎先收个藏，咱们慢慢聊。
