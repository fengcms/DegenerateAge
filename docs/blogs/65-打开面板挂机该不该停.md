# 末法纪元·游戏开发65：打开面板，挂机该不该停

### 前言

各位看官，角色正在自动打怪，我打开背包看看装备，战斗继续；点开铁匠，角色却停了。再打开设置，有时候世界还在走，有时候连怪物都冻结。

单看每一个窗口，似乎都能找到理由。放在一起，玩家却很难判断自己按下这个按钮，会不会打断刚才的事情。

《末法纪元》的面板规则经历过几轮调整，最后把可见状态、世界输入与真正暂停分开。本文沿这些变化，聊聊一个打开窗口的动作，为什么不该只有一个笼统的开关。

{{IMG:GAME-65-封面}}

### 先说当前希望玩家得到什么

普通信息窗与服务面板打开时，后台挂机可以继续，玩家自己评估危险区域中的操作风险。暂停、死亡和装备确认等流程，仍有各自明确的接管规则。

这不是所有游戏通用的唯一答案。早期NPC会话停战也有自己的产品依据，后来需求变成普通面板不影响挂机，才需要同步修改判断与测试。

写复盘时，应把当时规则与当前结果分开。不能一边引用旧文档里的NPC停战，一边又说随身服务期间战斗一直继续，让读者以为同一版本有两套承诺。

[第六十二篇]({{LINK:GAME-62}})讲过随身复用，后台事件频繁以后，交易预览也要相应适配。是否停战与材料保护不能靠各面板临时决定。

### 面板可见，只回答有没有窗口

当前panel_open由已打开面板集合推导，服务于可见状态与相关交互，不再代表所有世界控制都要封禁。

下面是实际登记逻辑：

```gdscript
func set_panel_open(panel_id: String, open: bool) -> void:
    if open:
        _open_panels[panel_id] = true
    else:
        _open_panels.erase(panel_id)
    panel_open = not _open_panels.is_empty()
```

集合比一个到处写的布尔值可靠。背包与人物并开，关掉其中一个，另一个仍然存在，不能直接把全局面板状态设成假。

但集合也不自动说明窗口的输入性质。可见、能否并开、是否挡世界键盘、是否暂停场景树，仍然是不同问题，需要分别给出规则。

### 为什么普通窗口会把自动寻路弄丢

历史故障里，玩家已经点了地图目的地，打开面板以后不动，关闭也不恢复。不是路线算法算错，而是角色更新提前返回，或者直接清掉了移动意图。

早返回让本帧走不到地图移动分支，清空状态则把下一帧恢复的依据也删了。两种原因叠在一起，玩家只看见“开面板把路打断了”。

因此修复不能仅在关闭时再下发一次目的地。应该先移除普通浮窗不该产生的取消，保留真正手动接管与暂停流程的原有语义。

[第十八篇]({{LINK:GAME-18}})讨论过控制来源，窗口打开不是一个新的移动命令，也不天然等于玩家已经手动接管角色。

{{IMG:GAME-65-三种状态}}

### 世界输入阻断，采用单独查询

当前角色、世界与快捷栏使用共用判断，识别明确的模态流程以及正在编辑的文字控件：

```gdscript
func world_controls_blocked() -> bool:
    for panel_id in WORLD_INPUT_BLOCKING_PANEL_IDS:
        if _open_panels.has(panel_id):
            return true
    var focus := get_viewport().gui_get_focus_owner()
    return focus != null and focus.is_visible_in_tree() and (focus is LineEdit or focus is TextEdit)
```

文字输入尤其重要。玩家在改键或输入名称时按方向字母，不应顺便驱动人物移动；不可见的旧焦点则不该长期把控制锁死。

查询只是描述谁接管世界输入，并不负责暂停整棵场景树。设置和存档即使阻断手动键盘，也要结合打开来源，判断世界是否已经被暂停菜单冻结。

### 真暂停，和不再作自动决策不同

历史实现曾有NPC会话集合，自动战斗遇到它就进入暂停决策状态，但场景树仍在运行，怪物未必一起停止。

后来这层NPC停战判据被移除，普通服务不再统一打断挂机。不能只对随身商店开一个例外，留下铁匠、仓库和任务继续沿旧口径。

真正的场景树暂停则由暂停菜单、死亡或确认流程按规则使用，自动战斗也识别它。它和“人物当前没有发出移动意图”不是同一种状态。

检查问题时可以同时记录场景树是否暂停、自动状态、当前路线与速度，而不是只看角色这一秒站着没动。角色可能在攻击、等待目标，也可能被输入规则挡住。

### 键盘能用，鼠标也要沿自己的路径检查

旧规则曾放行普通面板里的快捷键，却继续拒绝鼠标点快捷格，理由是防拖放误用。后来又专门调整，不能把这段历史写成当前仍然存在的限制。

现在关键在于事件有没有真正到目标控件，以及业务入口有没有多余守卫。键盘与鼠标到达同一动作以后，资格应沿共同规则检查。

拖拽落格与单击使用则需要不同验证。取消旧守卫以后，应证明拖进去只改变绑定，不会顺便吃药；正常点击又确实能执行。

这与[第五十六篇]({{LINK:GAME-56}})的入口思想一样：输入来源不同，不代表业务随意复制两套，但不同手势表达的意图仍要分清。

### 面板遮住的区域，仍然应该归界面

允许后台走动，不表示鼠标点按钮时也应穿透到地图。窗口内点击继续由GUI接收，窗口外能否交给世界，则沿命中与输入分发处理。

否则玩家点击出售，角色同时向那个屏幕位置跑；拖材料到格子，右键接管又取消挂机，操作会变得不可预测。

全屏根控件是否拦截、实际面板矩形在哪里、点击是否已被处理，都需要具体看。不要用一个全局面板可见标记，代替所有坐标和命中检查。

下一篇会专门讲拖拽与叠层。这里先明确两条可以同时成立的规则：后台系统继续运行，界面区域的当前输入仍然由界面负责。

### 并开规则，与置前规则也别混在一起

背包、人物、技能和坐骑属于常驻浮窗组；合成工作台还有与背包、人物并开的明确例外；重铸与背包也有材料操作需要。

当前共用并存查询维护这些关系，面板收到打开事件后决定自己是否关闭。不能每扇窗各复制一个朋友名单，改一处漏另一处。

而能并开以后，谁在上面、点击谁置前，是另一层窗口管理。把后窗关闭当然能解决遮挡，却破坏了并开用途，不是合理的层级修复。

服务切换还要释放临时选择与确认，不能窗口已经变了，旧任务延迟回调又把原来的交易状态写回来。

### 手动接管仍然有自己的优先级

普通面板打开时，玩家主动移动或攻击，可以按原规则取消旧寻路并触发自动战斗恢复等待。这是新的明确输入，不应被面板可见性掩盖。

反过来，设置编辑中的按键不应被自动战斗误认成手动接管。共享世界输入判断，能让角色与挂机对同一次输入作相容解释。

这种一致性需要沿真实主场景验证。直接调用一个动作函数，能够检查业务结果，却不能证明GUI焦点、快捷键处理与世界未处理输入之间没有冲突。

也别为了恢复挂机，把暂停菜单或死亡的保护一起拆掉。应删除的是过宽判断，保留的是仍有明确用途的控制边界。

### 用矩阵看，而不是只试背包

后续可以沿共用判断与真实输入用例复核：

```sh
rg -n 'world_controls_blocked|panels_coexist|WORLD_INPUT_BLOCKING_PANEL_IDS' autoload/game_state.gd
python3 tools/run_isolated_tests.py PanelAutoBattleTest InputFeedbackTest FloatingWindowInputTest
```

本文未运行游戏测试。实际至少对照无面板、普通浮窗、服务窗口、设置文字输入与暂停菜单，分别检查手动移动、快捷栏、自动路线和后台战斗。

关闭以后也要复查，避免残留焦点或已打开集合没有注销。窗口看不见但控制永远没回来，通常比刚打开就停止更难找到原因。

反馈也要对应实际状态。挂机开关仍然开启，但当前因手动接管暂候，与玩家已经关闭挂机不同。图标和阶段文案若只读一个开关，后台行为正确，玩家仍可能误以为系统卡住，应一起核对这些可观察信息。

### 小结

打开窗口可以改变可见状态，也可能接管输入或暂停世界，但这三件事不能被一个布尔值包办。

把规则拆清，普通面板不再无故丢路线，服务期间挂机保持预期，真正的模态流程仍然可靠。玩家无需理解输入分发，却应该能预测自己打开一扇窗以后，角色会继续做什么。
