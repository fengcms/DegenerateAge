# 末法纪元·游戏开发25：地图变大了，刷新怪物不能跟着越来越贵

### 前言

各位看官，地图扩大以后，多放一些刷新点，看起来是内容调整，实际上也会改变运行成本。

如果每次检查一个点，都重新数一遍当前活着多少怪，候选越多，重复统计就越多。玩家附近最后可能只有十来只敌人，刷新器却为了证明“已经满额”忙了好几轮。

《末法纪元》的大地图优化里，有一项就是把每轮预算统计复用起来。但这项改动不能只把计数挪到循环外，还要保证同轮生成、退场、死亡和持久刷新状态都正确。

这一篇聊刷新点、活动预算和时间状态，怎样分清又接在一起。

{{IMG:GAME-25-封面}}

### 刷新点数量，不等于同时活动数量

地图可以有许多候选点，提供路线变化和不同区域的遭遇；真正同时活着的怪物，则需要单独预算。

普通、精英和Boss的成本与用途不同，也不能只拿一个总数全部限制。当前刷新器按地图读取对应类型上限，旧图还有历史兼容口径。

因此扩图时先看三件事：点有多少，什么距离或解锁条件会激活，以及各类对象同时允许存在多少。只报“地图增加了一百个点”，不足以判断运行负担。

反过来，活动上限很小，也不代表刷新逻辑自然便宜。候选扫描、距离检查和重复计数仍然可能随点数增长。

### 每轮数一次，再维护本轮变化

旧式做法是在每个候选尝试生成前统计活怪。假设有一百个点，每次又扫描同一批对象，大部分查询只会重复得出相同答案。

项目现在在一轮处理开始时拿到活动快照，后面生成成功就增加，距离退场就减少。下面是源码中的生成分支：

```gdscript
var active := _active_counts()
# 中间遍历刷新点，并处理退场与等待条件。
# 对每个符合条件的点执行：
if _spawn(p, active):
    active[kind] = int(active.get(kind, 0)) + 1
```

这不是完整函数，循环与退场处理已省略。要点是快照属于这一轮，而且调用方明确维护成功变化。

如果只把初始计数缓存下来，却忘记同轮增加，后面的候选都看到旧余量，就可能一口气超额生成。

{{IMG:GAME-25-预算快照}}

### 失败不能扣预算，成功不能漏计

某个点离玩家太远、未解锁、倒计时未到或落点不合法，尝试失败，不应该占用活动名额。

生成成功以后，再把类型计数加上；退场实际移出活动集合，也应同步减少。同轮后面的候选看到的是更新过的局部事实。

独立调用_spawn时，可能没有外部快照。实现保留自行统计的兜底，让函数在两种调用方式下都能守上限，而不是假设所有调用方永远来自同一个循环。

这类接口最好说明谁负责维护计数。调用方和被调方如果同时递增，预算会越来越虚；两边都以为对方会处理，则上限失效。

### 满额也不能让其他状态停止推进

活动预算满了，不代表刷新器可以直接跳过整轮所有工作。还可能有等待期墓碑需要显示，已有对象需要按距离退场，失效实例引用需要被识别。

尤其墓碑是持久刷新状态的可视化，不应被“当前还不能生成新怪”的条件挡住。玩家跨图回来，Boss没到复活时间，也应该看到对应等待状态。

这也是为什么条件顺序有意义。先检查生成距离，再处理等待墓碑，可能使远处点在装配时永远漏掉标记。

优化重复统计时，要保留这些业务顺序，不能因为提前返回看起来省事，就漏掉正常玩家会依赖的反馈。

### 刷新倒计时不能只活在当前节点里

如果节点自己累加一个计时器，切图后释放，回来又从零开始，Boss可能立刻重生，或者等待被无故延长。

项目将刷新状态保存在跨场景数据里，使用世界时钟查询剩余时间。刷新器从统一状态读取，不再各自维护一份独立时钟。

这与[第九篇]({{LINK:GAME-09}})的生命周期分工相同：地图节点可以消失，玩家进度和刷新规则需要继续存在。

时间单位也要明确。游戏暂停、倍速、退出以后怎样处理，应遵循已有时钟语义，不能为了刷新优化擅自改成电脑系统时间。

{{IMG:GAME-25-刷新生命周期}}

### 刷新身份，要能跨地图装配找回来

记录倒计时，需要知道它属于哪个刷新点。当前实现使用地图、怪物身份和同种序号构成状态键，而不是直接拿整个候选数组下标当身份。

这样可以减少别种点位增删导致的错位。但稳定性仍然有边界：同种模板的序号规则如果改变，旧状态映射就需要检查，不能据此声称所有点位重排都自动兼容。

新增内容时，地图目录和怪物配置也要同步说明。刷新身份不仅是代码内部细节，它决定墓碑和剩余时间能否对应到正确对象。

[第十二篇]({{LINK:GAME-12}})讲维护入口，生成工具改点位也应沿统一目录流程，避免一边改地图、一边遗留旧说明。

### 活动范围和退场范围，需要看真实体验

生成距离和退场距离通常不会简单设成同一个值，否则玩家在边缘轻微移动，怪物可能反复生成和释放。

当前工程有各自的距离条件，也会影响自动找怪能看到哪些真实实例。把自动搜索扩大到全图，不会让尚未生成的敌人凭空进入候选。

同样，玩家追击过程中目标被远距离回收，会影响战斗体验。[第二十四篇]({{LINK:GAME-24}})提到过这条放大链路，不能只在刷新器里看“对象数量下降了”。

要调整范围，最好固定路线测生成、退场和再次返回，观察是否丢失不该丢的状态，而不是只测空场景节点数。

### 计数基线，也要能承受外部释放

一轮开始重新统计，有助于识别上一轮后被其他合法流程释放的实例。只维护一个永不复核的全局计数器，则可能因漏减一次永久失真。

当然，快照也有时间边界。若生成过程包含异步等待，等待期间其他事件能改活动集合，就不能直接沿用等待之前的预算继续提交。

当前讨论的是一轮同步处理中的复用。以后引入分帧或异步生成，要重新定义认领名额、失败归还和取消行为，不能把这段简化逻辑原样搬过去。

性能架构的可靠性，经常就在这些条件里。算法看起来更快，仍然要说明它在哪些调用时序下成立。

### 验收既检查扫描次数，也检查真实规则

可以给活动统计入口计数，初始化和满额刷新时确认没有退回逐候选全量扫描。随后检查同轮生成不会超上限，死亡以后能补位，精英不会占错普通预算。

再验证外部释放、远距离退场、返回、跨图倒计时和墓碑恢复。它们能发现“计数很省但状态不对”的优化。

仓库已有预算和章节遭遇用例，本轮未执行游戏测试，命令供发布时复核：

```sh
python3 tools/run_isolated_tests.py SpawnerBudgetTest ChapterTwoEncountersTest MapPerformanceTest
```

历史CPU对照可以说明重复工作下降，不能直接换算整帧或GPU收益。怪物AI、碰撞和表现仍然各有成本。

调优时还要固定测试阶段。刚进地图的批量装配、预算满额后的稳定检查、连续击杀后的补位，工作组成不同，不能拿其中最便宜的一段代表全部刷新成本。

如果增加节流，也应说明生成响应最晚会延迟多久，墓碑到期和解锁后的出现是否仍符合体验。减少查询次数可以做，但不能让玩家在合法刷新点空等很久，却没有任何反馈。先测量再决定预算，往往比统一把所有刷新降频更稳妥。

### 小结

大地图刷新要分清候选总量、活动预算和持久时间状态。每轮统计一次，再按实际变化维护局部快照，能减少重复工作，同时守住生成上限。

但墓碑、退场、身份与跨图倒计时都不能为了省扫描被跳过。各位看官扩图时，除了加多少点，也把同时活动数量、检查频率和最坏一轮成本一起记录下来。
