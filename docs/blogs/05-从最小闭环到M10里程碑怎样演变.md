# 末法纪元·游戏开发05：从最小闭环到M10，里程碑怎样一步步长出来

### 前言

各位看官，[上一篇]({{LINK:GAME-04}})把工程起点准备好了，现在可以往里加玩法了。

这时候最容易出现的安排，是把程序分成移动、战斗、背包、任务、地图几个大块，每块各做各的，最后统一接起来。

每个模块都在推进，看着挺忙。可如果有人问“现在这个版本能玩到哪一步”，回答可能还得等全部做完。

《末法纪元》的开发计划用了另一种组织方式：每个阶段都交出一段可以运行、可以验证的流程。回头看仓库里的M1、M2，一直到后来的M10，能看到游戏怎么沿着这些流程长起来。

{{IMG:GAME-05-封面}}

### M1先交出一个能继续玩的版本

第一阶段叫“货郎经济闭环”。名字里有货郎，实际覆盖了移动、普攻、怪物、掉落、背包、穿戴、交易、自动行为和存档。

为什么一次串这么多东西？因为它们共同回答一个问题：玩家能不能打到东西，用起来，处理掉多余物品，再带着进度继续玩？

这时候内容可以少。怪物不用铺满六章，装备也不用准备几百种。但闭环里的每个环节都得有落点。

```text
能移动 → 能战斗 → 能获得物品 → 能穿戴或出售 → 能保存进度
```

阶段出口还检查连续游玩和退出重进。角色能走、怪物会掉血，只是其中的步骤，不能代表整个阶段完成。

这些都是早期工程计划中的验收要求。历史记录里的通过结果属于当时的版本，介绍今天的状态时，还得对照当前实现。

### M2加目标，M3把世界接起来

闭环跑起来以后，下一步加任务。

任务让玩家知道为什么去打某类怪，以及完成以后能得到什么。此时击杀、拾取、奖励和存档已经有入口，任务可以沿着这些行为接进来。

再往后是多地图、车夫、精英和Boss。现在就要检查切图、解锁、地图状态和奖励之间的关系了。

从这个顺序能看出，每一批新增内容都借用了前面已经存在的能力。先有一次真实击杀，任务才能可靠统计；先有物品实例，任务奖励才知道往哪里放。

如果倒过来，先写一大堆任务配置，底下的击杀、奖励和地图还没跑通，验收就只能停在“数据看着没问题”。

### M4和M5，不能只管继续加功能

早期计划把成长深化和完整界面放在M4，再用M5做收口和MVP验收。

这个安排挺重要。东西做出来以后，需要留一段时间，把它们放到一起检查。

窗口变化会不会挤坏面板，快捷栏是不是接到真实操作，存档能不能恢复，导出的程序是不是也能启动，这些问题不会因为开发环境里已经“能玩”就自动消失。

而且，里程碑也会插入新的工作。高分辨率适配和出行体验等需求，都进入过后续计划。

所以别把里程碑编号理解成第一天就精确预测好的路线。它更像一组有记录的阶段承诺，随着问题出现，可以调整顺序和范围，但要留下理由。

### 后来的内容扩展，也需要先补共享地基

第三至六章扩展时，项目没有直接给每一章各写一套新系统。

工程总览先分了三类事情：数据适配、共享能力、逐章闭环。像怪物预算配置、Boss动作和任务发奖计划，属于多章都会用的能力，先处理一次，再逐章接入。

这一步能避免同一个问题在四章里修四次。

章节验收也不能只数地图和任务。要从前一章的进度出发，实际接上新任务，走过道路，打完敌人，获得奖励，再打开下一段内容。

地图登记进索引，却没有可达入口；任务文字已经写好，却没有对应的怪物。这些都不能算一章交付。

### M10为什么还要拆成很多小批次

后期循环玩法涉及数值曲线、动态等级装备、循环Boss、随身服务、重铸和药水续航。全塞进一次改动，验证会很难。

M10因此先做数值地基，再逐步接装备、掉落、场景和服务。

其中一个很具体的原因，是旧的等级校验边界可能与继续升级的行为冲突。如果高等级角色的存档先被判无效，后面再丰富循环奖励，也接不住玩家进度。

这类问题适合优先处理，而且应与后续新玩法分开验证。

**拆批次的依据，是依赖和风险。** 每批做完，都应该能说明它让哪个问题闭合了，以及哪些东西还没有接入。

### 把一个大阶段，拆成能失败的小步骤

以第一阶段的掉落和背包为例，不能一口气交代“做好打宝”，然后等所有界面都接完再看结果。可以先证明怪物死亡会生成合法物品，再证明实例能够进入背包，接着验证穿戴后的属性，最后检查存读档能保留同一件东西。

每一步都要留下一种容易看出来的失败。生成物品时模板不存在，应当明确报告；入包失败时物品不能凭空消失；穿戴拒绝时原来的装备关系要保持。只有成功路径，阶段结论会显得比真实情况乐观。

这并不要求每个小步骤都交一个完整产品。内部步骤可以暂时用测试场景验证，但阶段出口应该把这些步骤重新接到真实玩家流程里。否则我们只是收集了一堆独立通过的零件。

还有一种需要避免的安排，是让所有风险都留到最后一天。路径、实例保存和奖励一致性如果是这一阶段的地基，就尽早做小实验。它们一旦不成立，上面的界面即使画完，也可能要跟着返工。

相比给每项工作估一个看起来准确的完成比例，我更愿意先把依赖顺序画出来。哪一步可以独立确认，哪一步必须等前置完成，计划马上就具体多了。

### 进度不能只写百分之多少

“战斗完成80%”，听起来挺接近完成，可剩下的是一个按钮，还是死亡结算和存档链路？差别大了。

更有用的描述是：普攻已接通，技能配置已登记，但某个技能还没有进入实际施放名单；任务可以完成，但奖励计划还需要补持久化。

项目的后期记录里，就存在“配置已有、施放尚未接通”的历史快照。这种缺口写出来，后面的人才不会把表里有数据当成玩家已经能用。

[第二篇]({{LINK:GAME-02}})讲体验目标的验收，这里对应的是进度表达：把完成的行为和未完成的连接都说具体。

### 留下阶段快照，后面才知道自己改过什么

《末法纪元》的开发记录里，既有最初计划，也有后续交接与验收。读这些材料时，可以结合Git查看一个阶段最早交付了哪些变化，而不是只读今天已经滚动更新过的说明。

下面几条命令只读取历史，不会切换分支或修改工作区。搜索词用于定位相关提交，查到以后还要打开具体差异核对：

```sh
 git log --reverse --oneline --grep='feat(m1)'
 git log --oneline --grep='M10'
 git show --stat 993fe58a
```

第三条展示早期存档落地提交涉及的文件。它能帮助定位历史起点，不能替代那一版的运行验收，更不代表现在所有存档逻辑仍然和当时相同。

阶段快照还应该区分几种状态：设计已经确认，代码已经接入，定向测试已经执行，以及完整流程已经复核。一个技能的系数出现在配置里，只能证明其中一层；施放名单、资源消耗和自动策略还可能没有连上。

如果后来发现旧阶段的缺口，也不用把整个历史重写成“当时都没做”。保留原先验证的范围，记录新发现触及哪些条件，再安排补充修复，会更容易看清项目实际如何演变。

对读者来说，这种记录还能避免照着过期步骤做一半。文章用某个历史版本解释取舍时，就明确告诉他这是当时的状态；介绍现行入口时，再回到当前代码。阶段编号是索引，不是永久不变的行为规范。

各位看官自己复盘时，可以挑一个已完成阶段，试着写出“当时验证了什么、后来又补过什么”。如果完全写不出来，说明进度记录可能只有结论，缺少可以对照的证据。

### 小结

从M1到M10，编号背后是一串逐步扩展的可玩流程。

先跑通基础循环，再接目标和世界；共享问题先处理，内容逐段验收；到收口阶段，还要检查组合行为和实际交付环境。

各位看官给自己排计划时，可以少问一句“这个模块写多少了”，多问一句“这一批结束，能走通哪段流程”。答案往往会更实在。
