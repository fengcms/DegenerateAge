# 末法纪元·游戏开发59：背包容量，也是一个经济参数

### 前言

各位看官，背包不够用，加格子就行了吗？从界面看，只是再排几行；从玩法看，却会改变玩家多久回城、什么时候出售、愿意保留多少候选，以及金币花在哪里。

《末法纪元》的背包与仓库共享容量规则，后来把上限从两百扩到四百，又给价格曲线增加尾段。药品和如意的堆叠，也会改变同样数量格子能支撑多久。

本文就从容量出发，聊聊一项看似存储层的小功能，为什么需要同时考虑经济、操作频率和入包一致性。

{{IMG:GAME-59-封面}}

### 一格装备，和一格药水承担的压力不同

装备不可堆叠，每件都有自己的品质、词条、星级与身份。留十件候选就占十格，名字相同也不能合成一格数量十。

药品、如意等可堆叠物品，则可以在同一格里保存多份。它们的上限来自模板，不能拿装备占格规则直接推算消耗品的携带成本。

这意味着背包使用率不只由掉落总件数决定，还与物品结构有关。一百份药水可能只占少量格子，一百件装备却能让玩家很快面临筛选压力。

[第五十五篇]({{LINK:GAME-55}})讲过格子占满与能否接纳的差别。设计经济时也要保留这种区分，不能只看一个背包占用百分比就判断玩家是否需要立刻清包。

### 扩容花费，购买的是更长的操作间隔

多十格不仅多放十件，也让玩家可以更晚打开商店、攒更多同档材料、留出更丰富的比较选择。

因此扩容是一个金币出口，它的价值与刷装速度、候选保护和合成规则联动。掉落变多而容量不变，操作压力上升；自动出售更聪明以后，同样容量又可能显得宽裕。

这种变化不一定好或坏，但需要沿实际路线观察。如果每隔几分钟就必须清理，玩家可能觉得在做仓库管理员；完全没有容量约束，又可能让装备筛选长期被推迟。

容量目标应该说明希望玩家多久整理一次、哪些东西值得保留，而不是仅凭屏幕还能放下一行格子就继续加。

### 当前容量与扩容次数有统一关系

当前基础四十格，每次增加十格，最高四百。背包与仓库各自记录扩容进度，读取共同规则计算容量，不代表买一次就同时扩两处。

容量入口会夹住上限：

```gdscript
static func capacity(expansions: int) -> int:
    return mini(cap(), base_slots() + maxi(0, expansions) * expand_slots())
```

界面、扣费入口与读档检查应沿同一关系。若显示四百格，实际数组只有三百九十，玩家拖到最后一行才发现数据越界，问题就不只是排版。

同样，旧注释里可能还写着早期两百格，复盘应以现行配置为准，同时解释历史改造，不能把每份工程记录里的数值都混成今天的一套规则。

### 几何增长，到了尾段为什么要停一下

前段扩容使用几何费用，随着购买次数增加逐渐变贵。继续把同一倍率延伸到四百格，后几档价格会被推得很高，可能脱离当时经济承受能力。

当前把两百格作为几何段边界，后面以几何段最后一档费用为锚点，按配置的尾段增量定价。当前增量为零，尾段保持同价。

这不是把前面每档价格重新平均，也不是在两百格以后免费。已经形成的前段投入保留，新增容量采用明确的新段。

分段还有一个维护好处：以后想让尾段线性增加，只调整对应参数，不必改一串硬编码价格。但调整前仍应看玩家收入与其他金币出口，不能只觉得曲线看起来平滑就算平衡完成。

### 扩容成功，应该同时对应扣钱与真实空间

扩容入口先计算下一档费用，检查是否已到顶与金币是否足够，再扣款、增加扩容次数并调整真实数组容量，最后广播变化。

不能先让界面多画格子，等保存时才修改真实容量；也不能先扣钱，再发现已经封顶，靠弹提示让玩家自己接受。

当前下一档不存在时返回错误值，这与费用为零的合法动作有不同含义。调用方应明确禁用或提示达到上限，不要把负数误当成返金币。

扩容事件还会唤醒等待容量的掉落重试。新格子可见、真实可用、相关系统能感知，是同一个成功结果的不同观察角度。

### 堆叠必须先预检整份数量

如果一堆药水还差一份满，新掉落有十份，而背包没有其他空间，不能先塞进去一份，再返回入包失败。

那样地面物可能保留原来的十份，下一次重试又塞一份，最终重复获得；或者地面直接消失，剩下九份就被吞了。

当前添加入口先完整检查容量，失败时不动背包与输入物品，再分配已有堆与空格：

```gdscript
static func add(inv: Array, item: Dictionary) -> bool:
    if not has_space_for(inv, item):
        return false
    if not ItemUtil.is_stackable(item):
        inv[_first_empty(inv)] = item.duplicate(true)
        return true
```

后面才处理可堆叠物。先确保整份能容纳，再执行写入，使成功和失败语义保持简单，也便于购物、奖励和拾取共用。

### 同一种物品，也未必能合到同一堆

堆叠不能只看图标或名字。当前同堆判断比较类型、模板身份，并在排除数量后比较其余完整数据，避免把不同状态合在一起。

[第十篇]({{LINK:GAME-10}})讲模板与实例，到了容器整理仍需尊重数据边界。若以后某种材料带独立绑定状态或来源标记，不能为了腾格把差异直接抹掉。

装备则始终保留独立实例，不因为两个词条数组恰好一样，就合并成一个数量字段。容量整理不应该改变物品所有权与成长历史。

因此提高堆叠上限，只改变合法堆的数量边界，不自动授权跨状态混合。数据迁移也要沿明确规则处理，不能把所有同名物品一口气并起来。

### 整理背包，应该整理位置而不是重造东西

当前整理会分类排序，合并合法同堆，空格移到末尾，装备身份和词条保持不变。它的作用是让容量更容易使用，不是重新生成物品。

[第四十二篇]({{LINK:GAME-42}})的稳定身份，保证已经选中的材料可以在位置变化后重定位。若某个操作只记行号，整理以后再点确认，就可能处理错对象。

整理也不能让数量凭空增长。检查时应比较各类物品总数、装备ID集合与完整属性，而不是只看占用格子确实变少。

仓库与背包之间转移也类似：目标容器先验证整份可接纳，成功以后再从来源移除。两个容器都画出新数量，却少了一半真实物品，是比容量不足更严重的问题。

### 容量变大，运行成本也跟着扩大

四百格以后，清单、排序、候选排名与保存都可能处理更多对象。不能只把数组上限改大，却继续每帧重建整张背包面板。

当前许多流程按事件与一次提交准备上下文，避免逐行全包重算。扩容本身还需要检查长列表滚动、文字缩放与最后几行的拖放可达性。

不要因为有上限就认为成本可忽略。四百格乘上频繁掉落和多个打开面板，仍可能放大重复工作；具体是否成为瓶颈，应由相同场景的测量决定。

经济容量与计算容量都要说明数量规模，只是两者的验收方法不同，不能拿一次逻辑通过代替窗口性能和交互检查。

### 怎样验证这份容量真的可靠

后续可以从配置、整份预检与堆叠回归检查：

```sh
rg -n 'geoCap|tailStep|cap' data/warehouse.json
rg -n 'has_space_for|_same_stack|organize' scripts/systems/inventory.gd
python3 tools/run_isolated_tests.py PotionRuneStackTest
```

本文未运行游戏测试。实际用例应覆盖跨两百格的价格边界、最后一次扩容、金币不足、满格仍可叠加，以及只能容纳部分数量时整份拒绝。

保存再读取也要核对扩容次数与真实数组长度一致。经济体验则沿真实收入观察何时买得起、多久整理一次，不要把教学曲线或理想掉落数量直接当作实战结论。

### 小结

背包容量决定的不只是存储多少，还影响整理频率、材料积攒、候选保留与金币去向。扩容曲线和堆叠上限，需要放进整个经济循环一起理解。

实现上则守住整份预检、同堆边界和稳定身份。多出来的格子只有真实可用、不会吞物或复制物，才算玩家真正买到的空间。
