# 末法纪元·游戏开发53：掉落动画没飞完，奖励归谁

### 前言

各位看官，怪物倒下，装备从地上飞向人物，最后消失。这个画面大家都很熟，但程序到底应该在哪一刻把奖励放进背包？

等飞完才入包，似乎最符合眼睛看到的过程。可人物正在移动，可能切图，背包也可能被另一件掉落占满。动画越认真，结算反而越容易被这些变化打断。

《末法纪元》的掉落经历过立即吸走、落地保护期，再到认领与飞行分开的调整。这篇先沿这条演变讲清楚，玩家看到的动画，与程序确认奖励归属，为什么需要两个时刻。

{{IMG:GAME-53-封面}}

### 最早的问题，是东西太快消失

早期近战击杀时，怪物和散落物都处在自动拾取半径里，掉落生成后很快就被捡走。玩家看到金币提示，却没看见地上出现东西，很自然地怀疑奖励没有生成。

当时的诊断对比了击杀前后金币、背包条目和地面节点，确认账已经入了，缺的是可见过程。这种问题如果只看截图，很难分清没有生成，还是生成后立刻消失。

因此排查不能只问画面上有没有东西，还要问真实容器增加了什么，地面节点在哪个阶段退出。一个可见性问题与一笔结算丢失，修法完全不同。

工程记录里的近身距离与拾取半径，是当时版本的复现条件，不应该写成所有后续地图永远成立的常量关系。

### 加一段保护期，解决了眼睛，却改变了拾取条件

最初的改进是让掉落先在地面停一会儿，保护期结束再自动拾取。玩家终于看见了东西，单次站桩测试也很容易通过。

问题出在自动战斗。角色击杀之后会寻找下一个目标，不会为了掉落在原地等。保护期结束时，人可能已经跑远，物品便留在地上。

这不是简单地把等待时间再缩短一点就能彻底解决。缩短到几乎不可见，又回到原来的体验；拉长则更容易错过人物离开的窗口。

这里真正冲突的是两项前提：表现希望延迟消失，结算却要求玩家稍后仍然站在附近。要同时满足它们，需要改变职责边界，而不是不断调一个秒数。

### 先尝试认领，再演出收入背包的过程

后来主流掉落路径改为生成时尝试认领。成功以后，奖励已经进入真实状态，地面节点继续完成落地、停驻和飞行动画。

当前认领成功后的核心操作如下，前面的尝试还可能因容量或其他条件失败：

```gdscript
_claimed = true
remove_from_group("ground_items")
if not _fly_enabled():
    _announce_pickup()
    queue_free()
    return
```

从可拾取组移除，不等于立即销毁。它告诉自动战斗和拾取搜索：这件东西已经处理完了，不要再追过去，也不要第二次申请入包。

[第四十二篇]({{LINK:GAME-42}})讲过实例身份，在这里还要加上处理状态。同一个物品节点仍然存在，并不代表它仍有可领取的奖励。

### 动画飞向人物，不再决定钱和物品能不能到账

人物移动时，飞行表现可以追踪当前位置，避免飞到一块空地上。若目标失效、距离突变或动画超时，节点应按既定方式结束。

这些兜底负责清理视觉对象，不负责撤销已经成功的入账。否则一次切图或动画取消，就会让玩家背包里的物品也跟着消失。

同理，关闭掉落飞行动画，应当改变表现和提示时机，不改变奖励数量。一个节省视觉开销的设置，不能变成另一种经济规则。

代码里仍会保留出场与停驻阶段，具体节奏已经随后续表现调整继续变化。文章需要解释状态关系，不必把早期文档中的总时长当作当前所有掉落的统一保证。

### 提示出现得晚，不等于结算发生得晚

认领时可以静默入账，把拾取提示留到飞行结束，给玩家一个连贯的收获感。这意味着看到提示之前，背包可能已经有了那件装备。

这并不矛盾，前提是提示只是对已经完成结果的说明。不能在飞行结束回调里再次调用入包函数，误把播报当成第二次领取。

检查这类问题时，应该分别记录入账次数、认领状态与提示次数。只看界面弹出几条，很容易把重复提示误诊成重复发奖，也可能反过来漏掉静默重复入账。

批次掉落还会聚合提示，单件飞行动画不一定对应一条单件文字。屏幕上少几条消息不表示奖励减少，真实资产仍需要按实例完整核对。

### 入包失败，不能把未完成认领写成成功

生成即认领有一个重要限定：只是立即尝试，不是无条件成功。背包不能接纳物品，或者金币已封顶，掉落仍需走未认领分支。

此时不能先设已认领，再因为动画好看就让它飞走。玩家看到飞进背包，打开却没有东西，这才真正构成误导。

当前普通物品通过统一拾取门面处理，金币、坐骑等有自己的业务分支，结果成功以后才清理对应未领取记录。界面对象不应该绕开业务入口自己改背包。

精英和Boss的未领取战利品还有持久保护；普通未认领物则有自己的地面期限。不同来源的保护范围不能一概写成永不丢失，具体边界后面继续展开。

### 自动拾取关闭以后，也要保留另一条路

玩家关闭自动拾取，或者物品本来被设置为手动处理时，地面对象仍然需要保留点击与靠近等既有语义。

不能因为主要路径已经改成认领后飞行，就把所有地面物都当作无交互的特效。主流路径省掉的是一次走近等待，不是删除地面物品这一类对象。

这也是测试需要主动构造未认领样本的原因。正常战斗中自动认领率很高，长期看不到顺路拾取触发，不等于那条功能坏了，可能只是没有进入它的条件。

反过来，为了截图把东西故意放远，也不能代替真实近战掉落验收。截图证明能画出来，不能证明正常流程中玩家有机会看见。

### 节点生命周期，要与奖励生命周期分别核对

认领成功后，奖励由背包或金币状态持有，表现节点只保留完成演出需要的信息。动画结束必须释放，切图也不应留下旧目标引用。

未认领时，节点可能还对应一份可恢复记录，领取成功后要同步移除记录，防止重新进入地图又造出同一件。

因此排查至少分三份账：玩家已有资产、尚未领取记录、当前可见节点。它们有交接关系，却不能靠统计某一个节点组的数量推断全部结果。

例如飞行中的对象已经离开可拾取组，但仍是地图子节点。测试只断言组里为零，会漏掉动画残留；只断言节点还在，又可能误判重复可领取。

### 从业务次数验证，再看表现是否自然

后续复核可以从认领入口和已有诊断用例找起：

```sh
rg -n '_try_claim|_try_pickup|_clear_unclaimed_record|_announce_pickup' scripts/entities/ground_item.gd
python3 tools/run_isolated_tests.py SmokeTest
```

本文只核对代码与命令，没有执行游戏测试。实际验证应覆盖人物远离、动画开关、目标失效、切图、满包，以及同一掉落被连续点击。

成功分支检查奖励只入账一次、搜索不再追逐已认领物、表现最终释放。失败分支则检查真实奖励没有消失，后续条件恢复时仍能领取。

性能也应沿这两个生命周期观察。动画节点多时可以减少重复表现工作，但不能通过删未领取数据降低负载；长期挂机既看帧时间，也要看节点与内存是否持续增长。

发布时也可以配一张实际背包计数与飞行动画同屏的截图，说明视觉仍在进行而资产已到账。概念时序图负责解释顺序，运行截图负责证明当时版本的具体表现，两者不要相互冒充。

### 小结

掉落动画表达收获，认领决定归属。让成功入账先完成，表现随后安全结束，可以避免人物移动和场景切换反过来决定奖励是否存在。

但先认领始终以业务成功为前提，失败就保留未领取语义。把成功、失败和清理三条路讲清楚，画面才既好看，也可信。
