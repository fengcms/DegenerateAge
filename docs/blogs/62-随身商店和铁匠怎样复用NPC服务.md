# 末法纪元·游戏开发62：随身商店和铁匠，怎样复用NPC服务

### 前言

各位看官，循环图里刷得正起劲，药水不足要回城，装备要重铸也要回城。后来增加随身商店和铁匠，是不是把原面板复制一份，去掉NPC头像就行？

复制当然能很快做出一个窗口，但商品、手续费、托盘与修理规则会从此各有两份。以后改一处，另一处漏掉，玩家就会发现同样服务在两个入口对不上账。

《末法纪元》选择复用既有面板与业务能力，让道具负责入口，模式负责差异。本文作为第六卷收尾，讲这层复用如何落地，以及工具解锁、补领和后台战斗带来的额外约束。

{{IMG:GAME-62-封面}}

### 能打开面板，不等于功能已经交付

早期面板类道具有配置校验和说明文案，却缺少真正的执行分发。数据看起来合法，双击仍然提示不能使用，这是一条执行链断口。

后来用物品用途连接面板路由，再由路由打开登记好的服务。新增一个名称，必须同时检查校验、执行和说明，不能只让白名单接受字符串。

能力层先具备，并不表示应马上发道具。早期三件套的正常发放曾等服务完成以后再开放，避免玩家领到一个只有说明、没有内容的工具。

这条经验很通用：内部入口可以分阶段开发，玩家可获得的承诺却应该完整。复盘时应把当时尚未发放与今天已经能使用分开，不能只看旧方案的ready字段。

### 路由只负责分发，不替服务结算

当前PanelRouter登记面板身份、开放状态与标题，使用道具时转向对应事件。商店、铁匠与仓库各自继续完成已有业务。

下面是随身商店和铁匠的实际分发节选：

```gdscript
"shop":
    EventBus.shop_open_requested.emit(Shop.PORTABLE_SHOP_ID)
    return {"ok": true, "reason": ""}
"blacksmith":
    EventBus.blacksmith_panel_requested.emit("", "", true)
    return {"ok": true, "reason": ""}
```

一个传合成店铺身份，一个传随身模式，路由本身不扣金币、不修改背包，也不生成一份独立交易数据。

登记并不等于所有资格检查都在这里。道具持有、任务发放与服务自身条件仍由对应调用链负责，不能把一个可路由面板直接解释成任何玩家都已获得使用权限。

### 随身商店复用面板，货单由模板聚合

随身商店使用原货郎面板，购买与出售继续走同一服务。差异集中在店铺身份、标题、商品来源和购买价格。

当前货单从药品、杂项和如意模板聚合，过滤无价、任务物与任务用途，不包含装备。早期“各地商店并集”的设想会漏掉某些合法品类，所以落地没有机械照抄这句描述。

[第十篇]({{LINK:GAME-10}})讲数据权威，价格也一样。模板是基础价格来源，随身货单据此推导，不能再复制一份价格表，调整药水时还要到另一个文件手改。

以后新增合法商品可以按规则进入，但仍要经过启动校验和实际入口检查。数据驱动减少重复维护，不等于任何新条目都该无条件出现在商店里。

### 便利有价格，也有统一取整

随身商店购买采用基础价的一点二倍，并向上取整。当前使用整数比例表达，避免某些价格因浮点边界多算一枚金币。

实际价格函数的核心是：

```gdscript
return (base * PORTABLE_PRICE_NUM + (PORTABLE_PRICE_DEN - 1)) / PORTABLE_PRICE_DEN
```

这段依赖周围的正价格检查与整数除法处理，不能脱离上下文当成任意语言都相同的公式。

铁匠修理的随身倍率是一点五，升星与重铸使用各自已接入的成长费率；显示与扣款必须调用共同规则。修理按既定四舍五入，成长费率入口向上取整，两种口径不能为了统一外观随便互换。

回城因此仍保留节省费用的理由。便利并不只是删掉路程，也改变经济选择，应该让玩家在确认前看见真实代价。

### 注释写到保星，不代表费用已经接线

这里有一处写文章必须讲清的边界。费率模块的说明把保星也列入成长服务，但当前保星合成面板保存随身模式，并没有把它传入保星费用计算。

现行保星调用仍读取合成规划的基础费用，没有因为面板由随身工具打开就自动加价。不能照着模块注释，宣称所有成长服务今天已经一律加价。

本文按实际调用链描述这一差异，不顺手修改玩法。若后续要把保星费率接齐，应另行明确产品行为，并同时更新预览、确认和结算。

这也说明复用不能只查某个常量存在。参数有没有从入口传到最终消费点，才决定这项模式差异是否真的生效。

### 原服务的交易保护，也要跟着保留

复用货郎面板，意味着托盘、关闭退回、收藏保护和最终成交仍沿既有流程。不能觉得随身服务只是快捷入口，就直接绕过清单核对。

[第五十七篇]({{LINK:GAME-57}})讲过暂存与成交的区别，[第五十八篇]({{LINK:GAME-58}})说明实际入账与托盘认领。两个入口应共享这些承诺，而不是各自重新模拟。

铁匠也一样，升星概率、重铸锁定与材料资格继续由原业务入口执行。随身模式可以改变菜单和已明确的费用，不能悄悄改变产物分布或把验证简化掉。

因此验收要比较同一功能在城镇与随身模式下，哪些结果相同、哪些按规则不同，而不是只看两个窗口都能打开。

### 后台继续战斗，会暴露原面板的隐含前提

站在NPC旁操作时，库存变化可能较少；随身面板打开后，磨损、拾取、金币和等级都可能持续变化。

[第四十七篇]({{LINK:GAME-47}})的耐久误清，与[第四十八篇]({{LINK:GAME-48}})的确认反复重置，就是这种使用方式把旧前提暴露出来。

解决方法不是让所有服务强制暂停战斗，而是清楚区分无关变化与交易条款变化，关键提交同步终验，显示刷新按需要合并。

这部分也是复用成本。代码不复制，不代表拿到新场景就天然可靠；原服务对环境的假设需要逐项核对，尤其输入接管、面板互斥与关闭后的异步回调。

### 已发放事实，不等于当前物品就在背包

永久工具的解锁键保存已经发过的事实，实际道具可能在仓库。功能入口与补领不能把这两种状态混成一个布尔值。

当前补领会同时检查背包与仓库，已经持有就不再给，未获得解锁也不凭空赠送。背包满时可以尝试仓库，两处都满则明确记录失败。

这条规则依赖永久工具正常不可消耗、不可出售与不可丢弃。如果将来允许交易或丢弃，补领判据也必须重新设计，否则移走一件又补一件，会形成无限复制。

不能只在界面隐藏丢弃按钮。真正的不可丢弃检查要在业务入口，所有快捷键、拖放与未来调用者都受同一规则约束。

### 工具合并以后，旧工具不能又被补回来

当前还有整合服务入口，把多个能力放进一个便携面板。它仍只分发既有服务，不把交易和锻造逻辑复制进菜单。

工具升级任务可能回收旧工具，补领因此需要识别已完成兑换所退役的道具。否则玩家完成合并，下一次读档又收到一批旧工具，占用背包还破坏进度含义。

这项规则在当前补领代码中从任务兑换关系推导，不应再手工维护一份随身工具退役名单。新增能力时，检查发放、合并、丢弃和补领的完整链，比只加一个菜单按钮更重要。

### 验收要把持有与模式带进真实入口

后续复核可以从路由、价格和补领回归检查：

```sh
rg -n 'portable_price|aggregate_offers' scripts/systems/shop.gd
rg -n 'missing_tools|exchangeTools' scripts/systems/tool_reclaim.gd
python3 tools/run_isolated_tests.py PortableToolsTest PortableShopTest PortableBlacksmithTest ToolReclaimTest SuperPortablePanelTest
```

本文未运行游戏测试。应覆盖真实道具使用不消耗、未登记面板失败、随身与城镇价格差、修理显示实扣一致，以及工具在仓库时不重复补发。

还要检查窗口关闭、后台战斗和快捷键接管。菜单的数字键被处理以后，不应同时穿透到世界动作；准备结束的旧回调也不能重新打开已经关闭的界面。

### 小结

随身服务复用的是原有能力，道具与模式提供新入口和明确差异。商品、交易、锻造与存档继续保持各自权威，便利才不会变成另一套平行规则。

从发放到使用，从收费到补领，把整条链走通，才算玩家真正拥有了这件永久工具。第六卷到这里，经济循环不只关乎产出多少，也关乎每一次获得、保留与消费是否可靠。
