# 末法纪元·游戏开发79：旧存档，究竟要兼容到哪一版

### 前言

各位看官，新版本加一个字段，旧存档没有，补默认值就行。可装备模型彻底换过，旧词条含义变了，地图尺寸也改了，还是随便补几项就能继续吗？

《末法纪元》的存档经历过明确的最低读取边界，也保留了很多历史迁移代码。读到一段处理零版本的分支，不表示正式游戏今天仍然接受零版本档案。

这一篇接着文件恢复，专门聊兼容范围、迁移含义与拒读。可靠性不只是尽量读进来，也包括不把无法正确解释的内容悄悄变成另一份资产。

### 当前版本，与最低可读版本分别声明

当前源码把存档格式设为十六，最低可读为十一。两者承担不同职责：前者说明新快照写成什么形态，后者说明正式入口承诺接受什么历史范围。

常量如下，发布时应对照当时版本，不把本篇数字当成永久不变的产品承诺：

```gdscript
const CURRENT_SCHEMA := 16
const MIN_READABLE_SCHEMA := 11
```

旧于下限明确拒读，来自更新版本也不由旧客户端擅自猜。拒绝以后保留文件，给出可理解原因，而不是顺手创建空角色覆盖原进度。

[第四十一篇]({{LINK:GAME-41}})讲过早期三轴模型的破坏性升级，这种决定需要产品与工程明确承担，不能用一个看似兼容的字段掩盖数据含义已经不同。

### 迁移函数有旧分支，不等于入口能到达

当前迁移代码还留有某些更早版本处理，用于历史结构和直接单测。但正式读取先检查版本范围，低于下限不会因为函数里有代码就自动放行。

如果只搜索schema判断，很容易得出错误结论：这里写了零版本，所以零版本应该可导入。真正支持范围需要沿读取、备份、导入与应用的完整调用链看。

这也是注释可能落后的地方。有的旧说明还停在十五，当前常量已经十六。文章采用实际边界，再把历史说明当背景，不照抄一处文本推导全局行为。

测试直接调用内部函数，证明的是那段转换能执行，也不等于玩家入口承诺开放，接口层次要分清。

### 先识别版本，再迁移，再验最终形态

当前统一校验先确认原始输入是字典、版本在可读范围，以及部分基础字段类型与范围，再建立迁移副本，检查归一后的完整结构。

入口节选如下：

```gdscript
if not raw is Dictionary or not _whole(raw.get("schemaVersion"), MIN_READABLE_SCHEMA, CURRENT_SCHEMA):
    return _reject("schemaVersion 非法：%s" % str(raw.get("schemaVersion", "缺失") if raw is Dictionary else raw))
```

这里不是先相信版本号，后面仍核对装备、任务、容器与合法身份。把非法内容的数字改成十六，不会让它变成真正的新格式。

迁移不修改输入，便于失败后保留原始证据，也让导入流程能分别验证原始文件与最终准备写入的内容。

### 缺字段、错类型与未知值，不是同一种旧

新设置缺失，可以补默认；已经有字段却写成错误类型，可能需要拒绝；未知装备或过期计划，则按明确的专项迁移策略处理。

若把这些情况都当作旧档，任何损坏都能被一串默认值遮住。玩家看似进了游戏，装备、任务或额度却已经丢了一部分。

当前某些专项迁移会清理不可识别项，并在需要时提示丢弃数量。这种有边界的处理不能推广成所有非法字段都可以静默修复。

相反，也不能因为新增字段没出现，就拒绝所有历史快照。[第五十二篇]({{LINK:GAME-52}})的第五词条标记就是例子：缺失表示未解锁，不应该凭空补出一条随机属性。

### 物品快照，不能被最新平衡表重造

装备保存生成时的基础与倍率依据，后续调平衡不应在读档时把合法旧物品全按新表重算。

[第四十四篇]({{LINK:GAME-44}})说明十级一套改造保留合法历史实例。新掉落遵循新规则，不等于旧物品必须重新掷一次等级和词条。

迁移可以修正已确认的旧型号映射或字段含义，但必须有明确对应关系。靠名称相似随便换一件，看起来玩家还有武器，实际身份与价值已经改变。

因此验证不仅检查物品数量，还应检查ID、属性和成长标记。相同图标不足以证明兼容成功，进入游戏也不足以证明旧资产被正确解释。

### 地图迁移，需要自己的版本门

地图缩小或布局改造时，坐标、探索和地面奖励可能需要转换。不能只升级整档版本，就假设所有地图都经过相同历史。

当前某些地图有独立布局标记，确保只转换一次。若没有这层门，每次读取都按比例缩放，人物位置会一轮轮漂移。

有的改造只扩展可走区，可以保留旧坐标；有的尺寸收拢则需要映射。不同变化不能都用一条万能传送到中心处理，否则未领取奖励和探索也可能被重置。

这项兼容还应测试重复执行。迁移一次合法，再迁移一次应保持相同业务结果，不能重复发奖、扣物或改变已转换坐标。

{{IMG:GAME-79-迁移与保留}}

### 解锁白名单，也属于版本契约

任务交付可以在运行时写入某个键，但保存读取是否认识它，还依赖合法键集合。新增永久工具或章节门禁，不能只改发奖代码。

[第六十四篇]({{LINK:GAME-64}})提过整链测试的保存往返，正是为了抓当场能开门、退出后拒档这类问题。

数据重载后白名单缓存也需要失效，否则开发阶段更新任务，校验仍拿旧集合判断。缓存正确性与兼容策略在这里会相遇。

某个键未知时该拒绝、忽略还是专项迁移，应由字段语义决定，不能为了过一份旧夹具把全部白名单检查去掉。

### 导入和直接读取，别各写一份下限

当前导入使用共同最低版本，额外把更新客户端存档与过旧档案转成更清楚的提示。目标槽不会因为拒绝而被改写。

如果读取能接受十一，导入却仍然写死十二，玩家同一份文件从不同路径进来就会遇到矛盾。公共常量比两句相似判断更能减少这种漂移。

导入归一槽号、名字之后，再验最终内容；文件恢复则可能读取备份，两边都应沿一致结构契约。不能只保证主档路径正确，备用入口却允许绕过。

[第七十八篇]({{LINK:GAME-78}})讨论文件层，版本拒读与文件损坏需要分别反馈，恢复备份也不意味着可以跳过格式边界。

### 迁移以后，当前状态还要正常继续

旧技能升阶缺失时沿默认拥有关系恢复，旧满星装备不自动解锁第五条，工具缺失按已发放与实际持有补领，这些都是具体业务规则。

不能因为它们都发生在应用存档附近，就把迁移写成一个随意修世界的大函数。每项需要自己的触发条件、可重复性和结果检查。

尤其补领不能重新执行整条任务，把金币和其他奖励也再给一遍；地图恢复不能复活已经领取的掉落。兼容成功应保持后续操作语义，而不是只让结构校验变绿。

测试还应保留旧字段和相关快照对照，检查新默认只补必要部分，不把玩家成长重置为最新模板默认值。

### 版本测试，要有正反两边

当前范围里选代表性旧档，检查迁移、保存与再次读取；边界外则检查明确拒绝和目标字节不变。只测接受，抓不到错误放行；只测拒绝，也证明不了承诺的旧版本真的可用。

后续可从现有入口复核，本文没有执行测试：

```sh
python3 tools/run_isolated_tests.py SaveTransferTest SkillRankSaveTest FullStarReforgeTest
rg -n 'MIN_READABLE_SCHEMA|CURRENT_SCHEMA|_migrate' autoload/save_manager.gd
```

还要测试版本字段缺失、非整数、未来版本与低于下限，以及迁移重复执行。对照的应是业务内容，不只是版本号最后变成十六。

### 兼容范围，需要随交付一起维护

格式升级以后，文档、测试夹具与导入提示都应同步。保留旧分支可以解释历史，但要注明它是否仍在正式入口可达。

如果决定提高最低版本，应先明确影响与恢复途径，不是因为某条旧测试不好修就顺手拒绝。反过来，永远兼容也不是一句免费承诺，历史含义越多，维护成本越需要公开。

本篇采用当前代码事实，不改变任何存档政策。以后新版本可以有新的边界，但不能让玩家靠一次失败读档才知道承诺已经变了。

### 小结

兼容不是所有文件都尽量读进去，而是在明确范围内，正确解释并保留历史事实；范围以外清楚拒绝，文件仍留给玩家。

版本门、专项迁移与最终校验各守一层，再用重复迁移和保存往返验证。让旧存档继续走下去，比让版本号看起来已经更新，要多做很多具体工作。
