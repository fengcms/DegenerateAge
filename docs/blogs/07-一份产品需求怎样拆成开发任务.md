# 末法纪元·游戏开发07：从产品文档到代码，中间那一步怎么拆

### 前言

各位看官，[上一篇]({{LINK:GAME-06}})讲了任务契约，这一篇接着聊：一份产品需求已经写得挺细了，为什么还需要工程方案？

拿《末法纪元》的出行系统举例。玩家想要的事情很清楚：相邻地图可以免费走过去，车夫提供方便的直达服务，目的地要受解锁和到访规则约束。

听着像几个出口加一个传送菜单。

真打开代码，会发现它同时碰到地图数据、落点、扣费、世界切换、存档和UI。产品说明了要什么，工程还得决定从现在哪里接进去。

{{IMG:GAME-07-封面}}

### 第一步，先盘点已经有的东西

出行方案没有一上来就安排重写切图。

当时工程已经有车夫切图骨架、地图服务、事件总线、存档迁移、未领取战利品跨图重建等能力。

这些都应该进入“可复用”清单。否则新需求很容易长出第二套状态和第二条结算链，等到修Bug的时候，又得判断玩家究竟走了哪条入口。

剩下的缺口才是任务。例如道路出口与入口数据、独立落点、到访记录、目的地解析，以及地图标记。

这一步看起来慢，其实是在缩小真正要改的范围。知道哪里已经能用，才知道哪里需要补。

### 两份设计有冲突，先把冲突拿出来

还有一种情况比“没有设计”更麻烦：设计有两份，讲得都很肯定，但说的不是同一件事。

出行方案记录过费用模型的冲突。一份方案按地图对维护费用，后来的拓扑设计引入了另一种费用口径。

如果工程直接挑一个实现，代码可能没问题，却替产品做了一个没有说明的决定。

当时的处理是把冲突列成明确决策，最终第一章保留逐对费用矩阵，新的类型费用口径从后续章节生效。

这一段历史很值得保留。它让人知道为什么代码里出现不同阶段的规则，也避免后面的人看到“不统一”就顺手合并掉。

**工程任务可以细化设计，但不能悄悄替换已经约定的玩法。**

{{IMG:GAME-07-现状与缺口}}

### 按变化的边界拆，不只按文件夹拆

需求要跨四五个目录，任务不一定就拆成四五个目录。

比如道路切图这一批，可以同时包含出口数据、世界交互和实际落点。因为这几部分一起完成，才能走通“从A地图到B地图”这条行为。

反过来，只把数据字段加完，虽然可以提交一个技术步骤，却还没有交出玩家能用的道路。

所以拆任务时，要同时考虑两个层次：内部实现步骤怎么推进，以及哪几步合起来构成一个可验证成果。

涉及存档结构变化的内容，也可以单独安排验证批次。出行方案就将较低风险的基础工作放在前面，再处理到访状态和迁移。

这样一旦失败，定位范围相对清楚，也容易保留前面已经成立的结果。

### 把成功路径写完，再问失败会留下什么

切图成功当然要检查：地图对不对，落点对不对，费用扣没扣。

更要问，条件不满足时怎么办？

目标没解锁、金币不足、落点不合法、目标资源无法准备，这些情况是否会先扣费？玩家会不会停在一个新旧世界混杂的状态？

这里不展开具体提交顺序，后面的交通专题再详细讲。对任务拆解来说，关键是先把“不允许出现的中间态”写下来。

同样，步行和车夫是两个交互入口，但都需要验证原有未领取战利品在跨图后的恢复。能力已经存在，仍然要检查新的调用方式有没有绕过它。

复用不是免验收，而是不用再造一套实现。

### 给“免费走过去”补一组失败场景

可以顺着玩家的动作再拆一遍。角色靠近出口，看到交互提示，触发后进入目标地图，落在对应入口附近。路通了，才算这条行为的正常路径成立。

接着换条件：目标没解锁，玩家留在原图；目标入口配置不存在，不能随便降级成地图中心来掩盖错误；新场景准备失败，原来的进度和资源要有明确处理办法。

再加一层连续操作。玩家站在出口反复按交互键，会不会产生两次旅行请求？第一次切换已经开始，后续输入由谁拒绝？如果依赖延迟回调，回来时还是不是同一张地图？

这些问题并不是一开始都要写成复杂实现。先把允许和拒绝的行为写下来，工程才知道在哪里建立状态边界。否则最容易出现的局面，是每个入口单独补一条判断，后来规则稍变就漏掉一半。

最后再看持久状态。到访标记是在切换成功以后记录，还是发出请求就记录？玩家没真正到达，却已经解锁直达，会不会改变探索顺序？这种问题应当回到产品口径确认，不能只当一个方便的布尔值处理。

### 给任务一份能对照的交付清单

我会把这样的工程任务整理成几项：

| 要写清楚的内容 | 出行需求中的例子 |
|---|---|
| 当前已有能力 | 地图服务、切图事件、奖励重建 |
| 本批新增 | 道路交互、目的地解析或到访状态 |
| 依赖与顺序 | 前置能力完成，再开放对应目的地 |
| 失败边界 | 不满足条件时不留下扣费和切图半成品 |
| 验证入口 | 正常往返、拒绝条件、奖励恢复、存读档 |
| 已知限制 | 当时尚未覆盖的地图形状或跨章场景 |

这里最容易省掉的，是最后一项。

但限制写清楚，别人才能正确使用成果。当时只验证了某一类地图，就不要把“所有地图都可以”写进交付说明。

### 文档写完，还得回到游戏里

产品文档、工程方案、实施记录和审阅报告，分别承担不同工作。

产品文档维护目标与规则；工程方案说明如何从现状走到目标；实施记录留下实际改动和验证；审阅再检查遗漏及证据是否支持结论。

几份材料之间应该能找到彼此，但不必复制同一段正文。特别是配置数据，不能一边改JSON，一边忘了文档里还藏着另一套值。

等任务做完，应该用游戏里的实际行为反查：玩家能不能走通，数据能不能恢复，失败时有没有合理反馈。

不然文档越来越齐，游戏里仍然进不去下一张地图，这种“完整”也挺尴尬的。

### 一条任务卡，至少要能指出验证对象

下面给一份缩小后的任务卡示例，表达方式依据出行方案整理，不是正式数据结构，也不意味着这些字段会进入游戏：

```yaml
feature: 相邻地图免费步行
existing: MapService、地图事件、未领取奖励重建
change: 出口交互与目标入口解析
success: 到达对应落点，不扣旅行费用
reject: 未解锁、目标缺失、入口非法
persistence: 成功到访后更新对应状态
regression: 往返、重复输入、奖励恢复、读档
```

这张卡的价值，是让开发和验收指向同一件事。“支持步行”太宽，“从某个有效出口到达目标入口，失败时不改变地图和费用”就具体得多。

开始实现以后，还可以在任务卡旁边记下实际改到的入口和测试名称。如果发现需要改共享接口，就补上调用方影响面，而不是只记录最终新增了几个文件。

原先的验收用例也可能随着产品决策变化。比如车夫目的地从相邻连接变为城镇集群，旧断言如果表达的是旧口径，就要按明确决策更新；但不能顺手把“费用不足不扣钱”这样的有效约束也放宽。

因此，测试变化最好能说明是在扩展覆盖、更新过期场景，还是修复夹具。让审阅者看得出我们改变了什么，才能避免“最后都是绿色”掩盖真实语义变化。

各位看官如果发现任务卡写完以后仍然不知道先改哪里，可以退回去补现状调查。缺少当前入口和依赖，再详尽的未来流程也很难直接转成可靠代码。

### 小结

从产品到代码，中间的工程拆解要回答三件事：现在有什么，真正缺什么，以及这一批结束后怎样证明补上了。

《末法纪元》的出行方案还说明，冲突决策、前置依赖和已知限制，都应该在动手前尽量说清楚。
