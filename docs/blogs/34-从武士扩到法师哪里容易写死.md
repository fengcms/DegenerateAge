# 末法纪元·游戏开发34：从武士扩到法师，原来只有一个职业也会留下这么多假设

### 前言

各位看官，项目只有武士时，“玩家”与“近战角色”经常是同一个意思。

普攻默认贴身，技能面板遍历整张表，快捷栏填固定几个ID，生命法力沿一套公式成长。每一处都能用，直到要增加法师。

这时候只在人物创建界面多放一个选项，远远不够。旧代码里那些从来没有被叫作职业规则的默认值，会一起冒出来。

《末法纪元》的第二职业就是这样逐步接入的。这一篇聊框架、属性、技能与存档的交界，避免把法师做成远距离的武士换皮。

{{IMG:GAME-34-封面}}

### 先找到“只有一套规则”的位置

早期工程并没有独立职业概念。六项技能默认属于所有玩家，普攻射程也会被接近和自动停步逻辑复用。

加入新职业前，需要盘点这些入口：创建角色、派生属性、技能可用集合、默认快捷栏、手动请求、自动选择、存读档和显示名称。

这份清单比先设计一棵继承树更有用。职责没摸清，就复制一个法师玩家脚本，后面修公共移动或存档时又得同步两份。

[第九篇]({{LINK:GAME-09}})的分工仍然适用。共用生命周期保持，确实不同的职业定义显式提供，别让身份判断散满所有面板。

### 职业定义表达差异，不复制全部角色

当前PlayerClass从classes配置解析生命、法力、攻击等系数，普攻射程、基础技能和主动技能集合。

武士保留自身默认规则，法师定义另一套能力入口。调用方通过统一接口查询，而不是自己到处写“如果法师就……”来拼技能名单。

下面是职业归一的实际实现：

```gdscript
const DEFAULT_ID := "warrior"

static func normalize(id: String) -> String:
    return id if is_valid(id) else DEFAULT_ID
```

它为旧档或缺失身份提供默认职业。正式数据仍然要校验，不能因为这里有回退，就允许配置拼错也静默当作武士。

### 创建顺序也会影响职业结果

角色身份应该先确定，再生成依赖身份的默认快捷栏。否则玩家选了法师，却拿到武士普攻和技能配置。

这种问题不一定报错。那些技能ID都存在，面板能显示，只是归属不对。所以仅检查ID合法不够，还要核对当前职业是否允许使用。

读档和导入也要走相同归一与恢复口径，避免新建角色正常，旧档升级后出现另一套技能集合。

[第十篇]({{LINK:GAME-10}})讲模板与实例，职业定义是规则，玩家存档里的身份是选择结果，两者需要对应而不是互相替代。

{{IMG:GAME-34-职业入口}}

### 系数放错位置，会悄悄放大另一项属性

项目生命派生会使用基础攻防和装备贡献。职业攻击系数如果过早混进基础攻击，可能顺便提高生命，甚至与其他倍率重复叠加。

因此PlayerClass明确要求攻击系数在对应最终攻击入口使用，不要为方便塞入被其他公式共用的底数。

防御也不能简单按文案“法师脆”就打折。当前承伤是攻击减去部分防御的差值，防御小幅下降，实际伤害变化可能比同样比例的生命变化更剧烈。

想做职业差异，先画清公式依赖，再选择可解释的调整位置。不是每个乘数都可以互换顺序，尤其后面还有取整和下限。

### 高蓝量，要同时看成长来源

早期法师有较高法力倍率，但生命会受攻防和装备成长影响，法力原有底数主要随等级线性增加。高等级时，红蓝关系逐渐偏离职业预期。

后来的资源调整引入法师专属成长口径，并修改攻击法术计费参考池。不能继续引用早期“全部按最大蓝百分比”的方案，作为现行规则。

这说明职业差异不是创建时的一张静态对照表。低等级正常、高等级却变形，常常来自几项派生使用了不同成长来源。

本篇不展开费用公式，下一些资源专题会细讲。这里先记住：增加一个法力倍率，不等于整个成长链已经协调。

### 远程射程，不自动等于安全

自动战斗如果不会主动风筝，怪物还是能贴近法师。射程提供先手机会，却不保证持续拉开距离。

因此法师生存不能只靠“站得远”的文字说明。魔法盾、资源消耗和近距范围技的实际施放，都需要在被围攻场景验证。

同时射程还影响目标接近、停止距离、自动站位和技能命中集合。只改普攻配置，旧的近战停步逻辑可能仍把角色推到怪物脸上。

[第二十二篇]({{LINK:GAME-22}})讲自动调度，职业扩展会暴露它是否真正按能力查询，还是仍然写死一套战术。

{{IMG:GAME-34-派生与行为}}

### 普攻也需要有明确身份

早期只有基础斩击时，可以靠固定ID跳过主动技能评分。法师火球加入以后，若没有基础技能标记，就可能被自动选择当作零冷却主动技能反复参评。

当前职业定义提供基础技能，技能数据也表达相应性质。判断规则应围绕能力语义，不是只认识旧名字。

快捷栏拖拽、施放入口和显示说明都应读取相同归属。如果面板允许拖进不属于本职业的技能，再到执行时拒绝，玩家只会觉得按钮失效。

兼容旧快捷栏时则要明确清理或替换方式，不能把非法条目原样保留，又让每次加载反复报错。

### 共享装备，不等于忽略配装差异

项目没有因为第二职业就另造一套专属装备经济。共同模板和实例规则仍然沿用，但同一件装备对不同职业的价值会因资源与行为不同而变化。

例如法力不仅支撑输出，还承担盾的转嫁；生命词条又可能改变生存压力。比较职业时，不能只固定总攻击然后宣布已经平衡。

需要记录技能轮转、药水消耗、承伤和击杀条件。用极端测试装验证接口可以，不能替普通成长装备的体验作结论。

配置共享能降低内容维护成本，平衡验证却仍然要看组合，这两件事不会互相抵消。

### 旧档兼容，要尊重字段所在的位置

给玩家增加职业身份，可能触及原来只接受数值字段的验证逻辑。直接把字符串加进某个默认字典，若验证器仍按全数值处理，旧档可能被误判损坏。

因此新增字段要同时看生成、保存、读取、校验和导入，不是只修改默认玩家。迁移应保留旧身份语义，也避免重复赠送资源。

这类问题与[第八篇]({{LINK:GAME-08}})的完整度审查相连。新职业单独能跑，未必说明已有玩家还能顺利继续。

历史资料中的真实存档快照也要分清职业来源。没有身份字段的旧档，不能因为后来用法师探针重算，就称为真人法师配装。

### 怎样证明“法师接进来了”

先检查身份归一、技能归属和默认快捷栏，再看属性与射程，随后验证手动和自动施放、护盾、存档往返。

同时给武士保留回归。第二职业加入，不应该让原职业默认倍率或基础动作无声变化。

项目已有框架、远程与资源成长用例，本轮未执行以下游戏测试：

```sh
python3 tools/run_isolated_tests.py ClassFrameTest MageRangedTest MageResourceGrowthTest ClassBalanceTest
```

这些检查也不能代替长期玩法和平衡窗口验收。具体夹具、等级和装备条件要随结果一起记录。

还要对照数据与辅助函数说明。某处注释保留旧射程，配置后来已经调整，读文章时不能把两份数字同时当现状。实际行为由当前配置与调用链共同决定，说明文件则应记录为什么变化。这个核对过程看似琐碎，却能避免后续自动站位又按一个过期常量继续设计。

### 小结

第二职业会暴露原来被当成通用规则的单职业假设。把身份、能力集合、派生位置、行为与兼容接好，比增加一列系数更重要。

各位看官扩角色类型时，可以先搜索哪些地方默认“所有玩家都一样”，再决定哪些保持共享、哪些由定义提供。框架跟着真实差异长出来，通常更容易维护。
