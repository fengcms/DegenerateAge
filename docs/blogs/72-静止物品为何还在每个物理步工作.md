# 末法纪元·游戏开发72：静止物品，为何还在每个物理步工作

### 前言

各位看官，地面装备已经不动了，表现也换成共享图片，它还需要每个物理步找一次玩家、检查一次距离吗？单件看起来很便宜，两千多件一起做，成本就不再小。

《末法纪元》在静态表现优化以后，继续把合适的持久装备交给地图内共享调度。物品仍然存在，点击区域和奖励也保留，只是暂停没有意义的单件空转。

这篇专讲静止与唤醒。少执行一次回调很容易，确保腾格以后能恢复、鼠标立刻能用、时间没有少算或重复算，才是这项优化真正需要处理的部分。

{{IMG:GAME-72-封面}}

### 先说明谁能进入静止

不是所有掉落都应该停掉。当前接管的是高密度、共享表现已就绪、保护与停驻阶段结束、尚未认领的持久装备。

普通物品的地面期限、出场动画与认领飞行仍走原路径。它们有明确时间推进需求，不能因为都叫GroundItem就统一关闭处理。

[第五十三篇]({{LINK:GAME-53}})区分认领和表现，已经认领的对象更不应该再次加入待拾取静止集合，否则可能出现成功以后又被调度回来的错误。

进入资格应放在当前步处理完成以后核对。历史回归就发现过成功物品又被重新登记，原断言保留，修正了登记时机，而不是把预期数量改掉。

### 调度器属于当前地图，不属于全局世界

当前每个掉落根节点最多建立一个GroundLootIdle，持有该地图的静止集合。切图释放父节点，服务与引用一起退出。

这样既不用每件装备订阅一组全局事件，也不需要一个永远存在的管理器记住所有旧地图节点。资产持久记录仍由原系统负责，调度器不复制另一份奖励数据。

物品提前释放时要注销集合；集合为空，服务自身也停止物理处理。否则省掉单件回调，却留下一个永远醒着的空调度器，只是把问题换了位置。

所有权范围明确以后，退出测试也更简单：释放世界，检查节点回到基线附近，而不是猜某个全局字典是否还藏着旧对象。

### 一次查询玩家，扫描当前集合

服务通常按未缩放时间约十分之一秒检查一次，共享玩家位置、密度与版本，然后扫描需要唤醒的对象。

这是减少重复查询和回调，不是已经建立空间索引。最坏扫描仍与静止集合大小相关，文章不能把集中处理写成复杂度凭空变成常数。

同时，很多静止物品只有少数附近可能拾取，后续是否再做空间分桶，应该由当前规模和测量决定。先把已确认的空转拿掉，不代表必须一次完成所有候选方案。

[第七十一篇]({{LINK:GAME-71}})的经验仍然适用：每一阶段重新看剩余成本，不能拿最初计划表代替实际优先级。

{{IMG:GAME-72-共享调度}}

### 调度时间与物品时间，要各自算清楚

调度检查按未缩放步长限频，避免倍速把装饰检查放大；物品出场时间、相位和提示冷却，则需要按原游戏时间补回。

当前服务一边累计游戏秒，一边用除去倍率的步长推进检查预算。这两份时钟用途不同，不能为了统一都换成真实秒。

如果静止十秒以后醒来，装饰相位还停在进入时的位置，冷却也没走，说明省回调时把时间一起冻住了。反过来，醒来又多补一遍，就会让阶段提前结束。

[第六十九篇]({{LINK:GAME-69}})讲镜头独立真实时间，这里不能照搬结论。视觉相机与物品业务的计时职责不同，时间选择来自语义，不来自哪个公式更方便。

### 进入静止的第一步，最容易重复计时

物品在自己的物理回调里已经累加本步delta，随后登记到服务；若服务在它后面执行，共享时钟还会再推进同一物理步。

因此当前静止起点包含必要补偿，避免醒来把刚才已经经过的那一步再算一次。实际登记节选如下：

```gdscript
var pending_step := service.get_physics_process_delta_time() if Engine.is_in_physics_frame() and service._clock_frame != Engine.get_physics_frames() else 0.0
item._idle_started = service.game_clock+pending_step
item.set_physics_process(false)
```

这不是随便加一个很小偏移。它对应节点执行先后，必须用真实物理回调边界测试，而不是只在手动调用函数时传几个数字。

同一步进入又恢复，应保持累计时间正确。大批物品反复静止时，小误差也会变成可观察的阶段错位。

### 醒来补时间，恢复原入口

当前唤醒先从集合移除，再把累计游戏时间补进物品状态，清除服务引用，恢复物理处理。需要立即检查时，沿原物品入口推进一次。

核心补偿如下，省略前后的集合与状态处理：

```gdscript
var elapsed := maxf(0.0,game_clock-item._idle_started)
item._spawn_t += elapsed
item._phase += elapsed*3.0
item._blocked_cd = maxf(0.0,item._blocked_cd-elapsed)
```

调度器不自己重写入包或出售。真正交易仍经过既有门面，避免新增一条没有收藏保护、没有实际入账口径的快速路径。

共享服务负责何时让对象重新工作，物品负责当前是否能认领，业务层负责如何改变资产，这三层各自清楚，恢复才不会变成另一套平行结算。

### 腾格需要快，手动输入更不能等

库存或策略版本变化时，服务在下一物理步检查，允许原来失败的附近物品重试。旧调用直接腾格也有共享容量观察兜底。

普通走近可能增加一个短检查间隔，但悬停和点击同步恢复，不等待后台预算。玩家明确操作的响应，不应该被自动处理节流吞掉。

[第五十五篇]({{LINK:GAME-55}})已经说明失败版本的作用，版本未变时不反复交易，变化以后再试。静止服务复用这条规则，而不是每件再建一个计时器。

还要避免提前给所有远处物品都查询版本。历史试验发现那样反而增加成本，后来撤回，不能把一次失败尝试也算进优化收益。

### 多个物理补步，共享显示帧预算

腾出空间以后，积压装备可能同时满足条件。若同一帧瞬间恢复全部交易，刚清掉空转，又制造新的同步尖峰。

当前对自动拾取尝试设置每显示帧预算，多个物理补步共享，不是每补一次物理就重新获得一份额度。未处理完的留到下一显示帧继续。

这项限制延后的是自动队列，并不降低伤害、碰撞和技能结算频率。手动请求仍沿即时路径，真实奖励也不因此丢弃。

这里必须说清帧的种类。物理步、显示帧与游戏秒不是同义词，预算若绑定错计数器，倍速或卡顿下就可能悄悄放大。

### 密度与素材改变，退出静止恢复原表现

地图密度下降、缓存失效、模板或数据版本改变时，物品需要恢复绘制与原有更新。不能一直显示旧图，只因为当前已经睡着。

服务不保存另一套长期表现事实，而是检查当前缓存依据是否仍成立。悬停也会让对象恢复必要细节，避免静态优化隐藏用户正在查看的信息。

退出路径包括成功领取、手动交互、条件失效和节点释放，每一条都要正确清理集合。只测正常拾取，抓不到切图或物品外部释放后的残留引用。

### 历史窗口结果，支持什么结论

固定Boss与混合掉落压力夹具显示，静止调度减少了部分稳态负担，原有物品与持久记录数量保持，物理步没有通过降低战斗频率来减少。

但夹具冻结了玩家和部分流程，短时内存快照也不是一晚挂机不泄漏的证据。高倍速下仍未达到整帧目标，不能宣称全部卡顿已经解决。

复核入口如下，本文没有运行测试或重新测量：

```sh
python3 tools/run_isolated_tests.py GroundLootIdleTest LootRetryTest AutoSellPickupTest
python3 tools/run_isolated_tests.py DenseBossLootBenchmark --rendered
```

验证时还应反复切换密度上下阈值，确认恢复之后能再次进入静止，而不是第一次成功、第二次就遗留旧服务引用。这种往返比单次截图更能发现状态交接遗漏。

### 小结

静止物品可以暂停空转，但它的身份、时间和恢复资格不能一起暂停。共享调度只有把进入、补时、唤醒和退出都接好，才是完整优化。

少做重复查询，保留即时交互，自动工作有预算，真实结算走原路。这样的静止才只是少工作，不是让游戏世界少了一部分应该发生的事情。
