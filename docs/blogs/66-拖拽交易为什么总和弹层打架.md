# 末法纪元·游戏开发66：拖拽交易，为什么总和弹层打架

### 前言

各位看官，背包和合成窗口都打开了，装备也能拖起来，鼠标松开却没有反应。把窗口挪一下又正常，放大界面以后，落点还会偏半个格。

这类问题很容易被统称为拖拽不好用，但原因可能分别在输入拦截、窗口层级、坐标换算或材料资格。一个能看见的格子，并不一定是鼠标真正命中的对象。

本文沿《末法纪元》的双面板交易、合成材料格与浮窗置前，拆开这些层次。先找清是哪一步没接上，再谈怎样让操作顺手。

{{IMG:GAME-66-封面}}

### 拖起、接收和提交，是三段不同动作

拖起时生成载荷，描述来自哪里、具体物品和当时状态；接收区域判断是否愿意处理这类载荷；业务层再验证资格并改变选择或真实容器。

如果第一段正常，鼠标旁出现图标，只证明拖拽已经开始。不能据此断言目标格收到了事件，更不能证明材料满足合成规则。

[第四十二篇]({{LINK:GAME-42}})讲过稳定身份，这里载荷也不能只带一个原格号。拖动过程中可能发生整理、换装和磨损，落下时需要确认仍然对应原对象。

因此排查可以分别记录开始载荷、接收目标和业务结果。三个观察点越清楚，越不需要在满屏控件里到处试着改鼠标过滤参数。

### 全屏根控件，可能替所有子窗口挡住鼠标

一扇浮窗通常有全屏宿主、居中的布局容器和实际面板。真正需要接收鼠标的是标题、按钮与内容区，不一定是整张全屏矩形。

如果全屏根节点也停止鼠标事件，窗口外的背包即使露在下面，也可能点不到。调高图标层级，只会让它看起来更靠前，不一定改变命中归属。

当前共用浮窗让自身布局容器忽略鼠标，标题停止事件，标题中的非按钮装饰也忽略事件，把输入留给真正需要操作的控件。

这不是所有节点一律IGNORE或一律STOP。透明区域、可交互区域和背景装饰有不同职责，应根据真实矩形检查，不能靠随机切换参数试到眼前能用就结束。

### 视觉置前，与GUI命中需要同源

早期只给四个常驻窗写了置前名单，铁匠合成和其他服务窗没有接入。后来并开越来越多，就出现点击后窗也抬不上来的情况。

当前用浮窗分组登记，不再为每个新增面板复制一份名字清单。置前会调整兄弟节点顺序，再同步可见窗口的绘制层级。

关键片段如下，前面已经根据上层锚点算好目标位置：

```gdscript
if panel.get_index() != target:
    parent.move_child(panel, target)
_sync_z_order(parent)
```

在本项目的Control布局里，只提高z_index不能替代GUI命中顺序调整。否则玩家看见前窗，点击却落到后面的控件，表面越修越像随机故障。

### 普通浮窗，不能越过模态与拖拽表现的天花板

点击置前不等于把任何窗口移到整个UI树最末端。拖拽幽灵、反馈层和模态确认等仍然需要保持自己的上层位置。

当前层级服务寻找可见锚点，在普通浮窗范围内置前。这样点一下背包，不会把装备确认遮到下面，让玩家继续操作一个本应等待确认的流程。

Esc关闭对象也应与最上层窗口一致。点击抬前了合成窗，关闭键却关掉后面的角色窗，会破坏玩家刚刚建立的空间预期。

[第六十五篇]({{LINK:GAME-65}})讲并存规则，而这里处理并存之后的顺序。能不能同时存在、谁在上面、当前输入归谁，要相互配合，不能用关闭后窗代替层级管理。

### 拖窗坐标，要换到同一个空间

鼠标事件常带全局坐标，窗口位置却可能在经过界面缩放的逻辑空间里。直接拿两者相减，倍率一变，拖动速度和偏移就不对。

当前浮窗通过宿主画布变换的逆矩阵转换鼠标：

```gdscript
func _owner_mouse_position(event: InputEventMouse) -> Vector2:
    return owner_panel.get_global_transform_with_canvas().affine_inverse() * event.global_position
```

转换以后再计算拖拽偏移与边界，避免把显示倍率手工乘除到各个回调里。窗口标题在哪个坐标系，鼠标就先转换到那个坐标系。

这里不是让所有坐标都变成世界坐标。地图投影、UI逻辑位置与屏幕事件各有含义，最重要的是在跨边界时明确转换，而不是名字都叫position就直接相加。

### 格间缝隙，也属于玩家眼里的投放区域

材料格之间有留白，视觉上是一整组，鼠标松在缝里却完全不接收，会让玩家觉得操作要求过于精确。

当前合成格网按最近格中心决定目标：

```gdscript
var distance := point.distance_squared_to(slot.position + slot.size * 0.5)
if distance < best:
    best = distance
    nearest = slot.index
```

这段在已命中的格网区域内计算，不能推广成整个屏幕都吸附到最近格。接收区域边界仍然存在，格网也不会自行修改背包。

还要过滤隐藏或非材料子节点，不能把标题与辅助控件误当成槽位。返回的是业务格号，后续资格检查继续使用这个明确目标。

### 预选材料，不能照搬出售托盘的扣物动作

货郎托盘是把物品转移到待成交容器；合成材料格通常只是保留选择快照，确认前真实装备仍在原容器。

如果为了复用拖放外观，直接调用出售托盘移出逻辑，取消合成就得额外退还材料，还会引入满包退不回和存档所有权问题。

[第五十七篇]({{LINK:GAME-57}})讲过暂存时机，这里更需要看清语义。外观相同的格子，不代表拥有同一种资产归属。

当前合成接收后由面板保存身份与快照，最后才调用已有结算入口消耗。切服务、撤下材料或关闭，只清临时引用，不需要把一堆真实物品塞回去。

### 接收载荷之后，还要解释为什么不能用

格网可以接受背包装备载荷，再由业务层说明品质、星级、收藏与档位问题。这样玩家把东西放进去时，能得到具体原因。

但穿戴来源并非所有格都接受，保星旧料等目标要明确开放。不能看到载荷是装备，就无条件把身上的任何东西当作合成材料。

[第四十七篇]({{LINK:GAME-47}})还讨论过拖动期间耐久变化。允许的变化需要更新当前完整快照，原槽换了另一件则继续拒绝，不能用旧图标蒙混过去。

拖拽的流畅，不是放松材料资格。它是让命中和反馈可靠，再把业务判断交给正确入口，拒绝时也有清楚说明。

### 宽屏并排，窄屏要保证两边仍能操作

交易或合成需要同时看来源与目标，窄窗口加高倍率时，不应简单把一扇窗藏到另一扇后面。

可以按逻辑可用空间切成上下区域，并用各自滚动承载内容；文字保持玩家设置，按钮与材料格仍有可达位置。

默认停靠与用户拖过的位置也要分清。内容刷新不应每次把窗口拉回中央，布局模式切换又不能死守已经离开屏幕的旧坐标。

所以布局不仅测试打开瞬间，还要测试拖动、换服务、缩放与窗口尺寸变化之后。真正的操作链远比一张静态并排截图长。

### 同载荷测试，与真实鼠标测试互相补充

后续可以从格网、浮窗与定向用例复核：

```sh
rg -n 'slot_at|item_dropped' scripts/ui/fusion_material_grid.gd
rg -n 'raise_panel|_owner_mouse_position' scripts/ui/floating_window.gd
python3 tools/run_isolated_tests.py FloatingWindowInputTest EquipmentFusionUiTest --rendered
```

本文未运行游戏测试。同载荷调用适合检查资格、去重和预选不扣物；真实鼠标则要证明目标实际接得到事件，拖拽幽灵不被遮住，放在缝里也对应正确格位。

还要检查点击与拖放不会同时触发使用。逻辑入口通过，并不能代替不同倍率下的原生手感验收，更不能仅凭窗口成功渲染就宣称全部交互已验证。

重复投放同一件也要有确定结果。把已选材料拖到另一格，是交换、移动还是拒绝，应沿当前面板规则表达，不能让两个槽同时引用同一ID，等最后结算才突然说材料不足。尽早反馈既减少误操作，也让最终防重复检查只承担兜底职责。

### 小结

拖拽交易把输入、坐标、层级与业务选择连在一起。拆开拖起、接收和提交，统一视觉与命中顺序，再按真实语义处理材料，问题才容易定位。

玩家只需要把一件东西拖到看得见的格子里。程序则需要保证他看见的、点到的和最后处理的，始终是同一个目标。
