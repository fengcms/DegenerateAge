# 末法纪元·游戏开发21：624个候选点，需要跑624次完整寻路吗

### 前言

各位看官，自动巡游要选一些能去的位置，最直接的验证方法是什么？对每个候选跑一次寻路，路线不为空就留下。

这办法很容易写对第一版。可地图一大，候选成了几百个，就会把“只是想知道能不能去”变成几百次路径搜索和平滑。

《末法纪元》的大地图优化记录里，有一项很具体的验证：624个候选点，筛选阶段零次完整寻路。它没有删掉真实移动时的路线，而是把两个不同问题拆开了。

这一篇聊这种拆分，以及它什么时候成立、什么时候还不够。

### 先说清楚，调用方到底要什么

“从这里能不能到那里”和“具体沿哪条路走过去”，答案不是同一种数据。

前者只需要一个判断，可以用来过滤怪物、掉落或巡游点；后者要输出路径，还可能包含转角余量和平滑处理，供角色逐段移动。

如果候选还没选中，就为它构建完整路线，许多计算最后会直接丢掉。选怪只留一只，其余几十份路线没有进入执行；巡游也只会先走其中一段。

[第十九篇]({{LINK:GAME-19}})讲路径有体积和碰撞成本，这里更没有必要把它们当成一个便宜布尔查询反复调用。

### 连通区域可以先回答一部分问题

对一份固定通行布局，可以把互相可达的格子归到同一区域。起点和终点属于同一片，才有必要继续考虑完整路线。

区域标记需要遍历布局，但构建以后可以服务许多查询。不是每检查一个候选，就从头探索全图。

CaveLayout提供了这样的入口，下面摘取实际判断：

```gdscript
## 使用当前连通区域编号判断两格是否相通。
func reachable(from_cell: Vector2i, to_cell: Vector2i) -> bool:
    var component := component_at(from_cell)
    return component > 0 and component == component_at(to_cell)
```

这里的component_at内部会确保标记和当前导航版本一致，并处理对应格的解析。不能把这三行脱离布局语义，理解成任意图都能靠比较整数完成寻路。

### 四方向标记，为什么能服务八方向移动

项目允许八方向移动，同时禁止从阻挡格夹角斜穿。在这个规则下，合法斜行的两侧条件意味着仍然有对应的四邻接通行关系。

因此四方向连通标记可以用于判断这里的可达区域。若以后允许特殊斜穿、单向跳跃或传送，这个等价条件就可能失效，需要重新建模。

不要把某个项目成立的简化，当成所有导航问题的结论。连通性算法依赖实际移动边，规则变了，区域编号也要跟着变。

同样，动态门变化以后必须重建相关区域。[第二十篇]({{LINK:GAME-20}})已经讨论过版本失效，没有这一步，快速查询只会更快地返回错误答案。

### 筛选先便宜，选中以后再认真走

一个比较自然的处理顺序，是先检查候选是否还活着、是否符合开关、是否在允许范围，再做可达过滤，最后按选择策略确定目标。

真正需要移动时，再向导航器请求路线，并保留原来的碰撞间隙、路径平滑和偏航恢复。这里省掉的是未选中候选的工作，不是降低最终路线质量。

拾取也一样。物品已认领、距离太远、容量规则不允许，就没必要先给它算一条完整路径。便宜条件越早排除无效项，后面的计算越集中。

但过滤顺序不能改变业务语义。某些物品允许特殊容量处理，就应先使用统一规则判断，不能为了减少查询把所有“看起来满包”的情况一刀切掉。

### 624这个数字，该怎样读

优化记录中的624点来自当时具体地图和巡游构建入口。它证明那份夹具里，候选筛选没有再调用完整寻路，并不是所有地图永远都有624个点。

历史记录还给出了不同阶段的CPU计时，但它们属于单次无头对照，不能换算成玩家帧率。后续巡游间距和规划方法也继续调整，不能把旧候选数当成今天的固定参数。

所以引用这个案例时，最稳的结论是：把完整路线从批量可达筛选里移出去，减少了无用工作；具体耗时和体验收益仍要按当时场景解释。

这里的零次也只针对筛选阶段。玩家开始移动以后，当然仍然要构建和更新实际路线。

### 构建成本没有消失，只是变得可复用

连通标记要占内存，也要扫描布局。地图加载时准备，能减少首次开启自动巡游的集中卡顿，但会增加装配阶段的工作。

这不是免费优化。记录里就明确区分了准备阶段和游玩阶段的成本变化。把耗时挪到加载，并不能在报告里写成这部分计算凭空消失。

如果地图频繁改变障碍，区域重建也可能变成新瓶颈。要看变化频率、格子规模和查询数量，再决定是否需要更复杂的局部维护。

当前规模下，先复用一次准备结果，比预先引入增量图和线程更容易验证。后者要处理新的结果失效和线程边界，不应仅因为地图“大”就默认采用。

### 可达不等于路线短，也不等于现在适合过去

同一区域的两个点可能隔着很长的绕行。连通性只回答存在通路，不能替距离排序或巡游顺序提供真实路径长度。

更不能自动判断战斗是否安全。目标可达，但那里有危险技能；物品可达，但玩家当前被击倒；这些是其他规则需要处理的状态。

因此接口名称和返回含义要克制。一个可达过滤函数不应偷偷承诺“最快”“最近”或“最佳”。调用方知道它少回答了什么，才不会继续拿结果做错误推断。

如果玩法确实要按路径代价选目标，可以先用便宜条件缩小候选，再对少量对象求代价，作为另一项明确设计，不必退回全量平滑路线。

### 用行为计数验证，别只盯一个毫秒数

性能测试可以给寻路入口加调用计数，构建一批候选以后断言筛选没有请求完整路线。随后真的选一个目标移动，确认路线仍然被构建。

这比把机器上某次耗时写成硬阈值更稳定。硬件负载变化会影响毫秒数，调用链是否退回重复工作，则更容易被明确断言发现。

还需要拿区域判断与实际AStar结果对照，覆盖墙角、孤岛和门禁开关。算法跑得快，不代表边界条件自动正确。

下面是项目已有的检查入口。本轮文章没有运行这些测试：

```sh
python3 tools/run_isolated_tests.py CaveConnectivityTest MapPerformanceTest CaveNavigationTest
```

### 缓存失败，也能避免反复白忙

巡游构建结束以后可能没有合法候选。需要一个明确的已构建状态，区分“还没做”和“做过但为空”，否则每次空列表都触发重建。

但空结果也要绑定地图、区域和导航版本。门打开以后不能继续永久拒绝，角色进入另一片区域也应重新评估。

这和本篇的核心是同一件事：只计算真正需要的答案，并且保留答案成立的条件。不要为避免一次重复搜索，换来永远不再响应世界变化。

### 先找重复调用，而不是先换算法名字

排查时可以先沿一轮完整决策统计：查了多少候选，每个候选走了哪几层函数，哪些结果根本没有被使用。看到AStar耗时以后就换一种寻路算法，可能没有消除最主要的重复次数。

同样，一轮里起点属于哪个区域，通常可以先求一次复用，不必每个候选都做相同解析。便宜查询乘上很大的次数，也会形成可避免的工作。

这些改动仍要保留调用边界，不能通过跳过合法候选来减少计数。优化前后候选的规则含义相同，调用数量和成本再下降，结论才更容易成立。

### 小结

624个候选点的案例，价值在于识别了查询需求：筛选先判断连通，实际移动再生成完整路线。

共享准备、明确失效、保留正确碰撞，再用行为计数与路径对照验证，才是一条完整改进链。各位看官遇到循环里调用重操作时，可以先问：每个候选真的都需要这份完整结果吗？
