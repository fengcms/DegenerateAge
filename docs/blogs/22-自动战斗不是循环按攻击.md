# 末法纪元·游戏开发22：自动战斗，不是写一个循环替玩家按攻击

### 前言

各位看官，角色已经能移动、寻路和攻击，给它加自动战斗，好像只差定时找一只怪，再调用攻击函数。

空地上站一只木桩，这样确实可能跑起来。可怪物会死，背包会满，玩家会手动躲技能，路线也可能不存在。再加上喝药、技能和巡游，一个不停攻击的循环很快就开始互相抢工作。

《末法纪元》的自动控制因此有明确状态和优先级。这一篇先看整条决策链，后面的巡游和目标黏性再分别展开。

### 自动决策负责选动作，别另造战斗规则

自动攻击应该和手动攻击共用合法性检查：目标有效、范围满足、攻击准备好、资源和冷却允许。

如果自动路径直接扣怪物血量，它就可能绕过手动玩家必须遵守的条件。界面看着自动开关正常，数值却已经变成另一套玩法。

项目会通过玩家的攻击和施法入口执行动作。自动层判断当前更适合接近、攻击还是使用某个技能，不负责复制一份伤害公式。

这也让后续职业扩展更容易定位问题。技能本身不能用，去查技能规则；技能手动能用、自动却不选，才进一步查决策条件。

### 先处理强中断，再讨论打谁

关闭自动、死亡、旅行或读档，应该优先处理。玩家已经关掉开关，不能因为手动接管计时还没结束，就继续保留旧移动。

实际源码把关闭和死亡放在主要决策之前。下面是关闭分支的节选，省略了部分计时清理：

```gdscript
if not GameState.auto_battle_on:
    if _state != State.OFF:
        _player.set_auto_move(Vector2.ZERO)
        _target = null
        _loot = null
        _set_state(State.OFF)
    return
```

这段依赖前面的玩家有效性检查。它表达的是取消应当结束执行意图，而不只是把HUD图标换个颜色。

测试这类分支时，要在接近、攻击和拾取不同阶段关闭，确认旧动作都不会在下一步恢复。

### 状态名是说明，不是系统本身

当前工程列了搜怪、接近、攻击、搜物、接近物品、拾取、恢复、手动接管、受阻和巡游等状态。

有枚举还不够。每个状态都要定义进入条件、执行动作、何时退出，以及离开时清理什么。否则状态标签显示“攻击”，角色却仍拿着上一段巡游方向。

[第十八篇]({{LINK:GAME-18}})讲接管时清理旧意图，这里同样适用。状态机的价值在于把交接说清楚，而不是把一长串判断换成一长串名字。

还要区分状态与临时条件。某个技能冷却没好，并不一定要新增一个独立状态；它可能只是攻击阶段中的一个选择条件。

### 有目标时，不需要每帧重新选一只

目标还有效，决策就继续围绕它行动。死亡、释放、黑名单或明确中断以后，才进入重新搜索。

无目标时的搜索还要节流，不能每个物理步全量扫描。候选先经过有效性、开关和范围检查，再结合可达性与选择规则。

[第二十一篇]({{LINK:GAME-21}})说明了为什么候选筛选不应该生成完整路线。选中以后再交导航器接近，能把决策成本和实际移动成本分开。

搜索不到也不代表停机。可能当前附近没有实例化敌人，可能区域尚未探索，或者候选被规则排除了，需要进入合理的等待或巡游。

### 接近与攻击的切换，也有余量

角色到了攻击范围，就不该继续和目标互相挤。接近方向、停止距离和实际攻击范围需要配套，不能一个按格数、一个按像素，最后来回抖动。

目标移动以后，路线也要按既有导航条件更新，但不必每帧重新搜索所有敌人。目标选择和向目标移动，是两种不同工作。

被击退或击倒时，则要避免把正常受控当成永久卡住。系统可以暂时停止推动，等待状态恢复，再继续判断；具体目标切换的历史问题后面单独讲。

范围里没有合适技能时，还应有合法的普攻或等待回退，而不是因为某个技能条件失败就让整段自动逻辑返回空闲。

### 技能选择，要看能不能真的生效

范围技能可以考虑命中数量，单体技能适合少量硬目标，自身增益又有独立条件。不能把所有技能按伤害系数排一个序，就认为自动轮转完成了。

法师还要面对蓝量和护盾维护。资源不足时继续挥攻击技能，可能使防护断档；单纯只看当前目标，也可能漏掉身边已经进入范围的敌人。

这些规则需要按职业设计，不能全塞成通用的“最强技能”。但最终资源扣除和冷却仍然回统一施法入口，自动选择不能获得额外特权。

验证时也应包含低资源、未解锁、冷却中和无效目标，避免只有满状态角色能正常运行。

### 拾取和战斗，谁先谁后得有产品规则

自动拾取可能在某些场景优先处理附近可收取物品，但背包没空间、物品已认领或规则不允许，就不应该反复争夺移动。

尤其满背包是正常场景，不该每帧把所有掉落扫一遍，再得出同一个失败结果。候选检查可以节流，失败也可以按条件缓存；关键奖励则仍要保留。

如果地图配置了持久未领取奖励，还要考虑积压上限前的停战保护。不能为了继续挂机，悄悄删除真实奖励来维持看起来流畅。

本篇不展开掉落结算，重点是自动层必须尊重统一拾取与容量规则，而不是为了完成当前状态自行吞掉物品。

### 手动接管与巡游恢复，是两个不同出口

玩家按键接管以后，旧目标和自动方向要按规则清理。战斗自然结束，则可能需要回到之前的巡游进度。

如果两种情况都统一重置成最近巡游点，角色会反复走旧路；如果两种情况都保留原目标，手动躲开以后又可能立刻被拉回去。

因此中断原因要保留。自然任务切换可以续接，玩家明确改命令、切图或关闭自动，则按新的上下文重新定位。

这也是状态机值得记录转移原因的地方。只打印最后状态，不知道谁触发了变化，很多“突然跑走”的反馈仍然无法解释。

### 验收要走一段连续流程

可以让角色先无目标巡游，出现怪物后接近，进入攻击，击杀后拾取，再恢复巡游。中间插入手动接管和门禁变化，确认系统能重新回到合法状态。

每一段既看玩家行为，也看目标、方向和相关引用是否清理。怪物释放以后，HUD没有血条不等于自动层已经丢弃节点。

已有控制和洞穴自动用例可以作为入口。本轮只做静态核对，未执行这些命令：

```sh
python3 tools/run_isolated_tests.py AutoControlAcceptance CaveAutoBattleTest SmokeTest
```

连续运行还要看资源和节点是否积累，短流程通过不能当成长时间挂机证明。

### 日志应该解释状态为什么变

对自动系统有用的日志，通常是选中目标、目标失效、手动接管、路线失败和恢复巡游这些转折，不是每帧打印位置。

记录最好带目标实例身份和地图上下文。同名Boss可以同时存在，名字相同并不能证明追的是原来那只。

若某种失败会反复发生，还需要限频和明确计数。日志本身不能成为挂机时持续写盘的热点，更不能因为觉得报错烦，就吞掉关键失败提示。

还要检查时间口径。攻击、技能和移动沿游戏时间推进，某些查询预算则可能按现实时间限制。开倍速以后，如果所有扫描也跟着成倍增加，就会把本来有限的候选工作放大。该保留响应的动作继续及时执行，可以节流的查询另设预算，不能把整个状态机统一降频来换流畅。

### 小结

自动战斗是对共享动作入口的持续调度，需要处理目标、路线、资源、中断和恢复。

把状态与转移条件写清楚，再用连续流程验证，才比一个能打木桩的循环多出真正可用的行为。各位看官遇到自动角色发呆时，可以先问当前状态在等什么，而不是马上加快搜索频率。
