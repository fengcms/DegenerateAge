# 末法纪元·游戏开发44：十级一套装备，简化了什么

### 前言

各位看官，做装备系统的时候，很容易冒出一个主意：人物每升一级，都安排一套对应等级的新装备。等级一路上涨，掉落也一路更新，看起来相当顺畅。

问题是，角色升一级的时间，真的足够把十种部位都换一遍吗？如果来不及，玩家背包里就会塞满差一级、差两级的过渡品，模板、掉落、合成和比较提示也都跟着变碎。

《末法纪元》后来把后续装备收束到十级一套。这次变化并不是简单地把等级除以十，而是重新划清型号档位、部位门槛、生成来源和历史实例之间的关系。

### 十种部位，不等于十四套模板

先把一个数量问题说清。人物有十四个穿戴槽，但戒指等双槽共用同一种部位模板，并不是左右各维护一套数值。

因此一套装备围绕十种部位组织，再映射到十四个实际槽位。前六套从一级、十一级一直到五十一级起步，每套各部位按规则分布在一个十级区间里。

这么组织以后，内容作者能围绕一档装备讨论用途，而不是反复确认六十三与六十四级的戒指到底差在哪里。玩家也更容易理解自己当前正在攒哪一阶段的东西。

不过，套只是分类单位，不表示捡到其中一件就获得套装加成。品质、星级的成套规则还要另算，不能看到同一个“套”字就把两件事混为一谈。

### 一套里面，部位等级仍有先后

当前部位偏移从武器开始，依次到鞋子、护甲、头盔、护腕、护膝、盾牌、手镯、戒指和项链，分别占据零到九的偏移。

也就是说，六十一级这一档，武器门槛是六十一级，项链则是七十级。这种安排让一档里的换装分散发生，不会所有部位挤在同一个升级瞬间解锁。

但它也带来很明确的体验：在这一档的起点，玩家可能提前拿到还穿不了的后段部位。这是掉落与穿戴之间允许存在的间隔，不能看到红色等级就认定生成出错。

[第四十三篇]({{LINK:GAME-43}})讲替换目标，本篇再补上穿戴资格。目标选对了，并不代表人物等级已经满足；展示候选、允许拾取、允许穿上，是三种不同能力。

### 动态生成，归一的是档位而不是玩家等级

六十级以后，动态装备以循环模板为基础，按来源等级找到所属档，再加部位偏移。工厂负责这件事，掉落入口不必到处复制一遍等级换算。

下面摘取当前动态档位入口的核心，最后一段还处理了等级上限：

```gdscript
static func dynamic_tier_start(level: int) -> int:
    if level <= Balance.SOFTCAP_LEVEL:
        return level
    var base := DYNAMIC_BASE_TIER + TIER_SPAN
    var tier := base + int(floor(float(level - base) / float(TIER_SPAN))) * TIER_SPAN
    return mini(tier, INSTANCE_LEVEL_CAP - (TIER_SPAN - 1))
```

读代码一定要连同用途看。这个函数在六十级以内原样返回，不能拿来给所有装备分套，否则六十级就会被错误地解释成第六十级开头的一档。

通用分套有另一个入口。名字接近，并不意味着函数能互相替换，尤其一段逻辑既有手工配置区间，又有动态生成区间的时候。

### 为什么不直接夹到人物当前等级

假设六十一级怪物掉出这档的项链，门槛是七十级。一个看起来体贴的修正是，把它压到玩家当前等级，让玩家马上能戴。

这样做却悄悄改变了规则。相同来源、相同部位的产物，会因拾取者等级不同而不同；合成档位和材料比较也需要再解释，掉落不再只由原来的生成条件决定。

正确与否应当先由产品选择，再落进工厂，不能由某一个界面看着不舒服就临时修数值。当前实现保留部位偏移，提前拿到的装备可以等待等级，也可以进入其他允许的物品流程。

更重要的是，别把来源等级、实例门槛和人物等级都写成一个叫level的含糊变量。读代码时多写清一个语义，往往能少掉一整轮“为什么这件装备不能穿”的排查。

### 少维护模板，不等于少维护规则

循环模板确实降低了高等级内容的重复配置量。以后加一段等级范围，不必手工复制十几套几乎相同的数据，也减少了漏填某个部位的机会。

可是规则成本并没有消失。基础属性怎样随等级变化、词条倍率从哪里读、品质快照如何保存、上限怎样收尾，都必须有共同口径。

[第四十一篇]({{LINK:GAME-41}})讲过快照，这里尤其不能每次显示时重新套最新版模板。已经生成的实例应保存自己的数值依据，否则一次内容调整就能把玩家背包里的旧装备全部改样。

动态模板解决的是生产方式，不是把持久物品变成随时重算的临时投影。两者分清以后，后续调平衡才知道哪些影响新掉落，哪些需要明确迁移。

### 历史装备不必为了整齐全部重造

改造之前，高等级区间曾按更细等级生成实例。规则变成十级一套以后，旧存档里自然会留下不完全符合新分布的装备。

当前落地选择保留这些合法历史实例，而不是读档时把等级强行归一，再重掷一遍词条。否则名义上只是整理模板，实际却修改了玩家已经获得的资产。

这里不能倒过来宣称所有历史数据永远无条件接受。合法字段、合理范围与必要迁移仍要检查；只是新产物遵循新工厂，并不自动推出旧产物必须长成同一个样子。

工程文档里的当时方案也要与现行代码对照。有些记录是在解释为什么改，有些是在列预计结果，不能把其中每一句预测都写成今天已经量过的结论。

### 换装节奏会变成一段段锯齿

十级一套以后，人物等级上升时，并不是每一级都能拿到同等幅度的新装备。刚换上某个部位时收益明显，接下来几级靠其他部位补齐，直到进入下一档。

这会形成阶段性的起伏。[第三十八篇]({{LINK:GAME-38}})讨论过装备差距与战斗节奏，我们不能因为模板减少，就直接声称击杀时间也保持不变。

需要沿真实成长路线检查：这一档刚开始能穿什么，接近末尾时缺什么，掉落与等级推进能否支撑正常过渡。白装基线、品质提升和玩家主动投入的星级，应当分别观察，避免用高配样本遮住基础路线的问题。

还有一个很容易漏的场景：玩家跨档时没有马上获得整套新装备。测试若每十级直接把全身替换成理想装备，看到的是整齐的表格，未必是背包真实能够凑出的路线。

### 边界例子，比再多一个正常等级更有用

复核时可以沿工厂入口与对应测试定位：

```sh
rg -n 'dynamic_tier_start|suit_start|dynamic_level_for|make_equip_exact' scripts/systems/item_factory.gd
python3 tools/run_isolated_tests.py DynamicEquipTest ArenaDropTest PaceTest
```

本文只校对命令与源码，没有执行这些游戏测试。实际验证应重点看六十到六十一级、七十到七十一级，以及最后的等级封顶区间，不要只测中间一个常见等级。

当前上限是九千九百九十九，尾档要容纳全部十个部位，因此档首会被限制到九千九百九十。末段不是机械照搬前面每逢一开档的样式，边界规则应有自己的断言。

测试数值时还要辨认精确生成入口。有些建模用例需要保留任意指定等级，而正常掉落要遵守归一规则，不能为了让旧测试通过，把正常生产入口又改回逐级生成。

另外，出售预设与合成材料分类也会用到所属套。它们应该调用通用分套入口，不要看到动态掉落已经归一，就各写一段近似算法。分类规则越多处重复，越容易在六十级这类交界位置分出两种答案。

### 小结

十级一套省下的是重复模板与过碎的内容单位，留下的是清晰的档位、部位偏移和阶段换装节奏。

真正落地时，要把生成等级与穿戴门槛分开，把新生产规则与历史实例保护分开，再沿边界检查战斗过渡。少写几份数据只是开始，让几个系统都说同一种等级语言，这次整理才算完成。
