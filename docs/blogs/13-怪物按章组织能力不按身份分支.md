# 末法纪元·游戏开发13：怪物可以按章分，招式为什么不能跟着名字写死

### 前言

各位看官，[上一篇]({{LINK:GAME-12}})聊地图拆目录。怪物配置也遇到了类似问题：内容扩充以后，所有章节挤在一张表里，查找和修改都不方便。

但怪物这里，还有一层更容易纠缠的关系。

同一种外观能不能给两只怪用？一只怪换了名字，招式还会不会生效？复用一套动画，会不会顺便把伤害和掉落也继承过去？

如果这些问题都用monsterId解决，短期看很直接，后面复制一个模板就可能露馅。

{{IMG:GAME-13-封面}}

### 章节归属解决的是维护位置

当前怪物模板按章节文件组织，索引登记加载顺序，DataLoader聚合后仍提供monsters逻辑表。地图、任务和存档继续按稳定怪物ID引用。

怪物属于哪一章，按设计归属决定。第一章的怪物被别的地图复用，不需要复制到另一个章节里，更不应该产生两个相同ID。

这一点和刷新等级也要分开。一只模板可以按地图规则生成不同等级的实例，实际等级变了，不代表它在目录里要跟着搬家。

分章让内容好维护，对外身份仍然保持稳定。

### 外观复用，先把表现和玩法拆开

项目用appearanceId引用外观档案。图集、动画方向、帧率、锚点和头顶UI位置，可以在这层组织。

怪物的生命、攻击、经验、掉落和行为规则，则保留在玩法侧。

这样两只怪可以共用一套外观，又有不同的战斗身份。换外观时，也不必把奖励规则复制一遍。

尤其“技能”这个词要说清。攻击动画是一段表现；伤害范围、冷却和异常状态是规则。把两者塞进同一个美术档案，想借用狼的动作，可能顺手借走另一只狼的伤害。

[第十篇]({{LINK:GAME-10}})讲模板、实例和显示分层，这里也是同样的拆法：复用某一层，不等于所有层都绑定。

{{IMG:GAME-13-身份表现能力}}

### 按名字写分支，复制模板最容易暴露问题

有些行为最初只服务一只怪，用ID判断很快就能写出来。

比如识别某个Boss以后才增加弹数，或者识别某个章节前缀以后才启用特定预警。原怪能打，测试也可能一直通过。

可策划复制模板，改个ID，原本想保留的能力突然没了。因为规则并没有真正写在模板里，代码认的是旧身份。

11月3日的整改就处理了第二章一批这样的能力：预警模式、狂暴倍率、召唤、冲锋横扫、弹数、支援治疗等，改由模板字段表达，并补上校验。

整改记录还通过新身份克隆走真实发射入口，检查能力是否仍然生效。这个验证比只看JSON字段存在更有说服力。

### 数据驱动，不等于让JSON随便编程

把能力写成配置，也要控制表达范围。

弹数可以是有范围的整数，治疗间隔可以是合法时间，召唤目标可以是经过校验的怪物引用。程序提供明确能力，数据选择参数。

如果为了“万能”而让配置执行任意脚本，问题就换成另一套语言和生命周期管理了。当前需求未必需要走到这一步。

同样，也不必给每只怪都单独建立一个能力文件。原来的分章方案先落具体怪物与外观两层，独立能力档案只在真实复用需要时再抽取。

这里要区分方案里的预留设计和已经落地的字段，不能画一张三层图，就宣布完整通用能力系统已经实现。

{{IMG:GAME-13-能力验证}}

### 复制一只怪，应该改哪些东西

假设要做一只与旧怪共用外观、但掉落不同的新怪，先创建新的稳定身份，再指向已有appearanceId。地图刷新和任务目标引用新身份，奖励按新模板的掉落表计算。外观资源没有理由因为名字变化而重新复制一套。

如果还要复用某个招式，就检查该招式真正由哪些字段决定。只拷贝显示名称和基础攻击，可能漏掉能力参数；只拷贝一个旧怪ID，又会把任务统计和奖励来源混在一起。

下面是只表达关系的教学示例，使用虚构ID并省略正式字段，不是可以直接放进项目的完整怪物配置：

```json
{
  "id": "example_wolf_elite",
  "name": "示例精英狼",
  "kind": "elite",
  "appearanceId": "example_shared_wolf",
  "dropTableId": "example_elite_drops"
}
```

它表达的是“新玩法身份、已有表现引用、独立奖励来源”。正式接入仍要补齐数值和能力校验。外观相同也不意味着精英可以在交互和危险反馈上完全不可辨认，名字、体型或专用变体需要按实际设计验证。

此外，怪物模板不能直接变成每只怪的可变运行状态。当前生命、冷却和仇恨目标属于实例。两只怪引用同一个模板，一只进入狂暴，另一只不能因为共享字典也被动改变状态。

这与装备实例的道理相通，但怪物多了持续计时和目标引用，释放时也要特别检查有没有残留行为。

### 改组织方式，行为先得守住

从ID分支迁移到字段，第一轮目标通常是保持现有行为。原来的秒数、距离、倍率、阵营范围和奖励，都应有对照。

否则一边重组代码，一边改技能强度，结果变了以后，很难判断是迁移错误还是数值调整。

外观复用也不能直接写成帧率提升。共享资源可能减少重复维护，但预载范围、驻留纹理和释放时机，仍然需要单独测量。

后续整改中，静态纹理按地图生命周期管理、配置重载时失效相关缓存，就是另一层工作，不能用“外观已经复用”一笔带过。

### 用真实入口，证明配置没有被代码身份盖住

验证能力复用，可以把模板放到隔离测试数据里，赋予一个全新ID，再经过正式生成和施放路径。测试要观察真实弹数、召唤目标或治疗对象，而不是只断言字典中存在某个字段。

如果新身份没有获得相同行为，就沿着调用链查哪里还保留旧ID分支。还可以改变一个合法参数，确认效果真的变化；再给一个非法参数，确认加载器拒绝。这三步分别检查复用、参数生效和守卫有效。

对应项目已有的检查入口，可以从下面几条开始。它们只是演示验证路径，本轮文章修订没有运行游戏测试：

```sh
python3 tools/check_monster_catalog.py
python3 tools/run_isolated_tests.py MonsterAbilitiesTest ChapterTwoCombatTest
python3 tools/run_isolated_tests.py MonsterAppearanceReuseTest
```

目录检查关注章节登记和说明一致性；能力测试关注行为；外观复用测试检查另一条资源链。不能拿其中一条通过，替三条链路作出完整结论。

迁移旧分支时，也要给每个参数注明口径。狂暴倍率是替换还是相乘，治疗范围包含谁，冷却按哪种时间推进，召唤物是否继承某些状态，都可能影响已有玩法。字段变成配置以后，这些约定更需要让后来填表的人看懂。

还有一点，配置越灵活，组合越多。第一轮可以只支持已经验证的能力组合，对尚未定义的组合明确拒绝或列为未覆盖，不必承诺所有字段随意排列都合理。

做到这些，数据驱动才算从“表里能写”进入“程序确实按表执行”。新增怪物的成本会下降，但基础规则的正确性仍然由统一入口与验证来守住。

检查结果还应写回该章说明，告诉维护者这只怪在什么地图出现、为什么使用这套能力、哪些组合已经验证。把设计原因留在配置旁边，后来改数值时就不容易误删一个看似多余的字段。特别是跨章复用，登记位置和出现位置不同，说明里交代清楚，才能避免再复制一份模板来“方便查找”。

### 小结

章节组织回答配置放哪里，怪物ID回答具体是谁，appearanceId回答怎样表现，能力字段回答会做什么。

把这些关系拆开，新增怪物才能更多依靠已有规则，而不用每次给名字补一条代码分支。

各位看官检查数据驱动有没有落地，可以做个小实验：复制一份合法模板，只换稳定身份，原本应该复用的行为还能不能通过真实入口跑出来？
