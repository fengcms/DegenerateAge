# 末法纪元·游戏开发80：测试说通过，为什么游戏还可能坏着

> 本文回顾《末法纪元》的开发过程，技术描述以 2026 年 11 月 5 日审阅快照为准。封面为主题插画，内文图为机制示意。

### 前言

各位看官，测试跑完，退出码零，控制台也没看见红字，能不能说游戏没问题？如果异步流程还没走到断言，运行器就到了帧数上限退出，这个零又代表什么？

《末法纪元》的开发过程中，既修过测试提前结束被当作通过，也处理过长期不在默认集的旧用例、负向注入和导出资源遗漏。

这一篇作为八十篇规划的收尾，不介绍一个包治百病的测试数量，而是讲怎样判断手里的绿色结果究竟覆盖了什么。能回答这个问题，回归才真正帮助交付。

### 进程结束，与测试完成不是同一件事

异步用例可能等待信号、等待物理帧或场景切换。某一步报脚本错误，后面的完成逻辑没执行，进程仍然可能等到外部上限退出。

因此当前运行器除了退出状态，还检查脚本异常、失败文本与对应场景的成功完成标记。上限负责防止挂死，不负责替测试签字。

完成标记也不能只搜索输出里有没有PASS。别的场景、启动文字或诊断信息都可能含有这个词，需要当前场景身份和约定的行尾形态匹配。

历史上某些用例成功文字后多了后缀，运行器正确判为未完成。修正输出契约，不等于放宽业务断言，也不能为了省事改成任何包含成功都算通过。

### 超时，是一项结果，不是一种成功退出

运行器遇到脚本异常会尽早结束该场景，超时则保留失败信息。这样不用等长上限空转，也不会把没有结论的用例混进通过数。

但终止本身不能抹掉原因。报告需要区分断言失败、编译错误、运行异常与超时，下一步处理完全不同。

如果只保留汇总零或一，开发者还得重新跑一轮才能知道发生了什么；如果只留最后几行，又可能丢掉真正最早的脚本错误。

测试工具也有输入和输出契约。它不是一个无须验证的外部裁判，发现误判以后同样需要专门用例和明确纠正记录。

### 默认集，是经常跑的子集

当前默认集覆盖常见功能，但不是tests目录全部场景。后来章节的路线、战斗与任务用例若长期不被触达，就可能在默认绿色背后慢慢过期。

全量扫描增加发现范围，也明确排除纯夹具与必须真实窗口的渲染场景。当前发现入口的节选如下：

```python
def discover_all_tests() -> list[str]:
    return sorted(path.stem for path in (ROOT / "tests").glob("*.tscn")
                  if path.stem not in FIXTURE_SCENES and path.stem not in RENDER_ONLY_SCENES)
```

这段依赖运行器已有的路径和集合，只用于说明扫描边界，不是独立可执行脚本。全量二字必须附带它的实际定义，不能让读者以为所有GPU和交互都已经做过。

### 跳过，也不能悄悄变成通过

历史美术欠账曾单列为SKIP，说明断言正确但素材或布局过时，需要修交付内容。后来收口使原跳过项重新通过，当前集合为空。

不能因为测试不好修，就把它搬进长期跳过表；也不能为了汇总好看，把跳过算成成功。报告应同时列通过、失败、跳过与排除范围。

当地图正式变化时，夹具可以改用当前入口与坐标，但要保留真实通行和碰撞检查。修改旧数据依据，与削弱断言是两件事。

第64篇《六章内容，怎样避免任务和地图脱节》讲过整链测试会模拟完成目标，这种前提也应公开。覆盖任务链，不代表自动证明每条地形路线都能实际走通。

### 负向注入，证明测试真的会抓住故障

正常代码通过，只说明没有触发当前断言。把关键保护在一次性快照里拿掉，测试应红在指定位置，才能增加对检查能力的信心。

当前负向工具要求变异锚点唯一，基线先通过，每次独立修改，再验证预期失败，最后还原复核。工作区源码不被改写。

如果去掉NaN保护，却红在另一个格式错误上，不能叫负向成功。错误原因必须与目标契约对应，否则只是证明程序总有一种方式会失败。

第76篇《重铸闪退，为什么第一轮解释错了》讲过因果反证，负向测试也是同样方法：改变一个关键因素，再确认结果沿预期路径变化。

### 隔离，不只是给临时文件换个名字

测试会重置角色、写槽位、构造坏档或加载诊断场景，必须与玩家目录分开。当前运行器随机项目身份与独立用户路径，探针还有额外启动守卫。

不能只在测试函数开头写不读正式档，后面却让Autoload自动续档和退出保存仍指向真实槽。保护需要覆盖进程启动到退出整条链。

使用只读来源副本时，还要验证原文件哈希不变。诊断入口拒绝正式身份，不应该在拒绝之前已经创建保存目录或写偏好。

第78篇《本地存档，怎样写坏了还能救回来》的恢复测试尤其需要这样做。为了证明能救坏档，先把玩家好档写坏，是完全不可接受的验证方式。

### 固定快照，避免测到一半代码换了

并行开发或美术导入时，测试开始读取一部分源码，随后另一些文件变化，可能得到一份从未真正存在过的混合版本。

当前支持已提交快照运行，日常隔离也会复制相关内容。素材复用或工作区外部变化仍需按具体工具说明，不能看到快照选项就默认所有依赖都自动冻结。

历史某个提交全量通过，也只能证明那个快照。后续又改网格持有或首步时钟，应补对应验证，不能继续沿用旧的总数宣称覆盖最终代码。

写交付记录时列出快照、后续改动与补验范围，读者才知道哪份结果对应哪一份实现，而不是只看到最近一次大数字。

### 无头通过，不替代窗口与真实鼠标

无头适合状态、规则与CPU路径，图像像素、输入命中和实际绘制则需要合适窗口场景。渲染专用用例应明确运行，而不是在无头里假红或被静默忽略。

第68篇《悬停数字，为什么不跟血条更新》的悬停用例直接创建提示节点，可以证明事件同步，却不代替原生鼠标等待与屏幕位置。

第71篇《2400件掉落，先优化绘制还是寻路》的固定压力夹具也省略部分玩法，窗口数据不能冒充完整挂机FPS。测试叫什么不是重点，真实装了哪些系统才决定结论范围。

人工检查同样需要具体路径。看过一张截图不能证明拖拽成功，点过一次按钮也不能证明取消、失效和重复点击都可靠。

### 源工程正常，不等于导出包完整

编辑器能找到的动态JSON、字体或纹理，导出时可能漏掉；开发样板、测试和源稿也可能意外混入运行包。

当前资源包工具检查配置与引用边界，历史收口还在没有源工程资源的空环境加载导出包，确认正式资源存在、开发样板被排除。

但Mac资源包检查，不等于Windows可执行文件已经实机运行。相同排除规则可以复用，平台窗口、输入与启动仍有自己的验收。

因此发布说明要按实际做过的事情写。包能读取、资源清单完整、目标平台可运行和长时稳定，是几层逐步扩展的证据。

### 测试数量，不能替代风险判断

两百项里有一百项都检查同一层，也不能补上缺失的存档恢复。反过来，一条针对真实故障的窗口边界用例，可能比几十条照抄实现的断言更有价值。

新需求先说明行为契约、失败后状态和最危险边界，再决定用哪类测试。不要为了数量给每次可逆文案调整都添一套镜像断言，也别因为有冒烟就省掉跨域交易检查。

性能修改还要保留同场景对照与行为正确性。速度更快但少了奖励、漏了碰撞或泄露迷雾，不能当作通过，只是换了一种产品。

### 把当前验证入口分开写清楚

后续可以按目的选择，本文没有执行这些命令：

```sh
python3 tools/run_isolated_tests.py --all --committed-tree
python3 tools/run_isolated_tests.py ReforgeLayoutStabilityTest GroundGeometryCacheTest --rendered
python3 tools/verify_115_negative.py
```

第一组有明确扫描排除，第二组需要真实绘制，第三组在一次性快照中验证指定保护。没有任何一条单独代表所有平台、所有时长都已安全。

整理这些开发记录，我也会按同一条规矩区分证据。读过源码，可以解释调用顺序；复算过一个例子，可以核对那个公式；真正运行过对应场景，才能记录那份测试结果。文章里写下一条命令，并不代表命令已经执行。各位看官复用这些方法时，也把版本、条件和结果留在一起，后来才能知道一份结论还能用在哪些地方。

### 小结

测试通过，是一份有前提的证据。完成标记、场景覆盖、隔离身份、负向验证与导出边界一起说明，绿色结果才有清楚含义。

这个系列从立项写到交付，最终仍然落回同一个问题：玩家看到的承诺，程序有没有可靠兑现。把需求、实现和验证连成一条可追溯的链，比一句已经全部完善，更值得留下来。
