# 末法纪元·游戏开发67：高分屏，不是把所有控件乘一个数

### 前言

各位看官，游戏在普通窗口里看着挺好，换到高分屏，人物小、按钮小、文字也小。最直接的办法，是整个画布放大两倍。

可窗口变大以后，地图视野却没增加；界面和文字都设一百五，字又变成两百二十五；背包终于合适了，导出存档的文件选择器却仍然小一圈。

《末法纪元》的显示适配，就是沿这些实际问题逐步拆开。本文不列一张通用分辨率表，而是讲清地图、界面与文字各自的倍率，以及独立窗口为什么需要自己的处理入口。

{{IMG:GAME-67-封面}}

### 先问放大窗口，玩家希望得到什么

本项目选择放大窗口增加地图视野与排版空间，人物不随窗口同比变大。想把人物看大，则单独调整地图显示倍率。

如果根画布按固定基准整体拉伸，窗口从小变大，所有东西一起长大，世界可见范围却没变。技术上渲染正常，产品目标却没有实现。

因此适配第一步是确定窗口、视口和世界显示之间的关系，而不是马上调按钮字号。不同产品可以作不同选择，但同一个项目不能让几个设置互相抵消。

历史实现还对无头测试保留了适当分支，避免没有真实窗口的显示驱动把视口缩成错误尺寸。测试环境的配置差异要说明，不能用无头截图推断真实高分屏观感。

### 三条倍率，分别服务三种需要

地图倍率作用在相机，改变人物、地形和可见世界大小；界面倍率作用在UI画布，改变按钮与面板；文字倍率表达希望最终看到的字形大小。

这三条轴不是把地图、界面、字体全部串起来相乘。它们分别拥有自己的载体，只有文字位于已经缩放的父层时，需要补偿那一层影响。

地图放大也不会改变碰撞、技能射程或拾取距离。世界规则仍用原坐标，改变的是投影与可见范围，不能为了人物看起来大了，就同时增加攻击距离。

[第四十篇]({{LINK:GAME-40}})讨论过地面几何，显示形状与实际判定需要同源。缩放系统也应沿既有空间关系处理，而不是给每种技能另写一份屏幕倍率。

### 界面放大，逻辑排版空间反而缩小

假设窗口尺寸不变，界面倍率从一变成二，同样一个设计单位占的显示空间更大，能够容纳的设计宽高就要除以二。

当前界面应用入口先计算逻辑尺寸，核心如下：

```gdscript
var logical_size := viewport_size / scale_value
```

前面还会检查视口与倍率有效。根控件按这个空间排版，四边锚点才仍然贴合当前可见区域，而不是继续按未缩放的大画布把按钮放到屏幕外。

这也是高倍率不只是放大的一层原因。宽屏能并排的两个窗口，在同一物理窗口高倍率下可能需要上下布局与滚动，内容关系要重新安排。

### 文字一百五，不应该偷偷变成两百二十五

早期UI画布已经放大一百五，字体又按一百五加字号，最终相乘，文字明显过大，固定高度的HUD开始重叠。

后来把文字设置定义成最终字形倍率。界面树里的字体只补目标文字倍率除以当前界面倍率，代码入口如下：

```gdscript
_text_scale_node(ui, text_scale_value() / ui_scale_value())
```

这样两项都设一百五，最终字形仍是一百五，而不是二百二十五。世界文字同样需要考虑地图倍率，不能直接照搬UI里的补偿关系。

原始字号也要作为稳定基准保存。每次设置变化都拿上一次覆盖后的字号继续乘，会产生累积膨胀，来回切换几次就再也回不到初始大小。

### 动态创建的控件，也要进入同一规则

有些面板在启动时就建好，有些列表和提示在打开或刷新时才出现。只在主场景初始化时应用一次倍率，会漏掉后来的内容。

因此新增控件要沿统一的样式与倍率入口接入，不能在业务面板里随手写一个未经补偿的字号。标题、说明、按钮和下拉内容都需要按实际结构检查。

但这不意味着每帧递归整个UI树。缩放与布局应在设置变化、窗口变化和内容创建等明确时机更新，避免为了保持样式一致引入持续全量工作。

[第六十六篇]({{LINK:GAME-66}})讲拖拽坐标，显示倍率接对以后，输入坐标也要沿相同变换转换，不能出现看起来放大了、命中区域却仍在旧位置。

### 文件选择器，为什么没有跟着UI一起长大

存档导入导出的FileDialog属于Window，有自己的视口内容，不走普通CanvasItem的画布变换。父UI放大以后，它仍按原来的像素尺寸打开。

因此只改背包或存档面板没有用，文件选择器本身需要设置内容倍率，并把设计尺寸换算成实际弹层尺寸。

当前应用会把内部子窗口一起处理：

```gdscript
for window in [dialog] + dialog.find_children("*", "Window", true, false):
    (window as Window).content_scale_mode = Window.CONTENT_SCALE_MODE_CANVAS_ITEMS
    (window as Window).content_scale_factor = scale_value
```

内部覆盖确认、收藏菜单等也有自己的窗口边界。只放大外框，下一步弹出来的小确认仍然偏小，用户感受到的适配依然没有完成。

{{IMG:GAME-67-独立弹层}}

### 放大弹层，还要保证确认按钮留在窗口里

设计尺寸乘倍率，得到理想弹层大小；窗口不够时，再按可用设计空间限制，而不是让它越出游戏区域。

当前尺寸规划先计算父视口除以倍率的空间，再与设计尺寸取小，最后换回像素。这样小窗口高倍率仍能容纳弹层，内容不足部分交给合适布局处理。

仅缩外框、不缩放内部内容，会让两边口径又分开。仅缩小字体让它装下，则忽略了玩家主动选择的大字需求，也不是等价修复。

历史记录中的某个窗口尺寸和实测结果，可以解释当时为什么修；发布时若要配真实图，还应按当前引擎、分辨率与设置补拍，不把概念图当作今天的运行证据。

### 系统密度，不能看到二就再乘一次

高分屏可能报告系统缩放系数，项目又有手动显示适配。如果不先了解已经在哪一层生效，很容易重复补偿。

本项目口径是系统与引擎已经完成的逻辑单位处理，不在游戏内再无条件乘一份屏幕密度。手动系数也只应用一次，避免界面、文字和弹层各自重复叠加。

尤其百分之一百时，各窗口比例已经正确，不能因为检测到Retina，就把文件选择器额外翻倍。设备信息是判断依据，不是看到一个数字就必须乘进去的命令。

跨屏、原生窗口与嵌入弹层还可能有不同路径。当前修正有明确覆盖范围，不能从文件选择器通过，推导所有第三方或运行时生成的窗口都已经自动适配。

### 文字可读，还要检查内容是否可达

字体变大以后，长说明换行、列表行高、滚动区域和按钮位置都会变化。检查只看标题够不够大，很容易漏掉下方确认已经出屏。

实际要覆盖窄窗口、高倍率、长文本与多个窗口并开。并排改上下以后，两个来源区域仍需可操作，拖拽目标也不能被滚动条或透明层盖住。

设置回退也很重要。从两百调回一百，窗口应按新的空间重新约束，不能保留只适合旧倍率的位置，或者把字号再次当成新基准。

清晰度与大小同样分开看。位图被放大不一定更清晰，字体渲染正常也不代表所有图标都达到同样质量，美术资源需要自己的验收。

### 验证组合关系，比逐个勾设置更重要

后续可以沿倍率入口与定向回归复核：

```sh
rg -n 'apply_text_scale_to|apply_ui_scale_to_window|dialog_popup_size' scripts/systems/settings_runtime.gd
python3 tools/run_isolated_tests.py SettingsTest PanelChromeCoverageTest SaveTransferTest
```

本文未执行游戏测试。逻辑检查验证尺寸换算、范围与设置恢复，真实窗口检查文字、布局、输入和子弹层，不能互相替代。

还应同时改地图、UI和文字，确认最终关系符合约定。每项单独正常，组合以后仍可能重复相乘；默认百分之一百也要保留回归，避免修高倍率时破坏普通使用。

### 小结

高分屏适配先要分清想放大什么，再决定在哪一层应用一次倍率。地图视野、UI排版、最终字形和独立窗口，各有自己的空间关系。

尺寸算对只是基础，文字可读、按钮可达、鼠标命中一致才是完整体验。把这些规则收在共同入口，后续新面板才能自然接进来，而不是每次再试一遍神秘的乘除法。
