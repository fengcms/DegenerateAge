# 末法纪元·游戏开发74：耐久只变一点，为什么整个背包都刷新

### 前言

各位看官，身上一把武器耐久少了一点，背包里两百件装备的图标、样式和提示，却跟着重新处理了一轮。人物窗口明明关着，生命变化还在替它刷新整页。

单步调试时，这些动作都能很快完成。高倍速持续战斗以后，同一显示帧收到多轮通知，原本不显眼的重复工作就会集中出现。

《末法纪元》后来拆了人物与背包的更新范围。这篇重点讲变化到底影响什么，以及为什么合并信号以后，还需要继续区分物品展示、比较角标与真实属性。

{{IMG:GAME-74-封面}}

### 一个击杀，可以带来多种通知

磨损改变穿戴装备，收尾还可能广播装备、背包、生命与法力等事件。它们服务不同消费者，并不意味着每个消费者都需要整页重建。

旧人物面板把多类事件接到同一个刷新入口，十四槽图标、属性、适配卡和布局都重新处理。隐藏窗口也没有省掉这些工作。

背包虽然已经按帧合并，但把完整穿戴字典放进比较上下文。只要耐久字段不同，就认为所有装备比较条件都变了。

因此先把通知频率与每次工作范围分开看。只有合并没有缩小范围，可能把十次昂贵刷新变成一次，仍然超过本帧预算。

### 生命变化，不需要重建装备图标

人物面板现在按生命法力、目标适配与装备变化分别记录需要更新的部分，再由统一调度按当前可见状态处理。

血蓝变化更新数值，目标变化更新适配卡，真正装备内容变化再检查槽位。多个标记同时出现时，完整更新可以覆盖更小范围，避免重复做一遍。

[第六十八篇]({{LINK:GAME-68}})讲悬停提示沿事件局部同步，这里也是同一思路：事件告诉我们哪项事实变了，不是要求整个窗口重新初始化。

显示模型可以有短期快照，但真实结算仍从原入口读取。不能为了省显示计算，在面板里维护另一套生命和装备属性，反过来供战斗使用。

### 隐藏窗口，记录失效而不是继续画

关着的人物窗口不需要每次生命变化都更新文字和样式，但再次打开必须读取最新状态，不能把节流变成显示旧值。

当前隐藏时保留脏标记，打开走必要刷新。背景品质框也根据真实可见性停止处理，不是仅看自己局部visible是否为真。

父窗口隐藏，子边框可能仍然保留可见属性，若只判断这个属性，动画还会一直跑。应该使用整棵树里是否可见的语义。

这项修改也说明关闭窗口后的测试很重要。界面不在画面上，不表示它没有CPU工作；测量隐藏状态能发现不少平常看不到的开销。

### 普通磨损与破损跨零，不是同一变化

耐久从八百到七百九十九，装备仍完好，评分依据没有因此改变；从一到零，则会影响词条生效，相关比较必须重新计算。

当前背包的穿戴比较快照把耐久归一成完好或破损状态：

```gdscript
var comparison: Dictionary = item.duplicate()
comparison["durability"] = 0 if Durability.is_broken(item) else 1
worn[sid] = comparison
```

这份副本只用于比较上下文，不修改真实装备耐久。也不能把其他词条、星级和身份一起忽略，因为它们仍然影响候选判断。

[第四十一篇]({{LINK:GAME-41}})解释过耐久只关闭特定贡献，不是把品质和星级清零。优化的快照表达也应遵守实际规则，不能用错误模型换更少失效。

### 比较变化，只刷新需要的角标

穿戴目标或等级变化，会影响背包候选是否更强，但物品图标和名称可能完全没变。当前把角标更新与整格展示更新分开。

下面是相同物品分支的实际节选：

```gdscript
if same_item:
    if comparison_changed and is_equipment:
        _refresh_upgrade_badge(b2, it2)
    continue
```

它保留了必要评分变化，跳过样式、图标和提示重复装配。不能把“不重建格子”误读成“永远不再计算比较”。

详细装备比较在悬停时按最新数据生成，也减少了为未查看装备提前构建整份说明的工作。但提交动作仍须实时验证，显示快照不授予永久操作资格。

### 同值对象，也要检查是否换了实际引用

背包可能被读档整体替换，新字典内容看起来相同，但按钮还持有旧对象。如果只比较值，就会留下过期拖拽来源。

当前相同格判断还核对按钮持有的实例引用，必要时重新绑定。独立快照则捕捉原地修改，避免引用跟着变化导致比较永远相等。

[第四十二篇]({{LINK:GAME-42}})的身份、位置与快照，在显示增量更新中仍然各有用途。只优化数值相等，可能把交互正确性悄悄丢掉。

因此测试不能只修改一份字典，也要覆盖容器整体替换、整理、扩容与同内容新引用。图标仍然相同，不代表内部绑定已经正确。

{{IMG:GAME-74-展示与比较}}

### 人物槽位也可以只更新耐久展示

当前人物面板比较槽位快照，确认只有耐久变化时，更新耐久条与相关提示，不重新创建装备装饰和品质样式。

真正跨破损边界后，人物属性仍需沿当前状态计算。槽位外观局部更新，与角色数值是否失效，是不同层次。

这项区分很容易被一个“装备变更”大函数吞掉。一个通知可以广播给多个消费者，每个消费者再按自己的输入选择最小必要工作，不必为每种字段都新增一条全局信号。

但若以后某个新字段影响外观或比较，快照逻辑必须同步检查。增量更新不是写完一次就永远正确，契约随数据结构扩展也会变化。

### 品质边框，不该被相同品质反复重启

旧路径刷新时会重复设置品质，使动画不断回到起点；时间还受游戏倍速影响，打开满包就有大量细小动态工作。

当前相同品质直接返回，边框按真实时钟选帧，仅实际帧号变化才更新图集区域，隐藏后停止处理。

这保持了动画风格与图标尺寸，不是为了性能把品质区分直接删掉。[第六十九篇]({{LINK:GAME-69}})也说明视觉时间可以与玩法时间分开，但要按具体用途决定。

边框仍然有渲染成本，减少脚本更新不等于把所有持续绘制都消掉。如果打开满包仍慢，需要继续测量，而不是因使用真实时钟就宣布零开销。

### 显示帧合并，与同步点击复核并不冲突

同一显示帧多个通知可以合并刷新，避免每个物理补步都重建面板。但用户点击确认时，不能等待尚未执行的显示任务来判断材料是否有效。

[第四十八篇]({{LINK:GAME-48}})讲过同步终验，结算必须读当前真实状态。界面可以晚一点画，资产变化不能按旧预览先执行。

合并器还需要保留执行期间新来的请求，下一帧补一次最终更新。否则把pending清掉的顺序不对，面板会偶尔停在中间状态，下一次无关事件才恢复。

这层调度后面的布局专题还会继续展开，此处先明确它负责降低重复显示工作，不负责放宽业务一致性。

### 同步耗时和窗口帧时间，分别解释

历史分析先量隐藏人物的事件处理、背包普通刷新与磨损刷新，发现局部同步耗时就已值得处理。随后用固定Boss与掉落夹具比较窗口结果。

夹具没有真实击杀，按固定频率调用磨损入口，采样也较短。它支持观察变化方向，不能冒充真实存档持续挂机FPS。

后续复核可沿当前更新入口与布局回归检查，本文没有执行：

```sh
rg -n 'comparison_changed|_slot_snapshots|_flush_refresh' scripts/ui/inventory_panel.gd scripts/ui/character_panel.gd
python3 tools/run_isolated_tests.py EquipmentLayoutRegressionTest InventoryUpgradeBadgeTest QualityFrameTest --rendered
```

还应覆盖耐久跨零、修理、升级、隐藏再开、拖拽和双击，确保省掉的只是不必要重建。

界面打开与关闭都应保留同条件对照。隐藏事件仍然执行重活时，单看窗口打开后的帧率，很容易漏掉这部分共同基线。

### 小结

耐久只变一点，却刷新整包，根源常常是把变化通知直接等同于全量显示失效。

分开血蓝、槽位、比较与装饰，按显示帧合并，隐藏时停更，真正影响评分的边界仍然重算。增量更新不是少做正确工作，而是让每次变化只带动它真正影响的部分。
