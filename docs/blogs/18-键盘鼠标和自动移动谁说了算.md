# 末法纪元·游戏开发18：键盘、鼠标和自动移动，到底谁说了算

### 前言

各位看官，角色只支持键盘移动时，事情很简单：读方向，算速度，撞墙以后停住。

加上点击地面行走、点击怪物攻击、大地图导航和自动战斗以后，就开始热闹了。玩家按着方向键，自动控制还想往怪物那边走；背包里拖一件装备，世界也收到同一次鼠标点击；面板打开了，原来的路线又突然没了。

这些问题看起来都是“角色不听话”，根子却可能在不同地方。想解决它，先要明确谁在表达意图，谁有权接管，以及接管时应该清掉哪些旧状态。

这一篇结合《末法纪元》的玩家和自动控制入口，聊输入之间怎么交接。

### 输入设备多，不等于移动执行器也要多

键盘和鼠标只是不同的意图来源。最终移动仍然要经过同一套速度、碰撞和状态约束，不能鼠标路线直接改位置，键盘却走物理移动。

否则按键能撞墙停住，点击却穿过去；被击倒时手动不能动，自动方向仍在推动角色。规则被不同入口绕过，越修越像打地鼠。

项目里玩家节点承接最终方向，自动控制提供auto_move，手动操作按当前状态优先处理。这里的重点不是变量名，而是执行边界集中：想怎么走可以来自多处，真正能不能走由统一规则决定。

[第九篇]({{LINK:GAME-09}})讲过服务与实体职责，输入层与执行层也应该沿着这个边界理解。

### 接管不是把两个方向加起来

玩家想向左躲技能，自动战斗还想向右靠近目标。如果简单相加，角色可能原地停下，玩家感觉按键失灵。

正确的交接需要明确优先级。手动意图成立时，自动方向不能继续和它争夺执行权；手动结束以后，是否恢复自动，则按玩法约定处理。

项目有专门的手动命令入口。它会清理旧自动移动，并通知自动控制进入接管状态。点击怪物与点击地图，也会走对应命令流程，而不只是设置一个目的地。

这意味着“接管”是一段有开始、维持和结束的行为。不能只在按键按下那一帧改一个标志，下一帧自动逻辑又把方向写回来。

### 从源码看方向选择的最后一层

下面是玩家处理中与自动方向回退有关的实际节选。它依赖前面已经完成的输入和状态检查，不是一个可独立粘贴的完整移动函数：

```gdscript
if not manual_input_active and auto_move != Vector2.ZERO:
    dir = auto_move
```

这两行说明一条边界：自动方向只能在没有手动输入接管时使用。它并没有说明所有手动行为都来自键盘，点击行走和持续手动攻击也要进入相应状态。

因此调试时，不能只看方向键是否按下。角色可能正在执行一次鼠标命令，按键已经松开，命令却还没有结束。自动控制如果只检测物理键盘，就会过早抢回角色。

反过来，路线被取消以后，手动活动标志也要清理，否则自动永远等不到恢复机会。状态的进入和退出要成对检查。

### 打开面板，不必取消已经开始的路

项目历史上出现过：角色正沿自动路线走，打开任意面板就停住，关掉以后也不恢复。问题不只是世界输入被屏蔽，而是路线本身已经被丢弃。

这里要拆开两件事：面板拦截新的世界操作，以及世界里已经开始的行为是否继续。普通背包窗口可以接管鼠标，角色原来的行走却未必需要取消。

如果把“有面板”统一解释为“清空所有行为”，玩家每查看一次任务，都得重新点一次目的地。对允许边挂机边整理的游戏，这会非常别扭。

但暂停、死亡和真正阻断世界操作的状态，又有自己的规则。不能修了普通面板，就顺手允许所有情境继续攻击和移动。

### 鼠标消费了，别让世界再用一遍

背包拖拽完成、按钮确认、地图上的点击导航，都可能来自鼠标左键。它们的目标不同，需要清楚的事件接收边界。

玩家把装备放进出售托盘时，如果同一次点击又被世界识别为移动，角色就可能离开NPC；点击技能快捷栏，也不应该顺便把技能图标下面的地面设为目的地。

检查这类问题，可以记录输入经过哪个控件、是否已被处理、世界层还有没有继续解释。给角色移动加一个固定延迟，通常只是让重叠事件晚一点发生，并没有解决归属。

键盘也类似。文本输入框正在编辑数量时，数字键首先是输入内容，不应该同时触发技能。输入焦点和游戏动作，需要在接收位置明确区分。

### 一次取消，要留下什么状态

假设角色点击怪物后正在接近，玩家按方向键转身。接管时要停止旧的接近路线，清掉对应自动方向，按规则处理锁定目标和持续攻击意图。

如果只改方向，旧路线下一帧可能恢复；如果只删目标，导航器仍可能保留前一段方向；如果攻击意图还在，松开方向键又会突然冲回去。

这类问题适合做连续测试，而不是一条输入单独试一次。先点目标，再按键，再松开，再开关自动，观察每个阶段实际执行的意图。

切图和读档也是强中断。旧地图的目标和路线不能被新场景继承，即使屏幕上恰好又出现一只同名怪，也不是同一个节点。

### 恢复自动，需要一个可解释的条件

手动结束后立刻恢复，可能让玩家躲完技能又被拉回危险处；永远不恢复，又让自动开关的含义不清楚。

项目通过接管状态和恢复等待来处理，但具体等待按哪种时间推进、哪些行为会延长，都应读当前实现和规则。不能拿早期某次文档中的固定秒数，概括所有版本。

界面最好让玩家知道自动是否仍开启、当前是否处于手动接管。两个开关看起来相同，实际可能一个已关闭，一个只是暂时让出执行权。

说明清楚以后，玩家更容易判断“我需要重新打开自动”还是“等当前命令结束即可”，也方便排查程序有没有误清状态。

### 用交接矩阵，而不是只测三个按钮

验收可以按来源与中断交叉设计：自动接近时按键，自动攻击时点击地面，点击行走时打开背包，拖拽物品时点击世界，死亡后松开按键，再切图回来。

每个场景都检查当前方向、目标、路线和自动状态。单看角色动没动不够，有时它暂时站住了，旧指令仍藏在状态里。

仓库已有自动控制和洞穴实际移动用例，可作为入口。本轮只核对代码与记录，未执行以下游戏测试：

```sh
python3 tools/run_isolated_tests.py AutoControlAcceptance CaveAutoBattleTest
```

这些用例仍不能覆盖所有窗口焦点和拖拽操作，实际UI交接还需要窗口验收。

### 日志也要记录意图的切换

排查时最好少打印每帧方向，多记录状态改变：谁发起命令，旧命令为何取消，接管结束后恢复了什么。每帧刷一屏向量，很容易把真正发生变化的那一刻淹没。

如果输入来自UI，还应记录是否被控件消费；来自自动控制，则说明当前选择的是接近、攻击还是巡游。这样看到角色停住时，可以先判断是合理拒绝、没有目标，还是执行层真的没有响应。

日志也要限频，不把一次手动接管变成持续文件写入。最小记录能还原交接顺序，就足以帮助我们复核，不需要为了调试让正常移动本身变卡。

### 小结

多种输入共存，靠的是明确的意图优先级、统一执行入口和成对的状态清理。

面板接管输入、暂停世界、取消路线和关闭自动，是不同动作。各位看官遇到角色“不听话”时，把这几件事分别记录，往往比继续叠一个全局禁止开关更容易找准问题。
