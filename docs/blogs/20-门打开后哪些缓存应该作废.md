# 末法纪元·游戏开发20：一扇门打开以后，哪些缓存应该作废

### 前言

各位看官，静态地图里的路线已经能走通，加上一扇动态门，事情就没那么简单了。

门关着时找不到路，角色记住了“不可达”。任务完成以后门打开，碰撞也撤掉了，可自动战斗还是不肯过去。或者反过来，门已经关上，旧路线还在往门后推。

这时候再算一次AStar，可能暂时恢复。但如果没有弄清哪些结果依赖门的状态，后面还会在巡游、地图底图和候选筛选里遇到同样问题。

《末法纪元》用导航修订号协调这些缓存。这一篇聊它解决的关系，而不是只介绍一个计数器。

### 门改变的是通行事实

一扇逻辑门通常不只是一张图片。它可能同时影响可走格、导航网格和实际碰撞。画面打开但通行仍关着，玩家看见的是一条假路；只让导航通过而碰撞还在，又会顶在原地。

所以门状态应由明确入口更新，再让各个表现跟随。不能任务系统直接改某个碰撞节点，地图服务又单独维护另一份开门布尔值。

项目的布局入口会修改门禁格集合与AStar状态，同时递增导航版本。哪些系统依赖通行性，就根据这个版本决定旧结果是否还成立。

[第十九篇]({{LINK:GAME-19}})讲同源布局，动态门把“同源”从一次加载延伸到了运行中的变化。

### 版本号表达“条件变了”

下面是门禁更新中的实际核心节选，省略了门位置解析和逐格更新：

```gdscript
if open == _access_gate_cells.is_empty():
    return
navigation_revision += 1
_access_gate_cells.clear()
```

重复设置相同状态直接返回，真正改变通行条件才递增版本。这样可以避免每一帧重复应用任务状态，让所有缓存跟着无意义重建。

版本号本身不负责算路线，也不需要知道每个消费者是谁。它只说明：你上次根据旧条件得到的结果，现在需要重新判断。

计数器和布局对象身份要一起看。同一个版本数字出现在两张不同地图上，并不意味着缓存可以通用。

### 连通区域，也是一份会过期的结果

门关闭时，左右两侧可能被分成不同区域；打开以后，它们变成同一片。之前缓存的区域编号必须更新，否则即使AStar已经开放，候选筛选仍会把门后的目标拒绝。

CaveLayout用组件修订号判断是否重建连通标记。当前导航版本没变，可以复用；不同了，再按当前可走格重新计算。

这类缓存很容易被忽略，因为它看起来只是几个整数。可自动找怪和拾取先经过可达性过滤，错误的区域编号会让完整寻路根本没有机会执行。

因此“门开了但角色不走”，不能只在导航器里追AStar。先看目标有没有被上游筛掉，排查顺序才完整。

### 路线缓存要知道自己依赖哪一版布局

CaveNavigator记录布局对象和导航版本。它们不匹配时先清理旧路线，再继续按目标构建。

```gdscript
if ground.cave != _layout or ground.cave.navigation_revision != _revision:
    clear()
    _layout = ground.cave
    _revision = ground.cave.navigation_revision
```

这是源码节选，依赖函数前面的空对象检查。它表达的重点，是不能只检查目标格有没有变。

目标在同一格，门状态却变了，路线仍然需要更新；反过来，目标只在格内轻微移动，也不一定要重算整条路，末端修正可以按原有边界处理。

缓存条件写清楚以后，才能避免两个极端：每步重算，或者永远复用。

### 巡游路线和当前追击路线，不是同一份东西

自动控制还缓存了巡游候选和规划结果。门打开可能增加新的区域，旧巡游列表即使没有穿墙，也可能永远覆盖不到新地方。

所以巡游的地图身份、导航修订和当前连通区域都需要参与判断。真正需要重建时，旧游标如何处理也要明确，不能沿用已经越界的索引。

这里要区分“需要重建”和“立刻一次做完”。大地图规划如果成本较高，可以按已有预算逐步准备，但不能在准备过程中让角色使用一半旧、一半新的不一致状态。

后面的巡游专题会讲进度恢复，本篇先把失效条件说清楚。

### 地图显示也可能停在旧世界

门状态会影响地图底图与可走边界显示。如果底图只在首次打开时生成，运行中改门禁，玩家就可能看到仍被堵住的道路。

但更新底图不等于重新揭示整片地图。导航条件变化、探索记录变化和动态标记变化是不同输入，要按各自规则刷新。

玩家已经探索过门口，开门以后显示应当正确；门后没去过的地形，不能因为缓存重建而全部亮起来。性能优化和探索规则不能互相替代。

这也解释了为什么验收要把地图显示与路线放在一起。实体走对了，地图还停在旧状态，玩家照样会误判道路。

### 空结果，也得记住是在哪些条件下算出来的

一个角色被关在小区域里，合法巡游点可能就是空列表。如果程序每次看到空数组都当作“没初始化”，它会不断重算同一个失败结果。

于是需要区分未构建和已经构建但为空。后者仍然可以缓存，只是在门状态、位置所属区域或布局变化时失效。

这对不可达路线也适用。失败不是永远不再尝试，也不是每帧无条件重试，而是等待相关条件变化以后再试。

门打开这个例子很好地说明了缓存的完整含义：保存结果，还保存让结果成立的条件。

### 开门和关门，两边都要测

可以在隔离场景里固定起终点，先关门确认不可达，再开门确认区域和路线更新，最后关回去，检查旧路不会继续使用。

同时让角色站在两侧不同位置，观察巡游重建和方向清理。不要只测试最顺利的一次从门外走进去。

还要试重复设置。门已经打开，再调用同样状态，不应反复增长版本；真正切换一次，依赖缓存才更新。

项目已有连通、导航和地图缓存用例，下面是检查入口，本轮文章没有执行它们：

```sh
python3 tools/run_isolated_tests.py CaveConnectivityTest CaveNavigationTest MapCanvasCacheTest
```

### 不要让缓存主动猜业务剧情

缓存消费者只需要知道布局和版本，不必自己判断“玩家交了哪一段任务，所以大概门已打开”。剧情状态怎样转换成门禁，应该由明确业务入口负责。

这样以后门来自机关、任务或读档恢复，底层仍然沿同一套通行更新。否则每加一种开门方式，就要给路线、巡游和地图各补一条特殊判断。

读档也不能直接恢复一份包含旧节点引用的缓存。先恢复必要状态，生成当前布局，再由消费者准备自己的运行结果，更容易保证数据和场景一致。

### 失效的成本，也应该能解释

导航版本变化以后，多个消费者可能在同一帧发现自己过期。每个都从头扫描一遍全图，正确性恢复了，瞬时成本却可能集中爆发。

因此可以把共享连通标记由布局层准备一次，其他查询只读同一结果；巡游的额外规划再按自己的工作预算推进。失效通知负责说明条件改变，不要求每个系统重复完成同一份基础工作。

测量时要把首次重建和稳定查询分开。开门那一帧稍有成本，与每帧持续重复重建，是不同问题；只测稳定状态，也看不到前者是否超过预算。

如果以后增加更多动态障碍，再根据变化频率判断是否需要局部更新。当前只有有限门禁时，不必为了“将来可能很多”立即改成复杂增量图算法，先把已有共享计算与生命周期做清楚。

### 小结

门状态变了，需要更新的不只是AStar，还包括连通区域、路线、巡游与地图显示等依赖结果。

版本号让这些依赖有了可检查的失效条件。各位看官设计缓存时，可以先列一张“什么变化会让结果不再成立”的清单，再决定在哪里计算和保存。
