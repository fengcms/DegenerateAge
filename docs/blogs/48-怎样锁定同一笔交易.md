# 末法纪元·游戏开发48：点了确认还得重来，怎样锁定同一笔交易

### 前言

各位看官，材料都选好了，点击一次确认，面板提示这次会消耗什么。后台正好捡到几枚金币，再点一下，按钮却重新开始确认。

材料没丢，钱还变多了，玩家为什么反而不能继续？高频战斗里，两次点击之间总有事件，原本为防误操作设计的保护，最后成了让人不断重复的障碍。

[第四十七篇]({{LINK:GAME-47}})解决的是耐久变化误清材料。本篇继续往前走一步：哪些变化应该取消确认，哪些变化应该放行，以及怎样保证放行以后，消耗的仍是玩家第一次看过的那笔东西。

{{IMG:GAME-48-封面}}

### 一个布尔值，不足以表达玩家确认了什么

很多面板一开始只需要一个“已经确认”的状态。第一次点击设为真，第二次提交；库存变化时设回假，看起来谨慎又简单。

问题是，库存变化包含太多事情。药品叠加、金币增长、材料被卖掉、材料被收藏，都可能发出通知，但对这笔交易的意义完全不同。

直接删除重置同样不行。如果界面每次刷新都会重新挑材料，或者自动把不足的附加材料清空，确认状态虽然保住了，实际条款却已经换了。

所以要先回答：玩家刚才确认的到底是什么？材料身份、内容、费用、附加投入与产物去向，都应该变成能够比较的具体数据，而不是只记住他点过一次按钮。

### 保星锁定的是交易条款

当前保星第一次确认会保存两件材料的内容，排除允许变化的耐久，同时记录来源位置、四格如意选择、费用、产物等级和穿戴条件。

下面是当前条款返回结构的节选，前面已经准备好材料与位置：

```gdscript
return {"materials": materials, "locations": locations, "runes": _rune_choices.duplicate(),
    "cost": int(plan.cost), "level": int(plan.outputLevel),
    "wearable": EquipmentFusion.transfer_locked_level(int(plan.outputLevel), int(GameState.player.get("level", 1))) == 0}
```

这里没有把背包下标和当前金币余额一股脑锁进去。下标会整理，余额会随战斗涨落，它们不一定改变玩家准备购买的结果。

位置也不是完全忽略。旧料原来穿在身上还是放在背包，影响是否自动回原槽；同为穿戴，还要知道是哪一侧。来源含义变化了，就应重新展示结果。

### 无关变化放行，不是忽略最新状态

捡到药水、增加金币、同级经验增长、背包整理，只要这笔材料和条款仍成立，就不必让玩家重新确认。

材料仍然要按实例ID从当前容器定位，耐久仍然同步到最新完整快照，费用和库存也仍然检查。放行的是不改变意图的事件，不是准许使用过期数据。

[第四十二篇]({{LINK:GAME-42}})的稳定身份在这里派上用场。确认锁定的是两件具体装备，不是原来第三格和第七格，也不是“任意两件符合条件的紫装”。

同样，金币余额增加不影响约定费用；余额不足则不允许提交。判断标准不是这个事件重要不重要，而是它有没有改变交易内容，或者让履约条件不再满足。

{{IMG:GAME-48-条款与状态}}

### 如意不足，不能悄悄替玩家减配

早期下拉框刷新会根据库存，把已经不足的选项自动清空。放在普通预览里也许只是更新选择，放在确认之后，就可能把四枚如意变成两枚。

如果这时只保留确认布尔值，玩家批准的是四枚投入，最终执行的却是另一组抽样机会。这不是少扣一点材料那么简单，结果预期已经改变。

当前做法是保留已经选择的种类与数量，库存不足时显示缺项并禁用提交，不能自动降低本单投入。后来库存补足，还可以按原来的条款继续。

金币暂时不足也类似。足额与否是一条实时履约条件，约定费用没有变，就不必为了余额波动重新发明一笔交易。当然，实际扣钱前仍要同步复核，不能只相信按钮之前是亮的。

### 等级变化，要看是否跨过穿戴门槛

人物升级本身未必改变保星条款。如果产物原来就能穿，升一级以后仍然能穿，没有必要重新确认。

但若刚好跨过产物门槛，原来的“产物入包，旧槽暂空”变成“产物自动穿回”，最终结果发生了变化。当前会重新比较穿戴条件，让玩家看见新的说明。

[第四十六篇]({{LINK:GAME-46}})讲过原槽落点，这就是它对确认设计的影响。不能只锁材料与费用，却把同样重要的自动穿戴结果留在锁外。

这也是为什么同级经验增长不必监听成重新确认。需要锁定的是结果条件，不是所有可能间接影响结果的原始数值。

### 紫装献祭，还要防止新掉落混进本批

相似的问题也出现在紫装献祭。旧实现每次点击都重新选择低档优先的前二十件，新捡到一件低档紫装，就可能挤走原本预览里的某一件。

如果只移除库存变化重置，第二次点击就会消耗未被本次确认展示的装备。安全目标不能因为想减少点击而丢掉。

当前第一次点击固定本批实例ID、资格相关内容和预计经验。新掉落留给下一批，已经确认的数量不自动补齐，也不偷偷替换。

第二次从最新背包定位原批次，任一件离开、被收藏或相关字段改变，就整批拒绝。经验变化或无关拾取可以通过，因为它们并没有改变这批准备投入的装备。

{{IMG:GAME-48-固定批次}}

### 异步刷新可以等，点击检查不能等

连续战斗会发出成串通知。如果每来一次都重建控件、重算预览，后台战斗越密，面板本身越容易变成负担。

当前复用按显示帧合并的调度器，同一帧的后台刷新合成一次。锁定献祭批次后，也不必因无关新掉落不断重排整个候选列表。

不过点击按钮时，不能等尚未执行的刷新队列告诉自己结果。输入入口会同步重校验、更新必要预览，再进入既有同步结算，期间没有插入异步等待。

把显示工作推迟一点，与把关键判定推迟一点，性质不同。前者可以省重复工作，后者会留下“屏幕还没更新，所以先按旧条件扣了”的漏洞。

### 快照只活在这次面板会话里

这份确认记录不需要写进存档。关闭窗口、更换服务、手动改料或结算结束，都应清掉；下一次进入重新展示交易内容。

调度器也要跟随宿主生命周期。窗口关闭后，排队回调不能再悄悄更新已退出的界面，更不能持有材料快照不放。

规模同样明确：保星两件材料与四格如意，献祭最多二十件。提交献祭时一次扫描背包建立当前索引，再验证本批，不要每件材料各自全包扫描。

这些约束不需要夸张成一个通用交易平台。先把当前功能的数量、生命周期和失败边界讲清楚，就已经能避免大量隐蔽问题。

### 验证重点是两次点击之间发生了什么

后续复核可以沿条款比较与实际窗口用例检查：

```sh
rg -n '_transfer_terms|_locked_sacrifice|expected_terms' scripts/ui/equipment_fusion_panel.gd autoload/game_state.gd
python3 tools/run_isolated_tests.py EquipmentFusionUiTest EquipmentLayoutRegressionTest --rendered
```

本文没有执行游戏测试。既有工程记录通过窗口注入磨损、拾取、排序与金币通知，验证第二次点击只消耗原确认材料；也覆盖不足后补足、原料移位和等级跨门槛。

还应检查连点与结算后回填。完成以后，旧确认必须失效，新掉落不会继承上一次批准。若某件批内装备变了，整笔拒绝时库存、金币与经验应保持完整，不能先扣一半再弹错误。

这些证据说明定向业务行为得到覆盖，不代表已经测量高倍速实战帧率，也不代表所有场景的点击次数都有统计。文章应该把测试结论限制在真实记录支持的范围。

确认文案也应跟着固定批次显示，让玩家始终看得见本单范围；数据锁住了而提示仍追着实时列表跑，同样会制造误解。

### 小结

稳定确认的关键，是保存玩家批准的具体内容，再用最新状态验证能否按原条款执行。

无关变化不打断，相关变化不偷换，库存不足不减配，最终提交仍严格检查。这样两次确认才既保留保护作用，也不会变成后台战斗永远打断的按钮游戏。
