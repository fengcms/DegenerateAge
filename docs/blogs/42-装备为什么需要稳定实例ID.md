# 末法纪元·游戏开发42：背包整理以后，程序怎么认出原来那件装备

### 前言

各位看官，背包第八格有一把剑，玩家点一下，把它选成合成材料。随后自动拾取进来几件东西，玩家又整理了一次背包。

第二次点击确认，还应该消耗第八格吗？

显然不应该。格子表示当前摆放位置，玩家确认的却是某一件具体装备。位置变了，身份可以不变；身份相同，内容又可能已经被强化或收藏。

这一篇专门沿《末法纪元》的实例ID、材料重定位和快照检查，讲清“还是不是那件东西”与“还是不是刚才确认的条件”。

{{IMG:GAME-42-封面}}

### 型号相同，不代表可以互相替代

两把同名剑可以有不同品质、词条、星级和耐久。任务或掉落都引用模板ID，它回答是哪一种装备；instanceId回答具体是哪一件。

如果用模板ID当唯一身份，玩家有两件同型号材料时就分不清，出售、收藏和重铸都可能操作错对象。

名字和图标更不能代替身份。名称会本地化，图标可以复用，甚至完全相同的属性也可能属于两个独立实例。

[第十篇]({{LINK:GAME-10}})讲过数据分层，本篇重点是身份怎样穿过容器与交互，而不是再复制一份模板。

### 背包下标只能当一次读取位置

拖拽开始时记录下标很方便，但一旦操作跨过其他库存变化，提交前就应重新验证。

尤其持续战斗中，拾取、自动出售、合成和整理都可能改变数组内容。一个下标仍然合法，里面装的东西却已不同，边界检查不会替我们发现。

因此材料选择应保留稳定身份，确认时从当前允许容器重新找到它。查到的位置只是本次提交用的结果，不是永远不变的地址。

这并不要求每帧全包扫描。打开、改选或提交时按需要定位，结合事件与限额，能把工作放在明确时机。

### 穿戴槽也是位置，不是身份

戒指左槽和右槽都有明确位置，但玩家可以换装。一个重铸面板记住左槽以后，不能无条件把后来换进去的戒指当成原目标。

当前共用选择入口会同时核对槽位与实例ID，下面是实际节选：

```gdscript
var candidate: Variant = equipment.get(choice.key)
if candidate is Dictionary and String(candidate.get("instanceId", "")) == String(choice.id):
    return candidate
return {}
```

它依赖前面的索引和选择记录检查。找不到原实例时返回空，让上层明确拒绝或要求重新选择，而不是自动挑一件同类型物品补上。

{{IMG:GAME-42-身份与位置}}

### 找到了同一ID，还要确认内容没有换

玩家选材以后，原装备可能被升星、重铸、收藏或改变等级。它仍然是同一件，但已经不是当时那份材料状态。

GameState的合成入口会按身份重定位，并核对当前内容与提交快照。下面摘取这一层检查：

```gdscript
var found := find_owned_item(id)
if found.is_empty() or found.item != snapshot:
    return {"ok": false, "reason": Localization.tr_key("ui.review.game_state.011")}
```

这里的完整相等是一条严格结算边界。UI若允许某些无关变化，需要先按规则更新快照，再提交最新完整状态，而不是把结算检查直接删掉。

身份检查防选错物，内容检查防条件偷换，两层分别有用。

### 相同身份移动，规则也要看允许来源

装备从背包穿到身上，还是同一实例；但某种合成只允许背包材料，就不能因为ID找得到便一律接受。

源容器和拥有关系属于业务资格。仓库、穿戴、出售托盘等场景，各自要说明能不能参与，不应由一个“全局找得到”决定。

同样，玩家把装备暂存到托盘后，它需要有明确所有者，不能背包和托盘都保留可消费引用。

[第八篇]({{LINK:GAME-08}})的托盘漏存案例也说明，身份可靠之外，还需要容器交接与持久保护共同成立。

### 重复ID必须当异常，而不是自动去重消耗

四件材料如果同一个ID出现两次，不能把它当作两件装备。否则校验按四件通过，扣除时只找到三件，产物和成本就不一致。

提交会先检查空身份和重复身份，明确拒绝。批量计划也要按全体实例唯一性检查，不能每组单独合法、组与组之间重复用料。

如果读档出现重复ID，还要按存档策略处理，不能运行中随手改一个新ID，掩盖数据来源问题。

去重适用于某些用户输入，例如锁定属性列表；材料数量则有真实价值，不能靠悄悄去重凑出一个看起来成功的结果。

{{IMG:GAME-42-重定位与快照}}

### 新产物是否保留旧身份，要由规则定义

移动、穿戴、修理通常修改同一实例状态；把多件材料合成一件新装备，则涉及旧实例退出和新实例生成。

不能只因为产物保留了旧星级，就默认必须保留旧ID。身份语义要跟实际工厂与交易结果一致，不在UI里自行沿用。

验证时应记录输入与输出的身份关系，以及原材料是否确实离开容器。看到同名装备仍在，不等于旧材料没有被消耗。

后面的保星升级会详细讲保留什么、重掷什么。本篇先要求程序把物品流转说清楚，不把“保留投入”误解成所有字段原封不动。

### 快照也别持有一份会跟着变的引用

如果所谓选择快照直接引用背包中的字典，外部改了星级，它也跟着变，比较时就看不出任何差异。

需要冻结条件的地方，应按结构建立独立副本或不可变条款，再明确哪些字段允许刷新。深复制不是所有地方都要做，但该冻结的内容不能只是换个变量名。

[第四十一篇]({{LINK:GAME-41}})的属性快照是生成语义，这里的交易快照是玩家同意的条件。两者都叫快照，生命周期与用途不同。

关闭会话或完成交易以后，也应释放临时选择，别把过期目标带到下一次打开面板。

### 连续操作，比静态断言更容易暴露问题

可以选一件装备，整理背包后提交，确认消耗的仍是原ID；再替换原格子的物品，确认系统没有认错。

随后让选中装备被收藏、重铸、移出允许容器，验证请求拒绝且状态不变。最后提交一份重复材料，确保不能通过。

穿戴目标则测试同槽换装和左右槽交换。只比较槽名称，抓不到实例已经换人的情况。

这类测试的重点是操作间插入变化，不能每次选完立刻提交，永远避开问题窗口。

### 保存再读取，身份也应该能对上

物品进度恢复，需要保留合法实例身份和相关属性，不能读取时把所有装备重新生成随机ID。

否则收藏、已穿戴关系和待恢复状态可能无法对应。存档校验要检查结构与唯一性，而运行态节点引用不进入持久数据。

测试可以把同模板两件物品放在不同位置，保存、读取、交换，再核对身份与属性。只检查“仍然有两把剑”太弱。

本轮文章没有读取真实玩家档，也没有执行游戏测试，示例只说明复核路径。

### 使用已有入口检查完整链路

项目有装备、交易和重铸会话用例，命令如下：

```sh
python3 tools/run_isolated_tests.py EquipmentAxesTest EquipmentFusionTransactionTest ReforgeSessionTest
```

这些入口覆盖各自约束，不意味着运行过一个用例就证明所有容器安全。新增仓库或随身入口时，还要检查它们是否沿同一身份和快照规则接入。

错误提示也需要准确。原物品消失、条件变化和来源不允许，是不同原因；统一说“操作失败”，玩家就不知道该重新选还是补材料。

查找成本也要有边界。当前背包规模有限，关键提交时扫描一次可以解释；如果每个材料、每个显示帧都重复全量定位，批量操作仍会放大工作。

后续可以在一次提交里建立身份到位置的临时索引，所有材料复用，再在提交结束后释放。它与跨帧长期缓存不同，不需要为每次整理维护另一份永久事实。先明确调用次数，再决定是否需要索引，避免为了一个小容器提前增加同步负担。

### 小结

实例ID让程序认出具体物品，下标与槽位说明它现在在哪里，快照则确认它是否仍符合当时条件。

把这三层分开，整理、穿戴和持续战斗就不必天然打断所有操作，也不会以“位置还在”为由消费另一件东西。
