# 末法纪元·游戏开发06：和AI一起做游戏，需求为什么要写成契约

### 前言

各位看官，前几篇讲完目标、范围和阶段，这一篇聊AI协作。

《末法纪元》的工程里，除了程序和配置，还有不少产品文档、实施方案、交接记录和审阅报告。它们有个很实际的用途：让下一次改动接得上前面的决定。

AI可以帮忙写代码，但它拿到一句“帮我把自动出售做了”，仍然要自行理解很多东西：在哪里接，什么物品可以卖，哪些情况要保护，改完怎么判断没出事。

这些选择一旦猜错，代码可能照样跑，玩家拿到的行为却偏了。

所以这一篇想聊的是：怎样把任务说到可以检查，而不只是听起来明白。

### 一句功能描述里，藏着多少没说的决定

拿自动出售举例。

从玩家视角看，功能很直白：捡到不需要的装备，按规则卖掉，减少清包操作。

从实现视角看，至少有三件事需要定：什么时候判，按什么规则判，以及卖完怎样结算。

要是把判定直接接进通用的“添加物品”接口，购买和任务发奖也会经过这里。结果就可能变成刚买的装备、刚领的奖励，转眼被自动卖了。

当前项目规则因此明确：拾取自动出售只接在拾取入口，与出售清单共用判定策略。

这里真正重要的，是“拾取”和“获得物品”的语义区别。只给功能名称，不能保证实现自然落在正确位置。

### 契约写的是行为，不必全是接口定义

这里说的契约，可以很朴素：这次做什么，守住哪些规则，什么情况下失败，以及交付什么证据。

下面是按项目现有约束整理的任务说明示例，不是当时对话的逐字记录：

```text
目标：拾取装备时，按现有出售策略处理可出售项。
入口：只接拾取流程，不影响购买和任务奖励。
规则：复用现有判定，不再单写一套评分比较。
结算：金币用实际入账值，不能把挂牌价当到账额。
验证：分别检查拾取、购买、领奖和金币封顶场景。
```

比起“做得完善一点”，这些信息更容易落到代码，也更容易判断有没有做偏。

至于具体辅助函数怎么拆，可以留给实现阶段决定。没必要提前把每一行代码都写成需求。

### 有些规则，要跨越一轮对话继续生效

游戏开发会不断切换任务。今天修寻路，明天改装备，后天又接着处理背包刷新。

如果关键约束只存在于某一次聊天里，新的工作很容易看不见它。

项目把共用约定集中在根目录规则文件里。像地图配置与README同步、奖励结算唯一入口、性能测量口径、隔离存档，都属于后续任务会反复碰到的内容。

不过，规则文件也不能无限堆积。

共用规则适合放入口；具体玩法回产品文档；某次改动的实现与验证留在工程记录。入口里说明去哪里找，比把所有历史材料都复制进去更容易维护。

[第四篇]({{LINK:GAME-04}})讲目录职责，这里其实是同一个思路：信息也需要有明确的归属。

### 交给AI的上下文，要包含当前状态

还有一种常见的误差，是任务目标没错，起点认错了。

比如文档里有一项技能配置，不代表游戏已经能施放；旧方案说某种掉落会立即入包，也不能不看后来持久掉落的实现，直接照旧方案继续改。

因此，开工之前要读相关代码、数据、测试和最新交接，分清哪些是当前规则，哪些是历史记录。

交接也不能只写“已经完成”。最好说清完成了哪条流程、提交在哪里、验证覆盖什么、还剩什么限制。

这也是[上一篇]({{LINK:GAME-05}})强调阶段出口的原因。明确的起点和终点，能让协作少一些反复猜测。

### 让AI给证据，自己也要看证据的范围

“测试通过”四个字，还得继续问一句：通过了什么？

只跑了公式测试，不能证明实际战斗没有卡顿。无头测试通过，也不能证明高分屏上的按钮看得见、点得到。

性能尤其容易被一个好看的数字带偏。单模板掉落的稳态结果，和多个Boss持续战斗，是不同场景。把前者写成整个游戏稳定流畅，结论就越界了。

所以交付时，除了结果，还需要场景、版本、方法和限制。失败也要留得住，不能把断言放宽以后再报全绿。

这些要求同样适用于人写的改动。AI让产出速度变快，也让检查依据的重要性更明显了。

{{IMG:GAME-06-验证闭环}}

### 规则会更新，别把今天的经验倒写进第一天

回顾项目时，还有件事需要克制。

今天的规则入口已经很具体，包含许多性能、存档和交易约束。它们随着开发逐步积累，不能因为现在写在同一个文件里，就说立项时已经全想明白了。

有些限制来自真实故障，有些来自后续内容扩展。文章里该说明当时的状态，协作时也该允许规则在证据支持下更新。

契约能让变化清楚可查。它不需要假装项目永远没有新问题。

### 小结

和AI一起开发，功能名称只是任务的开头。

把行为边界、复用入口、失败处理和验收证据说清楚，再让实现去填细节，成果才更容易审阅和继续维护。

这篇没有讨论谁写了多少代码，也没有把仓库文档当成某次提示词的原文。更值得带走的，是一份任务怎么从“好像听懂了”变成“可以确认做对了”。
