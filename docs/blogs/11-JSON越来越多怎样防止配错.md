# 末法纪元·游戏开发11：JSON越写越多，怎样把配置错误拦在进游戏之前

### 前言

各位看官，做数据驱动的时候，最容易让人高兴的一件事，是改几个配置就能加内容。

不用再写一套怪物代码，填个模板，换张地图，新的敌人就出现了。可表越来越多，另一个问题也来了：填错怎么办？

JSON解析成功，只能证明括号、引号和逗号没把语法搞坏。掉落表引用了不存在的装备，概率写到合法范围外，出口连到一个不存在的地图，解析器可不会替我们判断。

《末法纪元》把不少检查放在DataLoader里。这一篇就聊从“读进来了”到“能放心使用”，中间还差什么。

### 第一层，字段自己先讲得通

最基本的是类型、必填项和范围。

数量应该是正整数，冷却要有明确时间单位，概率不能无限大。配置里写的是数字，也不代表就符合业务要求。

尤其JSON里的数字进入程序后，整数和浮点的表现需要留意。某个字段要求整数，校验应该检查值确实有限、没有小数、落在合法范围里，而不是只看它碰巧属于哪个运行时数值类型。

项目在能力配置整改中就处理过这类校验细节。把合法数值误拒绝，和放过非法数值一样，会影响内容接入。

错误信息也要能找到对象。只报“配置错误”，还得再扫整张表；报出表、ID、字段和原因，修起来就直接多了。

### 第二层，各张表之间要接得上

一只怪物引用掉落表，掉落表再引用装备或物品。地图会引用怪物、出口目标和布局。任务还会引用目标、奖励与解锁状态。

这些关系拼起来，已经是一张网。

ID唯一只是开始，还要检查每一条引用是否存在，引用的类型是否正确。有一个同名ID，不代表它就是这条规则需要的对象。

DataLoader针对装备、掉落、地图交通、技能、任务等分别有验证入口。按领域拆开检查，也比较容易说明一项约束属于哪条玩法。

[第十篇]({{LINK:GAME-10}})说模板与实例分开，配置验证主要守模板和规则入口；读档里的具体实例，还需要自己的结构与兼容验证，不能把两者混为一谈。

### 第三层，字段分别合法，组合仍可能不合理

再往下，就不是单字段能解决的事了。

道路出口存在，目标地图也存在，但目标入口落点不可用，照样走不过去。技能冷却、消耗都合法，但自动策略绕过了冷却，也不能靠配置检查兜住。

这时要分清静态关系和运行行为。

能从配置直接判断的约束，尽量在加载时检查；需要实体、碰撞和状态变化才能判断的，就交给对应场景测试。

不要为了让加载校验看起来万能，把整个游戏流程塞进启动阶段。它会增加成本，也让问题来源更难分辨。

### 掉落概率，尤其要把语义写清楚

项目约定里有一条很具体：掉落条目里的itemIds是等概率选择。不等概率要拆独立条目，通过chance表达。

为什么要明确到这个程度？因为“列表里重复放几个同样ID”看起来也能做权重，但维护者可能把它当重复数据去重。配置仍然能读，掉率却已经变了。

数据驱动真正依赖的是双方理解同一套语义。字段名叫chance，也要说清它作用在哪一层，不能默认每个人都会猜到。

类似的还有闪避点数和概率、破甲的保留比例与削减比例。值都可能写成数字，但方向搞反，结果差得很远。

### 别让默认值替正式错误遮羞

可选字段有默认值，很正常。兼容旧数据时，也可能需要补缺省。

但正式配置写错ID，如果静默退回某只默认怪物，场景还能跑，错误就会藏起来。等到掉落和任务统计不对，才发现地图从一开始生成的就不是想要的东西。

所以要区分“没填可选项”和“填了非法值”。前者按约定处理，后者明确拒绝或报告。

### 两行都叫数字，业务含义可能完全不同

假设某个能力允许发射一到五枚投射物。配置里写二是合法的，写二点五就不应该被截断成二，写一个极大值也不能照单全收。这里需要的是有限、整值、有界三个条件。

下面是一段独立的Python教学示例，用来说明约束，不是从Godot加载器搬出来的正式实现。它还特意排除了布尔值，因为在Python里布尔值会参与整数类型判断。

```python
def valid_projectile_count(value):
    """只接受一到五之间的有限整数值，不把布尔值当数量。"""
    import math
    return (
        type(value) in (int, float)
        and 1 <= value <= 5
        and math.isfinite(value)
        and value == math.floor(value)
    )

assert valid_projectile_count(2)
assert valid_projectile_count(2.0)
assert not valid_projectile_count(2.5)
assert not valid_projectile_count(True)
assert not valid_projectile_count(float("inf"))
assert not valid_projectile_count(float("nan"))
assert not valid_projectile_count(10 ** 1000)
assert not valid_projectile_count("2")
```

示例里的一到五是为了讲约束而设定的范围，不是宣称游戏所有能力都只能用这个弹数。正式范围要回到对应字段的设计。

校验也有顺序。这段Python先确认类型，再用业务范围短路拦下过大数值，最后检查有限性与整值。Python整数可以任意大，直接把超大整数交给math.isfinite，可能在转换为浮点数时抛出异常；校验器就没有按约定返回失败。这个顺序是本示例针对运行时特点的处理，不是要求所有语言都照搬。错误信息最好分别告诉维护者是哪一层失败，否则他可能把一个字段改成字符串来绕过报错，制造新的问题。

同样，概率和冷却即使都使用小数，也不能共用一个没有语义的“数字合法”检查就结束。概率的上界、时间单位以及是否允许零，都是具体玩法决定的。

### 校验也要能被证明有效

一张正确配置通过测试，说明正常路径能走，不代表守卫真的有用。

还可以在隔离环境里故意制造重复ID、断引用、越界数值，确认检查会拒绝，并指出正确的位置。这种负向验证，能防止校验函数存在却没有实际接到加载流程。

配置重载以后，依赖它的缓存也要知道版本变了。DataLoader维护revision，相关缓存可以据此失效。否则新配置读进来了，运行中却继续用旧计算结果，玩家看到的仍然不对。

这一轮文章只核对代码和已有记录，没有重新执行所有非法配置用例。正式验证时，要按改动涉及的领域选择对应测试。

### 错误配置的验证，要能安全地还原

负向测试可以从一份已知合法的配置开始，每次只改一个条件：删掉目标掉落表，制造重复ID，或者把数量改为小数。这样被拒绝以后，才能确认命中的是预期约束，而不是前面另一个错误碰巧挡住了加载。

不要直接在玩家日常使用的工程里反复破坏正式配置。把需要的数据复制到隔离目录，固定测试快照，验证结束后丢弃副本，更容易保证现场干净。

还要注意检查器返回的结果。某个脚本在屏幕上打印“发现错误”，最后却退出零，自动流程可能仍然把它当成功。相反，只有一个非零退出码而没有对象位置，也会让人很难修。人看的说明和程序看的状态都得有。

项目里有地图、怪物目录的只读检查入口，适合在对应内容变更后先做一层维护校验：

```sh
python3 tools/check_map_catalog.py
python3 tools/check_monster_catalog.py
```

这两条命令关注索引、目录和说明一致性等内容，不等于执行了全部战斗、掉落和任务验证。它们通过以后，仍然要根据变化选择场景测试。

配置重载还值得单独检查一次。改一个能力参数，再触发明确的重载入口，观察加载版本是否变化，相关缓存是否失效，旧对象是保留原快照还是采用新规则。这里不一定只有一种正确答案，但必须有一致的约定。

如果正式运行中不允许热重载，也可以限制这个能力只供开发和测试使用。关键是别让一个仅用于调试的入口，无意间成为玩家流程里的高频文件读取和全表重建。

从这个角度看，校验不是启动时多打一行“通过”，而是一套让错误尽早定位、让正确数据进入运行层的边界。内容越多，这条边界越值得认真维护。

### 小结

JSON能解析，只是数据进入工程的第一关。

字段约束、跨表引用、组合关系和运行行为，需要各自合适的检查。把语义讲清楚，再让校验真正拒绝错误，数据驱动才能在内容扩张时继续省事。
