# 末法纪元·游戏开发45：升星与套装，怎样互相放大

### 前言

各位看官，一把剑升到十二星，玩家当然希望它更厉害。如果全身都养到十二星，再给一份成套奖励，看起来也很自然。

可是，两份奖励究竟怎么叠？给每件装备先加一遍，汇总以后再加一遍行不行？攻击速度跟攻击力，都乘同一个系数行不行？

装备系统到了这里，问题已经不是多写几个百分号。本文沿《末法纪元》的升星与套装实现，拆开单件成长、全身门槛和最终属性缩放，看看数值怎样上涨，边界又该守在哪里。

### 单件星级，先作用在这件装备上

[第四十一篇]({{LINK:GAME-41}})讲过，品质与星级不是同一条轴。品质参与基础属性倍率，星级则按实例保存的系数，放大基础部分以及词条贡献。

当前升星系数配置是一星增加一成，十二星对应二点二倍。注意这是整体系数，不是把十二次升级逐次连乘成一个指数。

词条仍然是原来的词条，升星增加它的贡献，不会因为星星多了，就凭空多出几个新属性。这条边界很重要，否则升星与重铸、第五词条的职责会混在一起。

单件计算最后应有一个权威入口。人物属性、装备卡片与评分若各写一份简化公式，短期都能显示数字，长期却会在耐久、百分比属性和新词条上逐渐分叉。

### 升星概率，下标表示当前星级

当前最高十二星，成功率表的下标表示现在有几星，不是准备升到几星。因此下标零是零升一，下标十一才是十一升十二。

费用也按当前星级计算，下面是实际规则入口的节选：

```gdscript
static func cost(star: int) -> int:
    var params: Dictionary = config().get("costParams", {})
    return int(round(float(params.get("UP_BASE", 0)) * pow(float(params.get("UP_R", 1)), star)))
```

当前基础费用五百，递增系数一点五。这里列数字是解释配置含义，实际文章发布前仍应对照最新配置，不能把它写成永不调整的承诺。

失败保持原星级，但消耗这次规定的费用。加成功率的材料也有单独规划与校验，不应该先扣一枚再发现另外几枚不够。概率与扣费是同一次操作的组成部分，需要一起让玩家看明白。

### 套装奖励，看的不是星级总和

全身一件十二星、其余零星，不等于大家平均接近一星，也不满足全身六星的奖励。

当前套装规则遍历十四个标准槽，先检查是否穿满，再取最低品质和最低星级。最弱的一件决定能跨过哪一级门槛，这会鼓励玩家补齐短板，而不是只把资源堆给武器。

标准槽清单在这里也有实际用途。如果遍历存档里碰巧存在的键，一个多出来的脏字段可能被误算成装备，真正空着的标准槽反而漏掉。规则应该问十四个位置各有什么，不是问这个字典一共有多少东西。

### 品质档和星级档，分别判定再相加

当前品质奖励从白装零开始，逐档上升；星级奖励则在全身六星、八星、十星、十二星时跨档。两个条件各算各的，再把百分比相加。

例如全紫且全十二星，品质奖励两成，星级奖励两成，合起来四成。这个地方不是先乘一点二，再乘一点二得到四成四。

实际返回值直接表达了这种关系：

```gdscript
"pct": quality_pct + star_pct,
```

也不要把白装品质奖励为零，误读成白装永远不能获得任何套装收益。品质轴与星级轴独立，是否存在星级收益，还要看全身星级是否达标。

这种独立判定能让规则说得清楚，但也意味着改任何一轴，都要看看另一个条件叠上去以后有没有越过预期。只测单件或只测全零星，很容易漏掉真正的峰值组合。

### 单件涨幅与成套涨幅，不在同一层

星级先进入各件装备的贡献，套装百分比再由人物属性入口应用到应缩放的数值。这两层有先后，但品质奖励与星级奖励本身先相加，不能把“层”与“来源”混为一谈。

用一个只解释计算顺序的算例：某个应缩放的属性在套装处理前是一百，成套总奖励四成，处理后就是一百四十。不要在每件装备上提前加四成，汇总时又加四成。

同样，界面展示套装百分比时，只能展示这一层带来的加成，不能把已经包含在单件里的星级涨幅再算作套装奖励。否则玩家读到的“额外增加”会和最终面板对不上。

各层都有输入和输出，调试时沿边界打印少量数据，比对着最终面板猜是哪一个乘数多算了，更容易定位问题。

### 攻击间隔越小越好，不能跟攻击力一起乘

攻击力乘一点四，代表数值提高；攻击间隔乘一点四，却代表每次出手等得更久。这是给奖励写成了惩罚。

因此当前规则把正向属性和反向属性分开。攻击间隔使用除法，核心代码是：

```gdscript
static func inverse_scale(value: float, pct: float) -> float:
    var factor := 1.0 + maxf(-0.99, pct)
    return value / factor
```

如果原来一秒一次，四成奖励后间隔约为零点七一四秒。也别直接写成乘零点六，那会对应更大的频率增长，和其他属性的四成口径不一致。

暴击、闪避等属性还涉及自己的上限或结算约束。成套入口负责提供缩放，属性查询与战斗规则负责守住各自边界，不能为了统一计算，就假设所有字段都能无限增长。

### 套装提示要告诉玩家还差什么

只有一个“未激活”标签，玩家并不知道该补一件装备，还是把十几件装备一起升星。

当前规则结果除了总百分比，也给出缺槽数、下一品质档与所需件数、下一星级档与所需件数。界面可以据此说明短板，不必自己再遍历全身，另写一份近似判定。

达到顶档以后，下一档应明确为空或结束状态，不能拿一个默认零值继续显示“距离下一档还差零件”。这类小字如果不可靠，玩家很快就会不再看整个面板。

另外，耐久耗尽影响的是单件词条是否生效，装备仍然穿在那个槽里。不能为了表现损坏，把它临时算成空槽，导致另一套完全无关的成套资格也跟着消失。

### 先保住基线，再检查最高组合

检查这套规则时，我更关心几条边界：十四槽与十三槽、最低一件刚好跨档、品质够但星级不足、星级够但品质低，以及全身顶档。

还要单独保留普通路线的基线。没有星级投入的白装，不该因为加入套装系统，突然获得一份之前没有的额外收益。[第三十九篇]({{LINK:GAME-39}})讲过换装缓冲，基础路线若被悄悄抬高，原来的节奏判断就不成立了。

复核入口可以从这里找：

```sh
python3 tools/run_isolated_tests.py SetBonusTest EquipmentAxesTest
rg -n 'set_bonus_pct|inverse_scale|star_factor' autoload/game_state.gd scripts/systems
```

本文没有执行游戏测试，也没有测量新战斗速度。命令用于后续验证规则与调用关系，真实平衡仍需结合成长路线，而不是看到几个断言通过，就宣布全阶段已经稳定。

### 最后一件装备，可能值得优先投入

最低门槛会改变资源分配的直觉。十三件都到八星，只剩一件七星时，把这件补到八星，除了单件增益，还可能让全身跨过新的星级档。继续强化已经很高的武器，则未必带来同样的组合收益。

但这不是说任何时候都要机械追求最低项。升星费用、成功率、近期是否准备换装，都影响实际选择。程序应把条件和收益展示清楚，把决定留给玩家，而不是偷偷替玩家消费资源去补短板。

开发时也不能只比较升级前后那一件的评分，便断言整个人物提升了多少。是否触发套装需要读取全身状态，同一件装备在不同搭配里，边际收益可能不同。这正是单件评分适合做提示，却不适合包办最终判断的原因。

### 小结

单件升星给持续投入，套装门槛给补齐目标。两者互相作用，但计算层次和判定职责要分清。

把最低门槛、独立相加、正反向缩放和普通路线基线放在同一张检查表上，才能既让玩家感到成长，也让开发者解释得清每一份收益从哪里来。
