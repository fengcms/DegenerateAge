# 末法纪元·游戏开发41：装备等级、品质和星级，为什么要分三条轴

### 前言

各位看官，前面几卷已经出现了不少装备名词。这一卷开始，咱们把装备成长和交易流程认真拆一遍。

第一件事，是弄清等级、品质和星级各自负责什么。它们都能让装备变强，但如果所有差异都藏在模板里，玩家看到一个紫色名字，程序却不知道到底强在等级、稀有度还是强化投入。

《末法纪元》做过三轴改造，后来又继续调整档位、套装和重铸。这里按当前结算入口解释职责，同时保留历史变更的边界。

### 等级先确定成长阶段和穿戴门槛

装备等级既与生成基础有关，也约束能否穿戴。显示五十级，实际按一级基底生成，或者门槛仍读另一个模板值，都会让这条轴失去意义。

当前实例明确保留需求等级，显示、穿戴和相关规则沿统一入口读取。它不是怪物等级的直接别名，也不是角色每升级一次就自动重算旧装备。

[第十篇]({{LINK:GAME-10}})讲过生成快照。装备生成以后有自己的属性来源，等级提高需要明确操作，而不是读档时按玩家等级悄悄补齐。

### 品质表达同阶段的稀有价值

同一型号可以产生不同品质，品质影响基底倍率和合法词条等规则。这样普通武器和高品质武器可以共享型号，而不是每种颜色都复制一个专属强度模板。

如果紫装模板本来就手填了一份很高基底，再乘紫装倍率，就可能把同一层收益算两次。迁移时必须核对旧数据来源，不能只给每件装备新增一个quality字段。

品质也不保证所有组合都更强。高等级低品质和低等级满星高品质相比，要进入具体结算，不能只比较颜色。

### 星级记录对这一件物品的投入

升星作用在具体实例上，保留原始基底和词条，通过星级因子计算当前属性。不是每升一星就把存档里全部数值改大一次。

后者一旦重复调用或读档重算，很容易发生复利式增长，还难以还原原始属性。当前把未强化结果留在实例，能清楚解释“原来是什么、现在乘了什么”。

星级上限、费用、概率和失败处理属于强化规则，不能靠属性计算函数自己猜。结算入口只回答在这件物品当前状态下，实际属性是多少。

{{IMG:GAME-41-三轴职责}}

### 三条轴独立，不代表彼此没有组合

等级决定阶段基底，品质提供相应倍率和词条资格，星级放大该件物品的基础与已有词条。最后组合成实际属性。

但组合顺序有含义。当前基础属性同时乘品质与星级因子，原始词条乘星级；不能再把词条也无差别乘一次品质，改变原规则。

下面是EquipmentMath里的实际基础计算节选，省略输入结构检查：

```gdscript
var factor := float(item.get("qualityMultiplierSnapshot", 1.0)) * star_factor(item)
for stat in raw:
    result[String(stat)] = float(raw[stat]) * factor
```

它使用实例倍率快照，不是打开背包就读取一份新平衡表重新解释所有旧装备。

### 用一个小算例看清每层收益

假设某件物品原始攻击十，品质倍率一点五，星级因子一点二，另有原始攻击词条三。按本篇说明的结构，基础得到十八，词条得到三点六，合计二十一点六。

这是教学算例，不是正式生成器中某个型号的实际产物。它的用途是核对品质有没有重复乘、星级有没有漏乘词条。

面板如果拆成原始、品质增量和升星增量，几项应能还原同一最终结果。展示层读取分项，不再自己实现另一份公式。

[第二十九篇]({{LINK:GAME-29}})讲输入到伤害的链路，这里还只是装备属性，不能把它直接当成攻击最后扣掉的生命。

### 名字、颜色和等级，不要互相伪装

早期有专名装备或不同档位命名，后续简化以后，显示规则继续变化。但稳定型号与实例身份不能跟着展示文本随意重建。

玩家需要看到真实穿戴要求、品质和星级，而不是名字里写“高级”，实际仍属于旧档。详情也应区分基础属性和随机结果，减少误解。

图标可以复用，数值却不能靠图标暗示。反过来，美术暂未补齐，也不应该让程序把几种品质都当成同一条结算路径。

三轴清楚以后，表现能围绕规则解释，而不是反过来靠颜色和名字勉强维持差异。

### 耐久又是一层状态，别改写原始三轴

当前破损规则会影响词条实际生效，但保留基础属性。它不把品质降成白色，也不把星级直接清零。

因此展示完整潜力和读取当前实际属性，需要区分用途。评分与战斗汇总应使用统一的实际生效口径，不能一边按完好算，一边按破损算。

修复耐久以后恢复原有词条，不需要重新抽样，也不该得到一个新实例ID。状态变化与生成结果是不同层。

这说明三轴模型不是把所有装备信息压成三个数字，而是先把核心成长职责拆清，再让其他状态有明确作用位置。

### 套装属于角色组合，不写进每件装备

穿满一套满足品质与星级条件以后，角色可能获得额外收益。它依赖当前穿戴集合，脱下一件就可能变化。

如果把套装倍率预先写进每件装备快照，物品离开套装仍可能错误保留；再由角色汇总乘一次，又形成重复放大。

所以单件属性与全套派生分开计算。具体套装后面专篇展开，这里先明确它不是第四份藏在实例里的永久倍率。

同样，职业系数也需要放在正确最终入口，[第三十四篇]({{LINK:GAME-34}})已经讨论过它可能影响其他派生的问题。

### 历史三轴改造，不是无损迁移承诺

这次模型早期落地经历过明确授权的破坏性实例升级，后来整档最低版本也有自己的读取边界。不能把某次新字段迁移经验推广成所有旧装备都能兼容。

文章介绍当前计算结构，历史档位则已经被后续十级一套等规则调整。不要把原方案里的旧等级表当成现行目录。

复盘时应说明阶段：当时为什么改，哪些数据不再支持，今天又从哪里读取。这样读者不会用旧字段拼出一份看着合理、实际无法加载的实例。

兼容策略需要产品决定和工程落实，不能只靠提交标题里写一个破坏性标记。

### 生成来源统一，三轴才能一直一致

掉落、任务和商店如果各自复制模板、各自抽词条，同一个品质很容易在不同来源下产生不同结构。

共用ItemFactory构造实例，来源只负责选择型号、档位和品质等输入，再经过合法校验。这样新增来源时不必再发明一套星级乘法。

但统一入口不代表可以省略来源规则。任务是否固定奖励，商店是否允许某种品质，仍由业务定义，不能全部当成随机掉落。

生成、穿戴、强化和读取都遵守同一实例契约，才算三轴真正落地，而不是仅在UI增加三个标签。

### 验证用矩阵，不要只挑一件毕业装

可以固定型号，分别改变等级、品质和星级，确认每条轴只改变约定内容。再检查同名不同实例不会互相污染。

边界包括零星、满星、非法品质、需求等级不符、破损与修复，以及展示分项和实际汇总一致。

已有装备轴和动态装备测试可作为入口，本轮未运行游戏测试：

```sh
python3 tools/run_isolated_tests.py EquipmentAxesTest DynamicEquipTest SetBonusTest
```

矩阵结果还要接回正常成长场景，不能用极端满配通过就宣布所有低等级体验已经平衡。

### 小结

等级回答处在哪个成长阶段，品质表达同阶段的稀有价值，星级保留对具体物品的投入。三者通过统一结算组合，其他状态与角色派生再按明确边界接入。

各位看官设计装备时，可以先画一张属性来源表。每个值只写一个来源，再问它何时变化、是否需要快照，很多重复倍率就能提前暴露。
