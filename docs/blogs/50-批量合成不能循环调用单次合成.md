# 末法纪元·游戏开发50：批量合成，不能循环调用单次合成

### 前言

各位看官，单次四金合紫已经写好了，批量合成是不是循环调用十次就行？从复用代码的角度看，这个主意相当诱人。

可是，前六次成功，第七次发现材料变了，界面最后应该说成功还是失败？玩家原本确认的是整批，结果只做了一半，已经发出的通知和生成的装备又怎样撤回？

[第四十九篇]({{LINK:GAME-49}})讲清了材料分组。本篇继续讲执行过程：准备可以分多次，真实库存的修改仍然应该在最终检查通过后一次完成。

{{IMG:GAME-50-封面}}

### 单次函数正确，不代表循环以后仍然正确

单次合成可以在自己的范围里先验证、再扣料、再通知。循环调用时，每次完成都会真实改变背包，下一次看到的已经是另一份状态。

这不仅影响失败恢复，还可能把前一次产物重新纳入后续候选，或者让库存通知触发自动整理与其他面板逻辑。原本很短的业务边界被拆成许多个可观察的中间状态。

即使提前算好全部组，也无法靠一个异常捕获恢复所有副作用。背包可以复制回去，已经触发的提示、统计或外部观察未必能一起倒带。

因此批量复用应优先复用纯规则、产物工厂和校验入口，而不是机械复用那个已经会扣料、广播的单次完整动作。复用层次选错，少写几行反而增加更多补救代码。

### 把准备工作和真实提交分开

当前批量流程分成会话建立、规划、准备产物、最终复核和提交。前面这些阶段可以失败或取消，但都不应提前扣真实材料。

开始时保存本次候选与会话编号，规划器给出固定分组；准备任务根据组别生成临时产物，最后再检查真实背包里的原材料是否仍然成立。

“已经生成五件”在这里表示五件候选结果准备好了，不代表玩家已经获得五件装备，也不代表二十件金装已经被消耗。

进度提示应该与这个语义一致。如果把准备进度写成领取进度，玩家关闭窗口后发现没有装备，会以为系统吞了奖励。内部阶段叫什么，最终要能转成诚实的用户反馈。

### 分帧准备，限定的是每次工作量

背包若有四百件可用材料，最多形成一百组。一次把所有随机产物都生成完，可能把工作集中在一帧，因此当前任务按批推进。

实际任务的核心入口如下，省略后面的产物生成与验证：

```gdscript
func advance(limit: int = 8) -> void:
    var kinds := Equipment.slot_kinds()
    var stop := mini(groups.size(), outputs.size() + limit)
    while outputs.size() < stop and not failed:
        var group: Array = groups[outputs.size()]
```

默认一次最多准备八组，只写任务持有的临时数组。这个八是数量上限，不是保证每帧耗时固定，也不能直接换算成某个帧率收益。

分帧期间战斗与拾取仍可继续，所以最终还必须复核。如果觉得已经准备完大部分就能跳过检查，相当于把等待期间发生的真实变化全部忽略了。

### 随机任务也需要自己的上下文

当前会话保存种子，准备任务使用自己的随机数生成器，并记录已经存在的实例身份，避免临时产物之间或与已有物品撞ID。

[第三十篇]({{LINK:GAME-30}})讲过随机复现。这里把随机状态收在任务内部，至少能避免每推进一小段都依赖全局随机状态，导致分帧方式本身随意改变结果。

产物生成失败、实例非法或身份重复，任务标记失败，整批取消。已经准备的临时产物可以随会话释放，因为此时还没有扣任何真实材料。

不过会话种子并不自动构成完整的审计日志。要复现一次具体问题，仍需要对应输入、规则版本和调用过程，不能看到一个seed字段就宣称所有随机都已经可追踪。

### 最后复制的是当前背包

这一点容易写错：不能在窗口刚打开时复制一次背包，等几十帧后直接拿旧副本替换真实背包。

那样准备期间新拾取的东西会被旧副本覆盖掉。玩家明明看见药水进包，合成完成后却消失，原因不是合成吃了药水，而是提交覆盖了后来的状态。

当前流程在准备完成后，再从最新真实背包建立副本。按稳定ID复核原材料、得到最新下标，在这份当前副本里扣除原批次，并保留期间新增的其他物品。

[第四十八篇]({{LINK:GAME-48}})固定批次的意义在这里非常直接：本单材料不扩张，当前背包也不倒退。冻结操作意图与保持世界继续变化，可以同时成立。

### 先把所有产物放进副本，再替换真实容器

下面摘取最终提交阶段的关键部分，前面已经移除副本中的材料：

```gdscript
for output in job.outputs:
    if ids.has(output.instanceId) or not SaveManager._valid_item(output) or not Inventory.add(pending, output):
        cancel_gold_batch()
        return {"ok": false, "reason": Localization.tr_key("ui.batch.failed")}
    ids[output.instanceId] = true
var count := job.outputs.size()
inventory = pending
cancel_gold_batch()
EventBus.inventory_changed.emit()
EventBus.gold_batch_completed.emit(count)
```

所有产物都能合法加入副本以后，才把真实库存换过去。中间任意一件失败，真实背包仍然是提交前那份，没有半批材料被扣走。

四换一通常会减少占用格，但容量检查仍应走统一入口。不能因为数学上大多够放，就忽略实例合法性、堆叠规则或后续规则调整。

### 聚合通知，是业务完整性的延伸

当前整批提交只广播一次库存变化，再发一条批量完成事件。界面据此展示本批数量，不需要为每件产物刷一遍整个背包。

这既减少重复工作，也让其他系统看到完整状态。若每加入一件就广播，订阅方会观察到材料已扣、产物尚未放齐的过程，即使最后成功，也可能做出基于半成品状态的判断。

聚合提示不能减少真实奖励。屏幕上可以只说“获得若干件”，实际产物列表仍要完整入包、可保存、可查看。

同样，不应该为了让界面动起来，在准备期间先发正式完成事件。进度与完成是两类消息，调用方需要知道哪一个只是临时工作，哪一个已经改变真实资产。

### 会话失效与重复点击，别靠按钮变灰兜底

当前会话编号递增，新会话替换旧会话，取消以后旧编号不能继续推进。已经有准备任务时，也不会因为连点再启动第二个相同任务。

按钮禁用有帮助，但最终状态检查仍在业务入口。键盘事件、排队回调或未来新的调用者，都可能绕过某一次视觉状态。

关闭、重置和切换流程时要取消临时任务，让它持有的候选与随机产物及时释放。不要留下一个关闭以后继续跑、最后突然写进背包的幽灵任务。

这里使用的是当前进程内的短暂会话，并没有把每一步工作写进存档。若将来增加跨进程恢复，需要另行设计，不能把现有内存提交直接叫成持久事务。

### 测试应故意让准备中途的世界变化

后续验证可以沿实际业务入口与批量用例进行：

```sh
rg -n 'start_gold_batch|advance_gold_batch|inventory = pending' autoload/game_state.gd
python3 tools/run_isolated_tests.py GoldBatchFusionTest GoldBatchUiTest
```

本文没有执行游戏测试。检查时应在准备途中注入无关拾取、整理、组内材料收藏或移出，再核对完成或拒绝后真实背包中的实例集合。

也要覆盖产物失败、旧会话继续推进和重复启动。成功不只看产物数量，失败也不只看返回错误，而要检查没有扣料、没有漏掉新拾取物品、没有重复完成通知。

这些定向检查可以证明提交边界，却不能代替最大背包场景的帧时间采样。若要宣称性能改善，还需在相同设备、同样输入规模下比较，而不是只看用了分帧就下结论。

还有一点，准备阶段不能拿临时产物触发正式成就或出售判断。即使对象已经具备完整字段，它仍未归玩家所有。把这种所有权边界守住，取消任务时才只需释放候选，而无需逐一回滚后续系统。

### 小结

批量动作复用规则，不必复用带副作用的整段单次流程。临时产物可以分帧准备，真实库存则从当前状态建立副本，全部验证以后一次提交。

让失败停在副本里，让外部只看到完整结果，既保护玩家材料，也让界面和事件链更容易理解。这比在半完成以后补一套撤销逻辑，更值得一开始就安排好。
